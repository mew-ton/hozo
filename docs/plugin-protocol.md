# プラグインのプロトコル

## この文書が決めること

プラグインのマニフェスト、探し方、起動、標準入出力の JSON の形（出どころは設計書 §4.6）。hozoc 側は `internal/plugin`、プラグイン側の SDK は `plugin`（Go。`docs/packages.md`）。この形にした決定（要求の `ir` を `view` にし、`protocol` を足したこと、マニフェストの追加項目、プラグインとトランスパイラを分けたこと、基底と相乗りに分けたこと）の一覧は `docs/decisions.md`「決めたこと」。

**プラグイン**は入れるもの。マニフェストと、本体（WASM のファイル）と、あれば語彙を一つのディレクトリに持つ。**トランスパイラ**は、プラグインが提供する名前の付いた変換で、`hozo.toml` の単位が `transpilers` に名前を書いて選ぶ（`docs/config.md`「単位」）。二つの言葉の定義の持ち主はこの段落で、ほかの文書も同じ意味で使う: 起動される実行ファイルと、マニフェスト、語彙、起動の話は「プラグイン」、設定が選ぶもの、ファイルを出すもの、実装を出すものの話は「トランスパイラ」。

**語彙のプラグイン**は、トランスパイラとは別の役割: ある語彙の、言語に依らない決まりを確かめ、診断だけを返す。定義の持ち主は「語彙のプラグイン」。

**hozoc 本体は、コードを出力しない。** 書き出すファイルは、どれも、どれかのトランスパイラが `emit` の応答で返したもの。本体は特定の言語を知らず、型や op の形を決めるのは、言語ごとの基底のトランスパイラ（`docs/config.md`「基底と相乗り」）。本体がトランスパイラの選択を集めて形を決める仕組み（`select`）は持たない（「選択をなくしたこと」）。

## マニフェスト `hozo-plugin.toml`

```toml
name     = "go-http"            # プラグインの名前
wasm     = "plugin.wasm"        # プラグインの本体（WASM）。マニフェストのディレクトリからの相対パス
protocol = "0.26"               # このプラグインが話す docs/ir.md の version。0.x の間は、hozoc の版と、ぴったり同じ（「版の合わせ方」）

vocabulary = []                 # このプラグインが提供する語彙。マニフェストからの相対パス。省略時は []

[[transpiler]]                  # このプラグインが提供するトランスパイラ。いくつでも書ける
name        = "go-http"         # hozo.toml の transpilers に書く名前。必須
language    = "go"              # 出力する言語。必須。空でない文字列
requires    = ["go", "go-valid"]   # このトランスパイラが、出力の形を前提にするトランスパイラの名前。省略時は []（基底）
unsupported = []                # 意味を保てない記法（デコレータの FQN）。使われていれば CFG-6。省略時は []
seams       = []                # 継ぎ目を要るデコレータの FQN（docs/config.md「継ぎ目」）。例: ["rate.limited"]。省略時は []
interprets  = ["http.get", "http.post"]   # 解釈するデコレータの FQN（docs/config.md「解釈するトランスパイラ」）。省略時は []
requires_vocabulary = ["http"]  # このトランスパイラが、語彙のプラグインを要る語彙の名前空間。省略時は []

[read]                          # 語彙のプラグインが書く（「語彙のプラグイン」）。テーブルごと省けば、語彙のプラグインではない
namespaces = ["rate"]           # 読み解く語彙の名前空間の FQN。一つ以上

[import]
formats = []                    # 取り込める形式の名前。空なら import を持たない。テーブルごと省けば []

[coverage]
enabled = false                 # true なら hozoc tests で direction "coverage" を呼ぶ。テーブルごと省けば false
```

基底のマニフェストは、`requires` を書かない（`docs/plugin-go.md`「マニフェスト」）。

- **`wasm`** は、プラグインの本体: WASI（preview 1）の、コマンドの形（`_start` を持つ）の WASM のファイル。hozoc は、これを、本体の中の実行環境で動かす（「起動」）。
  - マニフェストのディレクトリからの、相対パスで書く。絶対パスと、ディレクトリの外に出るパス（`..`）と、空の文字列と、文字列でない値は、MAN-4。
  - ファイルが、あるかは、マニフェストを読むときには、確かめない（入っているだけで、使わないプラグインのために）。起動するときに、なければ、`Crashed`。
  - **`command`（子プロセスで起動するコマンド）は、なくした**（`docs/decisions.md`「決めたこと」413、414、426）。書けば MAN-6（「診断」）: `wasm` に書き直すことを、示す。子プロセスで起動する道は、開発用としても、ない。
- `[[transpiler]]` が一つもなければ `emit` を持たない。トランスパイラの名前はプラグインの名前と同じでも違ってもよい。一つのマニフェストの中で同じ名前を二度書けば MAN-4。
- **`requires`** は、このトランスパイラが依存するトランスパイラの名前の一覧。空なら**基底**、空でなければ**相乗り**（二つの言葉の定義と、単位に掛かる規則の持ち主は `docs/config.md`「基底と相乗り」: 単位は基底をちょうど一つ持ち、`requires` の名前はすべて単位の `transpilers` に書く）。
  - 書くのは、出力の形を前提にする相手のすべて。基底だけでなく、別の相乗り（検証の `go-valid` など）も書く。相手が依存するものまでは書かなくてよいが、単位の `transpilers` には、辿って届くすべてが要る（相手の `requires` が、相手について確かめられる）。
  - 相手は名前で指す。同じプラグインのトランスパイラでも、別のプラグインのものでもよい。その名前のトランスパイラが入っているかは、マニフェストでは確かめない（単位に書いたときに CFG-19 / CFG-14 で分かる）。
  - 自分の名前を書く、同じ名前を二度書く、文字列の配列でない、は MAN-4。
  - 依存は一方向で、オプションによらない（`docs/config.md`「基底と相乗り」）。
- **`seams`** は、このトランスパイラが継ぎ目を要るデコレータの FQN の一覧（継ぎ目の定義と、単位に掛かる規則の持ち主は `docs/config.md`「継ぎ目」）。このトランスパイラを書いた単位の基底は、単位の対象の op のうち、ここに書いたデコレータが付いたものを二層で出し、このトランスパイラは、その継ぎ目の中身を出す。
  - マニフェストに書くのは、宣言を静的にするため: 単位の継ぎ目は、設定とマニフェストだけから、どのトランスパイラを起動するより前に決まる。`emit` の応答で宣言する道はない（「選択をなくしたこと」）。
  - 書くのは、汎用のデコレータの FQN（名前付きデコレータの FQN は、どの適用にも当たらない）。その FQN のデコレータが宣言されているか、付けられる対象に op があるかは、確かめない。
  - 文字列の配列でない、空の文字列がある、同じ FQN を二度書く、は MAN-4。同じ単位の別のトランスパイラと重なるのは CFG-23（単位に書いたときに分かる）。
  - 基底（`requires` が空）も書ける。オプションによらない。
- **`requires_vocabulary`** は、このトランスパイラが、語彙のプラグインの検査を前提にする、語彙の名前空間の一覧（単位に掛かる規則の持ち主は「語彙のプラグイン」: 書いた名前空間を読み解く語彙のプラグインが、入っていなければ CFG-25）。
  - 書くのは、このトランスパイラが、使い方の検査を、自分では返さない語彙（`go-http` の `http`）。
  - 文字列の配列でない、空の文字列がある、同じ名前を二度書く、は MAN-4。
- **`[read]`** を書いたプラグインが、語彙のプラグイン。`namespaces` は、読み解く語彙の名前空間の FQN の一覧で、一つ以上、要る。
  - `namespaces` がない、空の配列、文字列の配列でない、空の文字列がある、同じ名前を二度書く、は MAN-4。
  - その名前空間が、宣言されているかは、確かめない（使われていなければ、頼まれないだけ）。
- `language` は、出力する言語の名前。中身は基底が決める（`"go"`、`"ts"`）。hozoc は、単位の中でそろっていること（CFG-16）だけを確かめ、名前の一覧を持たない。空の文字列は MAN-4。
- **`interprets`** は、このトランスパイラが解釈する（読んで、出力に使う）デコレータの FQN の一覧。hozoc は、これで、設定のどのトランスパイラも解釈しないデコレータを見つける（CFG-26。決まりの持ち主は `docs/config.md`「解釈するトランスパイラ」）。
  - `seams` に書いたデコレータは、解釈するものに数えるので、`interprets` には書かない。同じ FQN を、`seams` と `interprets` の両方に書けば MAN-4。
  - 書くのは、汎用のデコレータの FQN か、名前付きデコレータの FQN。その FQN のデコレータが宣言されているかは、確かめない（`seams` と同じ）。ワイルドカードはない。
  - 文字列の配列でない、空の文字列がある、同じ FQN を二度書く、は MAN-4。
  - 書いたとおりに解釈しているかを、hozoc は確かめない（プラグインの申告）。
- 言語を持つのはトランスパイラで、プラグインは持たない（一つのプラグインが言語の違うトランスパイラを提供してよい）。単位の言語の決め方は `docs/config.md`「基底と相乗り」。
- トランスパイラが受け取るオプション（`docs/config.md`「オプション」）は、マニフェストには書かない。キーと値の型を確かめるのはトランスパイラ自身で、一覧はそのプラグインの文書が持つ。
- `protocol` が、hozoc の `docs/ir.md` の `version` と合わなければ MAN-2（「版の合わせ方」。省いたときも、合わないものとして MAN-2）。
- 省いたときの値: `vocabulary` は `[]`、`[[transpiler]]` はなし、`requires` と `unsupported` と `seams` と `interprets` と `requires_vocabulary` は `[]`、`[read]` はなし（語彙のプラグインではない）、`[import]` は `formats = []`（`import` を持たない）、`[coverage]` は `enabled = false`（`coverage` を呼ばない）。`name` と `wasm` は省けない（MAN-4）。
- 前にあった `[check]`（検査のための頼みごと direction `check` を、呼ぶか）は、なくした（`docs/decisions.md`「決めたこと」416。「検査のための頼みごとを、なくしたこと」）。書けば、知らないキーで MAN-4。
- `vocabulary` の `.hozo` の読み込みは `docs/vocab.md`「読み込み」。

## 探索

**入っているプラグイン**は、次のディレクトリ d の直下で `<d>/<p>/hozo-plugin.toml` を持つディレクトリ p のすべて。p がプラグインの名前。同じ名前 p が複数の場所にあれば、次の順で最初に見つかったものだけを使う。プロジェクトの中、利用者の環境、ホームの順に、近いものを優先する。

1. `hozo.toml` の `[hozo].plugin_dirs` の各ディレクトリ（ルートからの相対パス）。
2. 環境変数 `HOZO_PLUGIN_PATH`（OS のパス区切りで複数）の各ディレクトリ。
3. `<ホーム>/.hozo/plugins`。

- 2 と 3 はプロジェクトの外の場所で、探索（`internal/plugin`）と解析（`internal/project`）は自分ではプロセスの環境を読まない。`hozoc` が、環境変数を `cli.hozo` の入力 `pluginPath` として（`docs/cli.md`「cli.hozo」）、ホームディレクトリを `cmd/hozoc` から受け取って渡す。渡されなければ 1 だけを探す。同じ入力から同じ結果にするためで、テストは実行する人の環境に入っているプラグインに左右されない（`docs/testing.md`「環境からの独立」）。
- 単位の `transpilers` の名前 t（`docs/config.md`「単位」）からトランスパイラを探す手続きの持ち主はここ: 入っているすべてのプラグインのマニフェストの `[[transpiler]]` の `name` から探す。どのプラグインにもなければ CFG-14。二つ以上のプラグインにあれば CFG-15（以降の処理は、上の順で最初のプラグインのものを使う）。
- **使うプラグイン**は、どれかの単位の `transpilers` に書かれたトランスパイラを提供するプラグイン（依存していても、書かれていなければ使うプラグインではない。足りない依存は CFG-19）。語彙を読むのも（`docs/vocab.md`「読み込み」）、起動するのも（「起動」）、使うプラグインだけ。入っているだけのプラグインは、名前を探す相手になる以外は何もしない。語彙のプラグインを、いつ起動するかは、単位に依らない別の決まり（「語彙のプラグイン」）。
- マニフェストは入っているプラグインのすべてについて読む（トランスパイラの名前を知るため）。読めないマニフェスト（MAN-4）と、`name` がディレクトリの名前 p と違うマニフェスト（MAN-3）は、使っていなくても報告する。`protocol` の不一致（MAN-2）は、使うプラグインにだけ報告する（ホームに入れた古いプラグインが、それを使わないプロジェクトを止めないようにするため）。
- 設定なし（`docs/config.md`「置き場と探し方」）のときは探索しない（選ぶ単位がない）。

## 語彙のプラグイン

`docs/decisions.md`「決めたこと」410、416、428。**語彙のプラグイン**は、ある語彙の、言語に依らない決まりを確かめるプラグイン: マニフェストに `[read]` を持つ（「マニフェスト `hozo-plugin.toml`」）。頼みごとは一つで、`read`（「read」）: 仕様を受け取り、診断を返す。今あるのは `http`（`docs/plugin-http.md`）、`valid`（`docs/plugin-valid.md`）、`db`（`docs/plugin-db.md`）。

| | 語彙のプラグイン | トランスパイラを提供するプラグイン |
|---|---|---|
| マニフェスト | `[read]` | `[[transpiler]]` |
| 選ぶのは | 仕様（その語彙のデコレータが、付いているか） | 設定（単位の `transpilers`） |
| 頼みごと | `read` | `emit` |
| 受け取るもの | 仕様 | 仕様と、受け持つ出力 |
| 返すもの | 診断 | 診断と、ファイル |

- **頼むのは、仕様が、その語彙を使っているとき。** 相手は、入っているプラグイン（「探索」）のうち、`[read]` の `namespaces` のどれかの名前空間のデコレータが、仕様のどこか（宣言、model のフィールド、分類のケース）に、一つでも付いているもの。出力の単位は、見ない: 単位が一つもない設定でも、頼む。
  - デコレータの名前空間は、適用の、汎用のデコレータの FQN（名前付きデコレータを通した適用は、展開した先。`docs/ir.md`「デコレータの適用」の `decorator`）から、最後の名前を除いたもの。
- **一度の実行で、プラグインごとに、多くて一回、起動する。** 順は、プラグインの名前の辞書順で、どの `emit` よりも先。
- **起動するのは、仕様と設定の検査（`docs/cli.md`「検査」の 1〜3）に、error がないときだけ。** `emit` と同じ理由（「起動」）: 語彙のプラグインも、検査を通った仕様を前提にする。
- **語彙のプラグインが error を返したら、`emit` は、頼まない。** トランスパイラは、語彙の決まりを通った仕様を前提にし、その語彙の使い方の診断を、自分では返さない（`docs/plugin-go-http.md`「診断」）。
- **`protocol` の合わない語彙のプラグイン（MAN-2）は、頼むときにだけ、報告する。** その語彙を使っていないプロジェクトを、止めない（「探索」の、使うプラグインと同じ理由）。
- **トランスパイラは、要る語彙のプラグインを、マニフェストの `requires_vocabulary` で言う。** 単位の `transpilers` に書いたトランスパイラが、そこに書いた名前空間を、`[read]` の `namespaces` に持つプラグインが、一つも入っていなければ CFG-25（`docs/config.md`「診断」）。確かめるのは、入っているかだけで、仕様が、その語彙を使っているかには、よらない。
- **同梱の語彙（`vocab/*.hozo`）の宣言は、hozoc が持ち、その決まりは、語彙のプラグインが持つ。** 宣言は、プラグインが入っていなくても、読める（`docs/vocab.md`「読み込み」）。語彙のプラグインは、hozoc に組み込まず、ほかのプラグインと同じに、探索で見つける。
- **語彙のプラグインが入っていなければ、その語彙の決まりは、確かめない。** 知らせもしない（`requires_vocabulary` に書いたトランスパイラが、単位にあるときの CFG-25 のほかは）。
- 設定なしのときは、探索しないので（「探索」）、語彙のプラグインにも、頼まない。
- 一つのマニフェストに、`[read]` と `[[transpiler]]` の両方を書いてよい（頼みごとは、別々に届く）。
- 語彙のプラグインが、自分の語彙の宣言（マニフェストの `vocabulary`）を配る形は、決めていない（`docs/open.md`「語彙とプラグイン」）: 今、`vocabulary` を読むのは、使うプラグインだけ（`docs/vocab.md`「読み込み」）。

## 起動

- **プラグインは、hozoc の中の、WASM の実行環境で動く**（`docs/decisions.md`「決めたこと」413、414）。子プロセスは、起こさない。プラグインに見えるのは、hozoc が渡したものだけ。

  | 渡すもの | 中身 |
  |---|---|
  | 標準入力 | 要求の JSON |
  | 標準出力 | 応答の JSON を、受け取る |
  | 標準エラー | hozoc の標準エラーに流す |
  | 時計 | 決まった値から始まり、読むたびに、決まった幅で進む、にせものの時計（今の時刻では、ない） |
  | 乱数 | 決まった並び（実行のたびに、同じ） |

  | 渡さないもの | プラグインの側から見ると |
  |---|---|
  | ファイル | ディレクトリが、一つも、見えない。開けない |
  | ネットワーク | つなげない。待ち受けても、外からは、届かない（Go で書いたプラグインの中では、待ち受けが、成功したように見える: プログラムの中だけの、にせもの） |
  | 環境変数 | 一つも、ない |
  | 引数 | ない（プログラムの名前も、ない） |
  | 作業ディレクトリ | ない |

  - **プラグインは、要求の中身だけから、答えを作る**（同 425）。同じ WASM に、同じ要求を渡せば、同じ答えが返る（時計と乱数を、決まった値にしているのは、このため）。
  - 眠ること（`sleep`）を頼まれても、実行環境は、待たない。
  - 前にあった、作業ディレクトリ（プロジェクトのルート）と、環境変数 `HOZO_PROJECT_ROOT`、`HOZO_PLUGIN_DIR` は、ない。
- **動いているプラグインを、途中で、止められる。** 言語サーバーが、検査を、やめさせるとき（`docs/lsp.md`「プラグインの診断」）は、動いている WASM を、その場で止める。止めた起動の答えは、ない: 診断にも、例外（`Crashed`）にも、しない（やめさせた側が、結果を捨てる）。
  - 途中で止められる形の WASM は、止まったかを見る点が入る分、遅い（下の「速さ」）。なので、その形を使うのは、言語サーバーだけ。`hozoc build` と `hozoc tests` は、速い形で動かす: 終わらないプラグインは、利用者が、コマンドごと止める。
  - hozoc は、時間の上限も、メモリの上限も、置かない。
- **WASM を、機械の言葉に直したものを、覚える**（同 426）。直すのは、WASM のファイルごとに、はじめの一度で、一つに、一秒から数秒、掛かる（関数ごとに、並べて直す）。
  - 置き場は、環境変数 `HOZO_CACHE_DIR` があれば、そのディレクトリ。なければ、OS の、利用者ごとのキャッシュの置き場（Go の `os.UserCacheDir`。Linux なら `~/.cache`）の下の `hozo`。どちらも、その下の `wasm/` を使う（途中で止められる形に直したものは、`wasm-stoppable/`。二つの形を、混ぜない）。
  - 置き場を、決められない・作れないときは、覚えずに、動く（実行のたびに、直す）。
  - 中身は、WASM のファイルの内容と、実行環境の版から決まるので、消しても、困らない（直し直すだけ）。hozoc は、古いものを、消さない: WASM が変わるたびに、増える（WASM 一つに、20 MB ほど）。
  - プラグインの答えを、覚えることは、していない（後の課題。同 426）。
- 標準入力に要求の JSON を一つ渡す。標準出力から応答の JSON を一つ読む。標準エラーは hozoc の標準エラーに、各行の先頭に `[<プラグイン名>] ` を付けて流す。
- **`emit` は、一度の実行で、プラグインごとに、多くて一回、起動する**（`docs/decisions.md`「決めたこと」411）。一つの要求に、仕様を一度だけ入れ、そのプラグインが**受け持つ出力**を並べる。応答も、出力ごとに並ぶ（「emit」）。
  - プラグイン P が受け持つ出力は、出力（単位と、その単位が出力する名前空間の組。`docs/config.md`「in」）のうち、単位の `transpilers` に、P のトランスパイラが、一つでもあるもの。並びは、単位の設定の順、その中は、名前空間の IR の順。
  - 出力ごとに、**頼むトランスパイラ**を並べる: その単位の `transpilers` のうち、P が提供するもの（`transpilers` に書いた順）。一つのプラグインの二つのトランスパイラを同じ単位に書いても、起動は一回。
  - 起動する順は、プラグインが、最初に現れた順（単位の設定の順、名前空間の IR の順、`transpilers` に書いた順に見て）。
  - 相手は、使うプラグイン（「探索」）。`protocol` の合わないプラグイン（MAN-2）は、起動しない。受け持つ出力が一つもないプラグイン（どの単位も、名前空間を出力しない）も、起動しない。
  - **起動するのは、仕様と設定の検査（`docs/cli.md`「検査」の 1〜3）に、error がないときだけ。** error があれば、`View` は、検査を通っていない仕様のもので、トランスパイラは、それを前提にしていない。先の error を直してから、プラグインの診断が出る。
  - **検査だけの実行（`hozoc build --no-emit`、言語サーバー）も、書き出す実行（`hozoc build`、`hozoc tests`）も、同じ頼みごとを使う**（同 416）: 検査は、応答の診断（`errors`、`warnings`）だけを使い、ファイルを書かない。書き出すときは、同じ応答のファイルを書く。hozoc は、一度の実行で、同じプラグインに、同じことを、二度、頼まない。
- **答えは、出力ごとに独立。** どのトランスパイラも、一つの出力の答えを、仕様と、その出力の `View` だけから作り、同じ要求のほかの出力にも、ほかのトランスパイラの応答（ファイル、warning）にも、依らない。相乗りは、基底の応答を見ずに、基底と同じファイルの置き場と名前を自分で求める（「相乗りが基底の形を知る方法」）。出力の並びと、`transpilers` に書いた順は、起動の順と診断の並びにだけ効き、書き出すファイルを変えない。
- `read` の相手と、順は「語彙のプラグイン」。語彙のプラグインが error を返した実行では、`emit` を、頼まない。
- `coverage` は、`hozoc tests` が、プラグインごとに、多くて一回起動する。相手と、渡すものは「coverage」。
- 並列には起動しない（診断の順序を決定的にするため）。
- 常駐（起こしたままにして、何度も頼む）は、しない: 「起こして、一つ頼んで、終わる」まま（同 411。エディタで要ると分かったときに、足す）。

**速さ**（実測。サンプル `tests/samples/shop-server` の、検査だけの実行 `hozoc build --no-emit`。七つの単位、六つのプラグイン。五回のうち、いちばん速い回）:

## 信頼の前提

`docs/decisions.md`「決めたこと」413、414。**プラグインは、サンドボックスの中で動く。** プラグインは、利用者が入れ、`hozo.toml` に、そのトランスパイラの名前を書いて選んだコードだが、hozoc は、それを、信頼しない: プラグインに見えるのは、hozoc が渡したもの（「起動」の表）だけで、利用者のファイルも、ネットワークも、環境変数も、見えない。

- **プラグインにできるのは、答えを返すことだけ。** 誤った答え（誤ったコード、誤った診断）は、返せる。
- **答えを確かめるのは、hozoc**（今までどおり）: 応答の形（「応答の形」）。書き出すファイルが、その出力の、出力先の下にあること（PLG-1）。同じファイルが、二度ないこと（PLG-2、CFG-5）。テストの対応表の形（PLG-4）。ファイルを書くのは、hozoc で、プラグインでは、ない。
- **出てきたコードが、何をするかは、hozoc は、見ない。** プラグインが返したコードを、ビルドして動かすのは、利用者で、その中身を確かめるのは、利用者の、ふだんの確かめ（レビュー、テスト）。

**起動する、きっかけ**（同 404、405、412）。プラグインを探す場所の一つ目は、プロジェクトの中（「探索」の 1）なので、どの WASM を動かすかは、リポジトリの中身が、決められる。サンドボックスが、あるので、動かしても、プロジェクトの外には、何も、起きない。hozoc が、プラグインを起動するのは、次のとき。

| きっかけ | 起動するか |
|---|---|
| `hozoc build`（`--no-emit` も）、`hozoc tests` | する |
| 言語サーバー（`hozoc lsp`） | クライアントが、許したときだけ（`docs/lsp.md`「プラグインの診断」の「許し」）。既定は、しない（サンドボックスが入る前に決めた形のまま。既定を変えるかは、決めていない: `docs/open.md`「文書と道具」） |

## 版の合わせ方

**今は、0.x で、ぴったり合わせる**（`docs/decisions.md`「決めたこと」467）: マニフェストの `protocol` が、hozoc の版と、同じでなければ MAN-2。要求の `protocol` が、プラグインの話す版と、同じでなければ、`code: "protocol"` の `error`。下の表の合わせ方（小さい版の大小）は、1.0（最初に、外へ出す版）から効く: 大きい版が 0 の間は、hozoc も SDK も、同じ版だけを、合う、とする。

版は「大きい版.小さい版」（`0.26`）で、hozoc の版は `docs/ir.md`「版」が持つ。足すだけの変更は、小さい版を上げ、壊す変更は、大きい版を上げる（上げ方の持ち主は、同じ見出し。`docs/decisions.md`「決めたこと」421）。

| 比べる所 | 合う | 合わなければ |
|---|---|---|
| hozoc が、マニフェストの `protocol` を読むとき | 大きい版が、hozoc と同じで、小さい版が、hozoc の小さい版以下 | MAN-2。起動しない |
| プラグインが、要求の `protocol` を読むとき | 大きい版が、プラグインの話す版と同じで、小さい版が、プラグインの小さい版以上 | `code: "protocol"` の `error`（「要求と応答」） |

- マニフェストの `protocol` は、「この版から上で、動く」の意味: 古いプラグインは、新しい小さい版の hozoc で、そのまま動く。新しいプラグインは、それより古い hozoc では、動かない（要る項目が、まだない）。
- 版の文字列は、十進の数二つを `.` でつないだもの。そう読めない文字列（空、`"1"`、`"1.x"`）は、合わない。
- 足された項目を、古い側が、読まずに済むように、**どちらの側も、知らない項目を、無視する**: プラグインは、要求の、知らない項目を（「要求と応答」）、hozoc は、応答の、知らない項目を、無視する。マニフェストの知らないキーは、別で、MAN-4 のまま（書き間違いを、黙って読み飛ばさない）。マニフェストのキーを足すことは、小さい版を上げる変更なので（`docs/ir.md`「版」）、新しいキーを書いたプラグインは、その版を名乗り、古い hozoc は、キーではなく、版（MAN-2）で断る。

## 要求と応答

すべての要求は `protocol`（`docs/ir.md` の `version` と同じ値。`view.version` とも等しい）と `direction` を持つ。プラグインは `protocol` が合わなければ `code: "protocol"`、`direction` を実装していなければ（`emit` なら、頼まれたトランスパイラの、どれかを実装していなければ）`code: "unsupported"` の `error` を返して終了コード 2 で終わる。`protocol` を先に確かめる。「合わない」の決まりは「版の合わせ方」で、`protocol` がない、`null`、文字列でない場合を含む。文字列でない `direction` は、実装していない `direction` と同じ。要求が JSON のオブジェクトとして読めなければ、応答を書かずに終了コード 1 で終わる（hozoc からは `Crashed`）。SDK はこの読み方を表（`plugin/testdata/request_head.json`）でテストする。

**プラグインは、要求の、知らない項目を、無視する**（`docs/decisions.md`「決めたこと」421）。要求のどの階層でも（`spec`、`program` の宣言、`outputs` の要素、`config` など）、プラグインが知らない名前の項目があってよく、読まないだけで、誤りにしない。SDK が、この読み方を持つ。hozoc も、応答の、知らない項目を、無視する（「版の合わせ方」）。

### 応答の形

終了コード 0 の標準出力は、JSON の値一つで、下の各 direction の応答の形をしていなければならない。hozoc は次を確かめ、違えば `MalformedOutput`（「起動」）。

- 応答は JSON のオブジェクト。
- **必須の項目**がある。`null` は「ない」と同じに扱う。`emit` の応答の `outputs`、その要素の `results`、その要素（トランスパイラ一つの答え）の `files` と `warnings`、`read` の応答の `errors` と `warnings`、`coverage` の応答の `recognized` と `files`（配列は、どれも、空でも `[]` で出す）。要素では、`files` の要素の `path` と `content`、`warnings` の要素の `message`、`errors` の要素の `code` と `message`、`coverage` の応答の `files` の要素の `path` と `lines`。
- **省ける項目**は、なくても `null` でもよい。`emit` の、トランスパイラ一つの答えの `errors`、`warnings` / `errors` の要素の `at`（省けば位置なし）。`errors` の要素の `severity` は見ない（常に error）。
- 書かれた項目の**型**が合う: 上の配列は配列、その要素はオブジェクト、`path` / `content` / `message` / `code` / `at` は文字列。`coverage` の応答の `recognized` は真偽値、`lines` は、1 以上の整数二つの配列（始まりの行、終わりの行。始まり ≦ 終わり）の配列。
- **知らない項目は無視する**。応答のどの階層でも、ここにない名前の項目があってよい（プラグインが新しい版の項目を書いていても、古い hozoc はそれを読まないだけ。版 0.3 までの `select` を書いたままの応答も、読まれないだけで通る）。項目の名前は大文字と小文字を区別する。

- **`emit` の応答の数が、要求と合う**: `outputs` の要素の数が、要求の `outputs` と同じで、その要素の `results` の数が、要求の、その出力の `transpilers` と同じ。

形が合った後に、ファイルを集める実行（`hozoc build`、`hozoc tests`）は、`path`（PLG-1 / PLG-2）と、テストの対応表（PLG-4）を確かめる。`hozoc build --no-emit` も、書かないだけで、集めて、確かめる（`docs/cli.md`「build」）。言語サーバーは、`files` を使わないので、確かめない。`import` の応答の形は、段階 6 で `hozoc import` と一緒に決める。

### read

語彙のプラグインへの、ただ一つの頼みごと（「語彙のプラグイン」）。

```jsonc
// 要求
{ "protocol": "0.26", "direction": "read",
  "spec": {                               // 仕様: emit の spec と同じ形（docs/ir.md「まとめた形」の Spec）
    "version": "0.26",
    "namespaces": { /* 名前空間の FQN → その名前空間を出力する単位ごとの設定。単位がなければ {} */ },
    "program": { /* docs/ir.md の Program */ } } }

// 応答
{ "errors":   [ { "code": "HTTP-5", "at": "server.login", "message": "..." } ],
  "warnings": [ { "at": "server.login", "message": "..." } ] }
```

- **`spec` は、`emit` の要求の `spec` と、同じもの**（同じ実行の中で、同じ中身）。出力ごとの部分（`outputs`）は、ない: 語彙のプラグインは、単位に依らない決まりだけを、確かめる。
- `errors` と `warnings` の要素は、`emit` の応答のものと、同じ形で、同じに扱う（「emit」: `at` の読み方、`errors` は error の診断で `CheckFailed`、同じ診断は、一度だけ）。`code` は、語彙のプラグインが決め、言語の名前を付けない（HTTP-*。`docs/plugin-http.md`「診断」）。
- `warnings` は warning の診断（コード `PLUGIN`、メッセージの先頭にプラグインの名前）。
- ファイルは、返せない（`files` を書いても、読まれない）。
- 応答は、同じ要求から同じバイト列でなければならない（「emit」と同じ）。

### emit

```jsonc
// 要求
{ "protocol": "0.26", "direction": "emit",
  "spec": {                               // 仕様: 出力に依らない部分（docs/ir.md「まとめた形」の Spec）。一度だけ
    "version": "0.26",
    "namespaces": { /* 名前空間の FQN → その名前空間を出力する単位ごとの設定 */ },
    "program": { /* docs/ir.md の Program */ } },
  "outputs": [                            // このプラグインが受け持つ出力（「起動」）。単位の設定の順、名前空間の IR の順
    { "transpilers": [ "go-valid", "go-http" ],   // この出力で頼むトランスパイラ（マニフェストの [[transpiler]] の name。単位の transpilers に書いた順）
      "view": { /* 出力ごとの部分（同 OutputView）。対象の名前空間は viewer、単位の設定は config */ } }
  ] }

// 応答
{ "outputs": [                            // 要求の outputs と、同じ数、同じ順
    { "results": [                        // その出力の transpilers と、同じ数、同じ順。トランスパイラ一つの答え
        { "files": [ { "path": "gen/server/validate.go", "content": "..." } ],   // path はプロジェクトのルートからの相対パスで、その出力の config.dir（Dir(U, N)）の下
          "warnings": [ { "at": "server.login", "message": "..." } ],            // at は FQN か、"file:line:col" の文字列
          "errors":   [ { "code": "GOHTTP-16", "at": "server.login", "message": "..." } ] },   // 省略可。一つでもあれば書き出さない
        { "files": [], "warnings": [] } ] }
  ] }
```

- **`View` は、二つに分けて送る**（`docs/ir.md`「まとめた形」）: 出力に依らない部分 `spec`（仕様の全体と、どの単位が、どの名前空間を、どこへ出力するか）を一度、出力ごとの部分を、`outputs` の要素の `view` に。トランスパイラが受け取る `View`（同「その名前空間から見た IR」）は、SDK が、二つを合わせて作る。
- **SDK が、並びを回す**: プラグインの書き手は、「トランスパイラ一つが、出力一つの `View` を受け取って、答えを一つ返す」関数を書く（`docs/packages.md`「`plugin`（公開）」の `Handler.Emit`）。SDK が、要求の `outputs` と `transpilers` の順に、それを呼び、応答に並べる。
- `transpilers` の要素は、単位の `transpilers` に書かれた名前のうち、このプラグインが提供するもの。複数のトランスパイラを提供するプラグインは、この名前で処理を分ける。
- **オプション**は、要求の別の項目ではなく、出力の `view.config.options` にある（`docs/ir.md`「その名前空間から見た IR」）。頼まれたトランスパイラへのオプションは `config.options[<トランスパイラの名前>]` で、書かれていなければキーがない（空のテーブルと同じに読む）。SDK がこの読み方を持つ（`docs/packages.md`「`plugin`（公開）」の `Options`）。知らないキーと、型の違う値は、トランスパイラが `errors` で返す。
- `path` は、その出力 (U, N) の出力先 Dir(U, N)（要求の、その出力の `view.config.dir`。`docs/config.md`「単位の対象」）の下のファイルでなければならない。そうでなければ PLG-1: 絶対パス、`..` でルートや Dir(U, N) の外へ出るパス、ルートの中の別のディレクトリ、別の出力の Dir、Dir(U, N) そのもの。比べるのは `./` や `..` を畳んだパス。出力先ごとの記録（`docs/cli.md`「書き出し」の `.hozoc-outputs.json`）と、出力先の持ち主を一つに決める規則（CFG-17）が、どの出力のファイルもその Dir の下にあることを前提にしているため。トランスパイラ一つの答えの中で同じ `path` が二度あれば PLG-2。どちらも `MalformedOutput` として終了する。同じ出力の二つのトランスパイラが同じ `path` を返せば CFG-5（`docs/config.md`「診断」）。
- `content` は UTF-8 の文字列。バイナリは出せない。
- `outputs`、`results`、`files`、`warnings` は空でも `[]` で出す。省けるのは `errors`（「応答の形」）。
- `warnings` は warning の診断（コード `PLUGIN`、メッセージの先頭にトランスパイラの名前）。**検査だけの実行でも、出る**（前は、書き出す実行でだけ出た）。
- `errors` は、トランスパイラがその入力を変換できない理由（語彙の使い方の誤り、オプションの誤り、その言語で形にできない宣言。`docs/plugin-go.md`「診断」の GO-*、`docs/plugin-go-cli.md`「診断」の CLI-* など）。`code` はプラグインが決める。error の診断として報告し、`CheckFailed` になる（`docs/diagnostics.md`「終了コード」）。メッセージには、名前を付けない（`code` が、プラグインの規則を示す）。どれかのトランスパイラが `errors` を返せば、検査は通らず、何も書き出さない（`docs/cli.md`「検査」「emit」）。
- `at` は FQN（その宣言の位置に付ける）か `"file:line:col"`。どちらでもなければ（省いたときも）位置なしで報告する。
- **同じ診断は、一度だけ報告する。** 同じ名前空間を、二つの単位が出力していれば、同じトランスパイラが、出力ごとに、同じ診断を返しうる。重さ、`code`、位置、メッセージが、すべて同じ診断は、hozoc が、最初の一つだけを残す。
- 応答は、同じ要求から同じバイト列でなければならない（`docs/requirements.md`「品質の要件」の決定性）。時刻、乱数、環境変数、実行する人の環境に入っているものに依らない。

### coverage

```jsonc
// 要求
{ "protocol": "0.26", "direction": "coverage",
  "coverage": { "path": "/home/me/shop/cover.out", "content": "mode: set\n..." },   // hozoc tests に渡された、カバレッジのファイル
  "files": [ "gen/server/servertest/http.go", "gen/server/servertest/leaves.go" ],  // 実行された行を知りたいファイル
  "outputs": [ { "index": 5, "base": "go", "dir": "gen/server", "options": { "go": { "module": "example.com/shop-server" } }, /* … */ } ] } // files を出した出力の設定

// 応答
{ "recognized": true,                                                                // このプラグインが読める形のファイルだったか
  "files": [ { "path": "gen/server/servertest/leaves.go", "lines": [ [159, 161], [163, 167] ] } ] }
```

カバレッジのファイル（テストを走らせる道具が書いた、実行された所の記録）から、「どのファイルの、どの行が、実行されたか」を取り出す direction。カバレッジの形は、言語と道具ごとに違うので、読むのは、その言語の基底のプラグイン。hozoc の本体は、応答の行を、テストの対応表（「テストの対応表」）と突き合わせるだけで、カバレッジの形を知らない（`docs/cli.md`「tests」）。

- **相手**は、単位の基底（`docs/config.md`「基底と相乗り」）を提供するプラグインのうち、`[coverage] enabled` のもの。プラグインごとに一回で、起動の順は、そのプラグインを基底に持つ単位の、設定の順。基底のプラグインが `[coverage] enabled` でない単位の分は、どのプラグインにも聞かない（その単位の対応表のテストは、TESTS-3。`docs/cli.md`「tests」）。
- `coverage.path` は、hozoc が読んだファイルの絶対パス（メッセージに使う。プラグインは、読み直さなくてよい）。`coverage.content` は、その中身。UTF-8 の文字列でないカバレッジは、渡せない。
- 要求の `files` は、そのプラグインを基底に持つ単位の出力の、対応表が指すファイル（プロジェクトのルートからの相対パス。重複なし、辞書順）。
- `recognized` が `false` なら、このプラグインが読める形のファイルではなかった（誤りではない。`files` は `[]`）。中身が、読める形の頭を持つのに、途中が壊れているときは、応答を書かずに、終了コード 1 で終わる（`Crashed`）。
- 応答の `files` は、要求の `files` のうち、カバレッジが測っていたファイルごとに、一つ。`lines` は、実行された所の、行の範囲（始まりの行と、終わりの行。1 始まりで、両端を含む）の列で、一度も実行されていないファイルなら `[]`。カバレッジが測っていなかったファイルは、要素を出さない（「測ったが、実行されていない」と「測っていない」を、hozoc が分けて報告する）。要求の `files` にないパスの要素は、読まれない。
- 要求の `outputs` は、`files` を出した出力（単位と名前空間の組）の設定（`docs/ir.md`「その名前空間から見た IR」の `NamespaceConfig`。単位の設定の順、その中は名前空間の IR の順）。プラグインは、ファイルを読まないので、言語のパッケージの名前など、設定から決まるものは、ここから取る（Go なら、`options.go.module`。`docs/plugin-go.md`「カバレッジを読む」）。
- `coverage` はトランスパイラごとではなくプラグインごとの処理で、要求は `spec` も、トランスパイラの名前も、持たない。
- 応答は、同じ要求から同じバイト列（「emit」と同じ）。

## テストの対応表

テストを受け取る口（ケースを受け取り、テストを走らせる関数。`docs/plugin-go.md`「単体テストの口」など）を出すトランスパイラは、`emit` の応答の `files` に、**テストの対応表**を一つ足す: 自分が出した、走らせる関数の、どの行が、どのテストか。`hozoc tests` が、カバレッジの「実行された行」と突き合わせて、求めるテストが走ったかを確かめるのに使う（`docs/cli.md`「tests」、`docs/decisions.md`「決めたこと」380）。

```jsonc
// gen/server/servertest/hozo-tests.go.json
{
  "tests": [
    { "name": "server.checkPassword/OK",                 // テストの名前（ラベル）
      "file": "gen/server/servertest/leaves.go",         // そのテストの行を持つファイル。プロジェクトのルートからの相対パス
      "lines": [160, 167] }                              // 始まりの行と、終わりの行（1 始まりで、両端を含む）
  ]
}
```

- **ファイルの名前**は `hozo-tests.<トランスパイラの名前>.json`。置き場は、Dir(U, N) の下なら、どこでもよい（Go のトランスパイラは、テストのパッケージのディレクトリ）。名前にトランスパイラの名前を入れるのは、同じディレクトリに、基底と相乗りが、それぞれの対応表を置けるようにするため（同じ `path` は CFG-5）。hozoc は、名前が `hozo-tests.` で始まり `.json` で終わるファイルを、対応表として読む。
- 対応表は、ほかの `files` と同じに書き出され、出力先ごとの記録（`docs/cli.md`「書き出し」の `.hozoc-outputs.json`）に載る。hozoc が、置き場から読み直すことはない: `hozoc tests` は、今の仕様から集め直した応答の対応表を使い、置き場のものは、それと同じ内容かを確かめるだけ（`docs/cli.md`「tests」）。
- **`lines` の約束**: その範囲の行のどこかが実行されるのは、そのテストが走ったときだけで、そのテストが走れば、その範囲のどこかが、必ず実行される。範囲をどう取るかは、トランスパイラが、その言語のカバレッジの数え方に合わせて決める（Go は `docs/plugin-go.md`「テストの対応表」）。
- `name` は、その対応表の中で重ならない。テストを受け取る口の文書が「テストの名前」と呼ぶもの（`<op の FQN>/<結果>` など）。
- `file` は、同じ答え（トランスパイラ一つの `files`）の `path` の一つ。
- テストを受け取る口を一つも出さない応答は、対応表を出さない。
- hozoc は、`emit` の応答のファイルを集めるとき（`hozoc build`、`hozoc tests`）に、対応表の形を確かめる。次のどれかなら PLG-4（`MalformedOutput`。「診断」）: 名前の `<トランスパイラの名前>` が、その答えを返したトランスパイラの名前でない。中身が、上の形の JSON でない（`tests` が配列でない、要素に `name`、`file`、`lines` のどれかがない、型が違う、`lines` が、1 以上の整数二つで、始まり ≦ 終わり、でない）。`name` が空か、重なる。`file` が、同じ答えの `files` にない。知らない項目は、読まれない（「応答の形」と同じ）。

## 相乗りが基底の形を知る方法

相乗りのトランスパイラは、基底が出すファイルの置き場と名前（パッケージ、型、メソッド、引数の並び）を前提に、自分のファイルを書く。前提にしてよいのは、`requires` に書いたトランスパイラの出力の形だけ。

- **知る手段は `View`（`spec` と、その出力の `view` を合わせたもの。「emit」）と SDK で、基底の応答ではない。** 基底の形は、`View`（仕様と設定）だけから決まる決定的な規則で、その規則の持ち主は基底の文書（Go なら `docs/plugin-go.md`）。規則を写した関数を、基底と同じリポジトリの公開の SDK が持ち（Go なら `plugin/golang`。`docs/packages.md`「`plugin/golang`（公開）」）、基底も相乗りも同じ関数を呼ぶ。相乗りが規則を自分で書き写すことはしない。
- 相乗りが、別の相乗りの出力の形（`go-valid` が `Validate` を出す型）を前提にするときも同じで、その規則を写した公開の SDK（`plugin/govalid`）を呼ぶ。
- `View` が形のために持つもの（`docs/ir.md`「その名前空間から見た IR」）:

| `View` の項目 | 相乗りが知ること |
|---|---|
| `config.dir`、`config.out` | 自分のファイルを置く Dir(U, N) |
| `config.transpilers`、`config.base` | 同じ単位に並ぶトランスパイラと、その基底（依存がそろっていることは、hozoc が CFG-19 / CFG-20 で確かめてから頼む） |
| `config.options` | 単位のすべてのトランスパイラへのオプション（基底のオプションで形が変わるなら、それを再現できる） |
| `config.seams` | 単位の継ぎ目（`docs/config.md`「継ぎ目」）: どのデコレータの継ぎ目を、単位のどのトランスパイラが宣言したか。基底はこれで二層にする op を決め、宣言したトランスパイラは、同じ値から、自分が中身を出す口を基底と同じに求める。ほかの相乗りも、基底の `New` の引数が増えることを、ここから知る |
| `files` | 単位の対象の宣言（`in`） |
| `namespaces` | ほかの名前空間の型の置き場（`docs/config.md`「型の置き場」）: どの単位が、どの基底で、どこへ出力するか |
| `program`、`ops` | 仕様のすべてと、計算した結果（例外、効果、読む状態、純粋さ、`bind` の位置） |
| `entries` | 入口ごとの、求めるケース（`docs/check.md`「入口ごとの、求めるケース」）: 起こりうる結果、例外の出どころ、そこへ、差し替えで入らせる方法、受ける道。プラグインは、同じ計算を、しない（`docs/decisions.md`「決めたこと」409） |

- 相乗りが足すファイルと公開の名前は、基底と、同じ基底のほかの相乗りのものと当たらないように、プラグインの文書で決める（`docs/plugin-go.md`「相乗りのファイル」が、Go の相乗りの決まりの持ち主）。当たったファイルは CFG-5 になる。

## 検査のための頼みごとを、なくしたこと

版 0.21 までは、検査のための頼みごと（direction `check`: `{ "view": … }` を受け取り、`{ "diagnostics": [ … ] }` を返す）と、マニフェストの `[check] enabled` があり、`hozoc build --no-emit` は、プラグインと出力の組ごとに `check` を、`hozoc build` は、その後に、トランスパイラと出力の組ごとに `emit` を、頼んでいた。版 0.22 でなくした（`docs/decisions.md`「決めたこと」411、416）。

- 言語のプラグインへの頼みごとは、`emit` の一つ。検査は、同じ答えの、診断だけを使う（「起動」）。
- `check` を、`emit` と同じ検査で答える SDK の関数（`CheckByEmit`）と、`Handler` の `Check` は、持たない。
- 語彙に固有の検査だけを返すプラグイン（トランスパイラを持たず、`check` だけを持つもの）は、書けなくなった。語彙のプラグインの頼みごと（読み解く。同 410、416）が入るまで、語彙の規則は、それを読むトランスパイラが、`emit` の `errors` で返す。
- direction `check` を送られたプラグインは、`code: "unsupported"` で断る（知らない direction）。

## 選択をなくしたこと

版 0.3 までの `emit` の応答は `select`（`roots` / `stops` / `states` / `wraps`）を持ち、hozoc が、単位のすべてのトランスパイラの `select` を合わせて、本体に組み込んだ出力（「既定の出力」）の対象を決めていた。版 0.4 でなくした（`docs/decisions.md`「決めたこと」77）。

- 何を出すかは、基底が、仕様と設定だけから決める（Go なら `docs/plugin-go.md`「出力の対象」: 型と状態はすべて、op は単位の対象のすべて）。トランスパイラが選ぶ余地はない。
- コードにしたくない op は、単位を置かない名前空間に書くか、`in` で外す（`docs/config.md`「in」）。
- デコレータに応じて包む関数を本体が生成する仕組み（`wraps`）もない。デコレータの意味は、それを読むトランスパイラが形にする（`docs/plugin-go.md`「デコレータ」）。op の中身の前後に処理を置くデコレータは、マニフェストの `seams` で継ぎ目を宣言する（`docs/config.md`「継ぎ目」）。`wraps` と違うのは、宣言が応答ではなくマニフェストにあり（起動の前に決まる）、口を出すのが本体ではなく基底で、中身を出すのが宣言したトランスパイラであること。
- SDK の `Select`、`Wrap` は持たない。「このデコレータが付いた、単位の対象の op」を集める関数（`OpsWith`）は、相乗りが自分の対象を探すための道具として残す。

設計書 §4.6 のマニフェストの `decorate` / `entry` / `stop` も持たない。

## 診断

| ID | 重さ | 意味 |
|---|---|---|
| MAN-2 | error | `protocol` が合わない（マニフェストの `protocol` が、「版の合わせ方」の決まりに合わない。または起動したプラグインが `code: "protocol"` で断った） |
| MAN-3 | error | マニフェストの `name` がディレクトリ名と違う |
| MAN-4 | error | マニフェストを読めない: ファイルを開けない、TOML の構文の誤り、値の型違い、知らないキー、`name` がない、`wasm` がない・空・文字列でない・相対パスでない・ディレクトリの外に出る、`[[transpiler]]` に `name` か `language` がない、`language` が空、`requires` に自分の名前か同じ名前が二度ある、`seams` に空の文字列か同じ FQN が二度ある、`interprets` に空の文字列か同じ FQN が二度ある、同じ FQN が `seams` と `interprets` の両方にある、`requires_vocabulary` に空の文字列か同じ名前が二度ある、同じ名前の `[[transpiler]]` が二つある、`[read]` の `namespaces` がない・空・空の文字列がある・同じ名前が二度ある。使うプラグインの `vocabulary` のファイルを読めないときも MAN-4 |
| MAN-5 | error | プラグインがその `direction`（`[read]` を書いたプラグインの `read` を含む）か、頼まれたトランスパイラを実装していない（マニフェストに書いてあるのに。起動したプラグインが `code: "unsupported"` で断った） |
| MAN-6 | error | マニフェストに `command` がある（子プロセスで起動するコマンド。なくした書き方: 「マニフェスト」の `wasm`）。メッセージは、`wasm` に、WASM のファイルの場所を書くことを、示す。使っていないプラグインにも、報告する（MAN-4 と同じ） |
| PLG-1 | — | 応答の `files` の `path` が、その出力の Dir(U, N) の下にない（「emit」） |
| PLG-2 | — | トランスパイラ一つの答えの中で同じ `path` が二度 |
| PLG-4 | — | 応答の `files` の、テストの対応表の、名前か中身が、約束の形でない（「テストの対応表」） |
| PLUGIN | warning | トランスパイラの `warnings`（「emit」）と、語彙のプラグインの `warnings`（「read」） |

- MAN-1 は欠番。マニフェストの `[emit]` の `entry` も `decorate` も空であることを報告していた規則で、`[emit]` を `[[transpiler]]` に替えたときになくなった。
- PLG-3 は欠番。応答の `select` が、対象の名前空間にない宣言、種類の違う宣言、単位の対象でない宣言、付いていないデコレータを指していることを報告していた規則で、`select` をなくした（「選択をなくしたこと」）ときになくなった。
- 番号は別の意味に使い回さない（`docs/config.md`「診断」と同じ。欠番の一覧は `docs/requirements.md`「検査の規則の一覧」）。
- MAN-4 の「`language` が `"go"` でも `"ts"` でもない」という条件はなくした（言語の名前は基底が決める。「マニフェスト」）。
- MAN-* は診断で、例外は `ConfigInvalid`。
- PLG-* は診断にならない（重さが「—」）。応答そのものが信用できないので、診断の一覧に足して続けることはせず、例外 `MalformedOutput` で終わる。ID は、その例外のメッセージの頭に書く（`プラグイン fake の出力が約束した形でない: PLG-1: …`）。`--format json` でも `diagnostics` には現れず、`{"error": "MalformedOutput"}` になる（`docs/plugin-go-cli.md`「実行と表示」の `JSONPresenter`）。「応答の形」の誤りも同じ例外で、ID は持たない。
- 終了コードは `docs/diagnostics.md`「終了コード」。

## SDK

Go の `plugin` パッケージ。形は `docs/packages.md`「`plugin`（公開）」。TS の SDK は、外した（`docs/decisions.md`「決めたこと」415）。
