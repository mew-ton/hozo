# テストの重さを、サンプルで数えた記録

## この文書が決めること

何も決めない。Hozo が求めるテスト（`ide-chain.md`「テストの規約」）を、サンプル `order-app`（`tests/samples/order-app/`。`main` の `ba94378`）に当てて、数えた記録。比べるために、サンプル `shop-server` の同じ数字も持つ。

- 数えるために、文書が決めていない点を、仮に決めた（「数え方」）。**仮の決めは、案**で、利用者が確かめていない（`open.md`「聞かずに決めて、確かめていない決定」）。
- 数字から決める点（作られたものだけを通るケースを、どう数え分けるか。公開した op の例外を、言い切る手段）は、`open.md`「Hozo の側の改善する点」が持つ。この文書は、その判断を書かない。

## 数え方

### 単位を足して、出させることは、できなかった

`order-app` は、仕様だけのサンプルで、単位（`[[emit]]`）を持たない。写しの `hozo.toml` に、Go の単位を足して、`hozoc emit` を掛けたが、次の診断で止まった。期待する出力から数えることは、できていない。

| 診断 | 止まった所 | 中身 |
|---|---|---|
| GO-3 | `shipping` と `carrier`、`inventory` と `ordering`、`carrier` と `carriergw` | 出力どうしの import が、循環している（互いの型を使う） |
| GOHTTP-5 | `shopApi.products`、`shopApi.product` | 経路の op の結果の型が、union（`catalog.Fulfilment`）を中に持つ |
| GOVALID-4 | `catalog.Product` のフィールド `fulfilment` | union のアームに、制約を持つ型がある |
| GOVALID-1 | `ordering.Checkout` のフィールド `lines` | `@valid.length` が、配列そのものに付いている |

単位を足す前に、CFG-22 も出た: 外の仕組みの名前空間（`psp`、`carriergw`、`assets`、`mailer`）と、語彙の名前空間（`http`、`webhook`）が、型と例外を持つので、同じ基底の単位が要る。足すと、外の仕組みの op は、その単位の、葉の op になる（単位のない名前空間の op ではなくなる）。

### 数えた道

数えたのは、IR から。写しを、設定ごと読み、入口ごとに、Go の SDK の `TestKitOf` と `ThrowSources`（`packages.md` の `plugin/golang`）を呼ぶ、一時の道具で数えた（リポジトリには、残していない）。

- **ケースの数**は、`plugin-go-http.md`「インテグレーションテストの口」の「必要なケース」の決まりを、道具に写して数えた: 正常、入口の層が断る結果（入力が、本文のフィールドか、`@http.required` のフィールドを持つ op）、例外の出どころごと。
- **道具の確かめ**: 同じ道具を `shop-server` に掛けると、38 のケース（人か AI が書く 18、Hozo が作る 20）になり、期待する出力の対応表（`gen/server/servertest/hozo-tests.go-http.json`）と合う。
- **写しに足した単位**は、どれも、基底 `go`: `type`、`http`、`webhook`、外の仕組みの四つ、`domain/` の十一、入口の三つ（`shopApi`、`staffApi`、`hooks`）。画面（`storefront`、`backoffice`）には、単位を置いていない。

### 言葉

| 言葉 | この記録での意味 |
|---|---|
| 入口 | `shopApi`、`staffApi`、`hooks` の、`@http.get` か `@http.post` の付いた op。25 |
| 外の仕組み | 名前空間 `psp`、`carriergw`、`assets`、`mailer` の op と、`clock.now`。10。単位を足したので、出どころの種類は葉になるが、人か AI が書いた中身には、数えない |
| 人か AI が書いた中身 | 本物として動く、葉の op（外の仕組みと、`never` を返す op を除く）と、述語で決まる、値の分類の判定 |
| 画面の側 | 名前空間 `storefront`、`backoffice` |

### 「道の上に、人か AI が書いた中身があるか」の決め方

ケースごとに、入口から、そのケースの終わり（正常のケースなら、op の終わり。例外のケースなら、出どころ）までの道を、仕様から辿って、三つに分ける。走らせては、いない。

| 分け | 条件 |
|---|---|
| ある | 道の上で、人か AI が書いた中身が、必ず、評価される |
| 用意しだい | 評価されるかが、ケースの用意で変わる（繰り返しの中。`throw` でないアームが、二つ以上ある `match` の、片方のアームの中） |
| ない | 道の上に、人か AI が書いた中身が、一つもない |

- **葉の op** は、呼ばれた所で、評価された、と数える。そのケースの出どころが、その葉なら、数えない（投げるのは、葉のにせもの）。
- **述語で決まる分類の `match`** は、`throw` でないアームが、一つだけなら、判定が、評価された、と数える。二つ以上あって、出どころが、その片方のアームの中なら、数えない（判定のにせものが、そのアームだと言う）。出どころが、その `match` の `throw` のアームなら、数えない（同じ）。
- **型で決まる分類の `match`、`read fn`、`effect fn`、外の仕組み、継ぎ目**は、数えない。
- **入口の層が断る結果**（`BadRequest`）は、op を呼ぶ前に終わるので、「ない」。
- **同じ出どころに、二つの道で届くとき**は、辿った順で、はじめの道で分ける。
- **「ある」は、その中身を、確かめている、という意味ではない。** Hozo が作るケースの結果（どの例外になるか）を決めるのは、いつも、にせもの（`ide-chain.md`「インテグレーションテストの作り直し」の「Hozo が作る、例外のケース」）。人か AI が書いた中身は、その手前で、失敗せずに通っただけ。

`export` の op は 96（入口が 25、外の仕組みの op が 10、ほかが 61）。どれも、サーバーの側。インテグレーションテストの口が出るのは、入口の 25 だけ。

## 分かったこと

- **`order-app` は、今の基底とプラグインでは、出せない。** 止めたのは、名前空間どうしの型の循環（GO-3）、union の通信の上の形（GOHTTP-5）、union の値の制約（GOVALID-4）、配列そのものの制約（GOVALID-1）。
- **外の仕組みの名前空間が、型を持つと、単位が要り、その op は、葉になる。** `shop-server` の `mailer` は、型を `type` に置いているので、単位がなく、外の仕組みの op として、にせものになる。`order-app` の `psp` や `carriergw` は、自分の型を持つ。
- **出どころごとに分けると、ケースは、例外の数の、およそ 1.5 倍になる**（96 が 142）。増える分は、ほぼ、`staffApi` の認証（四つの出どころが、13 の入口に）。
- **Hozo が作るケースは、全体の半分を超える**（186 のうち 107）。人か AI が書く例外のケースは 35 で、そのうち 11 は、出どころが見つからない例外。
- **出どころが見つからない例外は、読む者のないデコレータが運ぶもの**: 外の仕組みの op の `@http.post` が、呼ぶ側に足す例外、`@webhook.signed`、`@outside.failsAs`。
- **Hozo が作るケースで、道の上に、人か AI が書いた中身が「ない」ものは、`order-app` では、三つに一つ**（107 のうち 34）、`shop-server` では、ほとんど（20 のうち 17）。違いは、出どころの手前に、本物の葉があるか: `order-app` の `staffApi` は、認証の途中に、葉 `staff.requireFresh` があり、その先の出どころは、どれも、それを通る。
- **正常のケースには、ほぼ、人か AI が書いた中身がある**（25 のうち、必ずあるものが 20）。
- **葉に例外を一つ足すと、口のない `export` の op にも、同じくらい、広がる**（延べ 122 のうち、口のある入口が 59、口のない op が 63）。
- **`catches` を持つデコレータの適用は 67 で、そのうち 59 は、画面の側。**
