問いの中身（何が起きたか、選択肢、勧め）の持ち主は、行が「持ち主」の列で名指しする文書と見出し。この文書は、それを書き写さない。持ち主のない点だけは、この文書の「持ち主のない点」が、見出し一つにつき一つ持つ。

「要るもの」の列は、その点を閉じるのに要るもの:

| 要るもの | 意味 |
|---|---|
| 判断 | 利用者が、選択肢から選ぶ。聞き方は、リポジトリ直下の `CLAUDE.md`「判断は、一つずつ聞く」 |
| 設計 | 選択肢がまだない。設計を書いてから、判断を聞く |
| 確かめ | 聞かずに決めて、もう実装してある。利用者が、それでよいかを見る |
| 作業 | 判断は要らない。直すだけ |

## 一覧の直し方

- **点が決まったら**: 決定を `spec/decisions/` に足し（`CLAUDE.md`「決定は、spec/decisions/ に足す」）、持ち主の文書を直し、この文書の行（と、「持ち主のない点」の見出し）を消す。
- **新しい点を見つけたら**: 持ち主の文書に書き、この文書に一行を足す。持ち主にできる文書がなければ、「持ち主のない点」に見出しを足す。

## 持ち主のない点

### 出力のコードに出る、Hozo の概念の名前

方針（見込み）の持ち主は、`requirements.md`「出力に、Hozo の概念の名前を出さない」。当てる範囲は、出力の全体（決定 D288）。

今の Go の基底は、この方針に、合っていない: インターフェース `Leaves`、`Seams` を出し、`New` の引数 `leaves`、`seams` で、実装を受け取る（`plugin-go.md`「実装を受け取る口」「継ぎ目」）。今は、直さない。

決めていないこと:

- **方針を、原則にするか**: 今は、考え中。
- **当たる名前**: `Leaves`、`Seams` のほか、`Ops`、`<op>Body`、`New` が、当たるか。
- **代わりの形**: 概念の名前を出さずに、実装を受け取り、継ぎ目を通す形。
- **Go の基底を、いつ直すか**: 作り直しの段階（`requirements.md`「作り直しの段階」）の、どこに入れるか。
- **形が `nullable` の状態の単位の、`IsEmpty`**: 標準の分類 `nullable` のケースの名前は、`None` / `Some` になった（決定 D362）が、単位のメソッドは、`list` と同じ `IsEmpty` のまま（`plugin-go.md`「状態の単位」）。仕様の名前と、そろえるか。
- **道具が読む印**: `// <hozoc: generated>`、`// <hozoc: slot>`（決定 D287）と、ファイルの頭の `DO NOT EDIT` は、道具の名前と、Hozo の言葉を、コメントに出す。方針を、API に出る名前（型、関数、引数）と、道具が読む印（コメント）に、分けて当てるか（別のセッションのレビュー）。
- **TS の基底での、包む式の部品**: デコレータは、関数を包む式で写す（決定 D292）。`decorate` を、どこが持つか（SDK か、作ったコードか）。包む処理（`rateLimit`）の実装を、どこから受け取るか（`import` か、引数か）。

配線の op を手で書く道（決定 D283、D287）を、葉と同じ口（`Leaves`）に替える案は、この方針に、合わない。

### 段階を変える書き換え

行のケースを変える `put` の効果に `@db.update` を付けると、何も変わらない: 行の引数の型（`Order on Stage.Accepted`）は、前のケースにある行を渡すことを求め、`@db.update` は、渡した行の全体を書く。今は、それを DB-17 にして、効果の中身を人が書く（`plugin-db.md`「効果」、決定 D170）。サンプル `order-app` では、`db` のデコレータを付けた効果が、15 から 9 に減った（`tests/samples/order-app/README.md`「分かったこと」の F51）。

- **A: 今のまま。** 人が書く。
- **B: 「どの列を、どの引数で書き換えるか」を言う語彙を足す。** 行はキーで選び、書いた列だけを書き換える。

  ```ts
  @db.set("startedAt", "at")
  effect fn startJob(job: Job on Progress.Queued, at: datetime): effects jobs.put as Progress.InProduction;
  ```

- **C: `put` の行の引数を、書き換えた後の行にする。** 呼ぶ側の検査を、後のケースの側に移す。

勧めは B: `requirements.md`「出力を推論しない」の「人が書くコードを、できるだけ減らす」に合う。列の名前は、`@db.where` と同じく、デコレータの引数に書く。利用者に聞いて、答えを待っている。

### 否定の側の宣言

述語で決まる分類は、ケースの数だけ、人が述語を書く。`Awaiting` が `Complete` の否定であることは、仕様に書けず、二つが排他で、全体を覆うことは、書く人が担保する（`tests/samples/order-app/README.md`「分かったこと」の F45、F48。決定 D158 の（a））。

案: 否定の側を、導くのではなく、宣言する。

```ts
classify Gathered of Shipment { Complete; Awaiting: not Complete; }
```

述語は一つで済み、排他と網羅を、言語が保証できる。158 の（a）（言語も基底も、残りを導かない）とは、当たらない: 残りを黙って作るのではなく、書いてある。採るか、今のままにするかは、決めていない。

### ない側のケースの二つの書き方

`T?` の分類の「ない」側は、`<名前>: T? as none;` とも、ほかのケースが `T` を挙げているときの `<名前>: T? as else;` とも書ける（`check.md`「ない側のケース」「残りのケース」）。どちらを勧めるかの指針は、`requirements.md`「書き方の指針」にない。サンプルは、どちらも使っている。

### IR の純粋さ

`Op.signature.pure`（`check.md`「純粋」）は、IR に残っているが、基底 `go` は読まない（`plugin-go.md`「op の形」）。今、読む者はいない。使い道（テストの生成など）を決めて残すか、IR から消すかは、決めていない。消すなら、IR の版が上がる。

### 誤りを伝える三つの道

仕様が誤りを伝える道は、三つある。

| 道 | 仕様に現れるか | 受けられるか |
|---|---|---|
| 仕様の例外 | `throws` に現れる | デコレータの `catches` |
| 値（`T?`、union） | 戻り値の型に現れる | `match` |
| 分類の誤り | 現れない | 受けられない（`check.md`「閉じた分類」） |

使い分けは、ばらばらの場所にある: 分類の誤りと、ケースとして宣言することは `requirements.md`「書き方の指針」、例外の値が画面に届かないことは `tests/samples/order-app/README.md`「分かったこと」の F4、F5。境界（HTTP の入口、画面）で、どの道で何を伝えるかを、一か所にまとめた指針は、ない。書くかどうかは、決めていない。

### 基底の形を、データで渡す

相乗りは、基底の名前と置き場を、基底の規則の写しから自分で求める（`plugin-protocol.md`「相乗りが基底の形を知る方法」）。Go では、写しを一つのライブラリ（`plugin/golang`）で共有している。TS の基底（`requirements.md`「段階」の段階 5）では、同じ規則を `sdk/ts` にもう一度書くことになる。

案: 基底が出す名前と形を、規則ではなく、結果のデータとして `View` に載せる。採るかどうかは、段階 5 を始める前に決める。

### `shop-server` の、引数を持つ例外

サンプル `shop-server` の仕様が宣言する例外は、どれも引数を持たない。引数を持つ例外を通るのは、語彙の `http.BadRequest` だけ。サンプルに一つ足すかは、決めていない。足すなら、期待する出力（`gen/**`）を、先に手で書く。

### 自己生成が越えられない変更

生成物の形が変わる変更（`Leaves` や、状態の単位のメソッドの形が変わるもの）では、`make generate` が、手順の 3 で止まる: `internal/app` が、古い形と新しい形を、同時には満たせない（手順は `packages.md`「自己生成の手順」）。

これまでの越え方: リポジトリのルートで `go run ./cmd/hozoc build` を直に走らせ（同じ見出しが言う、確かめずに置き場へ書く道）、`internal/app` を新しい形に合わせ、`make generate` を二度走らせて、何も変わらないことを確かめる。

この場合の手順は、`packages.md` に書いていない。手順を書き足すか、道具（`internal/tools/selfgen`）を直すかは、決めていない。

### 設計書との違いの一覧の残り

- `cli.md`「cli.hozo」の、「設計書の `examples/hozoc.hozo` を元に、次を変えたもの」の一覧。
- `tests/corpus/design/README.md`「設計書から変えた箇所」。

コーパス `design` は、設計書の例を集めたものなので（`testing.md`「コーパス」）、写せなかった箇所の一覧は、コーパスの説明でもある。消すか、出どころの記録として残すかは、決めていない。

### `testing.md` と、仕様だけのサンプル

`testing.md`「サンプル」は、`TestSamples` が、サンプルごとに `check`、`files`、`go`、`transpilers/*` を確かめると言う。仕様だけのサンプルに作るのは、`check` だけ（`tests/samples/README.md`「仕様だけのサンプル」）。`testing.md` の文に、その断りと、持ち主の名指しを足す。

### 行の遷移の表示の二つの実装

行の遷移を文字にする組み立て（`as Progress.InProduction` の形）と、絞り込んだ型を文字にする組み立て（`Job on Progress.Queued` の形）が、`plugin/golang`（`RowDisplay`、`NarrowedParamsDisplay`）と、言語サーバーのホバーの二か所にある（絞り込んだ型は、`ir` の `CaseType.String` にも）。hozoc の本体は `plugin/golang` を import できない（`packages.md`「依存の向き」）。文書は、二つに同じ形を言う。食い違わないことを確かめるテストは、ない。

### `OutputsSync` の判定

状態の分類 `OutputsSync` の述語は、`UpToDate` と `OutOfDate` の二つで、どちらも、生成し直した内容とディスクを比べる（`cli.md`「手で書くもの」）。判定関数 `ClassifyOutputsSync` は、二つの述語を呼ぶので、生成し直し（トランスパイラの起動）が、二度走る。今、呼ぶのはテストだけ。
