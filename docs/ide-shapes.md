# 図形のプラグイン

## この文書が決めること

IDE のノート（`ide-screens.md`「ノート」）に置く図形と線を、プラグインが、どう定義するか。IDE の設計の段 3（`tools.md`「IDE の設計の段階」）の一部。

決まっていること（`decisions.md`「決めたこと」199、201、203）は、「決まっている前提」の節。**そのほかは、後で決める**（同 203）: この文書の、分け方、定義の項目、例、見た目のコードの形は、そのときの材料として残す案で、どれも、決まりではない。

## 決まっている前提

- **図形は、プラグインが作る。** IDE は、設計の手法ごとの図形を、自分では持たない。IDE が持つのは、図形を、自由に置き、つなぐ仕組み。
- **図形の定義が持つもの**: 形、入力の欄、線をつなぐ口（つなぎ口）、つなげる相手。
- **線の種類は、多くない。** プラグインが決めるのは、線の見た目（スタイル）と、「何と何の、どことどこを、どの線で結べて、結んだ結果、仕様（`.hozo`）が、どう変わるか」。
- **狙い**: 設計の手法は、数が多く、IDE が、すべてを作り込むことはできない。図形をプラグインにすれば、手法を、後から、誰でも足せる。
- **図形の見た目は、プラグインが、コードで書ける。** 決まった形と欄だけで描くと、どの図形も似通って、分かりにくいキャンバスになる（`decisions.md`「決めたこと」201）。
- **単純な図形には、省略形がある。** アイコンを出すだけ、のような図形は、コードを書かずに、宣言だけで定義できる。
- **図形の見た目を、プラグインの側が用意できること。これが、必須の要件。** 見た目を、何で書き、IDE に、どう載せるかは、後で決める。
- **具体的な見た目は、作図が、仕様の何に反映され、どんなハーネスが生まれるかを決めた後で、決める**（`ide-chain.md`。`decisions.md`「決めたこと」216）。

## 分け方

| 持つもの | 中身 |
|---|---|
| IDE | ノート（自由なキャンバス）。図形を置く、動かす、つなぐ、選ぶ、写す、戻す。ノートのファイルの読み書き。図形の定義を読み、そのとおりに描く。図形と仕様を、結び付けたままにする（仕様が変われば、図形が変わる。図形を直せば、仕様が変わる） |
| `hozoc` | 仕様を読み、検査する。仕様の要素と、そのつながりを、問い合わせに答えて返す。要素を直す操作（宣言を足す、名前を変える、など）を受けて、文面を書き換える |
| 図形のプラグイン | 図形と線の定義。それぞれが、仕様のどの要素、どのつながりに当たるか。置いたとき、つないだとき、直したときに、`hozoc` のどの操作を呼ぶか |

### 意味は宣言で、見た目はコードで

図形の定義は、二つの部分に分かれる。

| 部分 | 書き方 | 中身 | なぜ |
|---|---|---|---|
| 意味 | 宣言（データ） | 当たる要素、入力の欄と要素の項目の対応、つなぎ口、つなげる相手、入れ物、置いたとき・直したとき・消したときの操作 | IDE と `hozoc` が、実行する前に読めなければならない: 線を引けるかの判定と、仕様との結び付きは、見た目のコードを動かさずに決まる |
| 見た目 | コード。または、省略形（宣言） | 図形の描き方。欄を、どう並べ、どう飾るか | 手法ごとに、見て分かる違いを持たせる |

- 見た目のコードが受け取るのは、当たる要素の項目の値と、図形の様子（選ばれているか、大きさ、拡大の度合い）。返せるのは、「この欄を、この値に直したい」という求めだけ。仕様を変える道は、意味の部分に宣言した操作だけ。
- **IDE が、どの図形にも、同じに付けるもの**: 選んでいる枠、つなぎ口、大きさを変える取っ手、重ねの印（`ide-screens.md`「重ね」）。見た目のコードは、これらを描かない。プラグインが違っても、操作は、そろう。
- 色は、IDE の色の決まり（明るい、暗い）から取る。見た目のコードは、色そのものを決めない。
- ノートを縮めて見るとき、IDE は、見た目のコードを動かさず、図形のアイコンと名前だけを出す（図形の数が多いノートの、速さのため）。どの図形の定義も、アイコンを持つ。

プラグインは、文面を、自分では書き換えない。仕様を変える道は、`hozoc` の操作だけ（`tools.md`「操作」の「要素を直す」）。プラグインごとに、文面の書き方が食い違うことを防ぐ。

## 図形の定義

一つの図形の定義が持つもの。

| 項目 | 中身 | 例（状態） |
|---|---|---|
| 名前、説明、属する手法 | 置くものを選ぶところに出る | 「状態」。ステートマシン図 |
| アイコン | 置くものを選ぶところと、縮めて見るときに出す | — |
| 見た目 | コードで書く。または、省略形: 決まった形（角の丸い矩形、だ円、円柱、ひし形、人の形、囲み、札、など）と、出す欄を選ぶだけ | 省略形: 両端の丸い矩形に、名前 |
| 当たる要素 | 仕様の、どの要素か。要素の種類と、条件で言う。当たる要素のない図形は、自由な図形（付箋、ラベル） | 値の分類のケース |
| 入力の欄 | 図形が持つ欄と、それぞれが、要素のどの項目か。欄の種類は、一行の文、文章、選ぶもの、行の一覧（欄の組の繰り返し）。欄を、どう並べて見せるかは、見た目の側 | 名前 ← ケースの名前。説明 ← ケースの説明 |
| つなぎ口 | 線をつなげる場所と、名前 | 上、下、左、右 |
| 入れ物 | 中に入れられる図形と、入れたとき、出したときの操作。入れ物でなければ、持たない | —（担い手なら: 入口を入れると、その入口を、その担い手のものにする） |
| 置いたとき | 新しく描いたときに呼ぶ、`hozoc` の操作。すでにある要素を置くときは、何も呼ばない | 分類に、ケースを足す |
| 直したとき | 欄を打ち直したときに呼ぶ操作 | 名前を変える。説明を書く |
| 消したとき | 「仕様から消す」を選んだときに呼ぶ操作。「ノートから外す」は、何も呼ばない | ケースを消す |

## 線の定義

一つの線の定義が持つもの。

| 項目 | 中身 | 例（向き） |
|---|---|---|
| 名前、説明 | | 「向き」 |
| 結ぶもの | どの図形の、どのつなぎ口から、どの図形の、どのつなぎ口へ | 状態（どの口でも）から、状態（どの口でも）へ。同じ分類のケースどうし |
| 見た目 | 実線、破線、点線。矢じり。線の上の文 | 実線、矢じり。文は、効果の名前 |
| 当たるつながり | 仕様の、どのつながりか。**宣言**（人が引ける）か、**導いたもの**（自動で出るだけ）か | 宣言: 効果の行の遷移 |
| 引いたとき | 呼ぶ操作。導いた線は、持たない | 行の遷移を持つ効果を足す。名前を尋ねる |
| 消したとき | 呼ぶ操作 | その効果を消す |

置いてある二つの図形の間に、当たるつながりが、仕様にあれば、線は、引かなくても出る。

**異なる設計図の図形の間は、関連付けられない**（`decisions.md`「決めたこと」258）。設計図の単位は、ノートの領域（`ide-screens.md`「領域」。`decisions.md`「決めたこと」259）: 線の定義が、「結ぶもの」に挙げられるのは、同じ領域に置ける図形だけで、線は、領域をまたげない。狙いは、設計図ごとに、図形と、つなげる相手を、閉じて決められること。

## 定義の例

何を書くかを示すための例。書き方は、決めていない。

```toml
# 標準の図形: ステートマシン図
[[shape]]
name    = "状態"
method  = "ステートマシン図"
icon    = "state"
look    = { form = "pill", show = ["name"] }   # 見た目の省略形: 決まった形と、出す欄
binds   = "classify.case"                 # 値の分類のケース
fields  = [
  { label = "名前", to = "name" },
  { label = "説明", to = "description" },
]
handles = ["top", "right", "bottom", "left"]
on_create = "case.add"                    # 置いたとき
on_delete = "case.remove"

[[line]]
name      = "向き"
from      = "状態"
to        = "状態"
style     = { stroke = "solid", head = "arrow", label = "effect.name" }
binds     = "effect.row"                  # 宣言: 効果の行の遷移
on_create = "effect.add_row"              # 引いたとき
on_delete = "effect.remove"

[[line]]
name  = "起こす"
from  = "入口"
to    = "向き"
style = { stroke = "dashed", head = "arrow" }
binds = "derived:entry.causes"            # 導いたもの。引けない
```

```toml
# 語彙 page のプラグインが足す図形: 画面遷移図
[[shape]]
name   = "アプリの画面"
method = "画面遷移図"
icon   = "screen"
render = "shapes/screen.js"               # 見た目を、コードで書く: 独自の要素 <hozo-page-screen> を定義するファイル
binds  = { kind = "op", decorated = "page.route" }
fields = [
  { label = "名前", to = "description.summary" },
  { label = "パス", to = "decorator:page.route.path" },
]
```

## プラグインと、語彙

- **図形の定義は、今のプラグインに、足す。** プラグインは、語彙と、トランスパイラを提供している（`plugin-protocol.md`「この文書が決めること」）。図形の定義を、三つ目の提供するものにする。
- **語彙を提供するプラグインが、その語彙の図形も提供する。** 語彙の意味を知っているのは、そのプラグイン: 語彙 `page` のプラグインが、画面遷移図の図形を、語彙 `db` のプラグインが、ER 図の図形を提供する。IDE と `hozoc` は、語彙の意味を読まない（今の状態: `hozoc` は、語彙の意味を読まない。意味を形にするのは、それを読むトランスパイラ: `plugin-go.md`「デコレータ」）。
- **標準の図形**（入口、手順、もの、状態、データ、例外、コンテキスト、約束、付箋、囲み、ラベル）は、標準の語彙（`vocab.md`）と同じく、`hozoc` に同梱する。
- **仕様に書けない作図は、その手法のプラグインが、語彙（デコレータ）を定義して、受ける**（`decisions.md`「決めたこと」222。`ide-chain.md`「書けない作図の、反映の先」）。担い手、事前条件、遷移の条件、操作の行き先のように、手法が求めて、仕様にないもの（`open.md`「Hozo の側の改善する点」）は、その語彙と図形を、一つのプラグインが、組にして提供する。

## `hozoc` に要るもの

図形のプラグインが、定義の中で名指しするもの。どれも、今は、ない。

| 要るもの | 中身 |
|---|---|
| 要素の種類と、項目の、名前の一覧 | `classify.case`、`op`、`name`、`description` のように、定義が、仕様の要素と項目を指すための名前。もとは IR（`ir.md`） |
| つながりの、名前の一覧 | 宣言のつながり（効果の行の遷移、フィールドの型、デコレータの引数）と、導いたつながり（入口が起こす向き、入口から入口への受け渡し、入口が読み書きするデータ）。導いたつながりは、`hozoc` が計算する（`ide-needs.md`「情報」の「導く」の行） |
| 要素を直す操作の一覧 | 宣言を足す、消す、名前を変える、説明を書く、ケースを足す、行の遷移を持つ効果を足す、フィールドを足す、デコレータを付ける、外す、引数を変える。受けて、文面を書き換える |
| 問い合わせ | 「この定義に当たる要素を、すべて」「この二つの要素の間の、このつながり」に答える |

## 塊

順のあるもの（手順）と、表（状態の表、操作とデータの表）は、ふつうの図形と線では表せない（`ide-screens.md`「塊」）。

- **塊も、図形の一つで、プラグインが提供する。** 手順（配線）を直す図も、同じ: IDE の本体は、手順の図を、特別には持たない。その図を提供するプラグインが、見た目と、中で直したとき（一歩を、足す、消す、入れ替える）の、仕様の変化を決める（`decisions.md`「決めたこと」206）。
- 手順の塊は、言語の核（配線）の図なので、標準の図形として、同梱する。
- 作図になりうる塊（手順、やり取り）は、ノートの領域の種類にする。単体の表は、塊のまま、領域の外に置く（`ide-screens.md`「領域」。`decisions.md`「決めたこと」260）。
- 意味の部分に、「行の集まり」「列の集まり」「ますのつながり」「入れ子と順」を、宣言で言えるようにする必要がある。言い方は、決めていない。

## 決めていないこと

プラグインの細部は、後で決める（`decisions.md`「決めたこと」203）。決めるときの材料:

- **見た目を、何で書くか。** 有力な案は、画面の標準の部品（Web Components: プラグインが、図形ごとに、独自の要素を一つ定義する）。IDE の枠組み（React など）の部品で書く形は、プラグインが、IDE の枠組みと、その版に縛られる（一度、標準の部品と決めた: 同 202。203 で、後で決め直すものに戻した）。
- **見た目を、IDE に、どう載せるか。** 安全（プラグインのコードが、IDE の画面、手元のファイル、殻の機能に届かないこと）、見た目の隔離、ライブラリの共存、壊れにくさ、という非機能の要件が、掛かる。候補:
  - 隔離した iframe に載せる。要件は満たせるが、図形一つにつき一つでは、数（図形 300 のノート）と、操作（iframe の中のマウスの動きは、外に伝わらない: つかむ、線を引く、拡大する、が効かない）が苦しい。macOS の表示の部品は、iframe を別のプロセスに分けないので、プラグインが止まると、IDE も止まる。
  - 同じ画面に、直に載せる。速いが、安全は得られない。
  - 分ける: 同梱の標準の図形は直に、ほかのプラグインの図形は iframe に。縮めて見るときは、コードを動かさず、アイコンと名前だけ。
  - どれにしても、プラグインとの約束を、「値を受け取り、求めを出すだけ」の、メッセージで送れる形にしておけば、載せ方は、IDE の側で選べる。
- 定義の、意味の部分の書き方（ファイルの形と、置き場）。省略形で選べる、決まった形の一覧。
- 二つのプラグインが、同じ要素に当たる図形を定義したとき。
- 設計図（領域の種類）の定義の、持ち方: 一つのプラグインが、その設計図の図形と線を、まとめて定義する形にするか。今の標準の図形（`ide-screens.md`「結ばれた図形」）は、設計図ごとに、分かれていない。
- 自動で出る線（導いた線）を、領域の中だけにするか（案: 中だけ）。
- 塊の、意味の部分の言い方。
