# 図形のプラグイン

## この文書が決めること

IDE のノート（`ide-screens.md`「ノート」）に置く図形と線を、プラグインが、どう定義するか。IDE の設計の段 3（`tools.md`「IDE の設計の段階」）の一部。

決まっていること（`decisions.md`「決めたこと」199）は、「決まっている前提」の節。**そのほかは、案**で、利用者が確かめていない（`open.md`「聞かずに決めて、確かめていない決定」）。定義の書き方（ファイルの形）は、決めていない: この文書の例は、何を書くかを示すためのもので、書き方の決まりではない。

## 決まっている前提

- **図形は、プラグインが作る。** IDE は、設計の手法ごとの図形を、自分では持たない。IDE が持つのは、図形を、自由に置き、つなぐ仕組み。
- **図形の定義が持つもの**: 形、入力の欄、線をつなぐ口（つなぎ口）、つなげる相手。
- **線の種類は、多くない。** プラグインが決めるのは、線の見た目（スタイル）と、「何と何の、どことどこを、どの線で結べて、結んだ結果、仕様（`.hozo`）が、どう変わるか」。
- **狙い**: 設計の手法は、数が多く、IDE が、すべてを作り込むことはできない。図形をプラグインにすれば、手法を、後から、誰でも足せる。

## 分け方

| 持つもの | 中身 |
|---|---|
| IDE | ノート（自由なキャンバス）。図形を置く、動かす、つなぐ、選ぶ、写す、戻す。ノートのファイルの読み書き。図形の定義を読み、そのとおりに描く。図形と仕様を、結び付けたままにする（仕様が変われば、図形が変わる。図形を直せば、仕様が変わる） |
| `hozoc` | 仕様を読み、検査する。仕様の要素と、そのつながりを、問い合わせに答えて返す。要素を直す操作（宣言を足す、名前を変える、など）を受けて、文面を書き換える |
| 図形のプラグイン | 図形と線の定義。それぞれが、仕様のどの要素、どのつながりに当たるか。置いたとき、つないだとき、直したときに、`hozoc` のどの操作を呼ぶか |

プラグインは、文面を、自分では書き換えない。仕様を変える道は、`hozoc` の操作だけ（`tools.md`「操作」の「要素を直す」）。プラグインごとに、文面の書き方が食い違うことを防ぐ。

## 図形の定義

一つの図形の定義が持つもの。

| 項目 | 中身 | 例（状態） |
|---|---|---|
| 名前、説明、属する手法 | 置くものを選ぶところに出る | 「状態」。ステートマシン図 |
| 形 | 決まった形の中から選ぶ（角の丸い矩形、だ円、円柱、ひし形、人の形、囲み、など）。色は、役（主、補助、注意）で言い、色そのものは、IDE の色の決まりが持つ | 両端の丸い矩形 |
| 当たる要素 | 仕様の、どの要素か。要素の種類と、条件で言う。当たる要素のない図形は、自由な図形（付箋、ラベル） | 値の分類のケース |
| 入力の欄 | 図形の中に出す欄と、それぞれが、要素のどの項目か。欄の種類は、一行の文、文章、選ぶもの、行の一覧（欄の組の繰り返し） | 名前 ← ケースの名前。説明 ← ケースの説明 |
| つなぎ口 | 線をつなげる場所と、名前 | 上、下、左、右 |
| 入れ物 | 中に入れられる図形と、入れたとき、出したときの操作。入れ物でなければ、持たない | —（担い手なら: 入口を入れると、その入口を、その担い手のものにする） |
| 置いたとき | 新しく描いたときに呼ぶ、`hozoc` の操作。すでにある要素を置くときは、何も呼ばない | 分類に、ケースを足す |
| 直したとき | 欄を打ち直したときに呼ぶ操作 | 名前を変える。説明を書く |
| 消したとき | 「仕様から消す」を選んだときに呼ぶ操作。「ノートから外す」は、何も呼ばない | ケースを消す |

## 線の定義

一つの線の定義が持つもの。

| 項目 | 中身 | 例（向き） |
|---|---|---|
| 名前、説明 | | 「向き」 |
| 結ぶもの | どの図形の、どのつなぎ口から、どの図形の、どのつなぎ口へ | 状態（どの口でも）から、状態（どの口でも）へ。同じ分類のケースどうし |
| 見た目 | 実線、破線、点線。矢じり。線の上の文 | 実線、矢じり。文は、効果の名前 |
| 当たるつながり | 仕様の、どのつながりか。**宣言**（人が引ける）か、**導いたもの**（自動で出るだけ）か | 宣言: 効果の行の遷移 |
| 引いたとき | 呼ぶ操作。導いた線は、持たない | 行の遷移を持つ効果を足す。名前を尋ねる |
| 消したとき | 呼ぶ操作 | その効果を消す |

置いてある二つの図形の間に、当たるつながりが、仕様にあれば、線は、引かなくても出る。

## 定義の例

何を書くかを示すための例。書き方は、決めていない。

```toml
# 標準の図形: ステートマシン図
[[shape]]
name    = "状態"
method  = "ステートマシン図"
form    = "pill"
binds   = "classify.case"                 # 値の分類のケース
fields  = [
  { label = "名前", to = "name" },
  { label = "説明", to = "description" },
]
handles = ["top", "right", "bottom", "left"]
on_create = "case.add"                    # 置いたとき
on_delete = "case.remove"

[[line]]
name      = "向き"
from      = "状態"
to        = "状態"
style     = { stroke = "solid", head = "arrow", label = "effect.name" }
binds     = "effect.row"                  # 宣言: 効果の行の遷移
on_create = "effect.add_row"              # 引いたとき
on_delete = "effect.remove"

[[line]]
name  = "起こす"
from  = "入口"
to    = "向き"
style = { stroke = "dashed", head = "arrow" }
binds = "derived:entry.causes"            # 導いたもの。引けない
```

```toml
# 語彙 page のプラグインが足す図形: 画面遷移図
[[shape]]
name   = "アプリの画面"
method = "画面遷移図"
form   = "screen"
binds  = { kind = "op", decorated = "page.route" }
fields = [
  { label = "名前", to = "description.summary" },
  { label = "パス", to = "decorator:page.route.path" },
]
```

## プラグインと、語彙

- **図形の定義は、今のプラグインに、足す。** プラグインは、語彙と、トランスパイラを提供している（`plugin-protocol.md`「この文書が決めること」）。図形の定義を、三つ目の提供するものにする。
- **語彙を提供するプラグインが、その語彙の図形も提供する。** 語彙の意味を知っているのは、そのプラグイン: 語彙 `page` のプラグインが、画面遷移図の図形を、語彙 `db` のプラグインが、ER 図の図形を提供する。IDE と `hozoc` は、語彙の意味を読まない（今の状態: `hozoc` は、語彙の意味を読まない。意味を形にするのは、それを読むトランスパイラ: `plugin-go.md`「デコレータ」）。
- **標準の図形**（入口、手順、もの、状態、データ、失敗、コンテキスト、約束、付箋、囲み、ラベル）は、標準の語彙（`vocab.md`）と同じく、`hozoc` に同梱する。
- 手法が求めて、仕様にないもの（`open.md`「Hozo の側の改善する点」）のうち、語彙で言えるもの（担い手、画面の行き先、表の間の関連、約束）は、その語彙と図形を、一つのプラグインが、組にして提供できる。

## `hozoc` に要るもの

図形のプラグインが、定義の中で名指しするもの。どれも、今は、ない。

| 要るもの | 中身 |
|---|---|
| 要素の種類と、項目の、名前の一覧 | `classify.case`、`op`、`name`、`description` のように、定義が、仕様の要素と項目を指すための名前。もとは IR（`ir.md`） |
| つながりの、名前の一覧 | 宣言のつながり（効果の行の遷移、フィールドの型、デコレータの引数）と、導いたつながり（入口が起こす向き、入口から入口への受け渡し、入口が読み書きするデータ）。導いたつながりは、`hozoc` が計算する（`ide-needs.md`「情報」の「導く」の行） |
| 要素を直す操作の一覧 | 宣言を足す、消す、名前を変える、説明を書く、ケースを足す、行の遷移を持つ効果を足す、フィールドを足す、デコレータを付ける、外す、引数を変える。受けて、文面を書き換える |
| 問い合わせ | 「この定義に当たる要素を、すべて」「この二つの要素の間の、このつながり」に答える |

## 塊

順のあるもの（手順）と、表（状態の表、操作とデータの表）は、図形と線では表せない（`ide-screens.md`「塊」）。

- 塊も、図形の一つとして、同じ定義の仕組みに乗せたい: 入力の欄の種類に、「行の一覧」「入れ子の一覧」「表（行の集まり、列の集まり、ますのつながり）」を持たせる。
- 乗せられるかは、決めていない。手順の塊（配線の、入れ子と順）は、言語の核そのものなので、IDE が持つ、決まった欄の種類になる見込み。

## 決めていないこと

`open.md`「次の段」に置いたもの。

- **定義を、データだけで書くか、コードも許すか。** データだけなら、IDE が、決まった描き方で描く（どのプラグインの図形も、同じ操作感になり、安全）。コードを許すと、何でも描けるが、IDE の中で、プラグインのコードが動くことになる。
- 定義の書き方（ファイルの形と、置き場）。
- 形の一覧（決まった形で、足りるか）。
- 二つのプラグインが、同じ要素に当たる図形を定義したとき（一つの要素を、いくつもの図形で置けるのは、よい。置いていない要素を、はじめに、どの図形で置くか）。
- 塊を、定義の仕組みに乗せるか。
