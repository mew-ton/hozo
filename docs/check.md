# 検査

この節の細部は、決定 D581 が決めた。

## この文書が決めること

`hozoc build --no-emit` と `hozoc lsp` が IR（`docs/ir.md`）の上で行う計算と、規則ごとの検査の手続き・診断を決める。規則の ID と、短く言った意味は `docs/requirements.md`「検査の規則の一覧」にあり、ここでは、その手続きを書く。その一覧にない規則は、この文書の「診断」の各表が持ち主。名前の解決（`RES-*`）と型（`TYPE-*`、`LIT-1`）はそれぞれ `docs/resolve.md`「診断」、`docs/types.md`「診断」。

検査は IR が作れた後に行う。IR を作る途中（解析、解決、正規化）の誤りがあるファイルでも、作れた部分には検査を行う（`docs/requirements.md`「言語サーバー」）。一つの検査で見つかる誤りはすべて報告する。

## 状態の形

設計書 §5.2 の状態の形を、状態を分類で表す決定と、形と型を揃える決定（決定 S1〜S9、S21）に合わせて定める。

### 基底の状態

基底の状態は、名前空間が持つ値。型は宣言に書いた型（`State.type`。形の語と `?` / `[]` のどちらで書いても同じ。`docs/types.md`「形の書き方」）で、**形**はその型の最も外側から決まる。形は列数の範囲を表し、形ごとに組み込みの分類と組み込みの効果が決まる。

| 状態の型 | 形（`State.shape`） | 要素（`State.element`） | 列数 | 組み込みの分類 | 組み込みの効果 |
|---|---|---|---|---|---|
| `array(T)`（`list<T>`、`T[]`） | `list` | T | 0 以上 | `Empty` / `HasItems` | `post` / `put` / `delete` |
| `optional(T)`（`nullable<T>`、`T?`） | `nullable` | T | 0 か 1 | `None` / `Some` | `post` / `put` / `delete` |
| それ以外（`single<T>`、`T`） | `single` | その型 | ちょうど 1 | なし（常に一列） | `put` |

- 形を決めるのは最も外側だけ: `T[]?` は `nullable`（要素は `T[]`）、`T?[]` は `list`。`list` の要素は `optional` にできない（STATE-3）。
- 組み込みの分類は、形の型についての標準の分類（「分類」の「標準の分類」）を、その状態に当てたもの。
- 状態は、持ち主の名前空間の配線の中で、名前で値として読める（「op の宣言と本体」の「状態の参照」）。

組み込みの効果は列数の相対的な変化。`post` は増える、`put` は変わらない、`delete` は減る。組み込みの分類をどう変えるかは形から決まる。

| 形 | `post` | `put` | `delete` |
|---|---|---|---|
| `list` | どの場合でも → `HasItems` | `HasItems` → `HasItems` | `HasItems` → `Empty` か `HasItems` |
| `nullable` | `None` → `Some` | `Some` → `Some` | `Some` → `None` |

### 状態の分類

`classify` は、一つ以上の基底の状態を対象にして、その場合に名前を付ける。これを**状態の分類**と呼ぶ（型を対象にした `classify` は値の分類、op を対象にしたものは op の分類。「分類」）。状態の分類は、基底の状態と並ぶもう一つの「状態」でもある: 効果の宛先になり（「効果の宛先」）、配線が `match (by C)` で読み、Go の基底の出力では、述語で決まるものが、基底の状態と同じく状態の単位になる（`docs/plugin-go.md`「状態の単位」）。基底の状態と並べて言うときも「状態の分類」と呼び、別の言葉（「分類の状態」）は使わない。値の分類（§10.1）と同じく、名前と説明を宣言し、判定は述語として人が実装する（型で決まる分類を除く。「分類」の「ケースの判定」）。ケースが排他で、宣言したケースがすべてであること（「分類」の「閉じた分類」）も同じ。対象にできるのは宣言した名前空間の基底の状態だけで（CLS-3）、状態の分類を対象にはできない。効果が書き込む状態を宣言から直接読めるようにするため。

### 効果の宛先

一つの効果が変えるのは、一つの状態の一つの変化だけ。宛先は、基底の状態の組み込みの効果か、分類の遷移（`docs/grammar.md`「exception / effect / read」）。実装が二つの基底の状態を同時に変える効果は、その二つを対象にした状態の分類を宣言し、その遷移として書く。

**効果が書き込む状態**（`Effect.writes`）は、組み込みの効果ならその基底の状態、遷移なら、宛先が状態の分類ならその対象のすべての基底の状態、宛先が基底の状態ならその状態。

宛先が言うのは、どこに、何の操作で書くか。組み込みの効果は、それとは別に、受け取った行の状態がどうなるかを言える（`effects orders.put as Stage.InProduction`）。規則は「行の遷移」。

### read の宛先

`read` の宣言（`docs/grammar.md`「exception / effect / read」）が読むのは、基底の状態一つ。宛先（`Read.state`）は、宣言した名前空間の基底の状態で、別の名前空間の状態なら RES-5、状態でないもの（状態の分類を含む）なら RES-4（`docs/resolve.md`「位置ごとに受け付ける種類」）。状態の分類を宛先にできないのは、分類を読むのが配線の `match (by C)` だから。

### 検査器が遷移を使う範囲

検査器は、遷移のケースの所属（STATE-4）を確かめ、IR に載せるだけ。配線の行をまたいで状態の場合を追うこと（効果の後の `match` で到達しないアームの検出など）はしない。§7.3 の「不明」と絡むので、要るようになってから別に決める。例外と状態の場合を結びつける書き方（`AlreadyLoggedIn` は前の場合が合わなかったことを表す、など）も持たない（§16 の「状態 × 入力の表で分岐を網羅させる」に近づくため）。

リストの一部（「このユーザーのカート」）の場合は状態の分類では言えない。`read`（「状態に触れるもの」）で値を取ってから、値の分類か op の分類で書く。表の一行が、どのケースからどのケースへ進むかは、値の分類と、効果の行の遷移で書く（「行の遷移」）。

## 状態に触れるもの

状態を読み書きするのは、`read` と効果だけ。op は、それを組み合わせる。例外、効果、`read` を同じ書き方にする決定（決定 D133 ほか。段階 R4: `docs/requirements.md`「作り直しの段階」）を、検査の手続きにしたもの。構文は `docs/grammar.md`「exception / effect / read」「配線」。

この節の細部は、決定 D651 が決めた。

### read と効果

状態に触れる最小の単位は二つ。名前を付けた形（宣言）と、名前を付けない形がある。

| 単位 | 名前を付けた形 | 名前を付けない形 | すること |
|---|---|---|---|
| `read` | `read fn userByEmail(email: Email): User? reads users;` | 配線の値の位置に書いた状態の名前（「op の宣言と本体」の「状態の参照」） | 基底の状態一つを読んで、値を得る |
| 効果 | `effect fn createOrder(order: Order): effects orders.post;` | 配線で直に呼ぶ組み込みの効果（`orders.post(order);`。「直に呼ぶ組み込みの効果」） | 一つの状態の一つの変化（「状態の形」の「効果の宛先」） |

- **宣言の `reads` と `effects` は、その関数が、直に触れる先を言う。** `read fn` は、`reads` の状態を、ちょうど一つ読む。`effect fn` は、`effects` の宛先を、ちょうど一つ変える（`docs/grammar.md`「関数の宣言」）。op の節の `reads` と `effects` は、同じ関係を、本体が呼ぶものの合わせたものとして言う（「節に書く要素」）。
- `read` と `effect` の宣言は本体を持たない。中身は、デコレータを読むトランスパイラが出すか（`@db.find` など）、人が書く。どちらになるかは、言語は決めない。
- 宣言の引数と、`read` の結果の型は、書かれたままの約束で、検査器は宛先の状態の型と照らさない（`read fn count(): int reads orders;` も書ける）。照らすのは、デコレータを読むトランスパイラ（`docs/requirements.md`「出力を推論しない」）。
- **効果は、仕様の例外を投げられる。`read` は、投げない**（決定 D352）。効果の宣言の `throws`（`effect fn createUser(user: User): throws EmailTaken effects users.post;`）は、その効果が投げうる例外の並び（`Effect.throws`）。投げたとき、その効果は、起きていない: 状態は、変わっていない。同じ例外を二度書けば REL-1。いつ投げるかは、中身（トランスパイラが出すか、人が書く）が決め、言語は決めない。
- `read` と効果を使えるのは、宣言した名前空間（状態の持ち主）の配線だけ。別の名前空間は、その名前空間の op を通す（「配線からの呼び出し」の NS-6）。`export` は op にだけ付けられる（「op の宣言と本体」の「export」）。
- どの配線も呼んでいない `read` と効果は診断しない。

この節の細部は、決定 D595 が決めた。

### 配線からの呼び出し

配線は、`read` と効果を、op と同じ形で呼ぶ（`docs/grammar.md`「配線」の `Call`）。

| 呼ぶもの | 書ける位置 | 式の型 | その配線に足すもの |
|---|---|---|---|
| `read`（`userByEmail(email)`） | 値のある呼び出しを書ける位置（`val`、`=`、`collect`、`return`、アームの本体） | その `read` の結果の型（`Read.returns`） | 読む状態に、その宛先の状態（「計算」の「reads」） |
| 効果（`createOrder(order);`） | 値のない呼び出しを書ける位置（文、アームの本体） | 「値がない」 | 効果に、その効果。例外に、その効果の `throws`（「計算」の手順 0） |
| 組み込みの効果を直に（`orders.post(order);`） | 同上 | 「値がない」 | 効果に、直に書いた効果 `<状態>.<操作>`（「節に書く要素」） |

- 別の名前空間の `read` か効果（の宣言）を呼べば NS-6。別の名前空間の状態の組み込みの効果を直に呼べば RES-5（状態を名前で書けるのは、持ち主の名前空間だけ）。
- 引数の数と型は、op の呼び出しと同じ規則で確かめる（`docs/types.md`「呼び出しの引数」、「計算」の「必須の入力」）。`bind` は、`read` と効果の引数を埋めない（「計算」の「bind」）。
- 効果の呼び出しは、その配線の例外に、効果の `throws` を足す（「read と効果」）。op の呼び出しの例外と同じに、その配線の op が、節に書いていなくてよい（「節に書く要素」）。`read` の呼び出しと、直に呼ぶ組み込みの効果は、例外を増やさない。
- 値のある・ないの使い分けは op と同じ: `read` の呼び出しを`val` に受けずに書く、効果の呼び出しを `val` に受ける、はどちらも WIRE-2。

### 直に呼ぶ組み込みの効果

配線は、今の名前空間の基底の状態の組み込みの効果（「状態の形」の「基底の状態」）を、宣言なしに呼べる。書ける形と引数は、状態の形と操作から決まる。T は状態の要素の型（`State.element`）。

| 形 | 操作 | 呼び出し | 引数 |
|---|---|---|---|
| `list<T>` | `post` | `users.post(user);` | 足す列一つ（T） |
| `nullable<T>` | `post` | `token.post(t);` | 入れる値（T） |
| `nullable<T>` | `put` | `token.put(t);` | 置き換える値（T） |
| `nullable<T>` | `delete` | `token.delete();` | なし |
| `single<T>` | `put` | `title.put(t);` | 置き換える値（T） |
| `list<T>` | `put`、`delete` | — | 直には呼べない（STATE-6） |

- `list` の `put` と `delete` を直に呼べないのは、どの列を変えるか、消すかを、引数から決める規則がないから（キーに当たるものを、言語は持たない）。名前を付けた `effect` を宣言して呼ぶ（`effect fn removeOrder(id: OrderId): effects orders.delete;`）。どの列かは、その宣言の実装（デコレータか人）が決める。
- 形にない操作（`single` の `post` / `delete`）は STATE-1。
- 引数の数と型の誤りは、`read` や効果の宣言の呼び出しと同じ診断（`docs/types.md`「呼び出しの引数」）。
- 分類の遷移は、直には呼べない（`Checkout(…)` は RES-4）。名前を付けた `effect` の宛先にだけ書ける。
- 直に呼ぶ効果は、行の遷移を持たない（`as` を書く場所がない）。意味は、`as` を書かない宣言と同じ（「行の遷移」の「書き方と意味」）: `put` は、行の状態を変えない。行の状態を変えるなら、名前を付けた `effect` を宣言する。

### 葉の op

葉の op（本体を持たない op）は、人が中身を書く op で、状態に触れない。

- 葉の op は `reads` と `effects` の節を書けない（STATE-5）。状態を読み書きするなら、`read` か効果を宣言し、配線で呼ぶ。
- `throws` は書ける。葉の op の中身を、検査器は見ないので、書いた例外が、その op の例外のすべて（「計算」の「Sig(O, v)」の手順 0）。
- 葉の op が状態に触れるのは、付いたデコレータが運ぶ分だけ（「計算」の「デコレータが運ぶ reads と effects」）: デコレータの処理が状態に触れるのであって、葉の中身ではない。運ぶ節を持つデコレータは、配線の op にも付けられ、葉の op が節を書けないことは、それによらない。

### 節に書く要素

節（`throws`、`reads`、`effects`）に書くのは、その関数が、**自分で足す分**（決定 D381）。その関数の例外、読む状態、効果は、計算した分（本体と、呼ぶ先と、付いたデコレータから決まるもの。「計算」の「Sig(O, v)」「reads」）に、節に書いた分を、足したもの。三つの節とも、同じ決まり。

| 関数 | 節に書くもの |
|---|---|
| 中身のない関数（葉の op、`effect fn`、`read fn`） | 自分で足す分が、すべて。書いたものが、定義（「葉の op」、「read と効果」）。葉の op は、`reads` と `effects` を書けない（STATE-5） |
| 中身のある関数（配線の op） | 書かなくてよい（同 379）。書いたものは、計算した分に、足される |

配線の op の節:

- **書いた節と、計算した分を、過不足で照合して、エラーにすることは、しない。** 計算した分を、節に書いていなくてよく、計算した分にないものを、節に書いても、通る。「一つ書いたら、ぜんぶ書く」という決まりは、ない。
- **計算した分にあるもの**（本体か、呼ぶ先か、デコレータから、もう決まっている例外、状態、効果）を、節に書いても、何も変わらない。エラーではないが、勧めない（`docs/requirements.md`「書き方の指針」）。
- **計算した分にないもの**を、節に書けば、その op のものに、加わる: 例外は、出どころのない例外（「計算」の「Sig(O, v)」の手順 0 の `Declared(O)`）。効果と、読む状態は、葉の op に、デコレータが運んだときと、同じに数える（同「節に書いた効果」、「reads」）。
- **計算した分にない効果と状態を、節に書けば、warning**（決定 D451）: 効果は EFF-4、読む状態は READS-3（「診断」の「状態と効果」）。配線の op の本体は、仕様から、そのまま作られるので、本体も、呼ぶ先も、デコレータも行わない効果は、作られたコードの、どこでも起きない。呼び出しの書き忘れか、意図かを、検査器は決められないので、知らせる。ここで言う「計算した分」は、その節を書かなかったときの、その op の効果（Sig の F）と、読む状態（R）。例外（`throws`）には、出さない: 多めに書いた例外は、外への約束の幅（THROWS-2）。
- **関係を付けた `throws`**（`throws E prevents effects`、`throws E keeps effects`）は、その op の高さでの、`E` の宣言の、**上書き**（言い直し）: `throws E` とは、別の宣言で、「`E` が投げられたとき、この op の効果が、すべて、起きていない（起きている）」を言う。上書きは、計算した関係と合っているかを、確かめる（REL-4）。
  - 呼ぶ先が `prevents effects` と言った例外を、呼び元が `keeps effects` と書けば（向きを変える）、REL-4。
  - 呼び元が、同じ向きで書けば、言う範囲は、呼び元の効果のすべてに、広がる（呼ぶ先の効果 W1 に、呼び元が足した効果 W2 が、加わる）。W2 も、本当に、そうなら、通る。W2 が、例外の前に起きていれば、`prevents effects` とは言えず、REL-4。
- 節を書いていない配線の op に、節についての診断は、出ない。

節の要素は、宣言の名前でも、直にでも書ける（`docs/grammar.md`「op」）。デコレータの宣言の `reads` / `effects` の節の要素も同じ（「計算」の「デコレータが運ぶ reads と effects」）。

| 節 | 名前で書く（`named`） | 直に書く（`direct`） | 直に書いたものが指すもの |
|---|---|---|---|
| `reads` | `read` の宣言の名前（`reads userByEmail`） | 基底の状態の名前（`reads users`） | その状態を読むこと |
| `effects` | `effect` の宣言の名前か、効果のユニオンの名前（`effects addUser`） | `状態.操作`（`effects users.post`） | その状態の組み込みの効果（「状態の形」の「基底の状態」） |

- **効果は、書き方ごとに別のもの**として数える。直に書いた `users.post` は、状態 `users` の組み込みの効果 `post` そのもので、同じ宛先を持つ宣言（`effect fn addUser(user: User): effects users.post;`）とは別の効果。宣言した効果は、宛先が同じでも、宣言ごとに別。配線の本体が `users.post(user);` と呼べば直に書いた効果 `users.post` を、`addUser(user);` と呼べば宣言 `addUser` を持つ。効果を数えるところ（Sig の F と rel）は、どれもこの数え方に従う。
- **読む状態は、書き方によらない。** 読む状態（「計算」の「reads」の R）は基底の状態の集合で、`read` の宣言は、その宛先の状態として数える。`reads userByEmail`（`read fn userByEmail(…): User? reads users;`）と `reads users` は、同じ `users` を指す。本体が `userByEmail(email)` と呼んでも、`users` を名前で読んでも、R に入るのは `users`。
- 直に書いた効果の操作が、その状態の形になければ STATE-1。
- 分類の遷移は、直には書けない（`effects Checkout` は RES-4）。
- 節には、別の名前空間の効果、状態、`read` も書ける: 配線の効果と読む状態は、呼び出し先から名前空間をまたいで伝わる（EFF-1、「計算」の「reads」）。
- 一つの節に、名前で書いた要素と直に書いた要素を混ぜてよい。IR は、要素ごとに、どちらで書いたかを持つ（`docs/ir.md`「op」の `ReadRef`、`EffectRef`）。

この節の細部は、決定 D651 が決めた。

## 分類

`classify` の対象、置き場、閉じていること、ケースの型、ケースの判定、残りのケース、ない側のケース、`match` のアームが受けるケースを定める。設計書 §10.1〜§10.3 に、決定 S3、S16、S18、S21、S29 を当てたもの。構文は `docs/grammar.md`「classify」「配線」、型の規則は `docs/types.md`「絞り込み」。

この節の細部は、決定 D579、D605、D683 が決めた。

### 対象

| 分類 | 対象（`Classify.subject`） | 対象の型 | `match` |
|---|---|---|---|
| 値の分類 | 型一つ | その型 | `match (x by C)` |
| **op の分類** | op 一つ | その op の `returns` | `match (x by C)` |
| 状態の分類（「状態の形」） | 分類を宣言した名前空間の基底の状態一つ以上 | 状態ごとに、その状態の型 | `match (by C)` |
| 対象のない分類（下の「対象のない分類」） | `never` | `never`（当たる値がない） | 書けない |
| 例外の分類（下の「例外の分類」） | `any exception`（`Classify.subject` は `exception`） | ない（受けた例外は、値ではない） | `match (e by C)`、`catch (e by C)` |

- op の分類は、その op が返した値の分類（`classify Registration of findUser { ... }`）。対象の型をその op の `returns` とした値の分類として扱う。違いは、何を分類しているかが宣言の名前で読めることと、`as` の前の書き方だけ。
- `match (x by C)` の `x` は、型が対象の型に渡せる値ならよい（MATCH-6）。その op の呼び出しの結果である必要はない。値の出どころは追わない（「検査器が遷移を使う範囲」と同じく、検査器は配線の行をまたいで値を追わない）。
- 対象にできる op は、値を返す op（`returns` が `null` でも `never` でもない）。そうでなければ CLS-4。どの名前空間の op でもよく、`export` の有無によらない（対象にすることは呼び出しではない。「op の宣言と本体」の「export」）。
- 絞り込んだ型（`T on C.K`）を書けるのは、値の分類と op の分類。

### 対象のない分類

`classify C of never { … }` は、当たる値が、一つもない型（`never`）の分類（決定 D328、D329）。名前を並べるだけの宣言で、担い手や、要求のように、値がなく、仕様の、どこにも置かないものに使う。値の集まりに見えるもの（op の返り値を、分けたもの）は、op の分類で書く。

- **対象の種類は、増やさない。** 値の分類で、対象の型が `never`（`Classify.subject` は `type`）。
- **判定するものが、ない。** 述語を持たず、人が実装する述語も、ない（`Classify.decidedBy` は `none`。「ケースの判定」の 1〜3 は、当てない）。
- **ケースは、名前だけ。** `as` を書けば CLS-9。ケースは一つ以上（CLS-2）で、名前は重ならない（CLS-1）。
- **置けるのは、デコレータの所だけ。** ケースの前のデコレータ（`docs/grammar.md`「classify」）と、デコレータの引数（`@prd.usecase.of(Actor.Customer)`。`docs/types.md`「デコレータの引数」）。どの名前空間からも、修飾して指せる。
- **値の位置には、書けない。**

  | 書いた所 | 診断 |
  |---|---|
  | 型（`T on C.K`） | RES-4（`docs/resolve.md`「位置ごとに受け付ける種類」） |
  | `match (x by C)`、`match (by C)` | MATCH-7 |
  | 効果の遷移の宛先（`effect fn …: effects C as A -> B`） | RES-4 |
  | 行の遷移のケース（`as C.K`） | STATE-7（対象の型が、状態の要素の型でない。「行の遷移」の「結びつき」） |

- **何を出すかは、プラグインが決める。** 検査器も、基底も、対象のない分類から、何も導かない（`docs/requirements.md`「出力を推論しない」。Go の基底は、何も出さない: `docs/plugin-go.md`「分類」）。

この節の細部は、決定 D579 が決めた。

### 例外の分類

`classify C of any exception { … }` は、`catch` が受けた例外（「op の宣言と本体」の「例外を受ける」）を、型で分ける分類（決定 D422）。構文は `docs/grammar.md`「classify」。

- **対象は、受けた例外。** 型も、op も、状態も、指さない。
- **ケースは、例外の並びで決まる。** `K: any exception as E1 | E2;` は、受けた例外が `E1` か `E2` のとき。例外のユニオンは、要素に展開する。`R: any exception as else;` は、ほかのケースの、どの例外でもないとき（残りのケース。高々一つ: CLS-1）。述語は、持たない（`Classify.decidedBy` は `type`）。
- **ケースの書き方**（合わなければ CLS-10）: どのケースも、`any exception as …` を、ちょうど一つ持つ。同じ例外を、二つのケースに書かない。ほかの分類のケースに、`any exception as …` は、書けない。
- **使えるのは、受けた例外の `match` だけ**: `match (e by C)` と、その短い書き方 `catch (e by C)`。どの名前空間の分類でもよい。値の位置には、対象のない分類と同じに、書けない。

  | 書いた所 | 診断 |
  |---|---|
  | 値を対象にした `match (x by C)`、対象を書かない `match (by C)` | MATCH-7 |
  | 型（`T on C.K`）、効果の遷移の宛先（`effects C as A -> B`） | RES-4 |
  | 行の遷移のケース（`as C.K`） | STATE-7 |

- **受けた例外の `match` に書ける分類は、例外の分類だけ**（ほかの分類、`by list`、`by nullable` は MATCH-7）。
- **漏れは、静的に確かめる**（MATCH-10）: `try` のブロックが投げうる例外（「計算」の「Sig(O, v)」の「例外を受ける文」の、受ける例外の集まり）の、どれもが、分類の、どれかのケースに当たる。残りのケースがあれば、いつも満たす。アームが、分類のケースを、すべて受けることは、ほかの `match` と同じ（MATCH-2、MATCH-9）。
- 分類のケースのうち、受ける例外の集まりの、どの例外にも当たらないものは、診断しない（一つの分類を、いくつもの `try` で使える）。

この節の細部は、決定 D683 が決めた。

### 置き場

分類は、どの名前空間にも宣言でき、値の分類と op の分類は、どの名前空間からも使える。別の名前空間のものは修飾して書く（`match (user by store.Registration) { ... }`、`type.User on store.Registration.Registered`）。複数の担い手が共有する型の分類を、型と同じ名前空間にも、使う側の名前空間にも置ける。

状態の分類を `match (by C)` で読めるのは、その分類を宣言した名前空間の配線だけ。読むのは状態で、状態を読めるのは持ち主の名前空間だけだから（別の名前空間の状態の分類なら RES-5。`docs/resolve.md`「診断」）。

「`classify` は宣言した名前空間の中でだけ使える」（NS-4）はなくした（「診断」の「名前空間」）。

### 閉じた分類

分類は閉じている: 宣言したケースが、その分類のすべて。どのケースも名前を持ち、「ほかのどれでもない」を言う名前のないケースはない。

- **仕様が使わない場合は、宣言しない。** 相手が送ってくるほかの種類の通知のように、仕様がそこで何もしない場合に、ケースを足さない（勧めは `docs/requirements.md`「書き方の指針」）。
- **どのケースにも当たらない値は、分類の誤り。** `match` は、その値をどのアームにも渡さない（`else` のアームにも。「アームが受けるケース」）。どの値が当たらないかは「ケースの判定」。
- **分類の誤りは、仕様の例外ではない。** `throws` に書かず、`Signature` に入らず、デコレータの `catches` では受けられない。検査器は追わない。実行時にどう届くかは、トランスパイラが決める（Go の基底は `*runtime.ClassificationError`。`docs/plugin-go.md`「分類」）。
- **二つに分かれる判定も、両側に名前を付ける**（`classify Role of Member { Admin; Regular; }`）。成り立つ側だけを宣言する書き方はない。

### 標準の分類

`nullable` と `list` は、形の型についての標準の分類。宣言を持たず、名前は `match` の `by` の後ろにだけ書ける。どの値も、二つのケースのどちらかに当たる。

| 名前 | 対象の型 | ケース | 判定 | アームでの絞り込み |
|---|---|---|---|---|
| `nullable` | `nullable<T>`（`T?`） | `None` / `Some` | 値がなければ `None`、あれば `Some` | `Some` だけのアームで T |
| `list` | `list<T>`（`T[]`） | `Empty` / `HasItems` | 要素が一つもなければ `Empty`、あれば `HasItems` | なし |

- 対象は値。状態に限らない（`match (in.token by nullable) { ... }`、`match (order.lines by list) { ... }`）。状態は、名前で書けば値になる（`match (token by nullable) { ... }`）。
- 基底の状態の「組み込みの分類」（「状態の形」）は、この分類をその状態に当てたもの。遷移の宛先（`effect fn clearCart(): effects carts as HasItems -> Empty;`）になるのは、基底の状態に当てたものだけ（「効果の宛先」）。
- 自分で宣言する分類も、`nullable<T>` や `list<T>` を対象にできる（`classify Presence of nullable<User> { ... }`）。
- ケースの名前は、形ごとに違う（決定 D362）。`nullable` に、`list` のケースの名前（`Empty` / `HasItems`）を書けば、アームなら MATCH-2、状態の遷移なら STATE-4 で、メッセージが、その形のケース（`None` / `Some`）を並べる。

この節の細部は、決定 D605 が決めた。

### ケースの型

ケースは、そのケースのときに対象が何の型になるかを `対象 as T` で書ける（`Registered: findUser as type.User;`）。書かなければ今までどおり（`docs/types.md`「アームの中の対象の型」の 4）。

- `as` の前に書けるのは、その分類の対象: 値の分類なら `subject` の型と等しい型、op の分類ならその op、状態の分類なら対象の状態のどれか。それ以外を書けば CLS-5。一つのケースに同じ対象の `as` を二度書いても CLS-5。
- 状態の分類は、一つのケースに、対象の状態ごとの `as` を並べられる。値の分類と op の分類は対象が一つなので、`as` は一つ。
- `as` の後ろの T は、対象の型から絞り込める型でなければならない（`docs/types.md`「絞り込める型」。CLS-6）。
- **T にリテラルの型を書けるのは、対象の型が、閉じた型のときだけ**（CLS-11。決定 D483）。次のどちらか。どちらも、型で決まる絞り込み（`docs/types.md`「型で決まる絞り込み」の `literal` と `variant`）。
  1. 対象の型から `optional` を外した型が `boolean` で、T が `true` か `false`（`classify Flag of boolean { On: boolean as true; Off: boolean as false; }`）。
  2. 対象の型から `optional` を外した型が union（`arms`）で、T が、そのアームのどれかの型と等しい（`classify Level of Severity { Fatal: Severity as "error"; Other: Severity as else; }`）。
  開いた型（`string`、`int`、`float`）の対象を、`as "abc"`、`as 0` で分けることは、できない: 値の種類が、宣言で尽きない。分けるなら、項目の型を、リテラルの型をアームに持つ union にする（`docs/types.md`「リテラルの型」）。
- 意味: そのケースが成り立つとき、対象は T の値である。`match` のそのケースのアームの中で、対象の型は T になる（`docs/types.md`「アームの中の対象の型」）。
- `as` の後ろに、型の代わりに `else` を書いたケース（`Unregistered: findUser as else;`）は、残りに名前を付ける。規則は「残りのケース」。
- `as` の後ろに、型の代わりに `none` を書いたケース（`Absent: Order? as none;`）は、値がない側に名前を付ける。規則は「ない側のケース」。

### ケースの判定

分類のケースが何で決まるかは、宣言から二通りに分かれる（`Classify.decidedBy`）。対象のない分類（「対象のない分類」）は、そのどちらでもなく、判定を持たない（`none`）。

**型で決まる分類**（`type`）は、次のすべてを満たす分類。述語を持たず、どのケースに当たるかは値の型から決まる。

1. 対象が一つ（値の分類、op の分類、対象の状態が一つの状態の分類）。
2. ケースのすべてが、その対象の `as` を持つ。型を書いた `as` は、どれも型で決まる絞り込み（`docs/types.md`「型で決まる絞り込み」）。`as else` と `as none` は、型を書かない `as` で、この条件を満たす。
3. `as` に書いた型が、ケースの間ですべて違う。
4. （欠番。「残りを受けるものがある」という条件だった。残りを受けるケースがなくても、型で決まる分類。下の「当たらない値」）

当たるケースは、値が `as` の型に当たるケース。値がなければ、ない側のケース（「ない側のケース」。あれば）。どれにも当たらなければ、残りのケース（「残りのケース」。あれば）。条件 3 から、どの値も、高々一つのケースに当たる。`presence` の分類は、条件 2 と 3 から、型を書いたケースが一つだけになる。

```
classify Registration of findUser {     // findUser(email: Email): User?
  Registered:   findUser as User;       // 値があるとき
  Unregistered: findUser as else;       // 値がないとき（残りのケース）
}
```

**当たらない値**: 残りのケースがない分類では、次の値が、どのケースにも当たらない（分類の誤り。「閉じた分類」）。残りのケースがあれば、どの値も、ちょうど一つのケースに当たる。

| 絞り込み | どのケースにも当たらない値 |
|---|---|
| `presence` | 値がない（ない側のケースを `as none` で書いていれば、そういう値はない） |
| `variant` | 値が、どのケースも `as` に書かなかった型のアーム。書いた型が union のすべてのアームの型を覆っていれば、そういう値はない |
| `literal` | 値が、どのケースも `as` に書かなかった方の真偽の値。対象の型が `boolean?` なら、値がない、も。対象の型が `boolean` で、`true` と `false` の両方を書いていれば、そういう値はない |

値がない側を使わない分類は、型を書いたケースだけを宣言する（`classify Arrival of datetime? { Arrived: datetime? as datetime; }`）。値がないことは、分類の誤りになる。

標準の分類も型で決まる分類。

**述語で決まる分類**（`predicate`）は、それ以外のすべて。ケースごとに、述語を人が実装する。

- **ない側のケースを除く、すべてのケースが述語を持つ。** 「ほかのどの述語も真でない」ことから決まるケースはなく、言語は、残りを導かない。二つに分かれる分類なら、述語は二つ（`classify Gathered of Shipment { Complete; Awaiting; }` の `Complete` と `Awaiting`）。ない側のケース（「ない側のケース」）だけは、述語を持たず、値がないことで決まる。
- 述語は排他で、値が当たるのは、述語が真になった、ただ一つのケース。どの述語も真でない値は、どのケースにも当たらない（分類の誤り。「閉じた分類」）。
- **ない側のケースを持つ、述語で決まる分類**（`classify Life of Order? { Draft: Order? as Order; Placed: Order? as Order; Absent: Order? as none; }`）は、決め方が二段: 値がなければ、ない側のケース（型で決まる。述語は呼ばない）。値があれば、ほかのケースの述語で決まり、上の排他の規則は、その中に掛かる。
- 二つ以上の述語が真になるのは、述語の実装の誤りで、同じく分類の誤りとして届く。

`as` を持つケースは、次の意味を足す。

- 述語が真なら、対象は T の値である。述語を実装する人がそれを保証する（`string` の対象に `Valid: string as Email;` と書いたケースの述語は、値が `Email` の制約を満たすときだけ真を返す）。
- `as` が型で決まる絞り込みなら、値がその型に当たらないとき、述語が真でもそのケースは成り立たない。

同じ型に絞り込むケースが二つあれば（`Fresh: findSession as Session; Expired: findSession as Session;`）、条件 3 を満たさないので述語で決まる分類になる。

### 残りのケース

`<名前>: <対象> as else;` は、型で決まる分類（「ケースの判定」）の残りに、名前を付けたケース（**残りのケース**）。成り立つのは、対象の値が、ほかのケースが `as` に書いた型のどれにも当たらないとき: 絞り込みが `presence` なら値がないとき、`variant` なら、値が**残りのアーム**（型が、ほかのケースが `as` に書いた型のどれとも等しくないアーム）のとき、`literal` なら、値が、書かなかった方の真偽の値のとき（対象の型が `boolean?` なら、値がないときも）。述語を持たない。

残りのケースは、ほかのケースと同じく、`match` のアームにも、遷移のケースにも、名前で書く（MATCH-2）。

- **書けるのは、残りが型で決まるときだけ**（CLS-7）。次のどちらか。
  1. **型で決まる分類**: 残りのケースを除いたケースが一つ以上あり、それらが「ケースの判定」の条件 1〜3 を満たす。
  2. **残りが、ちょうど「値がない」**: 値の分類か op の分類で、対象の型が `T?`。残りのケースを除いたケースが一つ以上あり、どれも、対象を T に絞る `as`（`T? as T`。絞り込みは `presence`）を持つ。ケースが二つ以上で、同じ型 T を書いていても（条件 3 を満たさない、述語で決まる分類）、書ける: 値があればどれかの述語のケース、なければ残り、と型から分かれる。この残りのケースは、ない側のケース（「ない側のケース」）。
- どちらでもなければ、書けない。対象が二つ以上の状態の分類には書けない。述語のケース（`as` を持たないケース、述語の要る絞り込みのケース、2 に当たらない分類で同じ型を書いた二つのケース）の隣にも書けない: 「どの述語も真でない」ことは型から決まらない。そこで残りに名前を付けるなら、そのケースも述語のケースとして書く（`classify Gathered of Shipment { Complete; Awaiting; }`）。
- **残りがなければ書けない**（CLS-7）: 絞り込みが `variant` で、ほかのケースの型が union のすべてのアームの型を覆っていれば、残りのアームがない。絞り込みが `literal` で、対象の型が `boolean`、ほかのケースが `true` と `false` の両方を書いていれば、残りの値がない。対象の型が `boolean?` なら、残りは、ちょうど「値がない」で、書ける（この残りのケースは、ない側のケース。「ない側のケース」）。
- **残りは一つ**（CLS-1）: 残りのケースは一つの分類に高々一つ。
- `as` の前は、ほかのケースと同じく、その分類の対象（CLS-5）。
- 残りのケースが成り立つときの対象の型は `docs/types.md`「残りのケースでの対象の型」。
- 上の 1 で書いた残りのケースを持つ分類は、型で決まる分類で、どの値も、ちょうど一つのケースに当たる（「ケースの判定」の「当たらない値」）。2 で、ほかのケースが二つ以上の分類は、述語で決まる分類（同「ない側のケースを持つ、述語で決まる分類」）。

この節の細部は、決定 D767 が決めた。

### ない側のケース

対象の型が `T?` の分類で、「値がない」ときに成り立つケースを、**ない側のケース**と呼ぶ。型で決まり、述語を持たない。書き方は二つで、意味は同じ。

| 書き方 | 例 | 規則 |
|---|---|---|
| `<名前>: <対象> as none;` | `Absent: Order? as none;` | この節（CLS-8） |
| `<名前>: <対象> as else;` で、残りが、ちょうど「値がない」もの | `Missing: Order? as else;` | 「残りのケース」（CLS-7）。ほかのケースが、どれも `T? as T` のとき。または、対象の型が `boolean?` で、ほかのケースが `as true` と `as false` の二つのとき（`boolean?` の、値がない側は、`as none` では書けない: 下の CLS-8 の条件に当たらない） |

```
classify Life of Order? {
  Draft:  Order? as Order;     // 値があるとき。Draft か Placed かは、述語で決まる
  Placed: Order? as Order;
  Absent: Order? as none;      // 値がないとき。型で決まる
}
```

- **`as none` を書ける分類**（CLS-8）: 値の分類か op の分類で、対象の型が `T?`。`as none` のケースを除いたケースが一つ以上あり、どれも、対象を T に絞る `as`（`T? as T`）を持つ。「残りのケース」の 2 と同じ条件。状態の分類には書けない（値がない側は、対象が一つなら `as else` で書ける）。
- **ない側は一つ**（CLS-1）: `as none` は一つの分類に高々一つ。`as none` と `as else` を、一つの分類に両方は書けない（`as none` があれば、残りがない。CLS-7）。
- `as` の前は、ほかのケースと同じく、その分類の対象（CLS-5）。
- ない側のケースが成り立つときの対象の型は、対象の型のまま（`docs/types.md`「残りのケースでの対象の型」）。
- ほかのケースと同じく、`match` のアームに名前で書く（MATCH-2）。行の遷移では、「行がない」ことを言うケースになる（「行の遷移」の「行がないこと」）。
- IR は、ない側のケースの名前を持つ（`Classify.absent`。`docs/ir.md`「classify」）。

この節の細部は、決定 D767 が決めた。

### アームが受けるケース

`match` のアームは、分類のケースを分け合う: どのケースも、ちょうど一つのアームが受ける。構文は `docs/grammar.md`「配線」の `MatchArm` と `ElseArm`。

- **名前で並べたアーム**（`Draft, Cancelled => throw NotAccepted;`）は、並べたケースを受ける。並べるのは、その分類のケースで、一つの `match` に同じケースは一度だけ（MATCH-2）。
- **`else` のアーム**は、その分類が宣言したケースのうち、ほかのアームが並べなかったもののすべてを受ける。受けるケースは、IR に、宣言の順で置く（`MatchArm.cases`。`docs/ir.md`「配線」）。
- `else` のアームが受けるのは、宣言したケースだけ。どのケースにも当たらない値（「閉じた分類」）は、`else` のアームにも渡らない。
- `else` のアームがなければ、すべてのケースを名前で並べる（足りなければ MATCH-2）。`else` のアームがあれば、足りないケースはない。
- `else` のアームが受けるケースが一つもなければ（ほかのアームが、すべてのケースを並べている）MATCH-9。
- 標準の分類の `match` にも、同じに書ける（ケースは「標準の分類」の表）。
- `else` のアームの中の対象の型は `docs/types.md`「アームの中の対象の型」。`else` を使う場面の勧めは `docs/requirements.md`「書き方の指針」。

## 行の遷移

値の分類は、値一つの状態を言う。表（`list` の状態）なら、一行の状態（注文、支払い、仕事、出荷の、いまの段階）。**行の遷移**は、効果が、受け取った行の状態をどう変えるかを、その分類のケースで言うもの。前のケースは、行の引数の型（`docs/grammar.md`「型」の `OnType`）で言い、後のケースは、宛先の後ろの `as`（同「exception / effect / read」の `RowClause`）で言う。決定 D163〜D173、D369、「設計書から離れた決定」S30。

```ts
classify Stage of Order { Draft; Accepted; InProduction; Shipped; Cancelled; }

effect fn accept(order: Order):                                   effects orders.post as Stage.Accepted;       // Accepted で入る
effect fn startProduction(order: Order on Stage.Accepted):        effects orders.put  as Stage.InProduction;   // Accepted の行が InProduction になる
effect fn cancel(order: Order on Stage.Draft | Stage.Accepted):   effects orders.put  as Stage.Cancelled;
effect fn forceShip(order: Order):                                effects orders.put  as Stage.Shipped;        // どのケースからでも
effect fn revise(order: Order on Stage.Accepted):                 effects orders.put  as else;                 // 後のケースは決まっていない
effect fn patch(order: Order):                                    effects orders.put  as else;                 // 何も約束しない（抜け道）
effect fn rename(order: Order):                                   effects orders.put;                          // as がない: ケースは変わらない
effect fn import(order: Order):                                   effects orders.post;                         // 入るケースは決まっていない
```

この節の細部は、決定 D618、D619 が決めた。

### 行と、行の分類

- **行**は、効果が書き込む基底の状態（`Effect.writes` の一つ）の要素一つ。型は、その状態の要素の型 T（`State.element`）。`list<T>` なら列の一つ、`nullable<T>` と `single<T>` なら、その値。
- **行の分類**は、対象の型が T か `T?` の、値の分類。`T?` を対象にした分類は、「行がない」ことも、ケースとして言える（「行がないこと」）。
- 状態の分類の遷移（`effects Checkout as Shopping -> Ordered`。「状態の形」の「効果の宛先」）は、別のもの: 状態の全体の場合を言い、宛先そのものが、状態か、状態の分類。引数を持たないので、前も後も、`as` に矢印で書く。行の遷移は、宛先（`effects 状態.操作`）の後ろに、後のケースだけを足す。どちらも `as` で書き、宛先で分かれる（`docs/grammar.md`「exception / effect / read」）。

### 書き方と意味

| 書き方 | 意味 |
|---|---|
| 行の引数の型 `T on C.Ks` | 効果の前、行は、Ks（一つ以上のケース）のどれかにある。呼ぶ側は、そうと分かっている行しか、渡せない（「呼ぶ側」） |
| 行の引数の型 `T`（絞り込まない） | どのケースの行でも、受け取る |
| `as X` | 効果の後、行は X にある |
| `as else` | 後のケースは、決まっていない |
| `as` を書かない | 操作ごとに決まる（下の表） |

- **前は、引数の性質。後は、効果の約束。** 前のケースを、効果の節には、書かない。
- **一つの `as` が言うのは、一つの分類のこと。** 行の、ほかの分類については、`as` を書かない効果と同じ意味になる（`put` なら、変わらない）。二つの分類のケースを一度に変える効果は、`as else` と書くしかない。
- `as else` は、分類を名指ししない。行の分類のすべてについて、後のケースを、何も約束しない。
- **`put` は、`as` を書かなければ、行のケースを変えない。** だから、行のケースが変わる道は、宣言した行の遷移だけで、ほかにない。変わるかどうかを約束しない効果は、`as else` と書いて、そう言う。
- 行の引数を絞り込む分類と、`as` の分類は、同じでなくてもよい（`effect fn ship(order: Order on Paid.Yes): effects orders.put as Stage.Shipped;`: 支払いの済んだ行だけを受け取り、段階を `Shipped` にする）。
- 直に呼ぶ組み込みの効果（「状態に触れるもの」の「直に呼ぶ組み込みの効果」）は、`as` を書かない宣言と同じ意味。

### 操作ごとに書ける形

操作は、宛先の `post` / `put` / `delete`。N は、分類のない側のケース（「分類」の「ない側のケース」。対象の型が `T?` の分類にだけ、ありうる）。X は、それ以外のケース。合わない形は STATE-8。

| 操作 | `as` を書かない | 書ける形 | 書けない形 |
|---|---|---|---|
| `post` | 入る行のケースは、決まっていない | `as X`（X で入る） | `as N`: 入った行は、ある。`as else`: 入るケースが決まっていないなら、`as` を書かない |
| `put` | 行のケースは、変わらない | `as X`、`as else` | `as N`: 行をなくすのは `delete` |
| `delete` | どのケースの行でも消す。消した後の行は、ない | `as N`（行は、なくなる） | `as X`: 消した後の行は、ない。`as else`。ない側のケースを持たない分類（対象の型が T の分類は、どれも）のケースを書いた `as`: その分類には、「ない」を言うケースがない |

- `post` の前は、いつも、「行がない」。操作が言っているので、どこにも書かない。`post` の行の引数は、入る行。
- `put` と `delete` の行の引数を、ない側のケース N に絞り込んだ型（`Order on Life.Absent`）は、書けない（STATE-8）: 書き換える行、消す行は、ある。

### 結びつき

行の遷移は、書き込む状態と、効果の引数に結びつく。分類は、何の型の状態かを、もう決めている。合わなければ STATE-7。

1. `as` に書いたケース `C.K` の C は、値の分類で、対象の型が、書き込む状態の要素の型 T か、`T?` と等しい（`docs/types.md`「等しい」）。op の分類と状態の分類は、行の分類にならない。別の名前空間の分類でもよい（修飾して書く）。
2. K は、C のケース。
3. **行の引数**: 効果の引数（`Effect.params`）のうち、型が、T と等しいか、T を絞り込んだ型（`T on C.Ks`）のものが、ちょうど一つ。それが、状態を変える行。一つもないか、二つ以上あれば STATE-7。`as else` でも要る。型が `T[]`（行の並び）の引数は、行の引数に数えない。行の引数を絞り込む分類は、`as` の分類と、違ってもよい（`effect fn pack(order: Order on Stage.Accepted): effects orders.put as Packing.Packed;`）: そのとき、`as` の分類については、前は、どのケースでも。
4. 行の引数が運ぶ値: `put` と `delete` では、効果の前の行（どのケースにあるかを、引数の型が言う）。`post` では、入る行。

行の引数を持たない効果（行の並びをまとめて書く `effect fn saveAll(changed: Order[]): effects orders.put;`、識別子で消す `effect fn remove(id: OrderId): effects orders.delete;`）は、`as` を書けない。意味は「書き方と意味」の「`as` を書かない」のとおりなので、行のケースを変える `put` は、行を一つずつ受け取る効果として宣言する。

この節の細部は、決定 D618 が決めた。

### 行がないこと

対象の型が T の分類には、「行がない」を言うケースがない。その分類では、`delete` の効果に `as` を書けない（「操作ごとに書ける形」）。

行がないことを、名前のある状態として扱うなら、`T?` を対象にした分類を宣言し、ない側のケースを書く（「分類」の「ない側のケース」）。

```ts
classify Life of Order? {
  Draft:  Order? as Order;
  Placed: Order? as Order;
  Absent: Order? as none;
}

effect fn createDraft(order: Order):                effects orders.post   as Life.Draft;
effect fn place(order: Order on Life.Draft):        effects orders.put    as Life.Placed;
effect fn discardDraft(order: Order on Life.Draft): effects orders.delete as Life.Absent;    // 消せるのは、下書きだけ
```

消すものと、消さずにケースで言うものの分け方の勧めは `docs/requirements.md`「書き方の指針」。

### 呼ぶ側

行の引数を絞り込んだ効果は、そのケースにあると分かっている行でしか、呼べない。確かめるのは、型の検査（`docs/types.md`「呼び出しの引数」「互換」）で、行の遷移のための、別の検査は、ない: `T` の値は、`T on C.Ks` の引数に渡せない（TYPE-4。`match` のアームの中の対象なら MATCH-4）。

- ケースが分かっている値は、型が `T on C.Ks` の値。`match (x by C)` のアームの中の x は、その型を持つ（`docs/types.md`「アームの中の対象の型」）。引数や `val` に、その型を書いてもよい。
- op の引数も、同じ型で、同じことを言える（`fn restart(order: Order on Stage.Accepted)`）。効果だけの決まりではない。

```ts
export fn start(id: OrderId): throws NoOrder, NotAccepted {
  val order = byId(id);
  match (order by Stage) {
    Accepted => startProduction(order);     // order は、ここで Order on Stage.Accepted
    else     => throw NotAccepted;
  };
}

fn restart(order: Order on Stage.Accepted) {
  startProduction(order);                   // 引数の型が、そのまま渡せる
}

fn bad(order: Order) {
  startProduction(order);                   // TYPE-4: Order は、Order on Stage.Accepted に渡せない
}
```

この節の細部は、決定 D619 が決めた。

### 検査器が確かめないこと

- 効果の中身が、宣言した行の遷移のとおりに書くこと。中身は、デコレータを読むトランスパイラが出すか、人が書く（「状態に触れるもの」の「read と効果」）。宣言した向きのほかに行のケースが変わらないことと、`as` のない `put` が行のケースを変えないことを、生成したテストで確かめることは、まだ作っていない段階（`docs/requirements.md`「段階」）。IR は、そのために、状態、操作、行の引数（その型が、前のケース）、分類、後のケースを持つ（`docs/ir.md`「state / exception / effect」の `RowTransition`）。
- 動いているときに、渡ってきた行が、引数の型の言うケースにあること。確かめるのは、検査器ではなく、生成したコード: 効果の入口で確かめて、違えば、仕様の例外でない失敗にする（決定 D371。Go の基底の形は `docs/plugin-go.md`「効果の入口の確かめ」）。
- 渡した行が、保存してある行と同じものであること。検査器は、配線の行をまたいで値を追わない（「状態の形」の「検査器が遷移を使う範囲」）: ケースが分かっているのは、渡した値について。
- デコレータが運ぶ効果と、`halts` の効果（「計算」の「デコレータが運ぶ reads と effects」）。デコレータの処理は、仕様の上では行を受け取らないので、引数の型の検査は掛からない。

## op の宣言と本体

`export`、`never` を返す op、アームの `throw`、状態の参照、値の入れ物（`val`）、繰り返し（`for`）、`disjoint` の規則。決定 S17、S19、S20、S23 に、例外が引数を持つこと（`docs/grammar.md`「exception / effect / read」）を当てたもの。構文は `docs/grammar.md`「op」「配線」。 値の入れ物、繰り返し、`disjoint` は、決定 D294〜D343 を当てたもの。

### export

`export` を付けた op は、別の名前空間から呼べる。付けていない op は**内部の op**で、呼べるのは同じ名前空間の配線だけ。親と子の名前空間も、互いに別の名前空間（§3.2）。

別の名前空間の内部の op を呼べば NS-5。「呼ぶ」に当たるのは次の二つ。

| 呼び方 | 呼ぶ側の名前空間 |
|---|---|
| 配線の呼び出し（文、`val`、`=`、`collect`、`return`、アームの本体。`for` のブロックと、`disjoint` のアームの中も） | その配線の op の名前空間 |
| デコレータの引数に渡した op（`any op` の引数。名前付きのデコレータが固定した引数を含む） | デコレータを付けた宣言の名前空間（名前付きのデコレータの固定した引数なら、その別名の宣言の名前空間） |

当たらないもの: 分類の対象にする（`classify C of ns.op`）、ドキュメンテーションコメントの `@see`、`bind` の対象の名前空間に含まれること。

- `export` の対象は op だけ。型、例外、分類、デコレータは、修飾すればどこからでも参照できる。効果と `read` も、名前としてはどこからでも参照できる（配線の op の `effects` / `reads` の節、デコレータの引数、`@see`）が、配線から呼べるのは宣言した名前空間だけで、`export` で開くことはできない（「状態に触れるもの」の「配線からの呼び出し」の NS-6）。
- `bind` は、別の名前空間の内部の op には位置を作らない（「計算」の「bind」の 1）。呼べない op のために BIND-1 / BIND-2 を出さないため。
- 計算（Sig、`View.ops`）は `export` によらず、すべての op について行う。
- `export` は IR に載る（`Op.exported`）。検査が見るのは仕様の中の呼び出しだけで、`export` を付けた op をどの名前空間も呼んでいないことは診断しない（呼び手が、プラグインの出力や人が書くコードのように、仕様の外にいることがある）。
- 標準の語彙は op を宣言していないので、変えるものはない。プラグインの語彙が、利用者に呼ばせる op を宣言するなら、同じく `export` を付ける。

### never を返す op

`ReturnType` が `never` の op は、決して値を返さない。次のすべてを満たさなければ THROWS-3。

1. 葉である（本体を持たない）。
2. `throws` の例外（ユニオンを展開した後）が、ちょうど一つ。
3. その例外が引数を持たない（`Exception.params` が空）。
4. 引数を持たない。
5. デコレータが運ぶ `reads` も `effects` も持たない（「計算」の「デコレータが運ぶ reads と effects」）。節に書いたものは、葉なので STATE-5。
6. `catches` を持つデコレータが付いていない。

この op の中身は「その例外を投げる」と決まる（中身を出すのはトランスパイラ）。呼び出しの式の型は「返らない」で（`docs/types.md`「式の型」）、どの型の `match` のアームにも、どの型の `return` にも書ける。文として書けるのは本体の最後だけ（WIRE-9）。

### throw

アームの本体の `throw E`（`Absent => throw type.Unauthorized;`）と `throw E(値, …)`（`Exceeded => throw rate.LimitExceeded(wait);`）は、その例外を投げる。

- `E` は例外一つ。どの名前空間の例外でもよい。例外のユニオンやデコレータの引数は書けない（RES-4）。
- 引数は、例外の宣言の引数（`Exception.params`）に、位置で渡す値。数と型は、呼び出しと同じ規則で確かめる（`docs/types.md`「呼び出しの引数」、「計算」の「必須の入力」）。引数を持つ例外に、値を渡さずに `throw E` と書けば、必須の引数が足りない（BIND-4）。
- 計算では、例外が `E` だけで効果を持たない呼び出しとして数える（「計算」の手順 0）。`E` は、その配線の op の例外に加わる。配線の op が、`E` を `throws` の節に書いていなくてよい（「状態に触れるもの」の「節に書く要素」）。
- 式の型は「返らない」。

### 状態の参照

配線の値の位置（`Atom`）に、今の名前空間の状態を名前で書ける。型はその状態の型（`docs/types.md`「式の型」）。

- 同じ名前の引数、`val`、`for` の変数があれば、そちらを指す（`docs/resolve.md`「手続き」の 1 が 5 より先）。隠すこと自体は診断しない。状態と同じ名前の入力（`token`）は普通に書くもので、現在の名前空間の宣言がグローバルの宣言を隠すのを診断しないのと同じ。
- 別の名前空間の状態は書けない（RES-5）。その名前空間の op を通して読む。
- 名前で書いた状態は、その配線が読む状態に入る（「計算」の「reads」）。
- 呼び出しの引数に状態を名前で渡した位置は、明示した位置で、`bind` は埋めない（「計算」の「bind」）。`bind` は、書かなくても埋まる方として残る。
- できるのは読むことだけ。変えるのは効果（「状態に触れるもの」）。
- 状態を名前で読むことは、名前を付けない `read`（同「read と効果」）。

### 値の入れ物

`val` は、値が、一度だけ入る入れ物（`docs/grammar.md`「配線」）。配線は、値を受けて渡す意図を書くもので、`val` は、定数でも、変数でもない。

| 形 | 例 | 代入が済むとき |
|---|---|---|
| 値と一緒に宣言する | `val session = authenticate(token);` | その文が終わったとき |
| 空で宣言して、値を入れる | `val held;` … `held = holdStock(stock);` | 値を入れる文が終わったとき |
| 空で宣言して、集める | `val sent: Notice[];` … `sent collect notice;` | 集める文を囲む `for` を抜けたとき（「繰り返し」の「集める」） |

#### 見える範囲

- `val` が見えるのは、宣言したブロックの、宣言より下。中のブロック（`for` のブロック、`disjoint` のアーム）からも、見える。宣言したブロックを抜けると、見えない。
- `for` の変数が見えるのは、その `for` のブロックの中。
- 見えている名前（引数、外のブロックの `val`、同じブロックの上の `val`、囲んでいる `for` の変数）と同じ名前は、宣言できない（WIRE-4）。中のブロックが、外の名前を、隠すことは、ない。並んだブロック（`disjoint` の別々のアーム、続けて書いた二つの `for`）は、同じ名前を使える。
- 状態と同じ名前は、宣言できる（「状態の参照」）。

#### 代入が済んでいるか

代入の済んでいない `val` は、読めない（WIRE-10）。読むとは、値の位置（`Atom`）に、その名前を書くこと。

済んでいるかは、文の位置だけで決まる: 値を入れる文と、集める文は、文で、`match` のアームの本体（`docs/grammar.md`「配線」の `ArmBody`）には、書けない。場合によって、入ったり、入らなかったりする `val` は、ない。

文を、上から順に見て、代入の済んだ `val` の集まりを、次のように変える。

| 文 | 集まり |
|---|---|
| `val x = 式;`、`x = 式;` | 式を読んだ後で、`x` を足す |
| `xs collect 式;` | 変えない（「繰り返し」の「集める」） |
| `for (val v of 並び) { … }` | ブロックの中では、`v` が、済んでいる。抜けたとき、ブロックの中で集めた `val` のうち、ここで集め終わるもの（「繰り返し」の「集める」）を足す。ブロックの中で宣言した `val` は、見えなくなる |
| `disjoint { アーム … }` | どのアームも、`disjoint` の前の集まりから、始める: あるアームが入れた `val` は、別のアームでは、済んでいない。抜けたとき、どのアームが入れた `val` も、足す |
| `try { … } catch (e) { … }` | `catch` のブロックは、`try` の前の集まりから、始める。抜けたとき、`try` が入れ、`catch` も入れた `val` を足す。`catch` のブロックが「返らない」なら、`try` が入れた `val` のすべてを足す（「例外を受ける」） |

#### 値を入れる文

`x = 式;` の `x` は、次のすべてを満たす（満たさなければ WIRE-11）。

1. 空で宣言した `val`。引数、`for` の変数、値と一緒に宣言した `val`、状態には、入れられない。
2. 代入が、済んでいない。同じ `disjoint` の、別のアームが入れる `val` にも、集める `val` にも、入れられない（集める方は、決定 D549）。
3. `x` の宣言と、この文の間に、`for` がない。`for` の中から、その `for` の外の `val` に入れると、回ごとに入り、「一度だけ」に反する。外に出すには、集める（「繰り返し」の「集める」）。

- 空で宣言した `val` に、値を入れる文も、集める文も、一つもなければ WIRE-12。
- 式が「値がない」か「返らない」なら WIRE-2。型は `docs/types.md`「式の型」。
- 代入の済んだ `val` が、どこからも読まれなければ WIRE-8（warning）。
- 数の上限は WIRE-6。

### 繰り返し

`for (val v of 並び) { … }` は、並びの要素の一つずつに、並びの順に、ブロックを、一回ずつ行う。並びが空なら、一回も行わない。

- **並びは、型が `list<T>` の値。** `v` の型は `T`。並びでない（値がないかもしれない並び `T[]?` を含む）なら TYPE-17（`docs/types.md`「式の型」）。値がないかもしれない並びは、値があるときだけ、並びを受け取る op を、`match (… by nullable)` のアームから呼ぶ。
- **一つの回が失敗したら、止まる。** 残りの回は、動かない。失敗は、仕様の例外でも、そうでない失敗（中断、期限切れ、入出力の失敗）でも、同じ。言語は、前の回の効果を、取り消さない: 取り消すかは、設計で決める（op に、トランザクションのデコレータを付ける、など）。回ごとに、例外を受けて、次へ進む書き方は、配線には、ない: 止めては困る失敗は、繰り返しの中で呼ぶ op が、デコレータで受ける（勧めは `docs/requirements.md`「書き方の指針」）。
- **`return` は、書けない**（WIRE-13）。途中で終わらせるのは、例外だけ。「見つかるまで、探す」は、葉の op の中身に書く。
- **「返らない」文は、書けない**（WIRE-9）。
- 例外と効果の組の答えは「計算」の「Sig(O, v)」。前に `disjoint` を書いた形は「disjoint」。

この節の細部は、決定 D580 が決めた。

#### 集める

`xs collect 式;` は、繰り返しの、一回ずつの結果を、外の、並びの `val` に集める。`xs` は、次のすべてを満たす（満たさなければ WIRE-14）。

1. この文が、`for` のブロックの中にある（中の `disjoint` のアーム、中の `for` のブロックでも、よい）。
2. 空で宣言した `val`。
3. `xs` の宣言と、この文の間に、`for` が一つ以上ある（`for` の外で、宣言している）。
4. 代入が、済んでいない。同じ `disjoint` の、別のアームが値を入れる `val`（値を入れる文の 2 の裏）と、`try` か `catch` の片方だけが入れた `val`（「例外を受ける」）にも、集められない（決定 D549）。別のアームが集める `val` に、集めるのは、よい（下の「同じ `val` に、集める文を、いくつ書いてもよい」）。

- **集め終わるのは、`xs` の宣言と、この文の間にある `for` のうち、いちばん外のものを、抜けたとき。** そこで、代入が済む。それまで、`xs` は、読めない（WIRE-10）。直列の `for` でも、`disjoint for` でも、同じ。
- **一つの `val` に集められるのは、その、いちばん外の `for` の中からだけ。** 抜けると、代入が済むので、次の `for` では、集められない（4）。
- **同じ `val` に、集める文を、いくつ書いてもよい。** 並びの順は、回の順で、一つの回の中では、文を辿る順（「計算」の「Sig(O, v)」）。`disjoint for` と、`disjoint` のアームの中でも、同じ順: 実際に、並列に動かす基底も、この順に揃える。
- `xs` の型は `list<T>` で、式の型は、`T` に渡せる。型を書いていなければ、式の型から導く（`docs/types.md`「式の型」。合わなければ TYPE-17）。式が「値がない」か「返らない」なら WIRE-2。

```
val xs: X[];
for (val a of as) {
  for (val b of a.bs) {
    xs collect f(b);
  }
  use(xs);        // WIRE-10: まだ、集め終わっていない
}
use(xs);          // 通る: いちばん外の for を、抜けた
```

この節の細部は、決定 D580 が決めた。

### disjoint

`disjoint { アーム … }` は、アームどうしが、互いに触れないことを言う。`disjoint for (…) { … }` は、回どうしが、互いに触れないことを言う（回の一つずつを、アームと見る）。

- **言うのは、コードの性質で、動かし方ではない。** 並列に動かしても、直列に動かしても、よい。どう出すかは、基底が、出力する言語に合わせて決める（`docs/plugin-go.md`「文」）。
- **検査の計算は、アームを、書いた順に、直列に動いたとして行う**（「計算」の「Sig(O, v)」）。下の検査を通ったものは、実際に並列に動かしても、計算の答えが、変わらない。
- **例外は、ほかの文と同じ。** 投げられたら、処理を中断して、呼んだ側に伝わる。並列に動かしているなら、ほかのアームも、止める。言語は、起きた効果を、取り消さない。
- **同じ状態を、読むだけなら、重なってよい。**
- アームのブロックの中の `val` は、そのブロックの中だけで見える。外に出す値は、外の `val` に入れる。あるアームが入れる `val` を、別のアームは、読めず（WIRE-10）、入れられない（WIRE-11）。
- アームの中に、`return` は、書けない（WIRE-13）。「返らない」文も、書けない（WIRE-9）。

この節の細部は、決定 D581 が決めた。

#### 検査

アーム a（ブロックか、文の一つ。中の `for` と `disjoint` も含む）について、次を集める。Sc は「計算」の「Sig(O, v)」の手順 0 の表のもの。

- E(a): a の中の呼び出し c の、Sc.exceptions の和（アームの本体の `throw` を含む）。
- F(a): a の中の呼び出し c の、Sc.effects の和。
- W(a): F(a) の効果が書き込む状態（「効果の宛先」）。
- R(a): 「計算」の「reads」の 1、2 を、a の中の文に当てて集めた状態。

同じ `disjoint` の、別々のアーム a、b のすべての組について、確かめる。

| 規則 | 条件 | 理由 |
|---|---|---|
| DISJ-1 | E(a) が空でなく、F(b) が空でない | 順を入れ替えると、例外のときに、起きている効果が変わる |
| DISJ-2 | W(a) と R(b) に、同じ状態がある | 順を入れ替えると、読む値が変わる |
| DISJ-3 | W(a) と W(b) に、同じ状態 s があり、行で見て、通らない（下） | 同じ行に、二つのアームが書くと、順で、結果が変わる |

DISJ-3 は、s に書く呼び出し（a と b の中の、Sc.effects に、s に書き込む効果を持つ呼び出し）を、行で見る。T は、s の要素の型。

| 呼び出し | 行を受け取る引数 |
|---|---|
| 効果（宣言）の呼び出し | 引数のうち、型が、T と等しいか、T を絞り込んだ型（`T on C.K`）のものが、ちょうど一つあれば、それ（「行の遷移」の「結びつき」の、行の引数と、同じ決まり。`as` を書かない効果にも、当てる。決定 D551） |
| 直に呼ぶ組み込みの効果（`s.post(v)`、`s.put(v)`） | 値の引数。型が T と等しいとき |
| op の呼び出し | 引数のうち、型が、T と等しいか、T を絞り込んだ型（`T on C.K`）のものが、ちょうど一つあれば、それ。op の配線は、辿らない |

- 通るのは、s に書く呼び出しが、どれも、行を受け取り、a の呼び出しが渡した値と、b の呼び出しが渡した値が、どれも、同じでないとき。
- 行を受け取らない呼び出し（識別子で消す効果、行の並びをまとめて書く効果、分類の遷移の効果、別の状態の行だけを受け取る op）が、一つでもあれば、通らない。比べる値がなく、ぶつかるかどうかが、分からない。
- s が、並び（`list`）の状態でなければ、行がないので、通らない。
- 値が同じとは、渡した `Atom` が、同じ名前（`val`、引数、`for` の変数）の、同じパスか、同じ状態の、同じパスであること。リテラルと、レコードリテラルは、どの値とも、同じでない。

`disjoint for (val v of 並び) B` は、ブロック B を、a でも、b でもあるものとして、確かめる。

| 規則 | 条件 |
|---|---|
| DISJ-1 | E(B) が空でなく、F(B) が空でない |
| DISJ-2 | W(B) と R(B) に、同じ状態がある |
| DISJ-3 | W(B) の状態 s に書く呼び出しに、行を受け取らないものがある。または、渡した値が、`v` から始まる `Atom`（`v`、`v.f`）でない（どの回も、同じ値を渡す） |

```
disjoint for (val order of staleOrders) {
  expire(order);              // 通る: 回ごとに、違う行
}

disjoint for (val line of order.lines) {
  addLine(order, line);       // DISJ-3: どの回も、同じ order に書く
}
```

検査が、確かめないこと:

- **違う名前の値が、同じ行であること。** 同じ鍵で、二度引いた値や、並びに、同じものが二つあることは、ありうる。検査は、値の中身を追わない（「検査器が遷移を使う範囲」と同じ）。違う名前を渡していれば、書いた人の主張として、通す。
- **仕様の例外でない失敗。** どのアームからも起きうるが、検査が見るのは、仕様の例外（Sc.exceptions）だけ。

### 例外を受ける

`try { … } catch (e) { … }` は、`try` のブロックが投げた例外を、`catch` のブロックで受ける（決定 D419、D422。構文は `docs/grammar.md`「配線」）。

- **受けるのは、仕様の例外だけ。** `exception` で宣言した例外のうち、`try` のブロックが投げうるもの（「計算」の「Sig(O, v)」の「例外を受ける文」の、受ける例外の集まり）。仕様にない失敗（実装の不具合、基盤の障害）は、受けずに、そのまま伝わる。
- **`e` は、受けた例外の名前。値では、ない。** 書けるのは、`match (e by 分類)` の対象と、`throw e` だけ（ほかの値の位置に書けば WIRE-16）。見えるのは、その `catch` のブロックの中。名前の決まりは、`val` と同じ（見えている名前と同じなら WIRE-4）。`e` から、例外の引数を読む書き方は、ない（`docs/open.md`「言語」）。
- **`throw e` は、受けた例外を、そのまま、投げ直す。** 引数は、書かない（書けば WIRE-16）。`throw 例外` は、別の例外を投げる（「throw」）。`catch` のブロックの `throw` の文は、最後の文にだけ書ける（文法で閉じる）。アームの本体の `throw e` は、`e` が見える所なら、書ける。
- **`catch` のブロックが「返らない」**とは、最後の文が、`throw` の文か、「返らない」式の文（`docs/types.md`「式の型」）であること（`Catch.never`。`docs/ir.md`「配線」）。「返らない」文は、`catch` のブロックでは、最後にだけ書ける（WIRE-9）。
- **書ける所**: op とデコレータの本体のいちばん外、`for` のブロック、`try` と `catch` のブロック。`disjoint` のアームの中（アームの中の `for` も）には、書けない（WIRE-15）: アームが例外を出しうるかの検査（DISJ-1）を、受ける道と合わせて決めるまで、閉じておく（`docs/open.md`「言語」）。
- **`try` と `catch` のブロックに、`return` は書けない**（WIRE-13。`for` と同じ）。値は、外で宣言した `val` に入れて、渡す。
- **`val` の見える範囲**は、ほかのブロックと同じ（「値の入れ物」の「見える範囲」）。
- **値を入れる文**（`x = 式;`）は、`try` と `catch` の、どちらのブロックにも書ける。`catch` のブロックは、`try` の前の集まりから始める（`try` が、どこで止まったかは、決まらない）ので、`try` が入れた `val` に、`catch` も、入れられる。抜けた後に、代入が済んでいる `val` は、「値の入れ物」の「代入が済んでいるか」の表。片方だけが入れた `val` は、抜けた後、読めず（WIRE-10）、入れられず（WIRE-11）、集められない（WIRE-14）。

  ```
  val quote;
  try {
    quote = fetchQuote(item);
  } catch (e) {
    quote = fallbackQuote(item);
  }
  return quote;
  ```

- **集める文**は、`try` と `catch` のブロックにも書ける（「繰り返し」の「集める」の決まりのまま）。
- `catch (e by 分類) { … }` は、`catch (e) { match (e by 分類) { … } }` と同じ（IR でも、同じ形: `docs/ir.md`「配線」）。分類の決まりは「分類」の「例外の分類」。

## 計算

規則の検査に先立って、op ごとに次を計算し、`Op.signature`（`docs/ir.md`「op」）と `Call.bound` に置く。例外・効果・読む状態・純粋さと、`bind` で埋まる位置。計算は op の呼び出しの依存の順に行う。配線の呼び出しが循環していれば WIRE-7 で、循環に含まれる op は本体を無視して葉として計算する。計算の途中で出す診断（REL-4、DEC-5、DEC-16、WIRE-7）は Sig(O, ns(O)) を計算するときだけ出し、ほかの見る側の計算では出さない。

記法: op を O、O の名前空間を ns(O)、O に付いたデコレータの適用を内側から順に d₁ … dₙ（`Op.decorators` の末尾から先頭へ）。各 dᵢ の宣言を D(dᵢ) とし、`$param:` の参照はその適用の引数で置き換えてから使う。見る側の名前空間を v とする。

この節の細部は、決定 D685 が決めた。

### デコレータが運ぶ reads と effects

デコレータの宣言の `reads` / `effects` の節（`docs/grammar.md`「decorator の宣言」）は、そのデコレータの処理（op の始端と終端に足すもの）が読むものと持つ効果を言う。付いた op が葉でも配線でも、その op の関数の型（Sig）に加わる（決定 D149）。デコレータは、op の中身を変えない: 足した処理が触れる状態を、付いた op のものとして数えるだけ。

- **運ばれるもの**（`Op.carried`。`docs/ir.md`「op」）: O に付いたデコレータを書かれた順（`Op.decorators` の順）に、その宣言の節を書かれた順に見て、節の要素を並べたもの。要素は op の節と同じ形（「状態に触れるもの」の「節に書く要素」）で、デコレータの引数を指す要素（`$param:`）は、その適用の引数の値で置き換える: `any effect` の引数の値は名前で書いた効果（`named`）に、`any state` の引数の値は直に書いた状態（`direct`）になる。残りの引数なら、渡した値を書いた順にすべて。省略可能な引数を省いていれば、何も足さない。効果のユニオンは展開する。`reads` の要素は `carried.reads` に、`effects` の要素は `carried.effects` に入れ、それぞれ重複を最初の出現に寄せる。同じデコレータを何度も付けていれば（`@repeatable`）、適用ごとに足す。
- **葉の op** O が**直に読む状態**は、`Op.carried.reads` の要素ごとの状態（`read` の宣言ならその宛先、直に書いた状態ならその状態）を同じ順に並べ、重複を最初の出現に寄せたもの。**直に持つ効果**は、`Op.carried.effects`。葉は自分では状態に触れない（「状態に触れるもの」の「葉の op」）ので、運ばれるものがすべて。STATE-5 に当たった葉（節を書いた葉）は、書いたもの（`Op.reads`、`Op.effects`）を前に並べて、残りの計算を続ける。
- **配線の op** は、本体が行き着くものの後ろに、運ばれたものを並べる（効果は「Sig(O, v)」の手順 0、読む状態は「reads」）。デコレータの処理が、本体のどの行の前後で起きるかを、言語は決めないので、運ばれた効果の rel と succ は、本体の行の順からではなく、葉と同じに決める（同 手順 0）。
- **配線の op が節を書いていても、運ばれたものを、書かなくてよい。** 節に書くのは、その op が、自分で足す分で（「状態に触れるもの」の「節に書く要素」）、運ばれたものは、デコレータが足す。
- 葉の op が、自分では `reads` / `effects` の節を書けないこと（STATE-5）は、変わらない。デコレータが葉に運ぶことは、葉が節を書くことではない。
- 運ばれたものは、葉でも配線でも、付いた op の名前空間のものでなければならない: 別の名前空間の状態を読むもの（その状態、その状態の `read`）なら READS-1、別の名前空間の効果なら STATE-2。デコレータの処理は、op を呼ばずに状態に直に触れるので、配線が別の名前空間の op を呼んで行き着くもの（EFF-1、「reads」）とは違い、持ち主の名前空間に限る。
- 運ばれる効果はいくつでもよい。順序はデコレータの引数に書いた順で、それらをどう行うか（一体か、どの順か）は、そのデコレータを読むトランスパイラが決める。
- 呼び出し元への伝わり方は、葉に運ばれたものも、配線に運ばれたものも、配線が呼んだ効果と `read` と同じ（EFF-1、「reads」）。デコレータの付いた op は、もともと純粋でない（「純粋」の 1）ので、純粋さは変わらない。
- 呼び出しが循環している op（WIRE-7）は、葉として計算するので、節を書いた葉と同じ: 書いたもの（`Op.reads`、`Op.effects`）を前に、運ばれたものを後ろに並べる。

### コメントの中のタグ

決定 D477、D478。説明のコメントの中の、デコレータのタグ（`docs/grammar.md`「ドキュメンテーションコメント」）は、文章を、ただ一つの引数にした、デコレータの適用。その宣言の `decorators` に、ふつうの適用として入り（IR は、宣言の前に書いた適用と、区別しない）、適用の検査（名前の解決、DEC-1、DEC-11、DEC-13、CFG-26 など）は、そのまま当たる。DEC-13（二度付いている）は、コメントの中のタグと、宣言の前の適用を、合わせて数える。

コメントの中に書けるのは、**`@hint` の付いた、文字列を一つ取るデコレータ**だけ。`@hint` は、解釈されなくてよい、注記の印（「デコレータ」の `@hint`）: コメントの中に書けるのは、注記だけで、振る舞いを決めるデコレータ（`@http.get` など）は、宣言の前に書く。コメントが、振る舞いを変えることは、ない（決定 D480）。`@hint` のないデコレータを、コメントの中に書けば、DEC-29。文字列を一つ取る、とは: 引数が、ちょうど一つで、残りの引数（`...`）でなく、型が `string` 一つ（省ける引数 `名前: string?` でもよい）。引数を持たないデコレータ、二つ以上の引数を持つもの、型が `string` でないもの、型を二つ以上書いたもの、残りの引数だけのもの、名前付きデコレータ（引数を固定している）は、DEC-29。

この節の細部は、決定 D759 が決めた。

### デコレータの本体

決定 D392〜D394。本体のあるデコレータ（`docs/grammar.md`「デコレータの本体」）は、**付けた所で、広げたものとして扱う**: それを付けた op は、「その op の配線が、自分で、包んだ関数の呼び出し（`next()`。`docs/grammar.md`「デコレータの本体」）の前後の呼び出しを書いた」のと、同じに計算する。

- **計算**（「Sig(O, v)」の手順 i）: 本体を、配線の本体と同じに、手順 0 の表で計算する。包んだ関数の呼び出し の行の Sc は、そこまでの Sig（op の中身と、内側のデコレータ）。本体の行の順から、例外と効果の関係が決まるので、`prevents effects` / `keeps effects` を、宣言に書かなくてよい（包んだ関数の呼び出し より前で投げれば、op の効果は「起きていない」）。
- **節**（`throws`、`reads`、`effects`）は、書かなくてよく、書いた分は、計算に足す（「状態に触れるもの」の「節に書く要素」と、同じ決まり）。`catches` の節は、書けない（DEC-22）: 例外を受ける処理は、本体の `try` で書く（下）。
- **例外を受ける**（「op の宣言と本体」の「例外を受ける」）: 本体にも、`try` を書ける。包んだ関数の呼び出し を `try` のブロックに書くなら、最初の文で（`try { next(); … } catch (e) { … }`）、`catch` のブロックには、書けない（DEC-19）: 受ける道が、包んだ関数の呼び出し を、呼ばずに終わることも、二度呼ぶことも、なくなる。DEC-20 は、`try` の文を、`try` のブロックの中の回数で数える。
- **包んだ関数の呼び出し を `try` のブロックに持ち、`catch` のブロックが「返らない」でないデコレータは、値を返す op と、`never` を返す op には、付けられない**（DEC-27。DEC-4 と同じ理由: 受けた後に、返す値がない）。`catch` のブロックが「返らない」（受けて、記録して、投げ直す）なら、付けられる。
- **本体が呼べるのは、付けた op の名前空間の配線が、呼べるもの。** 宣言した名前空間の op に付けたなら、その名前空間の op、`read`、効果、状態。別の名前空間の op に付けたなら、`export` の op だけ（DEC-24）。本体の中の名前は、宣言した名前空間で解決するので、宣言の側の検査（NS-5、NS-6）は、宣言した名前空間から見て行う。
- **読む状態**（「reads」）と、**呼び出しの循環**（WIRE-7）には、本体の呼び出しを、付けた op のものとして数える。
- **`never` を返す op（「never を返す op」）に付けたとき**、包んだ関数の呼び出し は、「返らない」: 包んだ op は、いつも、例外を投げる。なので、包んだ関数の呼び出し（か、包んだ関数の呼び出し のアームを持つ `match`）の後ろに、文を持つデコレータは、`never` を返す op には、付けられない（DEC-25。後ろの文が、評価されない: WIRE-9 と、同じ理由）。後ろの文は、同じブロックの、下の文と、包んだ関数の呼び出しを `try` のブロックに持つなら、その `try` の文の下の文（`never` を返す op に付けられるのは、`catch` のブロックが「返らない」ものだけ: DEC-27。なので、`try` の文の下にも、届かない。決定 D550）。前で確かめるだけのデコレータ（包んだ関数の呼び出し が、最後）は、付けられる。本体が、状態に触れることを、`never` を返す op の条件（同 5）と、そろえるかは、決めていない（`docs/open.md`「言語」）。
- **二つ以上を付けたとき**の、外と内の順は、ほかのデコレータと同じ（`docs/ir.md`「デコレータの適用」: 先に書いたものが、外）。
- **まだ見ないこと**: 本体の呼び出しの、必須の入力（BIND-4）と、`bind` で埋まる位置（`Call.bound`）。本体の呼び出しには、`bind` が効かない。本体の `disjoint` の検査（「disjoint」の DISJ-1〜DISJ-3）: アームの中の 包んだ関数の呼び出し の Sc は、付けた op ごとに違うので、宣言の側だけでは決まらない（`docs/open.md`「言語」）。

この節の細部は、決定 D684 が決めた。

### Sig(O, v)

名前空間 v から O を呼んだときの関数の型。六つの値を持つ。

- E: 投げうる例外の列
- F: 効果の列（効果の数え方は「状態に触れるもの」の「節に書く要素」）
- rel(X, e): X ∈ E、e ∈ F ごとの `kept` / `prevented` / `unknown`
- succ(e): 成功のアームでの e の `kept` / `prevented` / `unknown`
- R: 読む状態の列（下の「reads」）
- pure: 純粋かどうか（下の「純粋」）

R と pure は v によらない（どの名前空間から見ても同じ）。

**手順 0（本体の分）**

葉の op:

- E = `Op.throws` の例外（`Declared(O)` と呼ぶ）。
- F = O が直に持つ効果（デコレータが運ぶ `Op.carried.effects`。「デコレータが運ぶ reads と effects」）。
- rel(X, e) = X を含む `ThrowsClause` の `relations` に `prevents` があれば `prevented`、`keeps` があれば `kept`。どちらもなければ `unknown`。両方あれば REL-5。
- succ(e) = `kept`。
- 運ばれた効果が投げる例外を、足す（下の「運ばれた効果が投げる例外」）。
- 呼び出しが循環している op（WIRE-7）は、本体を無視して、F = `Op.effects`（節に書いたもの）の後ろに `Op.carried.effects` を並べたもの（重複は最初の出現に寄せる）で、同じに計算する。

配線の op: 本体の文を、**辿る順**に見る。辿る順は、書いた順で、中のブロックにも入る: `for` は、ブロックの文を、上から。`disjoint` は、アームを、書いた順に、アームの中の文を、上から。`disjoint` も、`for` も、直列に動いたとして計算する（決定 D335）: `for` のブロック（`disjoint for` も）は、並びの順に、0 回以上、動き、前の回の効果は、起きている。

辿る順の i 番目の文の呼び出し（`val` / `=` / `collect` / 呼び出しの文 / `return` なら一つ、`match` ならアームごとの呼び出し）c について、Sc を次の表で決める。値（`Atom`）の本体と、式が `Atom` の文は、呼び出しを持たない。

| c | Sc.exceptions | Sc.effects | Sc.rel、Sc.succ |
|---|---|---|---|
| op の呼び出し | Sig(callee(c), ns(O)) のもの | 同左 | 同左 |
| 効果の呼び出し（`createOrder(order)`、`orders.post(order)`） | 宣言なら、その効果の `throws`（`Effect.throws`）。直に呼んだものなら、空 | その効果一つ（宣言なら `named`、直に呼んだものなら `direct`） | succ は `kept`。rel は、どの例外も `prevented`（投げたとき、その効果は、起きていない） |
| `read` の呼び出し | 空 | 空 | — |
| アームの本体の `throw X`（引数があっても同じ） | X だけ | 空 | —（出どころは、その文とその `throw`） |

- F = 各 Sc.effects を、辿る順、アームの順に連結し、重複を最初の出現に寄せたもの。
- E = 各 Sc.exceptions の和に `Declared(O)` を足したもの（節に書いただけで、本体から出ない例外も含む。THROWS-4）。O が `throws` の節を書いていなければ、`Declared(O)` は空で、E は、本体から出る例外。節に書いていない、本体から出る例外も、E に入る（「状態に触れるもの」の「節に書く要素」）。
- X の**出どころ**は、X ∈ Sc.exceptions となる (文 i, 呼び出し c) の組。出どころ一つにおける e の状態は、上から順に最初に当たるもの。「c′ が e を持つ」は、e ∈ Sc′.effects のこと:
  1. e を持つ c′ が、文 j < i にあり、c′ を囲む `for` が、どれも、文 i も囲んでいる（どの `for` にも囲まれていない c′ を含む） → `kept`（c′ は、必ず、先に動いている）
  2. e ∈ Sc.effects で、Sc.rel(X, e) が `kept` → `kept`
  3. e を持つ c′ が、文 j < i にあり、c′ を囲む `for` に、文 i を囲まないものがある → `unknown`（その `for` は、0 回かもしれない）
  4. e を持つ c′（c 自身でも、文 i より後ろでも）と、文 i を、ともに囲む `for` がある → `unknown`（前の回で、起きたかもしれない）
  5. e ∈ Sc.effects → Sc.rel(X, e)
  6. それ以外（`match` の文 i の別のアーム、文 j > i、どこにもない） → `prevented`
- rel(X, e) = すべての出どころで同じ状態ならその状態、違えば `unknown`。出どころのない X（`Declared(O)` だけにあるもの）は葉と同じく `Op.throws` の `relations` から決める。
- succ(e) = e を持つ呼び出し c ごとに、状態を集める: c が `for` に囲まれていれば `unknown`（0 回かもしれない）、そうでなければ Sc.succ(e)。集めたものが、すべて `kept` なら `kept`、すべて `prevented` なら `prevented`、それ以外は `unknown`。`match` の文で、一部のアームにしかない e は `unknown`。ただし本体が「返らない」アーム（`throw`、`never` を返す op の呼び出し。`docs/types.md`「式の型」）は、成功しないので数えない（`Registered => issueSession(...); Unregistered => throw X;` の `issueSession` の効果は、すべてのアームにあるものとして扱う）。
- `disjoint` のアームを、どの順に辿っても、rel と succ は、変わらない: 例外を出しうるアームと、効果を持つ、別のアームは、同じ `disjoint` に、書けない（DISJ-1。「op の宣言と本体」の「disjoint」）。
- `for` の中に効果を持つ op は、その効果について、「例外のとき、起きていない」（`prevents effects`）を、言えない（4 で `unknown` になり、REL-4）。
- **例外を受ける文**（`try { B } catch (e) { H }`。「op の宣言と本体」の「例外を受ける」）:
  - **受ける例外の集まり** C は、B の中の呼び出しと `throw` の Sc.exceptions の和。B の中の `try` が受けた分は、入らない。その `catch` のブロックから出る分は、入る。
  - B の中の呼び出しは、**出どころにならない**: その例外は、E に入らない。効果は、F に入る。
  - H の中の呼び出しと `throw` は、ほかの文と同じに、出どころになる。`throw e` は、C のすべての例外の出どころで、効果を持たない。受けた例外の `match (e by 分類)` のアームの本体の `throw e` は、C のうち、そのアームが受けるケースに当たる例外だけの出どころ（残りのケースには、ほかのケースの、どの例外でもないものが、当たる）。
  - 出どころ（文 i）から見た、e を持つ c′（文 j < i）の扱いを、上の 1〜6 に足す。B と H は、「動いたか、分からない」範囲として数える。

    | c′ の場所 | 文 i の場所 | 扱い |
    |---|---|---|
    | B | H | 3 と同じ（`unknown`: 例外が、c′ の前で起きたか、後で起きたかは、決まらない） |
    | B | この文より後ろ | H が「返らない」なら、囲まれていないのと同じ（B は、終わりまで動いている）。そうでなければ 3 と同じ |
    | H | この文より後ろ | H が「返らない」なら、c′ は、ないものとする（H が動けば、文 i には、来ない）。そうでなければ 3 と同じ |
    | B と B、H と H（同じ文の、同じブロック） | | 囲まれていないのと同じ |

  - succ(e): B の中の c は、H が「返らない」なら Sc.succ(e)、そうでなければ `unknown`（受けて、成功で終わる道では、e が起きたか、決まらない）。H の中の c は、H が「返らない」なら `prevented`（成功したなら、H は、動いていない）、そうでなければ `unknown`。
  - 受けた例外の `match (e by 分類)` の漏れ（MATCH-10）は、C と、分類のケースの例外を比べて、ここで確かめる。デコレータの本体の `try` では、付けた op ごとに、C が違うので、適用ごとに確かめる（位置は、適用）。
- **節に書いた効果**（`Op.effects`）e を、その順に見る。e ∈ F（本体が、もう、e に行き着いている）なら、何も変えない。e ∉ F なら、e を F の末尾に足し、rel(X, e) と succ(e) は、葉の op と同じ値: 各 X ∈ E について、X を含む `ThrowsClause` の `relations` から決めた状態（`prevents` なら `prevented`、`keeps` なら `kept`、どちらもなければ `unknown`）と、成功のアームの `kept`（本体は、e を行わないので、行の順からは、決まらない）。
- **運ばれた効果**（`Op.carried.effects`）e を、その順に、ここまでの F、rel、succ に足す。e の**デコレータの分**は、葉の op と同じ値: 各 X ∈ E について、X を含む `ThrowsClause` の `relations` から決めた状態（`prevents` なら `prevented`、`keeps` なら `kept`、どちらもなければ `unknown`）と、成功のアームの `kept`。
  - e ∉ F（本体は e に行き着かない）なら、e を F の末尾に足し、rel(X, e) と succ(e) は、デコレータの分。
  - e ∈ F（本体も e に行き着く）なら、F の位置はそのまま。rel(X, e) と succ(e) は、本体から決めた状態とデコレータの分が同じならその状態、違えば `unknown`。
- **運ばれた効果が投げる例外**（葉でも、配線でも）: 運ばれた効果 e が、宣言した効果で、`throws` を持てば、その例外 X を、E の末尾に足す（既にあれば、位置はそのまま）。op が `throws` に書いていなくてよい（デコレータの `throws` と同じ: 手順 i）。この出どころでの状態は、e は `prevented`（投げたとき、e は、起きていない）、ほかの効果は `unknown`（デコレータの処理が、本体のどの行の前後で起きるかを、言語は決めない）。X が、ここで初めて E に入るなら、rel(X, ·) は、その状態。X が、もう E にあれば、同じならその状態、違えば `unknown`。
- 配線の `Op.throws` に `relations` が書かれていれば、ここで計算した rel と比べる（REL-4。関係を付けた `throws` は、上書きで、計算と合っているかを確かめる: 「状態に触れるもの」の「節に書く要素」）。節に書いただけの効果と、運ばれた効果だけの組は、書かれた `relations` から決めたので、食い違わない。運ばれた効果が投げる例外を、op も `relations` を付けて書いていれば、その組も、同じに比べる（運ばれた効果のほかの効果は `unknown` なので、`prevents effects` とは、言えない）。

**手順 i = 1..n（デコレータ dᵢ を内側から）**

D = D(dᵢ) が、本体を持てば、節を適用する代わりに、本体を、手順 0 の表で計算し、その結果を、新しい Sig にする（「デコレータの本体」）。本体を持たなければ、次のとおり。

D = D(dᵢ) について、`catches` の節をすべて、次に `throws` の節をすべて、最後に `outer throws` の節をすべて適用する。`reads` / `effects` の節は、ここでは適用しない（葉でも配線でも、手順 0 と「reads」で数えてある）。

- `catches Xs mode`: 各 X ∈ Xs について、X ∉ E なら DEC-16（吸収する相手がない）。X ∈ E なら:
  - `recovers` / `ignores`: 各 e ∈ F について rel(X, e) ≠ `kept` なら succ(e) = `unknown`（§8.2「効果が不明な例外を `recovers` で吸収すると、成功のアームでもその効果は不明になる」）。X を E から除く。
  - `halts h`: X を E から除く。h ∉ F なら h を F の末尾に足し、残りのすべての Y ∈ E について rel(Y, h) = `prevented`、succ(h) = `prevented`。h ∈ F ならそのまま。h が `throws` を持てば、その例外 Z を、E の末尾に足す（既にあれば、位置はそのまま）: この出どころでの状態は、h が、ここで F に足したものなら、h は `prevented`、それ以外は、どの効果も `unknown`。Z が、もう E にあれば、同じならその状態、違えば `unknown`。
- `outer throws Ys relations`（`Decorator.outerThrows`）: v = ns(O) なら飛ばす（DEC-10: fn の外で起きる例外は、境界の外から見たときだけ、加わる。`docs/grammar.md`「decorator の宣言」）。そうでなければ、下の `throws` と同じに適用する。
- `throws Ys relations`: 各 Y ∈ Ys について、Y を E の末尾に足し（既にあれば位置はそのまま）、各 e ∈ F について `relations` から状態を決める（葉の rel と同じ規則。目的語の `effects` は F のすべて）。Y が既に E にあって状態が違えば `unknown`。

**結果**: `Signature.exceptions` = E、`effects` = F、`relations` = rel、`successEffects` = succ、`reads` = R、`pure` = pure。`Op.signature` = Sig(O, ns(O))。`View.ops` は Sig(O, viewer)（`docs/ir.md`「その名前空間から見た IR」）。

この節の細部は、決定 D582、D685 が決めた。

### reads

op が読む状態。`effects`（書く）と対になる、事実の記録（決定 S15）。状態を読むのは、配線が呼ぶ `read` と、配線が名前で書いた状態（「状態に触れるもの」の「read と効果」）で、op の R は、その op の本体が行き着くものと、付いたデコレータが運ぶもの（「デコレータが運ぶ reads と effects」）を集めたもの。

R は基底の状態の FQN の列で、op ごとに次のように決まる。デコレータが R に足すのは、`reads` の節が運ぶものだけ（「デコレータが運ぶ reads と effects」）。`throws` / `catches` の節は R を変えない。

葉の op: R = O が直に読む状態（デコレータが運ぶ分だけ。「デコレータが運ぶ reads と effects」）。別の名前空間の状態なら READS-1。

配線の op: 本体の文を、辿る順（「Sig(O, v)」の手順 0）に見て、次を出現順に集め、その後ろに、節に書いた状態（`Op.reads` の要素ごとの状態を、その順に）、運ばれた状態（`Op.carried.reads` の要素ごとの状態を、その順に。別の名前空間の状態なら READS-1）を並べ、重複を最初の出現に寄せる。一つの行の中の順は 1、2 の順。

1. `for` の文なら、頭の並びの `Atom` が参照する状態。`match` の行なら、その対象が読む状態: 対象の `Atom` が参照する状態。`match (by C)` なら、C の対象の状態を宣言の順に。
2. 行の式（`match` の行ならアームの順に、各アームの本体）ごとに、次の順:
   1. `Atom` が参照する状態（書かれた順。呼び出しの引数、レコードリテラルの中の値、`return` の値、アームの値を含む）。
   2. 呼び出しの `Call.bound` の状態（`bound` の順）。
   3. 呼び出し先が op なら、その Sig の R。`read` なら、その宛先の状態（`Read.state`）。効果なら、何も足さない（効果は書くもので、読むものではない）。

- R は名前空間をまたいで伝わる。`server` の配線が、`store.users` を読む `store.findUser` を呼べば、その配線の R に `store.users` が入る。効果（EFF-1）と同じ。
- 配線の op は `reads` を書かなくてよい。書いた要素の状態は、R に加わる（本体が、もう読んでいる状態なら、何も変わらない。要素の数え方は「状態に触れるもの」の「節に書く要素」）。書いた節と、本体が読む状態を、照合して、エラーにすることは、しない。計算した分にない状態を書けば、READS-3（warning。同）。
- 呼び出しが循環している op（WIRE-7）は、葉として R = `Op.reads` の要素の状態の後ろに、運ばれた状態を並べたもの。

### 純粋

op が純粋かどうかを、仕様から割り出す（決定 D60）。op そのものの性質で、見る側の名前空間にも `hozo.toml` にもよらない。診断は持たず、使うのはトランスパイラ（`Signature.pure`）。

pure(O) が真なのは、次のすべてを満たすとき。

1. O にデコレータが付いていない（`Op.decorators` が空。どのトランスパイラも読まない印のデコレータでも、付いていれば純粋でない）。
2. R が空（状態を読まない。配線なら、状態を名前で参照せず、状態の分類で `match` せず、`bind` で埋まる位置を持たず、`read` も、状態を読む op も呼ばない）。
3. F が空（効果を持たない。配線なら、効果も、効果を持つ op も呼ばない）。
4. 配線なら、本体が呼ぶ op がすべて純粋。

- `throws`、アームの `throw`、値の分類や op の分類での `match` は、純粋さを変えない。
- 呼び出しが循環している op（WIRE-7）は、葉として 1〜3 だけで決める。
- デコレータのない葉の op は、いつも純粋: 葉は自分では状態に触れない（「状態に触れるもの」の「葉の op」）。
- 外部の入出力をする op が純粋にならないことは、規則ではなく書き方から来る（`docs/requirements.md`「書き方の指針」）。

### bind

`Bind` b（名前空間 A、状態 s、対象 T）と op O について、埋める位置 Pos(b, O):

1. ns(O) が T.namespace と等しくない（`deep` なら T.namespace を接頭辞に持たない）→ Pos は空。位置を持つのは op だけで、`read`、効果、`throw` の引数は `bind` で埋まらない（その呼び出しの `Call.bound` は、いつも空）。ns(O) が A と違い、O に `export` がない（A から呼べない。「op の宣言と本体」の「export」）→ Pos は空。
2. s の `shape` が `list` → BIND-6。
3. τ = s の `element`。
4. O の各引数から、型が τ または `optional(τ)` の位置を集める。型が model（または model の `optional`）ならフィールドを再帰的に辿る。`array` の中は辿らない。インデックスの model（`docs/types.md`「インデックスの model」）は、フィールドを持たないので、その先は辿らない。辿っている途中で同じ model に戻ったら、そこで止める。位置はパス（`["in", "token"]`）。
5. 位置が 2 以上 → BIND-1。1 で、s の `shape` が `nullable` で、位置の型が `optional` でない → BIND-2。
6. 二つの `Bind` が同じ op の同じ位置に当たる → BIND-5。

A の配線の呼び出し c（callee O）の `Call.bound` は、A のすべての `Bind` の Pos(b, O) から、c が明示している位置を除いたもの（BIND-3）。位置が明示されているのは、パスの引数が `name` か `state` の `Atom` で渡されている（中身は分からないので明示とみなす）か、レコードリテラルの連なりがパスのフィールドを持つとき。

### 必須の入力（BIND-4）

各呼び出し c について、呼び出し先の各引数 p。呼び出し先は、op のほか、`read`、効果（`effect` の宣言と、直に呼ぶ組み込みの効果。引数は「状態に触れるもの」の「直に呼ぶ組み込みの効果」の表）、アームの本体の `throw`（引数は例外の `params`）。op でない呼び出し先では、`Call.bound` は空として読む。

- p の型が `optional` でなく、c の `args` に p がなく、`Call.bound` に `[p]` もなければ BIND-4。
- c の `args` に p がレコードリテラルで渡されていれば、`docs/types.md`「当てはまる」の手続きで、必須のフィールドが `Call.bound` のパスも含めて埋まっているかを再帰的に確かめる。足りなければ BIND-4（パスを示す）。レコードリテラルが、union のアームに入っていれば（`docs/types.md`「union に入れる」。IR の `arm`）、当てはめる先は、そのアームの型の model。

呼び出しの引数の外の、レコードリテラル（決定 D548）: `docs/types.md`「当てはまる」は、リテラルを model に当てはめるどの位置でも、必須のフィールドが埋まっていることを求める。呼び出しの引数のほかに、当てはめる位置は、`return` の式、型を書いた `val` に入れる式（宣言の式と、値を入れる文）、型を書いた `val` に集める式、`match` のアームの本体（`docs/types.md`「match の型」の 6）。デコレータの引数には、レコードリテラルを書けない（`docs/grammar.md`「デコレータ」の `ArgTerm`）。

- その位置のレコードリテラル r と、当てはめる先の model T について、上と同じ手続きで、必須のフィールドを再帰的に確かめる。`bind` は効かない（`Call.bound` は空として読む: `bind` が埋めるのは、op の引数だけ）。足りなければ BIND-4。パスは、r のフィールドの名前から始まる（`["user", "id"]`）。
- 呼び出しの引数の中のレコードリテラル（フィールドの値の、中のものを含む）は、上の、呼び出しの手続きだけが確かめる。
- デコレータの本体の中の呼び出しの引数は、確かめない（「デコレータの本体」の「まだ見ないこと」）。本体の中の、呼び出しの引数の外のレコードリテラルは、確かめる。

### 入口ごとの、求めるケース

本体は、View を作るときに、見る側の出力ごとに、入口の op 一つずつについて、インテグレーションテスト（`docs/ide-chain.md`「テストの規約」の「インテグレーションテストの作り直し」）が要るケースのうち、言語に依らない分を求め、`View.entries`（`docs/ir.md`「その名前空間から見た IR」）に置く（決定 D409）。求めるのは、例外の出どころと、そこへ、差し替えで入らせる方法と、受ける道。プラグインは、これを読み、同じ計算を、しない。

- **差し替え**は、流れの一部を、テストが、言ったとおりに振る舞うものに、置き換えること（Go では、にせもの: `docs/plugin-go.md`「テストのにせもの」）。
- **本体が決めないこと**は、二つ: 差し替えを、その言語で、できるか。入口を、どう呼ぶか。プラグインが決める（Go は `docs/plugin-go.md`「テストのにせもの」の「求めるケースを、にせものに当てる」）。
- **起こりうる結果**は、正常（`Entry.normal`: op が、`never` を返さなければ、ある。ケースは、一つ）と、例外（入口の `Op.signature.exceptions`。どれも、`Entry.sources` に、一つ以上の出どころを持つ）。
- **入口の層が断る結果は、求めない。** 入口の語彙のプラグインだけが知る（`docs/plugin-go-http.md`「必要なケース」の `BadRequest`）。
- この計算は、診断を出さない。

この節の細部は、決定 D668、D687、D688、D689、D690、D691 が決めた。

#### 入口

入口は、見る側の単位の対象の op のうち、`@entry` の付いたデコレータ（`Decorator.entry`。`docs/grammar.md`「decorator の宣言」）を、一つでも持つもの。`View.entries` の順は、op の宣言順。

- **単位の対象の op** は、見る側の名前空間の op のうち、`View.files` のファイルに宣言されたもの。
- **入口のデコレータを読むプラグインが、単位にあるかは、見ない。** 読む者のない入口も、数える（どこに見せるかは、決めていない: `docs/open.md`「語彙とプラグイン」）。

#### 流れ

流れは、入口の op から、呼び出しを辿って届く範囲。辿るのは、本物で通す所だけ。通さない所（**流れの端**）は、差し替える相手になる。

| 呼ぶ先 | 扱い |
|---|---|
| 同じ名前空間の、単位の対象の、配線の op | 中を辿る |
| 同じ名前空間の、本体のない op と、単位の対象でない配線の op | 葉。中は、辿らない |
| `effect fn`、`read fn`、状態 | 流れの端 |
| 別の名前空間 M の op で、M に、通す出力がない | 流れの端（外の仕組みの op） |
| 別の名前空間 M の op で、その op が、入口のデコレータを持つ | 流れの端（相手の入口。同 383、408）。M に、通す出力があっても、中は、辿らない |
| 別の名前空間 M の op で、そのほか | M の通す出力の中を、この表で辿る |

- **通す出力**: 出力 (U, N) から見た、別の名前空間 M の通す出力は、単位 U が M も出力するなら、それ。出力しなければ、U と同じ基底（`NamespaceConfig.base`）の単位のうち、M を出力するものが、ちょうど一つなら、それ。一つもなければ、通す出力は、ない。
- **二つ以上あれば、その入口のケースは、求めない。** `Entry.blocked` に理由を置き、`sources` と `caught` は、空にする。
- **通す出力の中の、単位の対象の op**: 見る側と同じ単位なら、`View.files` のファイルの op。別の単位なら、その名前空間のすべての op（別の単位の `in` を、View は持たない）。
- **op に付いたデコレータ**は、単位の対象の op のものだけを、外側から順に通る（同じデコレータは、一度）。本体のあるデコレータ（`docs/grammar.md`「デコレータの本体」）は、本体を、配線と同じに辿り、包んだ関数の呼び出し の所で、内側（次のデコレータ。最後は、op の中身）へ進む。本体のないデコレータは、差し替える相手で、中は、ない。
- 呼び出しが輪になる op（WIRE-7）は、二度目を、辿らない。

この節の細部は、決定 D668、D688 が決めた。

#### 出どころ

出どころは、流れの中で、例外を投げるもの。種類（`EntrySource.kind`）ごとに、何が、どの例外の出どころで、差し替えで、どう起こすか（`EntryStep` の `verb` は `throws`。相手の種類が、表の最後の列）:

| 種類 | 出どころ | 例外 | 例外を投げさせる相手（`EntryStep.kind`） |
|---|---|---|---|
| `leaf` | 葉 | 本体のない op は、節に書いた例外（`Op.throws`）。単位の対象でない配線の op は、`Op.signature.exceptions` | その op（`leaf`） |
| `effect` | 流れが呼ぶ `effect fn` | 宣言の `throws` | その効果（`effect`） |
| `external` | 流れの端の op（外の仕組みの op、相手の入口） | その op の `Op.signature.exceptions` | その op（`op`） |
| `boundary` | 別の名前空間から呼んだ op の、境界: その op に付いたデコレータの `outer throws`（op は、投げない。そこへ届くまでに、起きる: 同 407） | 節の例外 | その op（`op`） |
| `decorator` | 単位の対象の op に付いた、本体のないデコレータの `throws` | 節の例外 | その op の、そのデコレータ（`decorator`） |
| `arm` | 配線か、デコレータの本体の、`match` の `throw` のアーム。`catch` のブロックの `throw 例外` | その例外 | —（アームに、入らせる: 「入らせる方法」「例外を受ける文の中」） |
| `never` | `never` を返す、本体のない op | 節に書いた例外 | —（届けば、投げる） |
| `unknown` | —（入口の `Op.signature.exceptions` にあるのに、流れの中に、出どころが見つからない例外） | その例外 | —（起こせない。`why` に、理由） |

- **入口まで伝わらない例外は、出どころに数えない。** 出どころから入口までの、どれかの op の `Op.signature.exceptions` にない例外（デコレータの `catches` が受けるもの）。
- **`boundary` は、別の名前空間から呼ぶ op なら、流れの端でなくても、数える。** その op を、差し替えられるかは、プラグインが決める。
- **葉の op が、節に書いた例外を、その op に付いた、本体のないデコレータも投げるなら**、`decorator` の出どころだけを数える（`leaf` には、数えない）。
- **出どころの名前**（`EntrySource.label`）は、テストの名前の一部になる（`docs/plugin-go-http.md`「必要なケース」）:

| 種類 | 名前 |
|---|---|
| `leaf`、`effect`、`external`、`never` | その FQN（`server.requireFresh`、`mailer.send`） |
| `boundary`、`decorator` | `<op の FQN>@<デコレータの FQN>`（`server.login@rate.limited`） |
| `arm`（`match` のアーム） | `<配線の op の FQN>.<ケース>`（`server.sessionOf.LoggedOut`）。アームが、二つ以上のケースを受けるなら、`+` でつなぐ。デコレータの本体の中なら、`<op の FQN>@<デコレータの FQN>.<ケース>` |
| `arm`（`catch` のブロックの `throw 例外`） | `<配線の op の FQN>.catch`。デコレータの本体の中なら、`<op の FQN>@<デコレータの FQN>.catch`。受けた例外の `match` のアームの本体なら、後ろに、`.<ケース>` |
| `unknown` | 空 |

この節の細部は、決定 D668、D691 が決めた。

#### 入らせる方法

出どころに届くには、入口からの道の上の `match` の一つずつで、出どころへ向かうアームに、入らなければならない。入らせる方法（`EntrySource.steps`）は、正常のケースの用意に足す、差し替えに言うことの並びで、道の順。アームごとに、次の表の、上から、最初に当たる行:

| # | アーム | 入らせる方法（`EntryStep`） |
|---|---|---|
| 1 | `throw` でないアームで、その `match` の、`throw` でないアームが、それ一つだけ | 何もしない。正常のケースが、必ず、通る |
| 2 | 値がないこと（か、並びが空であること）で入るアーム: 受けるケースが、標準の分類の `None`・`Empty` か、ない側のケース（`Classify.absent`）の、一つだけ | 値の出どころが、「ない」を返す（`verb` は `none`。「値を、ないにする」） |
| 3 | 述語で決まる分類（`Classify.decidedBy` が `predicate`）のアーム | 分類の判定が、そのケースだと言う（`verb` は `is`、`kind` は `classify`、`case` は、アームが受けるケースのうち、ない側でない、最初のもの） |
| 4 | そのほか（値で決まり、入るのに、値が要るアームで、`throw` でないアームが、ほかにもある。2 で、値の出どころを、辿れない） | 入れない |

- **`throw` のアームそのもの**にも、2 と 3 を当てる（1 は、当たらない）。
- **状態の分類の `match`（`match by 分類`）**には、2 は、当たらない（対象の値が、ない）。
- **繰り返し（`for`）の中**にあるものは、入れない（正常のケースが、中を通るとは、限らない）。
- **道の上のすべてが、1〜3 なら、入れる**（`why` は、空）。一つでも、入れなければ、`steps` は、空で、`why` に、理由を置く。
- **`why` は、人に見せる、日本語の句。** 文言は、決めない。プラグインは、空かどうかだけを見る。
- **入れる理由**: `throw` のアームに入れば、その先がないので、差し替えが返す値は、中身のない値でよい。そこまで届く用意は、正常のケースのものを、使い回せる。

#### 値を、ないにする

「入らせる方法」の表の 2 は、`match` の対象の値の出どころを、次の表で辿り、行き着いた相手に、「ない」（か、空の並び）を返させる（`EntryStep.verb` は `none`）。

| 値 | 辿り方 |
|---|---|
| `read fn` の戻り値 | その read が、「ない」を返す（`kind` は `read`） |
| 流れの端の op の戻り値 | その op が、「ない」を返す（`op`） |
| 葉の戻り値 | その op が、「ない」を返す（`leaf`） |
| 単位の対象の、配線の op の戻り値 | その op の `return` の式（一つだけのとき）を、この表で辿る |
| 配線の op の引数 | 呼んだ側の、その引数の値を、この表で辿る |
| 状態そのもの | その状態が、「ない」（`state`） |
| 値と一緒に宣言した `val`（ほかに、その名前に入れる文がない） | その式を、この表で辿る |

- **「ない」を返せるのは、型が、省略可能か、並びのもの**だけ。
- **辿れない値**: 入口の op の引数（入力）。デコレータの引数。値の一部（フィールド）。出どころが、一つに決まらない値（`return` が二つ以上、入れる文が二つ以上）。`never` を返す op の戻り値。

#### 例外を受ける文の中

`try { … } catch (e) { … }`（「例外を受ける」）の、`try` のブロックの中の出どころは、`catch` が受けるので、そのままでは、出どころに数えない。出どころになるのは、`catch` のブロックが、投げるもの:

| `catch` のブロックの中 | 出どころ |
|---|---|
| `throw e`（文） | `try` のブロックの中の出どころを、そのまま（入らせる方法も、そのまま） |
| 受けた例外の `match` のアームの本体の `throw e` | 同じ。ただし、そのアームが受けるケースの例外のものだけ |
| `throw 例外`（文か、受けた例外の `match` のアームの本体） | 種類 `arm` の出どころ。入らせる方法は、`catch` に入らせる方法 |
| 呼び出し | 呼ぶ先の出どころ。入らせる方法の前に、`catch` に入らせる方法を足す |
| 受けた例外のものでない `match` の、アームの本体の `throw e` | `try` のブロックの中の出どころを、そのまま。ただし、入れない |

- **`catch` に入らせる方法**は、`try` のブロックの中の出どころのうち、入れる、最初のものに、投げさせること。受けた例外の `match` のアームなら、そのアームが受けるケースの例外のものから、選ぶ。一つもなければ、入れない。
- **入れ子**: 内側の `catch` が投げるものは、外側の `try` のブロックの中の出どころ。

この節の細部は、決定 D685、D689 が決めた。

#### 受ける道

受ける道は、`try` のブロックの中の出どころが投げた例外を、`catch` が受けて、投げずに終わる道（同 419）。入口の結果は、正常。`Entry.caught` に、受けられる出どころごとに、一つ置く（形は `EntrySource`: `exception` は、受けられる例外、`steps` は、その出どころに、投げさせる方法）。

| `catch` のブロック | 受ける道になる、`try` のブロックの中の出どころ |
|---|---|
| 受けた例外の `match` を持たず、「返らない」のでない（`Catch.never` が偽） | すべて |
| 受けた例外の `match` を持たず、「返らない」 | なし |
| 受けた例外の `match`（`catch (e by 分類)` も同じ）の、`throw` でないアーム | そのアームが受けるケースの例外のもの |

- **本体のあるデコレータの `try`** は、数える（本体は、配線と同じに辿る）。
- **本体のないデコレータの `catches` の節**は、数えない: そのデコレータは、流れの中では、差し替える相手で、受ける所が、流れにない。
- **同じ出どころ（例外と、名前が同じ）が、`sources` にもあれば、入れない**（`why` に、理由）: 差し替えは、どの呼び出しにも効くので、受ける道だけを、通せない。
- **受けた後の道への用意は、足さない。** `catch` のブロックが呼ぶものは、正常のケースの用意のまま、動く。

この節の細部は、決定 D690 が決めた。

#### 並び

- **`Entry.sources`** は、入口の `Op.signature.exceptions` の順。同じ例外の中は、見つけた順（流れを、文の順に、呼ぶ先を先に辿った順）。
- **`Entry.caught`** は、見つけた順。
- **例外と、名前が同じ出どころは、一つ。** 二つの道で届くなら、入れる、最初の道を残す。
