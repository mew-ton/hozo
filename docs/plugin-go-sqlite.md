# go-sqlite プラグイン

## この文書が決めること

`db` の語彙（`docs/vocab.md`「`db` の読み書きのデコレータ」「`db` の表と、しまい方」）の付いた状態を、SQLite の表と、その上の読み書きにするトランスパイラ `go-sqlite`。Go の基底 `go`（`docs/plugin-go.md`）に相乗りし、基底の**状態の単位**（`<状態>State`）と `SharedState` を満たす型を出す。プラグインは `plugins/go-sqlite/`。期待する出力の実物は、サンプル `tests/samples/shop-server/` の `gen/store/db.go`。

出すのは、仕様が `db` の語彙のデコレータで言ったものと、状態の形で決まる問い合わせだけ。デコレータが出すコードは、型に依らない（`docs/requirements.md`「出力を推論しない」）: 表も、列の型も、列の値の読み書きも、op の中身も、デコレータの引数だけから作り、型は、書いたものが食い違っていないかを確かめるのにだけ使う（食い違えば「診断」の error）。値で変わる振る舞い（値がないときは `NULL`、など）は、共通の補助が、実行時に決める（「補助」）。列が値を持たなくてよいかどうかは、デコレータ（`@db.nullable`）が言う（「表」）。`db` の語彙のデコレータを付けていない op は出さず、人が書き足す（足りなければコンパイルエラーになる）。

## マニフェスト

```toml
name     = "go-sqlite"
command  = ["go", "run", "github.com/mew-ton/hozo/plugins/go-sqlite"]
protocol = "0.5"

[[transpiler]]
name     = "go-sqlite"
language = "go"
requires = ["go"]
```

- 読む語彙は、状態の `@db.table`、フィールドの、しまい方（`@db.text` / `@db.int` / `@db.float` / `@db.bool` / `@db.time` / `@db.json`）と `@db.nullable` と `@db.key` / `@db.unique` / `@db.ref`、op の `@db.reads` / `@db.effects`、読み（`read` の宣言。「op の中身」）の `@db.find` / `@db.list`、効果の `@db.insert` / `@db.update` / `@db.delete`。語彙は提供しない。
- オプションはない。`[emit.options.go-sqlite]` にキーがあれば GOSQL-6。
- 制約（`@valid.*`）は確かめない（`go-valid` に依存しない）。足す前に確かめるかどうかは、境界を持つ相乗りの仕事（`docs/plugin-go-valid.md`「この文書が決めること」）。

## 出力

N の `@db.table` の付いた基底の状態（**表の状態**）が一つもなければ、ファイルを出さず warning を一つ返す。あれば、N の**入口のパッケージ**（`docs/plugin-go.md`「相乗りのファイル」）に `db.go` を一つ。先頭は `// Code generated by hozoc go-sqlite <版>; DO NOT EDIT.`。並びはどれも宣言順。import するのは `database/sql`（と `database/sql/driver`）、ほかの標準ライブラリ、型のパッケージだけで、ドライバは import しない。

公開の名前は次の種類。非公開の名前は `db` で始める。

| 名前 | 中身 |
|---|---|
| `const Schema` | 表ごとの `CREATE TABLE IF NOT EXISTS` を並べた SQL |
| `func CreateTables(ctx context.Context, db *sql.DB) error` | `Schema` を、受け取った `ctx` で実行する（`db.ExecContext(ctx, Schema)`）。するのは表を作ることだけ。すでにある表には触れない |
| `type <状態>Table struct{ db *sql.DB }` | 表の状態ごとに一つ。その状態の単位の実装。値の型で、同じ `db` から作った値は同じ表を読み書きする |
| `func New<状態>Table(db *sql.DB) <状態>Table` | 上の型を作る |
| `type SharedTable struct{ db *sql.DB }`、`func NewSharedTable(db *sql.DB) SharedTable` | 基底の `SharedState` の実装（「状態をまたぐ単位の型」）。出すときだけ |
| `type <C>Table struct{ db *sql.DB }`、`func New<C>Table(db *sql.DB) <C>Table` | 述語で決まる状態の分類 C の単位の、命令の実装（同）。出すときだけ |

`<状態>` は、状態の名前を先頭大文字にしたもの（`UsersTable`、`NewUsersTable`）。`<C>` は、状態の分類の名前を先頭大文字にしたもの。

ファイルの中の並び: `Schema`、`CreateTables`、単位ごとの型（基底の `states.go` と同じ並び: 表の状態と、型を出す状態の分類を宣言順に、最後に `SharedTable`。それぞれ、型、`New…`、あれば `var _`、メソッド）、表の model ごとの `dbArgs<Model>` と `dbScan<Model>`（表の状態の順。同じ model は一度）、補助（使うものだけ。「補助」の順）。

### 表

- 表の状態ごとに表一つ。名前は状態の名前。表の中身は、状態に付けた `@db.table(M)` の M（**表の model**）が言う: M のフィールドごとに列一つで、名前はフィールドの名前、順はフィールドの順。名前はいつも `"…"` で引用する。
- 状態の要素の型は、M と等しくなければならない（`@db.table(type.Order) state orders: list<type.Order>;`）。違えば GOSQL-1。表を状態の型から読まずに引数で名指しさせるのは、出力を決めるのがデコレータの引数だけだから（`docs/requirements.md`「出力を推論しない」）。
- 表の状態の形は `list` だけ。`nullable` と `single` の状態に `@db.table` が付いていれば GOSQL-2（一行だけの表の形を、まだ決めていない）。
- 列の型は、フィールドに付けた、しまい方のデコレータが決める（「しまい方」）。
- **`NOT NULL` は、`@db.nullable` を付けていない、すべての列に付ける。** 値がなくてよい列は、フィールドに `@db.nullable` を付けて言う（`@db.nullable @db.text nickname: string?`）。フィールドの型からは決めない。型は、食い違いを確かめるのにだけ使う: `@db.nullable` の付いたフィールドの型が省略可能でなければ GOSQL-18、省略可能なフィールド（`T?`）に `@db.nullable` がなければ GOSQL-19。値がないことの読み書きは「補助」。
- 制約: `@db.key` は `PRIMARY KEY`、`@db.unique` は `UNIQUE`。`@db.key` の付いたフィールドが二つ以上なら、列には付けず、表の末尾に `PRIMARY KEY ("a", "b")`。`@db.ref(M2)` は、`@db.table(M2)` の付いた表の状態が N に**ちょうど一つ**あり、M2 が `@db.key` をちょうど一つ持つとき、その表のその列への `REFERENCES "<表>" ("<列>")`。そうでなければ GOSQL-20（指す先の表か列が、一つに決まらない）。黙って制約を省くことはしない: 仕様に書いた参照が、気づかないうちに表から消える。
- 列の定義は `"<名前>" <型>[ NOT NULL][ PRIMARY KEY][ UNIQUE][ REFERENCES …]`。表は、列を二つの空白で字下げして一行ずつ、`,` で区切る。

```go
const Schema = `CREATE TABLE IF NOT EXISTS "sessions" (
  "token" TEXT NOT NULL PRIMARY KEY,
  "userId" TEXT NOT NULL REFERENCES "users" ("id"),
  "expiresAt" TEXT NOT NULL
);
`
```

- 外部キーが効くかどうか（SQLite の既定では効かない）、表の作り直し（移行）は、このトランスパイラの外。

### しまい方

表の model のフィールドは、**しまい方**のデコレータ（`docs/vocab.md`「`db` の表と、しまい方」）を、**ちょうど一つ**持つ。一つもないか、二つ以上あれば GOSQL-16。`CREATE TABLE` の列の型と、列の値の読み書きは、このデコレータだけで決まる。フィールドの型は、しまい方に合うかどうかを確かめるのにだけ使い、合わなければ GOSQL-17（`string` のフィールドに `@db.int`）。

| しまい方 | SQLite の列の型 | 列の値 | 合うフィールドの型（scalar は元の核の型で見る。どれも、その省略可能を含む） |
|---|---|---|---|
| `@db.text` | `TEXT` | 文字列そのまま | `string` |
| `@db.int` | `INTEGER` | 整数 | `int`、`Duration`（ナノ秒） |
| `@db.float` | `REAL` | 小数 | `float` |
| `@db.bool` | `INTEGER` | 0 か 1 | `boolean` |
| `@db.time` | `TEXT` | RFC 3339、UTC、小数部はいつも 9 桁の文字列（文字列の順が時刻の順になる） | `Time` |
| `@db.json` | `TEXT` | `encoding/json` の JSON の文字列 | `array`、`record`、model |

- しまい方の名前は、語彙が決めた、保存先の製品に依らない種類。SQLite の列の型に写すのは、このトランスパイラ（ほかの保存先のトランスパイラは、同じ種類を、自分の列の型に写す）。
- **一つのしまい方の中で、型によって変え方が分かれることはない。** `Duration` を `@db.int` に入れたのは、Go の値が `int` と同じ 64 ビットの整数で、同じ補助が同じに読み書きできるから。同じしまい方の二つの型が、別の変え方を要るようになったら、型で分けずに、しまい方を足す。
- union（`arms`）と、union を中に持つ `array` / `record` / model は、どのしまい方でも列にできない（GOSQL-3。JSON での union の形を、まだ決めていない）。
- `@db.json` の中の値の形（model のフィールド、配列の要素）は、`encoding/json` が、Go の型から決める。その中の model のフィールドに、しまい方のデコレータは要らない（付いていても読まない）。
- 表の model でない model のフィールドに付いた、しまい方のデコレータと、`@db.nullable`、`@db.key`、`@db.unique`、`@db.ref` は、読まない（何も出さず、確かめない）。

### 状態ごとの型

`<状態>Table` のメソッドは、基底のその状態の単位（`docs/plugin-go.md`「状態の単位」）のメソッドのうち、形で決まる問い合わせ（いつも）と、**`db` の語彙の op のデコレータ（`@db.reads`、`@db.effects`）を付けた op**（「op の中身」）。どの op がどの単位のメソッドになるか（op の置き場）は基底が決め、このトランスパイラは変えない。名前と形（`ctx`、引数、戻り値）は、基底のメソッドのまま（`plugin/golang` で求める）。受け取った `ctx` で `QueryContext` / `QueryRowContext` / `ExecContext` / `BeginTx` を呼ぶ。op に `export` が付いているかは見ない。

- 基底のメソッドをすべて持つ型には、`var _ <状態>State = <状態>Table{}` を出す。
- **デコレータを付けていない op があるとき**、その型は、その op のメソッドを持たない。型は `<状態>State` を満たさず、基底の `New` に渡す行がコンパイルできない。人は、この型を自分の型に埋め込み、足りないメソッドを書き足して、その型を `New` に渡す。`var _` は出さない。**warning も出さない**: デコレータを付けないのは、その op の中身を人が書くと、仕様を書いた人が選んだこと。
- すべて実装した型でも、埋め込んで一つのメソッドを書けば、そのメソッドだけを人のものにできる（一意の違反を見分けて、仕様の例外に写す、など）。

**形で決まる問い合わせの中身**（`list`）。状態の宣言の形から決まるもので、デコレータは要らない（形は言語の約束。`docs/check.md`「状態の形」）:

| メソッド | 中身 |
|---|---|
| `IsEmpty` | `SELECT COUNT(*) FROM "<表>"` の結果が 0 |
| `Get` | `SELECT <すべての列> FROM "<表>" ORDER BY rowid`（足した順） |

### 状態をまたぐ単位の型

基底が、表の状態の単位でないところに置いた op（`docs/plugin-go.md`「op の置き場」）のための型。どちらも `struct{ db *sql.DB }` の値の型で、メソッドは、その単位の op のうち `@db.effects` を付けたものだけ。

| 基底の口 | 型と、作る関数 | 出すとき | `var _` |
|---|---|---|---|
| `SharedState`（効果の宛先の単位が二つ以上に分かれた op） | `SharedTable`、`NewSharedTable(db *sql.DB) SharedTable` | `SharedState` の op に、`@db.effects` を付けたものが一つでもある | `SharedState` の op のすべてに付いていれば `var _ SharedState = SharedTable{}` |
| 述語で決まる状態の分類 C の単位 `<C>State`（C の遷移を宛先にする効果の op） | `<C>Table`、`New<C>Table(db *sql.DB) <C>Table` | `<C>State` の命令に、`@db.effects` を付けたものが一つでもある | 出さない（述語は人が書くので、`<C>State` を満たさない） |

- メソッドの足りない型の扱いは、「状態ごとの型」と同じ: 人が自分の型に埋め込んで、足りないメソッド（`<C>Table` なら、ケースの述語も）を書き足す。warning は出さない。
- 読みを一つ並べた `@db.reads` の op は、いつも表の状態の単位に置かれる（読む状態は、その読みの表一つ。GOSQL-14、GOSQL-21）ので、ここには来ない。読みを二つ以上並べた op は「未決: 複数の読みと、戻り値の型」。
- 型で決まる状態の分類の遷移と、基底の状態の遷移を宛先にする効果の op は、基底がその状態の単位に置くので、`<状態>Table` のメソッドになる。

### op の中身

op の中身は、op に付けた `db` の語彙のデコレータ（`@db.reads`、`@db.effects`）と、それが並べた読みと効果の宣言に付けたデコレータの、引数だけで決まる。読む側も書く側も二段で、理由の持ち主は `docs/requirements.md`「出力を推論しない」（読み・効果のデコレータは、それを行う op の実装に働く。デコレータのない op には、中身を出さない）。表は状態の名前で、列は文字列（表の model のフィールドの名前）で渡す。以下、表の状態を T、その表の model を M とする。

**読み**は、名前を付けた `read` の宣言（`read userByEmail on users;`。言語の持ち主は `docs/grammar.md`「read」、`docs/check.md`「reads」）。

**読む op** は、行う読みを `@db.reads(r)` で名指しする（デコレータが、r を op の `reads` として運ぶ。op は `reads` を書かない）。読みの宣言が、表から何を引くかを `@db.find` / `@db.list` で言う。**op は、読みが受け取るものを引数に取り、読みが引くものを返す。** この節が決めるのは、読みを一つ並べ、op の戻り値の型が、その読みの引くものと等しいとき。そうでないときは「未決: 複数の読みと、戻り値の型」。

```ts
@db.find(users, "email")
read userByEmail on users;

@db.reads(userByEmail)
export op findUser(email: type.Email): type.User?;
```

| 読みのデコレータ | 読みの宣言（合わなければ GOSQL-21） | 読みが受け取るもの（op の引数。合わなければ GOSQL-9） | 読みが引くもの | SQL |
|---|---|---|---|---|
| `@db.find(T, "c")` | `on T`。c は、M のただ一つの `@db.key` か、`@db.unique`（GOSQL-13） | 列 c に合う型の値一つ（「列と引数の型」） | `M?` | `SELECT <すべての列> FROM "<表>" WHERE "c" IS ?1`。行がなければ `nil` |
| `@db.list(T, "c")` | `on T` | 列 c に合う型の値一つ | `M[]` | `SELECT <すべての列> FROM "<表>" WHERE "c" IS ?1 ORDER BY rowid`（足した順） |
| `@db.list(T)` | `on T` | なし（op は引数を持たない） | `M[]` | `SELECT <すべての列> FROM "<表>" ORDER BY rowid` |

- 表を、読みの宣言の `on` から読まずに引数で名指しさせるのは、書く側と同じく、出力を決めるのがデコレータの引数だけだから。`on` の状態は、食い違いを確かめるのにだけ使う（GOSQL-21）。
- 読みは、`@db.find` / `@db.list` のうち、ちょうど一つを持つ（`@db.reads` に並べた読みがどちらも持たないか、一つの読みが二つ持てば GOSQL-22）。op に並べられていない読みのデコレータも、同じに確かめる（何も出さない）。
- 一つの読みを、二つ以上の op が `@db.reads` で名指ししてよい（同じ文のメソッドが、op ごとに出る）。
- **`@db.reads` のない op には、読みにデコレータが付いていても、中身を出さない**（`@db.find(users, "email") read userByEmail on users;` と `op findUser(email: type.Email): type.User? reads userByEmail;`。状態を直に書いた `reads users` も同じ）。読みのデコレータは、`@db.reads` でそれを行う op の中身の材料で、op のデコレータの代わりにはならない。その op は、人が書き足す（「状態ごとの型」）。

**書く op** は、行う効果を `@db.effects(e₁, …, eₙ)` で並べる（デコレータが、それらを op の `effects` として運ぶ。op は `effects` を書かない）。効果の宣言が、表に何をするかを `@db.insert` / `@db.update` / `@db.delete` で言う。**n 番目の効果が、op の n 番目の引数を受け取る。** 引数の数は効果の数と同じで、戻り値はない。

| 効果のデコレータ | 効果の宛先（合わなければ GOSQL-11） | 受け取る引数 | SQL |
|---|---|---|---|
| `@db.insert(T)` | 組み込みの効果なら `T.post` | M の行（型は M そのもの） | `INSERT INTO "<表>" (<すべての列>) VALUES (?1, …)` |
| `@db.update(T)` | 組み込みの効果なら `T.put` | M の行（同じ）。M は `@db.key` を一つ以上と、キーでない列を一つ以上持つ（GOSQL-15） | `UPDATE "<表>" SET <キーでない列> = ?… WHERE <キーの列> IS ?…`。書き換える行は、M の `@db.key` のフィールドが同じ行。行がなければ何もしない |
| `@db.delete(T, "c")` | 組み込みの効果なら `T.delete` | 列 c に合う型の値（「列と引数の型」） | `DELETE FROM "<表>" WHERE "c" IS ?1`。行がなければ何もしない |

- 表を、効果の宛先から読まずに引数で名指しさせるのは、出力を決めるのがデコレータの引数だけだから。効果の宛先が、状態の分類の遷移や基底の状態の遷移のとき（一つの効果が複数の状態に触れ、表はその一部、という場合を含む）は、操作の名前との照合はなく、T がその効果の書き込む状態（`Effect.writes`）の一つであればよい。
- 効果は、`@db.insert` / `@db.update` / `@db.delete` のうち、ちょうど一つを持つ（`@db.effects` に並べた効果が一つも持たないか、一つの効果が二つ以上持てば GOSQL-12）。op に並べられていない効果のデコレータも、同じに確かめる（何も出さない）。
- **効果が一つ**なら、文一つを `dbExec` で実行する。**二つ以上なら、一つのトランザクション**（「トランザクション」）。同じ効果を二度並べてもよい（文が二つになる）。
- 条件に書いた引数の値は、読む側も書く側も、名指しした列のしまい方の補助で包んで渡す（列 `email` が `@db.text` なら `dbText(email)`。「補助」）。列が `@db.nullable` を持てば、フィールドと同じに `dbNullable` を足す（`dbText(email, dbNullable)`）。引数の型では、形を変えない。
- op は、デコレータが言う以外のものを読み書きしない: `db` の op のデコレータ（`@db.reads`、`@db.effects`）はちょうど一つで、op が直に読むものと直に持つ効果（`docs/check.md`「デコレータが運ぶ reads と effects」）は、そのデコレータが運ぶものだけ。そうでなければ GOSQL-14（`@db.reads` の op が自分で `effects` を書いている、運ばれる読みのほかに `reads users` を書いている、など）。`@db.reads()` に読みが、`@db.effects()` に効果が、一つもないときも同じ。
- デコレータで言えないもの（順序、件数と位置、等しいかどうかでない比較、複数の列の条件、一意の違反を例外に写すこと）は、その op にデコレータを付けず、人が書く。

### 未決: 複数の読みと、戻り値の型

`@db.reads` は、読みを二つ以上並べられ（`@db.reads(userById, ordersOfUser)`。いくつかの行を合わせた型を返す op のため）、op の戻り値の型は、読みの引くもの（`M?`、`M[]`）と等しくなくてよい（`docs/decisions.md`「決めたこと」129）。この二つの形で何を出すかは、次の二点が決まっていないので、まだ決めていない。

| 決まっていないこと | 決められない理由 |
|---|---|
| 戻り値の型が、読みの引くものと違うとき、op の返す値を、誰が、読みの結果から作るか | 型を見て組み立て方を決めることは、できない（`docs/requirements.md`「出力を推論しない」） |
| 読みを二つ以上並べたとき、op のどの引数が、どの読みに渡るか | 書く側の「n 番目の効果が、n 番目の引数」は、そのままは当てはまらない: 引数を受け取らない読み（列のない `@db.list`）と、同じ引数を受け取る二つの読みがありうる |

- 決まるまで、この二つの形を error にする診断は、持たない（GOSQL-9 と GOSQL-10 の `@db.reads` の分は、読みが一つのときの引数だけ）。何を出すかも、決めていない。
- サンプルと、このトランスパイラの単体テストは、決まるまで、この二つの形を入力にしない。

### 列と引数の型

値を、名指しした列と比べるところ（読みの `@db.find`、`@db.list` と、効果の `@db.delete` の条件）のすべてに掛かる、ただ一つの規則（`docs/decisions.md`「決めたこと」96）。「引数」は、その読みか効果が受け取る、op の引数:

**引数の型は、列の型（M のそのフィールドの型）と等しくなければならない。列の型が union なら、引数は、その一部でよい。** `T?` は「T」と「値がない」の union と数える。向きは一方だけで、列より広い引数は GOSQL-9。

この規則は、書いたものの整合の検査で、出力を変えない。**条件の SQL は、型によらず、いつも `"c" IS ?n`**（`@db.update` のキーの条件も同じ）。SQLite の `IS` は、両辺に値があれば `=` と同じで、両辺が `NULL` のとき真になる。引数に値があるかどうかは、実行時に補助が見る（値のないポインタは `NULL`）。その結果:

| 列の型 | 引数の型 | 合う行 |
|---|---|---|
| `T` | `T` | 列の値が、引数と同じ行 |
| `T?` | `T` | 同じ。値のない行（`NULL`）は、どの値にも合わない |
| `T?` | `T?` | 引数に値があれば、同じ。値がなければ、値のない行 |
| `T` | `T?` | —（GOSQL-9。列より広い） |

- 「等しい」は `docs/types.md`「等しい」。scalar は名前で比べる（`type.Token` の列に `string` の引数は渡せない）。
- 今、列にできる union は `T?` だけ（アームを持つ union は列にできない。GOSQL-3）。
- 引数に値がないとき、問い合わせをやめて「ない」を返すことはしない（その規則は、なくした）。値がないときにどうするかは、呼ぶ側の配線が、呼ぶ前に決める（`match … by nullable` か、場合に名前を付けた分類。`docs/requirements.md`「書き方の指針」）。

### トランザクション

`@db.effects` に効果を二つ以上並べた op は、**一つのトランザクションで、書いた順に**文を実行する。どれかが失敗すれば、どれも残らない。

```go
// PlaceOrder は op store.placeOrder（@db.effects）: 一つのトランザクションで、書いた順に行う。効果 store.createOrder（@db.insert）で、表 "orders" に、引数 order の行を足す。効果 store.notifyUser（@db.insert）で、表 "notifications" に、引数 notification の行を足す。どれかが失敗すれば、どれも残らない。
func (t SharedTable) PlaceOrder(ctx context.Context, order pkgtype.Order, notification pkgtype.Notification) error {
	args1, err := dbArgsOrder(order)
	if err != nil {
		return err
	}
	args2, err := dbArgsNotification(notification)
	if err != nil {
		return err
	}
	tx, err := t.db.BeginTx(ctx, nil)
	if err != nil {
		return err
	}
	defer tx.Rollback()
	if _, err := tx.ExecContext(ctx,
		`INSERT INTO "orders" ("id", "userId", "lines", "placedAt") VALUES (?1, ?2, ?3, ?4)`, args1...); err != nil {
		return err
	}
	if _, err := tx.ExecContext(ctx,
		`INSERT INTO "notifications" ("userId", "message") VALUES (?1, ?2)`, args2...); err != nil {
		return err
	}
	return tx.Commit()
}
```

メソッドの本体は、この順:

1. 行を受け取る効果（`@db.insert`、`@db.update`）ごとに、効果の順で、`args<i>, err := dbArgs<Model>(<引数>)` と、その `err` の確認。`<i>` は、効果が何番目か（1 始まり）。値を列の形にできなければ、トランザクションを始めない。
2. `tx, err := t.db.BeginTx(ctx, nil)` と、その `err` の確認。
3. `defer tx.Rollback()`。途中で返れば取り消す。確定した後の `Rollback` は何もしない（その戻り値は見ない）。
4. 効果ごとに、効果の順で、`if _, err := tx.ExecContext(ctx, <文>, <値>); err != nil { return err }`。`<値>` は、行を受け取る効果なら `args<i>...`、`@db.delete` なら、列のしまい方の補助で包んだ引数（`dbText(token)`。「op の中身」）。
5. `return tx.Commit()`。

- どの単位の型のメソッドでも同じ形（宛先の単位が一つなら `<状態>Table`、分かれれば `SharedTable`、述語で決まる状態の分類なら `<C>Table`）。型が持つのは `*sql.DB` だけで、トランザクションは、メソッドの中で始めて終える。
- 複数の op にまたがるトランザクション（配線の二つの呼び出しを一つにする）は、ない: 一緒に行うものは、一つの op の `@db.effects` に並べる。

### 補助

列ごと、op ごとに出すコードは、型によらず同じ形で、違いは、共通の補助の中にある。使うものだけを、この順で、ファイルの末尾に出す。

| 名前 | 中身 |
|---|---|
| `dbArgs<Model>(row <Model>) ([]any, error)` | model を、列の順の値にする。本体は `return dbArgs(<列>, …)` の一行で、`<列>` は、フィールドごとに `<しまい方の補助>(row.<F>)`。`@db.nullable` の付いたフィールドは `<しまい方の補助>(row.<F>, dbNullable)`。使うものだけ: 出すメソッドのどれかが、その model の行を受け取る（`@db.insert` か `@db.update` の効果を持つ）ときに出す（`dbScan<Model>` は、`Get` が使うので、いつも出る） |
| `dbScan<Model>(r dbRow) (<Model>, error)` | 列の順の値を model に読む。本体は `r.Scan(<列>, …)` で、`<列>` は、フィールドごとに `<しまい方の補助>(&row.<F>)`。`@db.nullable` の付いたフィールドは `<しまい方の補助>(&row.<F>, dbNullable)` |
| `dbRow` | `*sql.Row` と `*sql.Rows` が共に持つ `Scan(dest ...any) error` |
| `dbOption`、`dbNullable` | 列の読み書きに、フィールドのデコレータが足すこと（`type dbOption int`）と、`@db.nullable` の印（`const dbNullable dbOption = 1`）。`dbCol` と一緒に、いつも出す |
| `dbCol` | 列一つ: しまい方と、Go の値（書くときはフィールドの値か、列と比べる引数。読むときはフィールドへのポインタ）と、渡された `dbOption`。`database/sql` が、書くときに `Value`（`driver.Valuer`）を、読むときに `Scan`（`sql.Scanner`）を呼ぶ |
| `dbArgs(cols ...dbCol) ([]any, error)` | 列の並びを、文に渡す値の並びにする |
| `dbString` | 列の値を、文字列として読む（`@db.text`、`@db.time`、`@db.json` の補助が使う） |
| `dbText`、`dbInt`、`dbFloat`、`dbBool`、`dbTimeLayout` と `dbTime`、`dbJSON` | しまい方ごとの補助 `func(v any, opts ...dbOption) dbCol`。「しまい方」の表の、列の値への変え方と、その逆。使うしまい方の分だけ、この順で |
| `dbExec` | 行を返さない文を実行する |
| `dbIsEmpty` | 行の数を返す問い合わせの結果が 0 かどうか |
| `dbGet[R]` | 問い合わせの一行を読む。行がなければ（`sql.ErrNoRows`）`nil` |
| `dbList[R]` | 問い合わせのすべての行を読む |

```go
// dbArgsOrder は type.Order を、表 "orders" の列の順の値にする。
func dbArgsOrder(row pkgtype.Order) ([]any, error) {
	return dbArgs(dbText(row.Id), dbText(row.UserId), dbJSON(row.Lines), dbTime(row.PlacedAt))
}

// dbScanOrder は、表 "orders" の列の順の値を type.Order に読む。
func dbScanOrder(r dbRow) (pkgtype.Order, error) {
	var row pkgtype.Order
	if err := r.Scan(dbText(&row.Id), dbText(&row.UserId), dbJSON(&row.Lines), dbTime(&row.PlacedAt)); err != nil {
		return pkgtype.Order{}, err
	}
	return row, nil
}
```

- **フィールドの型は、この二つの関数の形を変えない。** scalar か核の型か、省略可能かどうかで、書き分けない。行に足すのは、デコレータが言ったことだけ: `@db.nullable` の付いたフィールドは、しまい方の補助の最後の引数に `dbNullable` を足す（`dbText(row.Nickname, dbNullable)`、`dbText(&row.Nickname, dbNullable)`）。
- **値がないこと（`NULL`）は、`dbCol` が、実行時に、渡された Go の値と `dbNullable` を見て決める**（`reflect`）。
  - 書くとき: 値のないポインタは `NULL`（`@db.nullable` の列の、値のない省略可能なフィールド。列と比べる、値のない引数）。`dbNullable` の列では、値のないスライスとマップ（`T[]?`、`Record<K, V>?` の `nil`）も `NULL` で、`@db.json` でも、JSON の `null` という文字列にはしない。`dbNullable` のない列の、値のないスライスとマップは、しまい方のまま書く（`@db.json` なら、`encoding/json` が出す文字列 `null`）。
  - 読むとき: `NULL` を読めるのは、`dbNullable` の列だけで、読む先は、値がない（`nil`）。ほかの列に `NULL` があれば、エラー（その列は `NOT NULL` なので、`Schema` で作った表では起きない）。値があれば、読む先がポインタなら、置く先を作って読む。
- しまい方の補助に、合わない型の値が渡ることは、GOSQL-17 が先に断るので、ない（そのときの振る舞いは、決めない）。`dbNullable` のない列に、省略可能なフィールドの値が渡ることも、GOSQL-19 が先に断るので、ない。型の食い違いをコンパイルエラーにする形（型引数）にしないのは、省略可能な値と、そうでない値を、一つの関数で、型を書かずに受け取れないため（`docs/plugin-go-http.md`「補助」の末尾と同じ理由）。
- 補助の中身は、サンプルの `gen/store/db.go` の通り（`dbInt`、`dbFloat`、`dbBool` は、サンプルが使わないので、`go-sqlite` の単体テストのゴールデンが固定する。`docs/testing.md`「単体テスト」）。

メソッドの引数の名前は、基底と同じ規則で仕様の引数名から作る。このファイルが使う名前（レシーバの `t`、`ctx`、`args`、`args<数>`、`tx`、`err`、import するパッケージの名前、このファイルの非公開の名前）と当たれば、末尾に `_` を付ける。`dbArgs<Model>` と `dbScan<Model>` の中の局所の名前（`row`、`r`、`err`）は、import するパッケージの名前と当たれば、当たらなくなるまで末尾に `_` を付ける（その名前のパッケージの型を、本体が書けなくなるため。`docs/plugin-go.md`「パッケージと import パス」の「import の名前」の、相乗りの側の決まり）。`<Model>` は model の Go の型の名前で、別の名前空間の同じ名前の model と当たれば、後の方に `2`、`3`、… を付ける。

### メソッドの形とコメント

```go
// FindUser は op store.findUser（@db.reads）: 読み store.userByEmail（@db.find）で、表 "users" から、"email"（@db.unique）が引数 email と同じ行を引く。なければ nil。
func (t UsersTable) FindUser(ctx context.Context, email pkgtype.Email) (*pkgtype.User, error) {
	return dbGet(ctx, t.db, dbScanUser,
		`SELECT "id", "email", "name", "hash" FROM "users" WHERE "email" IS ?1`, dbText(email))
}

// AddUser は op store.addUser（@db.effects）: 効果 store.createUser（@db.insert）で、表 "users" に、引数 user の行を足す。
func (t UsersTable) AddUser(ctx context.Context, user pkgtype.User) error {
	args, err := dbArgsUser(user)
	if err != nil {
		return err
	}
	return dbExec(ctx, t.db,
		`INSERT INTO "users" ("id", "email", "name", "hash") VALUES (?1, ?2, ?3, ?4)`, args...)
}

// RemoveSession は op store.removeSession（@db.effects）: 効果 store.deleteSession（@db.delete）で、表 "sessions" から、"token" が引数 token と同じ行を消す。行がなければ何もしない。
func (t SessionsTable) RemoveSession(ctx context.Context, token pkgtype.Token) error {
	return dbExec(ctx, t.db, `DELETE FROM "sessions" WHERE "token" IS ?1`, dbText(token))
}
```

- `SELECT`（`COUNT` を除く）、`INSERT`、`UPDATE` の文は、呼び出しの二行目に書く。`SELECT COUNT(*)` と `DELETE` の文は、呼び出しと同じ行に書く。トランザクションの中の `tx.ExecContext` も同じ。
- 効果が一つの op の、行の値の変数は `args`。二つ以上なら `args<i>`（「トランザクション」）。
- コメントは、宣言ごとに一行（単位の型は二行）。途中で折り返さない。

| 宣言 | コメント |
|---|---|
| `Schema` | `// Schema は @db.table の状態の表を作る SQL（SQLite）。状態ごとに表一つ、その model のフィールドごとに列一つ。` |
| `CreateTables` | `// CreateTables は db に、@db.table の状態の表を作る（Schema を実行する）。すでにある表には触れない。` |
| `<状態>Table` | `// <状態>Table は状態 <FQN> の単位（<状態>State）の、表 "<表>" の上の実装。` と `// メソッドは、形で決まる問い合わせ（IsEmpty、Get）と、この単位の葉の op のうち、db の語彙のデコレータを付けたもの（<句>）。`。句は、すべてに付いていれば（op が一つもないときを含む）`この単位では、すべて`、そうでなければ `付けていない op: <op 名を「、」で>` |
| `New<状態>Table` | `// New<状態>Table は db の表 "<表>" の上の <状態>Table を返す。表は CreateTables が作る。` |
| `SharedTable` | `// SharedTable は、複数の状態にまたがる葉の op（SharedState）の、db の上の実装。` と `// メソッドは、SharedState の op のうち、db の語彙のデコレータを付けたもの（<句>）。`。句は `<状態>Table` と同じ |
| `NewSharedTable` | `// NewSharedTable は db の上の SharedTable を返す。表は CreateTables が作る。` |
| `<C>Table` | `// <C>Table は状態の分類 <FQN> の単位（<C>State）の命令の、db の上の実装。` と `// メソッドは、<C>State の命令のうち、db の語彙のデコレータを付けたもの（<句>）。ケースの述語は、埋め込んで書き足す。`。句は同じ |
| `New<C>Table` | `// New<C>Table は db の上の <C>Table を返す。表は CreateTables が作る。` |
| `IsEmpty` | `// IsEmpty は形で決まる問い合わせ: 表 "<表>" に行が一つもなければ true。` |
| `Get` | `// Get は形で決まる問い合わせ: 表 "<表>" の行を、足した順にすべて引く。` |
| `@db.reads` の op（読みが一つ） | `// <メソッド名> は op <FQN>（@db.reads）: <読みの句>` |
| `@db.effects` の op（効果が一つ） | `// <メソッド名> は op <FQN>（@db.effects）: <効果の句>` |
| `@db.effects` の op（効果が二つ以上） | `// <メソッド名> は op <FQN>（@db.effects）: 一つのトランザクションで、書いた順に行う。<効果の句を、効果の順に、区切りなしで>どれかが失敗すれば、どれも残らない。` |
| `dbArgs<Model>` / `dbScan<Model>` | `// dbArgs<Model> は <model の FQN> を、表 "<表>" の列の順の値にする。` / `// dbScan<Model> は、表 "<表>" の列の順の値を <model の FQN> に読む。`（表は、その model を `@db.table` で名指しした最初の表の状態） |

読みの句は、読みのデコレータごとに一文（列のない `@db.list` は、最後の行）:

| 読みのデコレータ | 読みの句 |
|---|---|
| `@db.find` | `読み <読みの FQN>（@db.find）で、表 "<表>" から、"<列>"（<@db.key か @db.unique>）が引数 <引数名> と同じ行を引く。なければ nil。` |
| `@db.list`（列がある） | `読み <読みの FQN>（@db.list）で、表 "<表>" から、"<列>" が引数 <引数名> と同じ行を、足した順にすべて引く。` |
| `@db.list`（列がない） | `読み <読みの FQN>（@db.list）で、表 "<表>" の行を、足した順にすべて引く。` |

効果の句は、効果のデコレータごとに一文:

| 効果のデコレータ | 効果の句 |
|---|---|
| `@db.insert` | `効果 <効果の FQN>（@db.insert）で、表 "<表>" に、引数 <引数名> の行を足す。` |
| `@db.update` | `効果 <効果の FQN>（@db.update）で、表 "<表>" の、キーが引数 <引数名> と同じ行を書き換える。行がなければ何もしない。` |
| `@db.delete` | `効果 <効果の FQN>（@db.delete）で、表 "<表>" から、"<列>" が引数 <引数名> と同じ行を消す。行がなければ何もしない。` |

補助のコメントは、サンプルの通り。

## 診断

`emit` の応答の `errors` で返す。

| ID | 重さ | 意味 |
|---|---|---|
| GOSQL-1 | error | `@db.table(M)` の付いた状態の要素の型が、M と等しくない（要素が model でないときを含む）。位置は状態 |
| GOSQL-2 | error | `@db.table` の付いた状態の形が `list` でない（`nullable`、`single`）。位置は状態 |
| GOSQL-3 | error | 表の model に、どのしまい方でも列にできない型のフィールドがある（union と、union を中に持つ型）。位置は model |
| GOSQL-4 | error | このトランスパイラの公開の名前（`Schema`、`CreateTables`、`<状態>Table`、`New<状態>Table`、出すなら `SharedTable`、`NewSharedTable`、`<C>Table`、`New<C>Table`）が、N の定義のパッケージの名前（型など。`docs/plugin-go.md`「名前」）と当たる。位置は当たった宣言。このトランスパイラの公開の名前どうし（状態 `users` の `NewUsersTable` と、状態 `newUsers` の `NewUsersTable`。状態 `shared` の `SharedTable` と、`SharedState` の `SharedTable`）も同じで、位置は後ろの宣言 |
| GOSQL-6 | error | `[emit.options.go-sqlite]` に、知らないキーがある。位置なし |
| GOSQL-7 | error | `db` の語彙のデコレータ（`@db.find`、`@db.list`、`@db.insert`、`@db.update`、`@db.delete`）の引数の状態が、N の表の状態でない（`@db.table` が付いていない、別の名前空間の状態）。位置はデコレータを付けた宣言（読みか効果） |
| GOSQL-8 | error | デコレータの引数の列の名前が、その表の model のフィールドにない。位置はデコレータを付けた宣言（読みか効果） |

- GOSQL-5 は欠番。「状態の単位のメソッドの名前が、このファイルの型のフィールド `db` と当たる（op `db`）」という規則だったが、起きない: メソッドの名前は op 名の先頭を大文字にしたもの（`Db`。`docs/plugin-go.md`「名前」）で、フィールド `db` とは別の名前。番号は別の意味に使い回さない（欠番の一覧は `docs/requirements.md`「検査の規則の一覧」）。
- GOSQL-1、GOSQL-3、GOSQL-7〜GOSQL-22 は、書いたものの整合の検査: デコレータが言ったことと、状態・model・op・読み・効果の宣言が食い違っていれば、出力を型に合わせて変えずに error にする（`docs/requirements.md`「出力を推論しない」）。`db` の op のデコレータを配線の op に付けたときは、hozoc が先に DEC-17 を、`@db.find` / `@db.list` を読みでない宣言（op など）に付けたときは、DEC-1 を返す（`docs/check.md`「デコレータ」）。GOSQL-7〜GOSQL-10、GOSQL-13、GOSQL-14 は、`@db.find` / `@db.list` を読みに、`@db.reads` を op に付ける形（`docs/decisions.md`「決めたこと」128）に合わせて、同じ規則を書き直した。
- warning（コードは `PLUGIN`）は一つ: 表の状態が一つもない。`db` の語彙のデコレータを付けていない op には、warning を出さない（「状態ごとの型」）。
- Dir(U, N) の上に `go.mod` がないことは、基底が報告する（GO-1。`docs/plugin-go.md`「診断」）。このトランスパイラは、型のパッケージの import パスを求められないので、ファイルも診断も返さない。
- `@db.table` は、どの保存先かを言わない。同じ `@db.table` の状態を別の保存先にするのは、別のトランスパイラを並べた別の単位（か、人が書く実装）。`@db.key` / `@db.unique` / `@db.ref` の意味（重なれば失敗する、など）は、このトランスパイラの出力にしかなく、ほかの実装が同じ振る舞いをすることは、仕様からは言えない。
