# go-sqlite プラグイン

## この文書が決めること

`db` の語彙（`docs/vocab.md`「`db` の語彙」）の付いた状態を、SQLite の表と、その上の読み書きにするトランスパイラ `go-sqlite`。Go の基底 `go`（`docs/plugin-go.md`）に相乗りし、基底の**状態の単位**（`<状態>State`）を満たす型と、`@db.transaction` の継ぎ目の実装を出す。プラグインは `plugins/go-sqlite/`。期待する出力の実物は、サンプル `tests/samples/shop-server/` の `gen/store/db.go`。

出すものは、付ける先で二つに分かれる（原則の持ち主は `docs/requirements.md`「出力を推論しない」）。

| 付ける先 | このトランスパイラがすること |
|---|---|
| op 以外（状態、表の model のフィールド、`read`、効果） | **宣言の全体から、中身を作る。** 表は、`read` なら `reads` の状態、効果なら宛先（`effects` の後ろ）の状態。列は、引数の名前。引くものは、`read` の結果の型。列が値を持たなくてよいかは、フィールドの型の `?`。デコレータが言うのは、宣言が言っていないことだけ（表であること、しまい方、キー、引くか足すか消すか、決まった値の条件、並べ方）。書いたものが食い違っていれば「診断」の error |
| op（`@db.transaction`） | **op の中身は決めない。** 中身の前後に、トランザクションの始めと終わりを足すだけ（継ぎ目）。出すコードは、op の型に依らない |

`db` のデコレータを付けていない `read` と効果の中身は出さず、人が書き足す（足りなければコンパイルエラーになる。「状態ごとの型」）。しまい方だけは、型から当てない: 同じ型を、いくつものしまい方でしまえる（「しまい方」）。

## マニフェスト

```toml
name     = "go-sqlite"
command  = ["go", "run", "github.com/mew-ton/hozo/plugins/go-sqlite"]
protocol = "0.18"

[[transpiler]]
name     = "go-sqlite"
language = "go"
requires = ["go"]
seams    = ["db.transaction"]

[check]
enabled = true
```

`[check]` は、`emit` が `errors` で返す誤りを、検査の段（`hozoc check`）でも返すためのもの（`docs/plugin-protocol.md`「check」）。

- 読む語彙は、状態の `@db.table`、フィールドの、しまい方（`@db.text` / `@db.int` / `@db.float` / `@db.bool` / `@db.datetime` / `@db.date` / `@db.time` / `@db.json`）と `@db.key` / `@db.unique` / `@db.ref`、`read` の `@db.find` / `@db.list` / `@db.where` / `@db.latest`、効果の `@db.insert` / `@db.update` / `@db.delete`、op の `@db.transaction`。語彙は提供しない。
- **`@db.transaction` は継ぎ目**（`seams`。`docs/config.md`「継ぎ目」）: このトランスパイラを並べた単位では、基底が、`@db.transaction` の付いた op を二層で出し、継ぎ目の口（`Seams` のメソッド）を出す。中身は、このトランスパイラが出す（「トランザクション」）。並べていない単位では、`@db.transaction` は印で、何も起きない（同「継ぎ目」の「読む者がなければ、何も出ない」）。
- オプションはない。`[emit.options.go-sqlite]` にキーがあれば GOSQL-6。
- 制約（`@valid.*`）は確かめない（`go-valid` に依存しない）。足す前に確かめるかどうかは、境界を持つ相乗りの仕事（`docs/plugin-go-valid.md`「この文書が決めること」）。

## 出力

N の `@db.table` の付いた基底の状態（**表の状態**）が一つもなければ、ファイルを出さず warning を一つ返す（N の op に `@db.transaction` が付いていれば、warning ではなく GOSQL-29）。あれば、N の**入口のパッケージ**（`docs/plugin-go.md`「相乗りのファイル」）に `db.go` を一つ。先頭は `// Code generated by hozoc go-sqlite <版>; DO NOT EDIT.`。並びはどれも宣言順。import するのは `database/sql`（と `database/sql/driver`）、ほかの標準ライブラリ、`runtime`（トランザクションの鍵。「トランザクション」）、型のパッケージだけで、ドライバは import しない。

公開の名前は次の種類。非公開の名前は `db` で始める。

| 名前 | 中身 |
|---|---|
| `const Schema` | 表ごとの `CREATE TABLE IF NOT EXISTS` を並べた SQL |
| `func CreateTables(ctx context.Context, db *sql.DB) error` | `Schema` を、受け取った `ctx` で実行する（`db.ExecContext(ctx, Schema)`）。するのは表を作ることだけ。すでにある表には触れない |
| `type Querier interface`、`func Conn(ctx context.Context, db *sql.DB) Querier` | 文を実行する先: `ctx` がトランザクションを運んでいればそれ、なければ `db`（「トランザクション」）。いつも出す |
| `type <状態>Table struct{ db *sql.DB }` | 表の状態ごとに一つ。その状態の単位の実装。値の型で、同じ `db` から作った値は同じ表を読み書きする |
| `func New<状態>Table(db *sql.DB) <状態>Table` | 上の型を作る |
| `type DbSeams struct{ db *sql.DB }`、`func NewDbSeams(db *sql.DB) DbSeams` | `@db.transaction` の継ぎ目の実装（「トランザクション」）。出すときだけ |

`<状態>` は、状態の名前を先頭大文字にしたもの（`UsersTable`、`NewUsersTable`）。

ファイルの中の並び: `Schema`、`CreateTables`、`Querier`、`Conn`、表の状態ごとの型（宣言順。それぞれ、型、`New…`、あれば `var _`、メソッド）、`DbSeams`（型、`NewDbSeams`、あれば `var _`、メソッド）、表の model ごとの `dbArgs<Model>` と `dbScan<Model>`（表の状態の順。同じ model は一度）、補助（使うものだけ。「補助」の順）。

### 表

- 表の状態ごとに表一つ。名前は状態の名前。**表の model** M は、状態の要素の型（`State.element`。`@db.table state orders: list<type.Order>;` なら `type.Order`）で、`@db.table` は引数を持たない。要素の型が model でなければ GOSQL-1。M のフィールドごとに列一つで、名前はフィールドの名前、順はフィールドの順。名前はいつも `"…"` で引用する。
- 表の状態の形は `list` だけ。`nullable` と `single` の状態に `@db.table` が付いていれば GOSQL-2（一行だけの表の形を、まだ決めていない）。
- 列の型は、フィールドに付けた、しまい方のデコレータが決める（「しまい方」）。
- **`NOT NULL` は、フィールドの型が省略可能（`T?`）でない、すべての列に付ける。** 省略可能なフィールドの列は、値がなくてよい（`@db.text nickname: string?`）。フィールドの型に書いてあることなので、別のデコレータは要らない。値がないことの読み書きは「補助」。
- 制約: `@db.key` は `PRIMARY KEY`、`@db.unique` は `UNIQUE`。`@db.key` の付いたフィールドが二つ以上なら、列には付けず、表の末尾に `PRIMARY KEY ("a", "b")`。`@db.ref(M2)` は、要素の型が M2 の表の状態が N に**ちょうど一つ**あり、M2 が `@db.key` をちょうど一つ持つとき、その表のその列への `REFERENCES "<表>" ("<列>")`。そうでなければ GOSQL-20（指す先の表か列が、一つに決まらない）。黙って制約を省くことはしない: 仕様に書いた参照が、気づかないうちに表から消える。
- 列の定義は `"<名前>" <型>[ NOT NULL][ PRIMARY KEY][ UNIQUE][ REFERENCES …]`。表は、列を二つの空白で字下げして一行ずつ、`,` で区切る。

```go
const Schema = `CREATE TABLE IF NOT EXISTS "sessions" (
  "token" TEXT NOT NULL PRIMARY KEY,
  "userId" TEXT NOT NULL REFERENCES "users" ("id"),
  "expiresAt" TEXT NOT NULL
);
`
```

- 外部キーが効くかどうか（SQLite の既定では効かない）、表の作り直し（移行）は、このトランスパイラの外。

### しまい方

表の model のフィールドは、**しまい方**のデコレータ（`docs/vocab.md`「`db` の表と、しまい方」）を、**ちょうど一つ**持つ。一つもないか、二つ以上あれば GOSQL-16。`CREATE TABLE` の列の型と、列の値の読み書きは、このデコレータで決まる。**しまい方は、フィールドの型から当てない**: 型が言っているのは値の形で、どうしまうかではない（`string` を文字列の列にも、JSON の列にもしまえる）。フィールドの型は、しまい方に合うかどうかを確かめるのに使い、合わなければ GOSQL-17（`string` のフィールドに `@db.int`）。

| しまい方 | SQLite の列の型 | 列の値 | 合うフィールドの型（scalar は元の核の型で見る。どれも、その省略可能を含む） |
|---|---|---|---|
| `@db.text` | `TEXT` | 文字列そのまま | `string` |
| `@db.int` | `INTEGER` | 整数 | `int`、`duration`（ナノ秒） |
| `@db.float` | `REAL` | 小数 | `float` |
| `@db.bool` | `INTEGER` | 0 か 1 | `boolean` |
| `@db.datetime` | `TEXT` | RFC 3339、UTC、小数部はいつも 9 桁の文字列（文字列の順が、瞬間の順になる） | `datetime` |
| `@db.date` | `TEXT` | `2026-11-21` の形の文字列（文字列の順が、日付の順になる） | `date` |
| `@db.time` | `TEXT` | `09:30:00.000000000` の形の文字列。小数部はいつも 9 桁（文字列の順が、時刻の順になる） | `time` |
| `@db.json` | `TEXT` | `encoding/json` の JSON の文字列 | `array`、model（インデックスの model を含む） |

- しまい方の名前は、語彙が決めた、保存先の製品に依らない種類。SQLite の列の型に写すのは、このトランスパイラ（ほかの保存先のトランスパイラは、同じ種類を、自分の列の型に写す）。
- **一つのしまい方の中で、型によって変え方が分かれることはない。** `duration` を `@db.int` に入れたのは、Go の値が `int` と同じ 64 ビットの整数で、同じ補助が同じに読み書きできるから。同じしまい方の二つの型が、別の変え方を要るようになったら、型で分けずに、しまい方を足す。
- union（`arms`）と、union を中に持つ `array` / model は、どのしまい方でも列にできない（GOSQL-3。JSON での union の形を、まだ決めていない）。
- `@db.json` の中の値の形（model のフィールド、配列の要素）は、`encoding/json` が、Go の型から決める。その中の model のフィールドに、しまい方のデコレータは要らない（付いていても読まない）。
- 表の model でない model のフィールドに付いた、しまい方のデコレータと、`@db.key`、`@db.unique`、`@db.ref` は、読まない（何も出さず、確かめない）。

### 状態ごとの型

`<状態>Table` のメソッドは、基底のその状態の単位（`docs/plugin-go.md`「状態の単位」）のメソッドのうち、次のもの。名前と形（`ctx`、引数、戻り値）は、基底のメソッドのまま（`plugin/golang` で求める）で、並びも基底の単位と同じ。

| 基底の単位のメソッド | このトランスパイラが出すか |
|---|---|
| 形で決まる問い合わせ（`IsEmpty`、`Get`） | いつも |
| 形で決まる命令 `Post`（配線が `users.post(user);` と直に呼ぶとき、基底が単位に出す） | いつも（単位にあれば）。表の状態は `list` だけなので、ほかの操作は単位に現れない |
| `read` | `@db.find` か `@db.list` を付けたものだけ（「read の中身」） |
| 効果 | `@db.insert` / `@db.update` / `@db.delete` を付けたものだけ（「効果の中身」） |

- 基底のメソッドをすべて持つ型には、`var _ <状態>State = <状態>Table{}` を出す。
- **デコレータを付けていない `read` か効果があるとき**、その型は、そのメソッドを持たない。型は `<状態>State` を満たさず、基底の `New` に渡す行がコンパイルできない。人は、この型を自分の型に埋め込み、足りないメソッドを書き足して、その型を `New` に渡す。`var _` は出さない。**warning も出さない**: デコレータを付けないのは、その中身を人が書くと、仕様を書いた人が選んだこと。
- 人が書き足すメソッドは、文を、`db` を直に使わずに `Conn(ctx, db)` を通して実行する（「トランザクション」）。
- すべて実装した型でも、埋め込んで一つのメソッドを書けば、そのメソッドだけを人のものにできる（条件に合う行だけを書き換える、など）。人が書く効果が、仕様の例外を返すなら、その例外は、効果の `throws` に書いてある（`docs/check.md`「read と効果」）。
- 表の状態でない状態の単位と、述語で決まる状態の分類の単位（`<C>State`）の型は、出さない（人が書く）。

**形で決まるメソッドの中身**（`list`）。状態の宣言の形から決まるもので、デコレータは要らない（形は言語の約束。`docs/check.md`「状態の形」）:

| メソッド | 中身 |
|---|---|
| `IsEmpty` | `SELECT COUNT(*) FROM "<表>"` の結果が 0 |
| `Get` | `SELECT <すべての列> FROM "<表>" ORDER BY rowid`（足した順） |
| `Post` | `INSERT INTO "<表>" (<すべての列>) VALUES (?1, …)`（`@db.insert` の効果と同じ文。引数 `value` の行を足す） |

### read の中身

`read` の宣言（`docs/grammar.md`「exception / effect / read」）に `@db.find` か `@db.list` を付ければ、その `read` のメソッドを出す。以下、宣言の `reads` の状態を T、その表の model を M とする。

```ts
/** そのユーザーの、いちばん新しい注文。まだ注文がなければ、ない */
@db.find
@db.latest("placedAt")
read fn latestOrderOf(userId: type.UserId): type.Order? reads orders;
```

**宣言から読むもの**（デコレータは、これをもう一度言わない）:

| 宣言の部分 | 読むこと | 合わなければ |
|---|---|---|
| `reads T` | 表。T は、N の表の状態 | GOSQL-7 |
| 引数（`Read.params`） | **条件**。引数ごとに、その名前の列が、引数の値と同じ。引数の名前は、M のフィールドの名前で、型は、その列に合う（「列と引数の型」） | 名前のフィールドがなければ GOSQL-8、型が合わなければ GOSQL-9 |
| 結果の型（`Read.returns`） | 引くもの。`@db.find` なら `M?`、`@db.list` なら `M[]` | GOSQL-10 |

**デコレータが言うこと**:

| デコレータ | 言うこと | 決まり |
|---|---|---|
| `@db.find` | 条件に合う一行を引く。なければ `nil` | `@db.list` と一緒には付けられない（GOSQL-22）。一行に決まらなければ GOSQL-13（下） |
| `@db.list` | 条件に合う行を、すべて引く。条件が一つもなければ、すべての行 | 同上 |
| `@db.where("c", v)`（何度でも） | 条件を足す: 列 c が、リテラル v と同じ | `@db.find` か `@db.list` の付いた `read` にだけ（GOSQL-24）。c は M のフィールドの名前（GOSQL-8）。v は、列 c の型に渡せる（GOSQL-26。下） |
| `@db.latest("c")` | 並べ方: 列 c の新しい順 | `@db.find` か `@db.list` の付いた `read` にだけ（GOSQL-24）。c は M のフィールドの名前（GOSQL-8）で、しまい方が `@db.datetime` / `@db.date` / `@db.time` / `@db.int` / `@db.float`（GOSQL-27） |

- **条件**は、引数（宣言の順）の後ろに、`@db.where`（書いた順）を並べたもの。**どれも満たす行**が合う（`AND`）。一つの列を、二つの条件に書けない（引数と `@db.where`、二つの `@db.where`）。書いていれば GOSQL-25。
- **`@db.find` は、一行に決まる**ものでなければならない。次のどれかを満たさなければ GOSQL-13:
  1. 条件の列が、M の `@db.key` のフィールドを**すべて**含む（M が `@db.key` を一つ以上持つとき）。
  2. 条件の列が、`@db.unique` のフィールドを一つ以上含む。
  3. `@db.latest` が付いている（条件に合う行のうち、いちばん新しい一行に決まる。条件がなくてもよい）。
- **`@db.latest("c")` の「新しい順」**は、列 c の値の大きい順（瞬間、日付、時刻なら、後のものが先）。c の値が同じ行は、後から足した行が先。c が値を持たない行（省略可能な列）は、最後。`@db.list` に足せば、その順のすべての行。`@db.find` に足せば、その順の最初の一行（上の 1 か 2 も満たしていれば、合う行は一つなので、結果は変わらない）。`@db.latest` のない `@db.list` は、足した順。
- **`@db.where` のリテラル**は、列のフィールドの型（scalar は元の核の型。省略可能は外して見る）に渡せなければならない（`docs/types.md`「互換」の 10: 整数のリテラルは `float` にも渡せる）。しまい方が `@db.datetime`、`@db.date`、`@db.time`、`@db.json` の列には、渡せるリテラルがない。
- **SQL** は、この形。`<条件>` は、条件ごとの `"<列>" IS ?<n>` を ` AND ` でつないだもの（n は 1 からの通し番号）で、条件がなければ `WHERE` ごと書かない。

| デコレータ | SQL |
|---|---|
| `@db.find` | `SELECT <すべての列> FROM "<表>" WHERE <条件>`。行がなければ `nil` |
| `@db.find` と `@db.latest("c")` | `SELECT <すべての列> FROM "<表>"[ WHERE <条件>] ORDER BY "c" DESC, rowid DESC LIMIT 1`。行がなければ `nil` |
| `@db.list` | `SELECT <すべての列> FROM "<表>"[ WHERE <条件>] ORDER BY rowid`（足した順） |
| `@db.list` と `@db.latest("c")` | `SELECT <すべての列> FROM "<表>"[ WHERE <条件>] ORDER BY "c" DESC, rowid DESC` |

- 文に渡す値は、条件の順に、その列のしまい方の補助で包む（列 `email` が `@db.text` なら、引数は `dbText(email)`、リテラルは `dbText("paid")`。「補助」）。列のフィールドが省略可能なら、フィールドと同じに `dbNullable` を足す（`dbText(email, dbNullable)`）。`@db.where` のリテラルの Go での書き方は、基底と同じ（`docs/plugin-go.md`「値」の表の `literal` の行）で、`@db.float` の列に渡した整数のリテラルは、小数のリテラルで書く（`1.0`）。
- `@db.find` も `@db.list` も付けていない `read` には、何も出さない（`@db.where` か `@db.latest` だけが付いていれば GOSQL-24）。その `read` は、人が書き足す（「状態ごとの型」）。
- この語彙で言えないもの（等しいかどうかでない比較、件数と位置、二つ以上の列での並べ方、いくつかの表を合わせた結果）は、その `read` にデコレータを付けず、人が書く。
- 列は引数の名前なので、仕様の予約語（`docs/grammar.md`「予約語」: `string`、`any`、`on`、`to`、`by` など）と同じ名前のフィールドの列は、引数の条件にできない（フィールドの名前には予約語を書けるが、引数の名前には書けない）。その列で引くなら、フィールドの名前を変えるか、その `read` を人が書く。`@db.where` と `@db.latest` の `column` は文字列なので、名指しできる。`@db.delete` の効果の引数も同じ。

### 効果の中身

効果の宣言に `@db.insert` / `@db.update` / `@db.delete` を付ければ、その効果のメソッドを出す。表 T は、効果の宛先の状態で、M はその表の model。

```ts
/** 注文を作る */
@db.insert
effect fn createOrder(order: type.Order): effects orders.post;

/** ログインセッションを消す */
@db.delete
effect fn deleteSession(token: type.Token): effects sessions.delete;
```

| デコレータ | 効果の宛先（合わなければ GOSQL-11） | 引数（合わなければ GOSQL-9） | SQL |
|---|---|---|---|
| `@db.insert` | `T.post` | M の行一つ（引数は一つで、型は M そのものか、M を分類のケースで絞り込んだ型 `M on C.K`: 行の引数。`docs/check.md`「行の遷移」の「行と、行の分類」） | `INSERT INTO "<表>" (<すべての列>) VALUES (?1, …)` |
| `@db.update` | `T.put` | M の行一つ（同じ）。M は `@db.key` を一つ以上と、キーでない列を一つ以上持つ（GOSQL-15） | `UPDATE "<表>" SET <キーでない列> = ?… WHERE <キーの列> IS ?…`。書き換える行は、M の `@db.key` のフィールドが、引数の行と同じ行。行がなければ何もしない |
| `@db.delete` | `T.delete` | **条件**: 引数ごとに、その名前の列が、引数の値と同じ（`read` と同じ決まり。名前のフィールドがなければ GOSQL-8、型は「列と引数の型」）。引数は一つ以上（GOSQL-28） | `DELETE FROM "<表>" WHERE <条件>`。どの条件も満たす行をすべて消す。行がなければ何もしない |

- T は、N の表の状態（GOSQL-7）。**宛先は、組み込みの効果でなければならない**: 分類の遷移を宛先にする効果（`effect fn e(): effects Checkout as Shopping -> Ordered;`）に `db` のデコレータが付いていれば GOSQL-11（一つの遷移が、どの表に何をするかは、宣言からは決まらない）。その効果は、人が書く。
- 効果は、`@db.insert` / `@db.update` / `@db.delete` の三つのうち、高々一つを持つ（二つ以上なら GOSQL-12）。
- `@db.delete` の条件の値の渡し方は、`read` と同じ（「read の中身」）。
- **未決: 引数のない `@db.delete`**。「引数がなければ、すべての行」は、`@db.list` では決めたが、消す方では決めていない（書き忘れた引数が、表を空にする）。決まるまで GOSQL-28。
- **`@db.conflict(E)`** は、`@db.insert` か `@db.update` と一緒に付ける（`docs/vocab.md`「`db` の read と効果」。`docs/decisions.md`「決めたこと」353）。文が、表の一意の制約（`@db.key` の `PRIMARY KEY` と、`@db.unique` の `UNIQUE`。「表」）に当たったら、例外 E を返す。当たらなければ、SQL は、上の表のまま。

  ```
  /** ユーザーを登録する。同じ email のユーザーが、もういれば、投げる */
  @db.insert @db.conflict(type.EmailTaken)
  effect fn createUser(user: type.User): throws type.EmailTaken effects users.post;
  ```

  - `@db.insert` も `@db.update` も持たない効果に付いていれば GOSQL-31。
  - E は、その効果の `throws` にあり、引数を持たない例外（どちらかが違えば GOSQL-32）。引数を持つ例外は、このトランスパイラが値を埋められないので、その効果は、人が書く。
  - **一意の違反の見分け方**: 文を実行したエラーの文（`err.Error()`）が、`UNIQUE constraint failed` を含むこと。SQLite そのものが出す文で、`PRIMARY KEY` の違反も、この文で出る。`database/sql` のドライバの型には、依らない（生成したコードは、ドライバを import しない）。ほかの失敗は、今までどおり、そのまま返す。
  - 返すのは、例外の値（`<型>{}`。`docs/plugin-go.md`「exception」）。もとのエラーは、包まない。
- **`db` のデコレータで中身を作る効果の `throws` は、`@db.conflict` が名指しした例外だけ。** ほかの例外が `throws` にあれば GOSQL-33（このトランスパイラは、それを投げるコードを出せない）。
- この語彙で言えないもの（制約ごとに別の例外に写すこと、引数を持つ例外を投げること、条件に合う行だけの書き換え）は、その効果にデコレータを付けず、人が書く。

**行の遷移を持つ効果**（`Effect.row`。`docs/check.md`「行の遷移」）に `db` のデコレータを付けても、SQL は、上の表のまま変わらない。行のケースは、述語で決まる分類のもので、列とは限らない（どの列がどの値ならどのケースかは、仕様のどこにも書いていない）ので、このトランスパイラは、ケースを SQL にできない。

| デコレータ | SQL がすること | SQL が確かめないこと |
|---|---|---|
| `@db.insert`（`post`） | 引数の行を、そのまま足す | 足した行が、`as` の後のケースにあること。行を作る側（配線と、葉の op）が担う |
| `@db.update`（`put`） | 引数の行のすべての列を、キーが同じ行に書く | 保存してある行が、前のケースにあること（`WHERE` に足すものがない）。書いた後の行が、後のケースにあること |
| `@db.delete`（`delete`） | 付けられない（下） | — |

- **`@db.update` は、後のケースが、行の引数の型の言う、前のケースの並びにないとき、付けられない**（GOSQL-30）: `effect fn start(order: Order on Stage.Accepted): effects orders.put as Stage.InProduction;` に渡る行は、`Accepted` にあると分かっている行（`docs/check.md`「行の遷移」の「呼ぶ側」）。`@db.update` は、その行を、そのまま書く。書いた後の行も `Accepted` のままで、宣言した `InProduction` にならない。行を `InProduction` にする書き方（どの列を、何に変えるか）は、宣言から決まらないので、その効果は、人が書く（遷移を宛先にする効果と同じ扱い: GOSQL-11）。付けられるのは、行の引数を、その分類で絞り込んでいない形（`effect fn forceShip(order: Order): effects orders.put as Stage.Shipped;`: 渡した行が、もう `Shipped` でありうる）、後のケースが、前のケースの並びにある形、`as else` の形。
- **`@db.delete` は、行の遷移を持つ効果に、付けられない**: 行の遷移を持つ効果は、行を引数に取る（STATE-7）。`@db.delete` の引数は、列の条件で、行の引数の名前の列は、ない（GOSQL-8）。その効果は、人が書く。**未決: 行を受け取る `@db.delete`**（キーが、引数の行と同じ行を消す）。決まるまで、今の規則のまま。
- 生成するメソッドのコメントは、行の遷移を確かめないことを言う（「メソッドの形とコメント」の「効果の句」）。確かめないのは、このメソッド。絞り込んだ引数（効果の前のケース）は、基底が、`New` で包んだ単位の入口で確かめる（`docs/plugin-go.md`「効果の入口の確かめ」）ので、コメントの「（<絞り込んだ引数の表示>、…）は、確かめない。」は、前のケースについては、このメソッドの中のことだけを言う。文を直すかは、決めていない（`docs/open.md`「語彙とプラグイン」）。

### 列と引数の型

値を、名前の同じ列と比べるところ（`read` と、`@db.delete` の効果の、引数の条件）のすべてに掛かる、ただ一つの規則（`docs/decisions.md`「決めたこと」96）:

**引数の型は、列の型（M のそのフィールドの型）と等しくなければならない。列の型が union なら、引数は、その一部でよい。** `T?` は「T」と「値がない」の union と数える。向きは一方だけで、列より広い引数は GOSQL-9。

この規則は、書いたものの整合の検査で、出力を変えない。**条件の SQL は、型によらず、いつも `"c" IS ?n`**（`@db.update` のキーの条件と、`@db.where` の条件も同じ）。SQLite の `IS` は、両辺に値があれば `=` と同じで、両辺が `NULL` のとき真になる。引数に値があるかどうかは、実行時に補助が見る（値のないポインタは `NULL`）。その結果:

| 列の型 | 引数の型 | 合う行 |
|---|---|---|
| `T` | `T` | 列の値が、引数と同じ行 |
| `T?` | `T` | 同じ。値のない行（`NULL`）は、どの値にも合わない |
| `T?` | `T?` | 引数に値があれば、同じ。値がなければ、値のない行 |
| `T` | `T?` | —（GOSQL-9。列より広い） |

- 「等しい」は `docs/types.md`「等しい」。scalar は名前で比べる（`type.Token` の列に `string` の引数は渡せない）。
- 今、列にできる union は `T?` だけ（アームを持つ union は列にできない。GOSQL-3）。
- 引数に値がないとき、問い合わせをやめて「ない」を返すことはしない。値がないときにどうするかは、呼ぶ側の配線が、呼ぶ前に決める（`match … by nullable` か、場合に名前を付けた分類。`docs/requirements.md`「書き方の指針」）。

### トランザクション

`@db.transaction` を付けた op は、**その op が DB にすることのすべてを、一つのトランザクションで行う**。op が失敗すれば、どれも残らない。

```ts
/** 注文と、その通知の記録を、一緒に足す。どちらも足すか、どちらも足さない */
@db.transaction
export fn placeOrder(order: type.Order, notification: type.Notification) {
  createOrder(order);
  notifyUser(notification);
}
```

op のデコレータなので、op の中身（配線の本体か、人が書く葉）は変えない。基底が、その op を二層で出し（`docs/plugin-go.md`「継ぎ目」）、このトランスパイラは、継ぎ目の実装 `DbSeams` を出す:

```go
// DbSeams は、@db.transaction の継ぎ目（Seams のメソッドのうち、このデコレータの分）の、db の上の実装。New の引数 seams に渡す。
// トランザクションに入るのは、中身が、受け取った ctx で、同じ db に、Conn を通してすること（このファイルの型のメソッドは、どれもそう）。
type DbSeams struct{ db *sql.DB }

// NewDbSeams は db の上の DbSeams を返す。状態の単位の実装（New<状態>Table）に渡したのと同じ db を渡す。
func NewDbSeams(db *sql.DB) DbSeams { return DbSeams{db: db} }

var _ Seams = DbSeams{}

// PlaceOrderDbTransaction は op store.placeOrder に付いた @db.transaction の継ぎ目: 中身を、一つのトランザクションの中で呼ぶ。中身が失敗すれば、取り消す。
func (s DbSeams) PlaceOrderDbTransaction(ctx context.Context, order pkgtype.Order, notification pkgtype.Notification, body func(ctx context.Context, order pkgtype.Order, notification pkgtype.Notification) error) error {
	_, err := dbTransaction(ctx, s.db, func(ctx context.Context) (struct{}, error) {
		return struct{}{}, body(ctx, order, notification)
	})
	return err
}
```

- **対象**は、基底の `Seams` のメソッドのうち、このトランスパイラが宣言した継ぎ目のもの（`plugin/golang` の `ShapeOf(view).Seams` のうち、`Transpiler` が `go-sqlite` のもの）。一つもなければ、`DbSeams` も `dbTransaction` も出さない。メソッドは、対象の並びのまま、基底と同じ名前と形（`SeamMethod`、`SeamSignature`）。
- **メソッドの本体は、二つの形**。呼ぶ相手（`body`）の形を写したもので、することは同じ（`docs/plugin-go-http.md`「出力」の 4 と同じ理由）。op の引数と戻り値の型で、ほかに変わるところはない。

| op の形 | 本体 |
|---|---|
| 戻り値がある | `return dbTransaction(ctx, s.db, func(ctx context.Context) (<戻り値の型>, error) { return body(ctx, <引数>) })` |
| 戻り値がない | 上の例（`struct{}` を値にして、`error` だけを返す） |

- **`var _ Seams = DbSeams{}`** は、基底の `Seams` のメソッドが、すべて対象のときだけ出す（単位に、継ぎ目を宣言したほかのトランスパイラがいれば、人が、それぞれの型を一つの構造体に埋め込む。`docs/plugin-go.md`「継ぎ目の実装」）。
- op の入力と出力の値は変えない（`docs/requirements.md`「書き方の指針」）: 受け取った引数を、そのまま `body` に渡す。成功すれば、`body` の戻り値を、そのまま返す。失敗すれば、戻り値は零値。

**始め方と終わり方**は、補助 `dbTransaction` 一つにある:

```go
// dbTransaction は、body を、db の一つのトランザクションの中で呼ぶ: 始めて、body を呼び、確定する。
// トランザクションは、body に渡す ctx が運ぶ（鍵は runtime.DBTxKey）。body が失敗すれば（確定に失敗しても）取り消して、零値とそのエラーを返す。
// ctx が、すでに db のトランザクションを運んでいれば（入れ子。別の名前空間の継ぎ目が始めたものでも）、新しく始めずに、それに加わる: 確定も取り消しも、いちばん外側がする。
func dbTransaction[R any](ctx context.Context, db *sql.DB, body func(ctx context.Context) (R, error)) (R, error) {
	if _, ok := ctx.Value(runtime.DBTxKey{DB: db}).(*sql.Tx); ok {
		return body(ctx)
	}
	var zero R
	tx, err := db.BeginTx(ctx, nil)
	if err != nil {
		return zero, err
	}
	defer tx.Rollback()
	out, err := body(context.WithValue(ctx, runtime.DBTxKey{DB: db}, tx))
	if err != nil {
		return zero, err
	}
	if err := tx.Commit(); err != nil {
		return zero, err
	}
	return out, nil
}
```

| 起きること | 結果 |
|---|---|
| `body` が成功する | 確定する（`Commit`）。確定に失敗すれば、取り消して、そのエラー |
| `body` がエラーを返す（仕様の例外も、ほかのエラーも同じ） | 取り消して（`Rollback`）、そのエラーを、そのまま返す |
| `body` が panic する | 取り消してから、panic が続く（`defer tx.Rollback()`） |
| 始められない（中断された `ctx` など） | `body` を呼ばずに、そのエラー |

**表のメソッドが、トランザクションに入る仕組み**: トランザクション（`*sql.Tx`）は、`body` に渡す `ctx` が運ぶ（`context.WithValue`。鍵は、`runtime` パッケージの公開の型 `runtime.DBTxKey` に `db` を入れたもの: `runtime.DBTxKey{DB: db}`）。文を実行するところは、どれも `Conn(ctx, db)` を通り、`ctx` が、その `db` のトランザクションを運んでいれば、それで実行する。

```go
// Querier は *sql.DB と *sql.Tx が共に持つ、文の実行。
type Querier interface {
	ExecContext(ctx context.Context, query string, args ...any) (sql.Result, error)
	QueryContext(ctx context.Context, query string, args ...any) (*sql.Rows, error)
	QueryRowContext(ctx context.Context, query string, args ...any) *sql.Row
}

// Conn は、ctx で文を実行する先: ctx が db のトランザクション（@db.transaction の継ぎ目が始めたもの）を運んでいれば、それ。なければ db。
// このファイルの型のメソッドは、どれもこれを通す。人が書き足すメソッドも、db を直に使わずに、これを通す（通さなければ、トランザクションに入らない）。
// 鍵は runtime.DBTxKey（db ごとに一つ。どの名前空間の出力も同じ鍵を使う）なので、別の名前空間の継ぎ目が、同じ db に始めたトランザクションにも入る。
func Conn(ctx context.Context, db *sql.DB) Querier {
	if tx, ok := ctx.Value(runtime.DBTxKey{DB: db}).(*sql.Tx); ok {
		return tx
	}
	return db
}
```

- **`ctx` で運ぶ理由**: 継ぎ目から表のメソッドへ届く道が、`ctx` しかない。間にあるのは基底が出した配線で、状態の単位のメソッドの引数は、基底が決め（`ctx` と、宣言の引数だけ。相乗りは変えられない: `docs/plugin-go.md`「相乗りのファイル」）、配線は、受け取った `ctx` を、呼ぶ先にそのまま渡す（同「op の形」）。表の型は `New` に渡した値のままで、呼び出しごとに差し替えられない。型のフィールドに「今のトランザクション」を持てば、並行の呼び出しが混ざる。トランザクションは、op の引数の代わりではなく、呼び出しの間だけのもの（標準の `context` が値を運ぶ用途）。
- **鍵を `runtime` に置く理由**: 鍵は、**同じ `db` を使う、すべての名前空間の出力が共有する**（`docs/plugin-go.md`「runtime パッケージ」の `DBTxKey`）。`context` は、鍵を `==` で比べるので、鍵の型が出力のパッケージごとに別（非公開の型）なら、同じ `db` の上でも、別の名前空間の出力は、そのトランザクションを見つけられない: `@db.transaction` の付いた op が呼んだ、別の名前空間の op の文が、トランザクションの外で実行される（取り消されず、SQLite では、書き手が一つなので、トランザクションが終わるまで待つ）。型を一つにすれば、どの出力の `Conn` も、どの出力の継ぎ目が始めたトランザクションでも、`db` が同じなら見つける。鍵の値は `db` を持つので、別の `db` のトランザクションとは混ざらない。
- **入るもの**: `body` が、受け取った `ctx`（か、そこから作った `ctx`）で呼んだ、同じ `db` の上の、`go-sqlite` の出力の型のメソッド（`read`、効果、形で決まるメソッド。**別の名前空間の出力の型を含む**）と、`Conn` を通した人のメソッド。読む方も入るので、op の中の `read` は、同じ op が先に書いたものを見る。`@db.transaction` の付いた op が、別の名前空間の op を呼び、その先が同じ `db` の表を読み書きすれば、それも、同じトランザクション。
- **入らないもの**（取り消されない。SQLite は書き手が一つなので、同じデータベースへの、トランザクションの外からの書き込みは、トランザクションが終わるまで待つ）:

| 入らないもの | 理由 |
|---|---|
| 別の `ctx`（`context.Background()` など）で呼んだメソッド | トランザクションを運んでいない |
| 別の `db` の上の型のメソッド（同じ名前空間でも、別の名前空間でも） | 鍵が `db` ごと |
| `db` を直に使う人のコード | `Conn` を通していない |
| ほかの保存先の実装（人がメモリの上に書いた単位など） | DB ではない |

- **入れ子**（トランザクションの中の op が、`@db.transaction` の付いた op を呼ぶ。同じ `db`。内側が、別の名前空間の op でも同じ）: 内側は、新しいトランザクションを始めずに、外側のものに**加わる**。内側の継ぎ目は、`body` を、そのまま呼ぶだけ。確定するのも、取り消すのも、いちばん外側。内側が失敗し、その失敗がいちばん外側の op の失敗になれば、すべてが取り消される。内側の失敗を、途中のデコレータが吸収して（`catches … recovers`）、外側が成功したときは、内側が失敗までにしたことも、外側と一緒に確定される（内側だけを取り消すこと — セーブポイント — は、しない）。
- 別の `db` の `DbSeams` を入れ子にすれば、`db` ごとに別のトランザクションになる（二つを一緒に確定する仕組みは、ない）。
- トランザクションの分離のしかたは、`BeginTx(ctx, nil)`（ドライバの既定）。
- **継ぎ目が掛かるのは、op の持ち主の名前空間の出力**（`docs/plugin-go.md`「内側のフォルダと、別の名前空間」）で、これは変わらない: 別の名前空間 M の op を呼ぶ側（N）は、M の op の継ぎ目を持たない。名前空間をまたぐのは、トランザクションそのもの（`ctx` が運ぶ `*sql.Tx`）だけ。N の `@db.transaction` の op が M の op を呼べば、M の表のメソッドは、N の継ぎ目が始めたトランザクションで文を実行し、M の op が自分の `@db.transaction` を持っていれば、M の継ぎ目は、それに加わる（入れ子）。
- これまでの形から変えたこと: 鍵は、出力のパッケージごとの非公開の型 `dbTxKey` だった。同じ `db` の上でも、別の名前空間の op が読み書きする表は、トランザクションに入らなかった（「未決: 別の名前空間をまたぐトランザクション」）。鍵を `runtime.DBTxKey` にして、入るようにした。

### 補助

列ごと、メソッドごとに出すコードは同じ形で、違いは、共通の補助の中にある。使うものだけを、この順で、ファイルの末尾に出す。

| 名前 | 中身 |
|---|---|
| `dbArgs<Model>(row <Model>) ([]any, error)` | model を、列の順の値にする。本体は `return dbArgs(<列>, …)` の一行で、`<列>` は、フィールドごとに `<しまい方の補助>(row.<F>)`。省略可能なフィールドは `<しまい方の補助>(row.<F>, dbNullable)`。使うものだけ: 出すメソッドのどれかが、その model の行を受け取る（`@db.insert` か `@db.update` の効果か、形で決まる `Post`）ときに出す（`dbScan<Model>` は、`Get` が使うので、いつも出る） |
| `dbScan<Model>(r dbRow) (<Model>, error)` | 列の順の値を model に読む。本体は `r.Scan(<列>, …)` で、`<列>` は、フィールドごとに `<しまい方の補助>(&row.<F>)`。省略可能なフィールドは `<しまい方の補助>(&row.<F>, dbNullable)` |
| `dbRow` | `*sql.Row` と `*sql.Rows` が共に持つ `Scan(dest ...any) error` |
| `dbOption`、`dbNullable` | 列の読み書きに、フィールドの宣言が足すこと（`type dbOption int`）と、省略可能なフィールドの印（`const dbNullable dbOption = 1`）。`dbCol` と一緒に、いつも出す |
| `dbCol` | 列一つ: しまい方と、Go の値（書くときはフィールドの値か、列と比べる引数かリテラル。読むときはフィールドへのポインタ）と、渡された `dbOption`。`database/sql` が、書くときに `Value`（`driver.Valuer`）を、読むときに `Scan`（`sql.Scanner`）を呼ぶ |
| `dbArgs(cols ...dbCol) ([]any, error)` | 列の並びを、文に渡す値の並びにする |
| `dbString` | 列の値を、文字列として読む（`@db.text`、`@db.datetime`、`@db.date`、`@db.time`、`@db.json` の補助が使う） |
| `dbText`、`dbInt`、`dbFloat`、`dbBool`、`dbDatetimeLayout` と `dbDatetime`、`dbDate`、`dbTime`、`dbJSON` | しまい方ごとの補助 `func(v any, opts ...dbOption) dbCol`。「しまい方」の表の、列の値への変え方と、その逆。使うしまい方の分だけ、この順で |
| `dbTransaction` | トランザクションの始め方と終わり方（「トランザクション」）。`DbSeams` を出すときだけ。鍵は、このファイルの名前ではなく、`runtime.DBTxKey`（`Conn` も使うので、`runtime` は、いつも import する） |
| `dbExec` | 行を返さない文を実行する |
| `dbConflict(err, conflict error) error` | `err` が、一意の制約の違反（「効果の中身」の「一意の違反の見分け方」）なら `conflict` を、ほかは `err` を、そのまま返す。`@db.conflict` を付けた効果があるときだけ（`strings` を import するのも、そのときだけ） |
| `dbIsEmpty` | 行の数を返す問い合わせの結果が 0 かどうか |
| `dbGet[R]` | 問い合わせの一行を読む。行がなければ（`sql.ErrNoRows`）`nil` |
| `dbList[R]` | 問い合わせのすべての行を読む |

```go
// dbArgsOrder は type.Order を、表 "orders" の列の順の値にする。
func dbArgsOrder(row pkgtype.Order) ([]any, error) {
	return dbArgs(dbText(row.Id), dbText(row.UserId), dbJSON(row.Lines), dbDatetime(row.PlacedAt))
}

// dbScanOrder は、表 "orders" の列の順の値を type.Order に読む。
func dbScanOrder(r dbRow) (pkgtype.Order, error) {
	var row pkgtype.Order
	if err := r.Scan(dbText(&row.Id), dbText(&row.UserId), dbJSON(&row.Lines), dbDatetime(&row.PlacedAt)); err != nil {
		return pkgtype.Order{}, err
	}
	return row, nil
}
```

- `dbExec`、`dbIsEmpty`、`dbGet`、`dbList` は、`*sql.DB` を受け取り、文を `Conn(ctx, db)` で実行する（「トランザクション」）。表のメソッドの本体は、トランザクションの有無で変わらない。
- **行に足すのは、宣言が言ったことだけ**: フィールドごとの補助は、しまい方のデコレータが選び、省略可能なフィールド（`T?`）は、最後の引数に `dbNullable` を足す（`dbText(row.Nickname, dbNullable)`、`dbText(&row.Nickname, dbNullable)`）。scalar か核の型かでは、書き分けない。
- **値がないこと（`NULL`）は、`dbCol` が、実行時に、渡された Go の値と `dbNullable` を見て決める**（`reflect`）。
  - 書くとき: 値のないポインタは `NULL`（省略可能なフィールドの、値のない値。列と比べる、値のない引数）。`dbNullable` の列では、値のないスライスとマップ（`T[]?` と、省略可能な、インデックスの model の `nil`）も `NULL` で、`@db.json` でも、JSON の `null` という文字列にはしない。`dbNullable` のない列の、値のないスライスとマップは、しまい方のまま書く（`@db.json` なら、`encoding/json` が出す文字列 `null`）。
  - 読むとき: `NULL` を読めるのは、`dbNullable` の列だけで、読む先は、値がない（`nil`）。ほかの列に `NULL` があれば、エラー（その列は `NOT NULL` なので、`Schema` で作った表では起きない）。値があれば、読む先がポインタなら、置く先を作って読む。
- しまい方の補助に、合わない型の値が渡ることは、GOSQL-17 と GOSQL-26 が先に断るので、ない（そのときの振る舞いは、決めない）。型の食い違いをコンパイルエラーにする形（型引数）にしないのは、省略可能な値と、そうでない値を、一つの関数で、型を書かずに受け取れないため（`docs/plugin-go-http.md`「補助」の末尾と同じ理由）。
- 補助の中身は、サンプルの `gen/store/db.go` の通り（`dbInt`、`dbFloat`、`dbBool` は、サンプルが使わないので、`go-sqlite` の単体テストのゴールデンが固定する。`docs/testing.md`「単体テスト」）。

メソッドの引数の名前は、基底と同じ規則で仕様の引数名から作る。このファイルが使う名前（表のメソッドのレシーバ `t`、継ぎ目のメソッドのレシーバ `s`、`ctx`、`args`、`err`、import するパッケージの名前、このファイルの非公開の名前）と当たれば、末尾に `_` を付ける。`dbArgs<Model>` と `dbScan<Model>` の中の局所の名前（`row`、`r`、`err`）と、継ぎ目のメソッドの中の局所の名前（レシーバ `s`、`ctx`、`err`、`body`）は、import するパッケージの名前と当たれば、当たらなくなるまで末尾に `_` を付ける（その名前のパッケージの型を、本体が書けなくなるため: 継ぎ目のメソッドの本体は、関数リテラルに、op の戻り値の型を書く。`docs/plugin-go.md`「パッケージと import パス」の「import の名前」の、相乗りの側の決まり）。継ぎ目のメソッドでは、引数の局所の名前とも当たらないようにする（名前空間 `s` の型を返し、引数 `s` を持つ op なら、引数が `s_`、レシーバが `s__`）。基底の `Seams` のメソッドとは、引数の名前だけが違い、形（型の並び）は同じ。`<Model>` は model の Go の型の名前で、別の名前空間の同じ名前の model と当たれば、後の方に `2`、`3`、… を付ける。

### メソッドの形とコメント

```go
// UserByEmail は read store.userByEmail（@db.find）: 表 "users" から、"email" が引数 email と同じ行を引く。なければ nil。
func (t UsersTable) UserByEmail(ctx context.Context, email pkgtype.Email) (*pkgtype.User, error) {
	return dbGet(ctx, t.db, dbScanUser,
		`SELECT "id", "email", "name", "hash" FROM "users" WHERE "email" IS ?1`, dbText(email))
}

// LatestOrderOf は read store.latestOrderOf（@db.find、@db.latest）: 表 "orders" から、"userId" が引数 userId と同じ行のうち、"placedAt" がいちばん新しい行を引く。なければ nil。
func (t OrdersTable) LatestOrderOf(ctx context.Context, userId pkgtype.UserId) (*pkgtype.Order, error) {
	return dbGet(ctx, t.db, dbScanOrder,
		`SELECT "id", "userId", "lines", "placedAt" FROM "orders" WHERE "userId" IS ?1 ORDER BY "placedAt" DESC, rowid DESC LIMIT 1`, dbText(userId))
}

// CreateUser は効果 store.createUser（@db.insert）: 表 "users" に、引数 user の行を足す。
func (t UsersTable) CreateUser(ctx context.Context, user pkgtype.User) error {
	args, err := dbArgsUser(user)
	if err != nil {
		return err
	}
	return dbExec(ctx, t.db,
		`INSERT INTO "users" ("id", "email", "name", "hash") VALUES (?1, ?2, ?3, ?4)`, args...)
}

// DeleteSession は効果 store.deleteSession（@db.delete）: 表 "sessions" から、"token" が引数 token と同じ行を消す。行がなければ何もしない。
func (t SessionsTable) DeleteSession(ctx context.Context, token pkgtype.Token) error {
	return dbExec(ctx, t.db, `DELETE FROM "sessions" WHERE "token" IS ?1`, dbText(token))
}
```

`@db.conflict` を付けた効果は、`dbExec` の呼び出しを、`dbConflict(…, <例外の値>)` で包む。包む行は、`return dbConflict(dbExec(ctx, t.db,` で、文の行の末尾は `args...), <例外の値>)`:

```go
// CreateUser は効果 store.createUser（@db.insert、@db.conflict）: 表 "users" に、引数 user の行を足す。一意の制約に当たれば、例外 type.EmailTaken を返す。
func (t UsersTable) CreateUser(ctx context.Context, user pkgtype.User) error {
	args, err := dbArgsUser(user)
	if err != nil {
		return err
	}
	return dbConflict(dbExec(ctx, t.db,
		`INSERT INTO "users" ("id", "email", "name", "hash") VALUES (?1, ?2, ?3, ?4)`, args...), pkgtype.EmailTaken{})
}

// dbConflict は、err が、一意の制約（キーを含む）の違反なら、conflict を返す。ほかは、err を、そのまま返す。
func dbConflict(err, conflict error) error {
	if err != nil && strings.Contains(err.Error(), "UNIQUE constraint failed") {
		return conflict
	}
	return err
}
```

- `@db.find` は `dbGet`、`@db.list` は `dbList`、効果は `dbExec`。行を受け取る効果（`@db.insert`、`@db.update`）と `Post` は、先に `args, err := dbArgs<Model>(<引数>)` と、その `err` の確認を置く（値を列の形にできなければ、文を実行しない）。
- `SELECT`（`COUNT` を除く）、`INSERT`、`UPDATE` の文は、呼び出しの二行目に書く。`SELECT COUNT(*)` と `DELETE` の文は、呼び出しと同じ行に書く。
- コメントは、宣言ごとに一行（型は二行）。途中で折り返さない。

| 宣言 | コメント |
|---|---|
| `Schema` | `// Schema は @db.table の状態の表を作る SQL（SQLite）。状態ごとに表一つ、その model のフィールドごとに列一つ。` |
| `CreateTables` | `// CreateTables は db に、@db.table の状態の表を作る（Schema を実行する）。すでにある表には触れない。` |
| `Querier`、`Conn`、`DbSeams`、`NewDbSeams`、`dbTransaction` | 「トランザクション」のコードの通り |
| `<状態>Table` | `// <状態>Table は状態 <FQN> の単位（<状態>State）の、表 "<表>" の上の実装。` と `// メソッドは、形で決まる問い合わせ（IsEmpty、Get）と、この単位の read と効果のうち、db の語彙のデコレータを付けたもの（<句>）。`。句は、すべてに付いていれば（`read` も効果も一つもないときを含む）`この単位では、すべて`、そうでなければ `付けていないもの: <read と効果の名前を、単位の並びで「、」で>`。単位が `Post` を持つなら、`（IsEmpty、Get）` の後ろに `と命令（Post）` を足す |
| `New<状態>Table` | `// New<状態>Table は db の表 "<表>" の上の <状態>Table を返す。表は CreateTables が作る。` |
| `IsEmpty` | `// IsEmpty は形で決まる問い合わせ: 表 "<表>" に行が一つもなければ true。` |
| `Get` | `// Get は形で決まる問い合わせ: 表 "<表>" の行を、足した順にすべて引く。` |
| `Post` | `// Post は形で決まる命令: 表 "<表>" に、引数 value の行を足す。` |
| `read` | `// <メソッド名> は read <FQN>（<@デコレータ>）: <read の句>`。`<@デコレータ>` は、付いた `db` のデコレータの名前を、`@db.find` / `@db.list`、`@db.where`（いくつあっても一度）、`@db.latest` の順に「、」でつないだもの |
| 効果 | `// <メソッド名> は効果 <FQN>（<@デコレータ>）: <効果の句>`。`<@デコレータ>` は、`@db.insert` / `@db.update` / `@db.delete` と、付いていれば `@db.conflict` を、この順に「、」でつないだもの |
| 継ぎ目のメソッド | `// <メソッド名> は op <FQN> に付いた @db.transaction の継ぎ目: 中身を、一つのトランザクションの中で呼ぶ。中身が失敗すれば、取り消す。` |
| `dbArgs<Model>` / `dbScan<Model>` | `// dbArgs<Model> は <model の FQN> を、表 "<表>" の列の順の値にする。` / `// dbScan<Model> は、表 "<表>" の列の順の値を <model の FQN> に読む。`（表は、その model を要素に持つ、最初の表の状態） |

`read` の句。`<条件>` は、条件ごとの `"<列>" が<相手>と同じ` を「で、」でつないだもの（相手は、引数なら `引数 <引数名> `、`@db.where` なら ` <仕様に書いたままのリテラル> `。前後の空白は、この通り。リテラルは、IR の値から、仕様の書き方（`docs/grammar.md`「リテラル」）に書き直したもの: 文字列は `"…"`（`"` と `\` と改行、タブ、復帰は、エスケープ）、整数は 10 進、小数は、指数を使わない、いつも小数点を持つ形（`9.5`、`2.0`）、真偽値は `true` / `false`）:

| `read` のデコレータ | `read` の句 |
|---|---|
| `@db.find` | `表 "<表>" から、<条件>行を引く。なければ nil。` |
| `@db.find` と `@db.latest`（条件がある） | `表 "<表>" から、<条件>行のうち、"<列>" がいちばん新しい行を引く。なければ nil。` |
| `@db.find` と `@db.latest`（条件がない） | `表 "<表>" から、"<列>" がいちばん新しい行を引く。なければ nil。` |
| `@db.list`（条件がある） | `表 "<表>" から、<条件>行を、足した順にすべて引く。` |
| `@db.list`（条件がない） | `表 "<表>" の行を、足した順にすべて引く。` |
| `@db.list` と `@db.latest`（条件がある） | `表 "<表>" から、<条件>行を、"<列>" の新しい順にすべて引く。` |
| `@db.list` と `@db.latest`（条件がない） | `表 "<表>" の行を、"<列>" の新しい順にすべて引く。` |

効果の句:

| 効果のデコレータ | 効果の句 |
|---|---|
| `@db.insert` | `表 "<表>" に、引数 <引数名> の行を足す。` |
| `@db.update` | `表 "<表>" の、キーが引数 <引数名> と同じ行を書き換える。行がなければ何もしない。` |
| `@db.delete` | `表 "<表>" から、<条件>行を消す。行がなければ何もしない。` |

`@db.conflict(E)` を付けた効果は、効果の句の後ろに、空白なしで一文を足す: `一意の制約に当たれば、例外 <E の FQN> を返す。`。行の遷移の一文も足すときは、こちらが先。

行の遷移を持つ効果（`Effect.row`）は、効果の句の後ろに、空白なしで一文を足す: `行の遷移（<行の遷移の表示>）は、確かめない。`（表示の形は `docs/plugin-go.md`「コメント」の「行の遷移の表示」）。絞り込んだ引数があれば、その表示を、前に、`、` でつなぐ: `行の遷移（<絞り込んだ引数の表示>、<行の遷移の表示>）は、確かめない。`（同「絞り込んだ引数の表示」。行の引数なら、効果の前のケース）。GOSQL-30 のメッセージも、同じ並びで言う。

```go
// AcceptOrder は効果 shop.acceptOrder（@db.insert）: 表 "orders" に、引数 order の行を足す。行の遷移（as shop.Stage.Accepted）は、確かめない。
```

補助のコメントは、サンプルの通り。

## 診断

`emit` の応答の `errors` で返し、同じものを、検査の段（direction `check`）でも返す（`docs/plugin-protocol.md`「check」）。

| ID | 重さ | 意味 |
|---|---|---|
| GOSQL-1 | error | `@db.table` の付いた状態の要素の型が、model でないか、インデックスの model（フィールドを持たない。「表」）。位置は状態 |
| GOSQL-2 | error | `@db.table` の付いた状態の形が `list` でない（`nullable`、`single`）。位置は状態 |
| GOSQL-3 | error | 表の model に、どのしまい方でも列にできない型のフィールドがある（union と、union を中に持つ型）。位置は model |
| GOSQL-4 | error | このトランスパイラの公開の名前（`Schema`、`CreateTables`、`Querier`、`Conn`、`<状態>Table`、`New<状態>Table`、出すなら `DbSeams`、`NewDbSeams`）が、N の定義のパッケージの名前（型など。`docs/plugin-go.md`「名前」）と当たる。位置は当たった宣言。このトランスパイラの公開の名前どうし（状態 `users` の `NewUsersTable` と、状態 `newUsers` の `NewUsersTable`）も同じで、位置は後ろの宣言 |
| GOSQL-6 | error | `[emit.options.go-sqlite]` に、知らないキーがある。位置なし |
| GOSQL-7 | error | `db` のデコレータを付けた `read` の `reads` の状態か、効果の宛先の状態が、N の表の状態でない（`@db.table` が付いていない）。位置は、その `read` か効果 |
| GOSQL-8 | error | 列を名指しするもの（`read` と `@db.delete` の効果の引数の名前、`@db.where` と `@db.latest` の `column`）が、表の model のフィールドにない。位置は、その `read` か効果 |
| GOSQL-9 | error | 引数が、デコレータの言うものと合わない: 条件の引数（`read` と、`@db.delete` の効果）の型が、列に合わない（「列と引数の型」）。`@db.insert` / `@db.update` の効果の引数が、表の model の行一つでない。位置は、その `read` か効果 |
| GOSQL-10 | error | `read` の結果の型が、デコレータの言うものと合わない: `@db.find` は `M?`、`@db.list` は `M[]`（M は表の model）。位置は `read` |

| GOSQL-12 | error | 一つの効果が、`@db.insert` / `@db.update` / `@db.delete` のうち二つ以上を持つ。位置は効果 |
| GOSQL-13 | error | `@db.find` の `read` が、一行に決まらない: 条件の列が、表の model の `@db.key` のすべても、`@db.unique` の列も含まず、`@db.latest` もない（「read の中身」）。位置は `read` |
| GOSQL-15 | error | `@db.update` の表の model が、`@db.key` を一つも持たないか、キーでない列を一つも持たない。位置は効果 |
| GOSQL-16 | error | 表の model のフィールドが、しまい方のデコレータ（`@db.text` / `@db.int` / `@db.float` / `@db.bool` / `@db.datetime` / `@db.date` / `@db.time` / `@db.json`）を一つも持たないか、二つ以上持つ（「しまい方」）。位置は model |
| GOSQL-17 | error | しまい方が、フィールドの型に合わない（「しまい方」の表）。メッセージに、フィールド、しまい方、型を示す。位置は model |
| GOSQL-20 | error | 表の model のフィールドの `@db.ref(M2)` の指す先が、一つに決まらない: 要素の型が M2 の表の状態が、N にないか、二つ以上ある。または、M2 の `@db.key` が一つでない（「表」）。位置は model |
| GOSQL-22 | error | 一つの `read` が、`@db.find` と `@db.list` の両方を持つ。位置は `read` |

- 欠番（番号は別の意味に使い回さない。欠番の一覧は `docs/requirements.md`「検査の規則の一覧」）:

| 欠番 | 規則だったもの | なくなった理由 |
|---|---|---|
| GOSQL-5 | 状態の単位のメソッドの名前が、このファイルの型のフィールド `db` と当たる（op `db`） | 起きない: メソッドの名前は先頭を大文字にしたもの（`Db`。`docs/plugin-go.md`「名前」）で、フィールド `db` とは別の名前 |
| GOSQL-14 | op が、`db` の op のデコレータ（`@db.reads`、`@db.effects`）の言う以外のものを読み書きする | op の中身を言うデコレータを、なくした（op は、`read` と効果を呼ぶ配線） |
| GOSQL-18、GOSQL-19 | `@db.nullable` と、フィールドの型（省略可能かどうか）の食い違い | `@db.nullable` をなくした（値がなくてよいかは、フィールドの型の `?`） |
| GOSQL-21 | `read` のデコレータの表が、`read` の読む状態でない | デコレータは、表を引数に取らない（表は、`reads` の状態） |
| GOSQL-23 | `@db.reads` に、`read` を二つ以上並べている（決まるまでの間だけの規則） | `@db.reads` をなくした |

- GOSQL-1、GOSQL-7〜GOSQL-13、GOSQL-22 は、同じ規則を、今の書き方（引数のない `@db.table`、`read` と効果の宣言の引数と宛先）に合わせて書き直した。GOSQL-12 と GOSQL-22 の、`@db.effects` / `@db.reads` に並べたものについての半分は、なくなった。
- 一つの食い違いを、重ねて報告しない: 表にならなかった状態（GOSQL-1 か GOSQL-2 を返した）を `reads` の状態か宛先にする `read` と効果に、GOSQL-7 は出さない。GOSQL-12、GOSQL-22、GOSQL-24 を返した宣言と、宛先が分類の遷移の効果（GOSQL-11）は、ほかの検査をしない（デコレータが何を言っているのかが、決まらない）。条件の列がフィールドになかった（GOSQL-8）`@db.find` に、GOSQL-13 は出さない（一行に決まるかどうかを、言えない）。一つの `read` が同じ列を三度名指ししていても、GOSQL-25 は、列ごとに一つ。
- どれも、書いたものの整合の検査: デコレータと宣言が食い違っていれば、黙って何かを出すことも、出さないこともせず、error にする（`docs/requirements.md`「出力を推論しない」）。`db` のデコレータを、付けられない宣言に付けたとき（`@db.find` を op に、など）は、hozoc が先に DEC-1 を返す（`docs/check.md`「デコレータ」）。
- warning（コードは `PLUGIN`）は一つ: 表の状態が一つもない（GOSQL-29 のときは出さない）。`db` のデコレータを付けていない `read` と効果には、warning を出さない（「状態ごとの型」）。
- Dir(U, N) の上に `go.mod` がないことは、基底が報告する（GO-1。`docs/plugin-go.md`「診断」）。このトランスパイラは、型のパッケージの import パスを求められないので、ファイルも診断も返さない。
- `@db.table` は、どの保存先かを言わない。同じ `@db.table` の状態を別の保存先にするのは、別のトランスパイラを並べた別の単位（か、人が書く実装）。`@db.key` / `@db.unique` / `@db.ref` と `@db.transaction` の意味（重なれば失敗する、失敗すれば取り消す、など）は、このトランスパイラの出力にしかなく、ほかの実装が同じ振る舞いをすることは、仕様からは言えない。
