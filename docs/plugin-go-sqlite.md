# go-sqlite プラグイン

## この文書が決めること

`db` の語彙（`docs/vocab.md`「同梱する語彙」「`db` の読み書きのデコレータ」）の付いた状態を、SQLite の表と、その上の読み書きにするトランスパイラ `go-sqlite`。Go の基底 `go`（`docs/plugin-go.md`）に相乗りし、基底の**状態の単位**（`<状態>State`）と `SharedState` を満たす型を出す。プラグインは `plugins/go-sqlite/`。期待する出力の実物は、サンプル `tests/samples/shop-server/` の `gen/store/db.go`。

出すのは、仕様が `db` の語彙のデコレータで言ったものと、状態の形で決まる問い合わせだけ。型や書き方から出力を推し量ることはしない（`docs/requirements.md`「出力を推論しない」）: 何を出すかはデコレータの引数だけで決まり、型は、書いたものが食い違っていないかを確かめるのにだけ使う（食い違えば「診断」の error）。`db` の語彙のデコレータを付けていない op は出さず、人が書き足す（足りなければコンパイルエラーになる）。

## マニフェスト

```toml
name     = "go-sqlite"
command  = ["go", "run", "github.com/mew-ton/hozo/plugins/go-sqlite"]
protocol = "0.5"

[[transpiler]]
name     = "go-sqlite"
language = "go"
requires = ["go"]
```

- 読む語彙は、状態の `@db`、フィールドの `@db.key` / `@db.unique` / `@db.ref`、op の `@db.find` / `@db.list` / `@db.effects`、効果の `@db.insert` / `@db.update` / `@db.delete`。語彙は提供しない。
- オプションはない。`[emit.options.go-sqlite]` にキーがあれば GOSQL-6。
- 制約（`@valid.*`）は確かめない（`go-valid` に依存しない）。足す前に確かめるかどうかは、境界を持つ相乗りの仕事（`docs/plugin-go-valid.md`「この文書が決めること」）。

## 出力

N の `@db` の付いた基底の状態（**表の状態**）が一つもなければ、ファイルを出さず warning を一つ返す。あれば、N の**入口のパッケージ**（`docs/plugin-go.md`「相乗りのファイル」）に `db.go` を一つ。先頭は `// Code generated by hozoc go-sqlite <版>; DO NOT EDIT.`。並びはどれも宣言順。import するのは `database/sql` と標準ライブラリ、型のパッケージだけで、ドライバは import しない。

公開の名前は次の種類。非公開の名前は `db` で始める。

| 名前 | 中身 |
|---|---|
| `const Schema` | 表ごとの `CREATE TABLE IF NOT EXISTS` を並べた SQL |
| `func CreateTables(ctx context.Context, db *sql.DB) error` | `Schema` を、受け取った `ctx` で実行する（`db.ExecContext(ctx, Schema)`）。するのは表を作ることだけ。すでにある表には触れない |
| `type <状態>Table struct{ db *sql.DB }` | 表の状態ごとに一つ。その状態の単位の実装。値の型で、同じ `db` から作った値は同じ表を読み書きする |
| `func New<状態>Table(db *sql.DB) <状態>Table` | 上の型を作る |
| `type SharedTable struct{ db *sql.DB }`、`func NewSharedTable(db *sql.DB) SharedTable` | 基底の `SharedState` の実装（「状態をまたぐ単位の型」）。出すときだけ |
| `type <C>Table struct{ db *sql.DB }`、`func New<C>Table(db *sql.DB) <C>Table` | 述語で決まる状態の分類 C の単位の、命令の実装（同）。出すときだけ |

`<状態>` は、状態の名前を先頭大文字にしたもの（`UsersTable`、`NewUsersTable`）。`<C>` は、状態の分類の名前を先頭大文字にしたもの。

ファイルの中の並び: `Schema`、`CreateTables`、単位ごとの型（基底の `states.go` と同じ並び: 表の状態と、型を出す状態の分類を宣言順に、最後に `SharedTable`。それぞれ、型、`New…`、あれば `var _`、メソッド）、要素の model ごとの `dbArgs<Model>` と `dbScan<Model>`（表の状態の順。同じ model は一度）、補助（使うものだけ。下の順）。

### 表

- 表の状態ごとに表一つ。名前は状態の名前。要素の model のフィールドごとに列一つで、名前はフィールドの名前、順はフィールドの順。名前はいつも `"…"` で引用する。
- 表の状態の形は `list` だけ。`nullable` と `single` の状態に `@db` が付いていれば GOSQL-2（一行だけの表の形を、まだ決めていない）。要素が model への `ref` でなければ GOSQL-1。
- 列の型と、値の変え方:

| フィールドの型（scalar は元の核の型で見る） | 列の型 | 書く値（`dbArgs`） | 読み方（`dbScan`） |
|---|---|---|---|
| `string` | `TEXT` | 核の型なら `row.<F>`、scalar なら `string(row.<F>)` | `&row.<F>` に直に読む |
| `int` | `INTEGER` | `row.<F>` / `int64(row.<F>)` | 同上 |
| `float` | `REAL` | `row.<F>` / `float64(row.<F>)` | 同上 |
| `boolean` | `INTEGER`（0 か 1） | `row.<F>` / `bool(row.<F>)` | 核の型なら同上。scalar なら `(*bool)(&row.<F>)`（`database/sql` は、名前付きの真偽値の型には整数を読めない） |
| `Duration` | `INTEGER`（ナノ秒） | `int64(row.<F>)` | 同上 |
| `Time` | `TEXT`（RFC 3339、UTC、小数部はいつも 9 桁。文字列の順が時刻の順になる） | `dbTime(row.<F>)` / `dbTime(time.Time(row.<F>))` | 文字列の変数に読んでから `dbParseTime` |
| `array`、`record`、model | `TEXT`（`encoding/json` の JSON） | `json.Marshal` した文字列 | 文字列の変数に読んでから `json.Unmarshal` |
| union（`arms`）と、union を中に持つ `array` / `record` / model | — | GOSQL-3（JSON での union の形を、まだ決めていない） | |

- 省略可能でない列は `NOT NULL`。**省略可能な列**は `NOT NULL` を付けず、値がなければ `NULL`。書く値は `dbOpt(row.<F>)`（`nil` なら `nil`、あれば上の表の値）、`Time` は `dbOptTime(row.<F>)`、JSON の型は `nil` なら `nil`。Go で名前付きの型（scalar と、`Duration`）は、ポインタを、書く値の型へのポインタに変えて渡す（`dbOpt((*string)(row.<F>))`、`dbOptTime((*time.Time)(row.<F>))`）。読むときは、直に読める型は `&row.<F>`（`database/sql` が `NULL` を `nil` のポインタにする）、`Time` と JSON の型は `sql.NullString` に読んで、`Valid` のときだけ変える。`boolean` が元の scalar は、`*bool` の変数に読んでから、ポインタの型を変える。
- 制約: `@db.key` は `PRIMARY KEY`、`@db.unique` は `UNIQUE`。`@db.key` の付いたフィールドが二つ以上なら、列には付けず、表の末尾に `PRIMARY KEY ("a", "b")`。`@db.ref(M)` は、要素が `M` である表の状態が N に**ちょうど一つ**あり、`M` が `@db.key` をちょうど一つ持つとき、その表のその列への `REFERENCES "<表>" ("<列>")`。そうでなければ制約なし。
- 列の定義は `"<名前>" <型>[ NOT NULL][ PRIMARY KEY][ UNIQUE][ REFERENCES …]`。表は、列を二つの空白で字下げして一行ずつ、`,` で区切る。

```go
const Schema = `CREATE TABLE IF NOT EXISTS "sessions" (
  "token" TEXT NOT NULL PRIMARY KEY,
  "userId" TEXT NOT NULL REFERENCES "users" ("id"),
  "expiresAt" TEXT NOT NULL
);
`
```

- 外部キーが効くかどうか（SQLite の既定では効かない）、表の作り直し（移行）は、このトランスパイラの外。

### 状態ごとの型

`<状態>Table` のメソッドは、基底のその状態の単位（`docs/plugin-go.md`「状態の単位」）のメソッドのうち、形で決まる問い合わせ（いつも）と、**`db` の語彙の op のデコレータ（`@db.find`、`@db.list`、`@db.effects`）を付けた op**（「op の中身」）。どの op がどの単位のメソッドになるか（op の置き場）は基底が決め、このトランスパイラは変えない。名前と形（`ctx`、引数、戻り値）は、基底のメソッドのまま（`plugin/golang` で求める）。受け取った `ctx` で `QueryContext` / `QueryRowContext` / `ExecContext` / `BeginTx` を呼ぶ。op に `export` が付いているかは見ない。

- 基底のメソッドをすべて持つ型には、`var _ <状態>State = <状態>Table{}` を出す。
- **デコレータを付けていない op があるとき**、その型は、その op のメソッドを持たない。型は `<状態>State` を満たさず、基底の `New` に渡す行がコンパイルできない。人は、この型を自分の型に埋め込み、足りないメソッドを書き足して、その型を `New` に渡す。`var _` は出さない。**warning も出さない**: デコレータを付けないのは、その op の中身を人が書くと、仕様を書いた人が選んだこと。
- すべて実装した型でも、埋め込んで一つのメソッドを書けば、そのメソッドだけを人のものにできる（一意の違反を見分けて、仕様の例外に写す、など）。

**形で決まる問い合わせの中身**（`list`）。状態の宣言の形から決まるもので、デコレータは要らない（形は言語の約束。`docs/check.md`「状態の形」）:

| メソッド | 中身 |
|---|---|
| `IsEmpty` | `SELECT COUNT(*) FROM "<表>"` の結果が 0 |
| `Get` | `SELECT <すべての列> FROM "<表>" ORDER BY rowid`（足した順） |

### 状態をまたぐ単位の型

基底が、表の状態の単位でないところに置いた op（`docs/plugin-go.md`「op の置き場」）のための型。どちらも `struct{ db *sql.DB }` の値の型で、メソッドは、その単位の op のうち `@db.effects` を付けたものだけ。

| 基底の口 | 型と、作る関数 | 出すとき | `var _` |
|---|---|---|---|
| `SharedState`（効果の宛先の単位が二つ以上に分かれた op） | `SharedTable`、`NewSharedTable(db *sql.DB) SharedTable` | `SharedState` の op に、`@db.effects` を付けたものが一つでもある | `SharedState` の op のすべてに付いていれば `var _ SharedState = SharedTable{}` |
| 述語で決まる状態の分類 C の単位 `<C>State`（C の遷移を宛先にする効果の op） | `<C>Table`、`New<C>Table(db *sql.DB) <C>Table` | `<C>State` の命令に、`@db.effects` を付けたものが一つでもある | 出さない（述語は人が書くので、`<C>State` を満たさない） |

- メソッドの足りない型の扱いは、「状態ごとの型」と同じ: 人が自分の型に埋め込んで、足りないメソッド（`<C>Table` なら、ケースの述語も）を書き足す。warning は出さない。
- 読む op（`@db.find`、`@db.list`）は、いつも表の状態の単位に置かれる（読む状態は、名指しした表一つ。GOSQL-14）ので、ここには来ない。
- 型で決まる状態の分類の遷移と、基底の状態の遷移を宛先にする効果の op は、基底がその状態の単位に置くので、`<状態>Table` のメソッドになる。

### op の中身

op の中身は、op に付けた `db` の語彙のデコレータの引数だけで決まる。表は状態の名前で、列は文字列（表の要素の model のフィールドの名前）で渡す。以下、表の状態を T、その要素の model を M とする。

**読む op**（デコレータが、T を op の `reads` として運ぶ。op は `reads` を書かない）:

| デコレータ | op の形（合わなければ「診断」） | SQL |
|---|---|---|
| `@db.find(T, "c")` | 引数は一つで、型は列 c に合う（「列と引数の型」）。戻り値は `M?`。c は、M のただ一つの `@db.key` か、`@db.unique` | `SELECT <すべての列> FROM "<表>" WHERE "c" = ?1`。行がなければ `nil` |
| `@db.list(T, "c")` | 引数は一つで、型は列 c に合う。戻り値は `M[]` | `SELECT <すべての列> FROM "<表>" WHERE "c" = ?1 ORDER BY rowid`（足した順） |
| `@db.list(T)` | 引数はない。戻り値は `M[]` | `SELECT <すべての列> FROM "<表>" ORDER BY rowid` |

**書く op** は、行う効果を `@db.effects(e₁, …, eₙ)` で並べる（デコレータが、それらを op の `effects` として運ぶ。op は `effects` を書かない）。効果の宣言が、表に何をするかを `@db.insert` / `@db.update` / `@db.delete` で言う。**n 番目の効果が、op の n 番目の引数を受け取る。** 引数の数は効果の数と同じで、戻り値はない。

| 効果のデコレータ | 効果の宛先（合わなければ GOSQL-11） | 受け取る引数 | SQL |
|---|---|---|---|
| `@db.insert(T)` | 組み込みの効果なら `T.post` | M の行（型は M そのもの） | `INSERT INTO "<表>" (<すべての列>) VALUES (?1, …)` |
| `@db.update(T)` | 組み込みの効果なら `T.put` | M の行（同じ）。M は `@db.key` を一つ以上と、キーでない列を一つ以上持つ（GOSQL-15） | `UPDATE "<表>" SET <キーでない列> = ?… WHERE <キーの列> = ?…`。書き換える行は、M の `@db.key` のフィールドが同じ行。行がなければ何もしない |
| `@db.delete(T, "c")` | 組み込みの効果なら `T.delete` | 列 c に合う型の値（「列と引数の型」） | `DELETE FROM "<表>" WHERE "c" = ?1`。行がなければ何もしない |

- 表を、効果の宛先から読まずに引数で名指しさせるのは、出力を決めるのがデコレータの引数だけだから。効果の宛先が、状態の分類の遷移や基底の状態の遷移のとき（一つの効果が複数の状態に触れ、表はその一部、という場合を含む）は、操作の名前との照合はなく、T がその効果の書き込む状態（`Effect.writes`）の一つであればよい。
- 効果は、`@db.insert` / `@db.update` / `@db.delete` のうち、ちょうど一つを持つ（`@db.effects` に並べた効果が一つも持たないか、一つの効果が二つ以上持てば GOSQL-12）。op に並べられていない効果のデコレータも、同じに確かめる（何も出さない）。
- **効果が一つ**なら、文一つを `dbExec` で実行する。**二つ以上なら、一つのトランザクション**（「トランザクション」）。同じ効果を二度並べてもよい（文が二つになる）。
- 条件に書いた引数の値は、列の「書く値」の形で渡す（`string(email)`。省略可能な引数は、省略可能な列の書く値と同じ形）。
- op は、デコレータが言う以外のものを読み書きしない: `db` の op のデコレータはちょうど一つで、op が直に読む状態と直に持つ効果（`docs/check.md`「デコレータが運ぶ reads と effects」）は、そのデコレータが運ぶものだけ。そうでなければ GOSQL-14（`@db.find` の op が自分で `effects` を書いている、など）。`@db.effects()` に効果が一つもないときも同じ。
- デコレータで言えないもの（順序、件数と位置、等しいかどうかでない比較、複数の列の条件、一意の違反を例外に写すこと）は、その op にデコレータを付けず、人が書く。

### 列と引数の型

値を、名指しした列と比べるところ（`@db.find`、`@db.list`、`@db.delete` の条件）のすべてに掛かる、ただ一つの規則（`docs/decisions.md`「決めたこと」96）:

**引数の型は、列の型（M のそのフィールドの型）と等しくなければならない。列の型が union なら、引数は、その一部でよい。** `T?` は「T」と「値がない」の union と数える。向きは一方だけで、列より広い引数は GOSQL-9。

| 列の型 | 引数の型 | 条件 | |
|---|---|---|---|
| `T` | `T` | `"c" = ?n` | |
| `T?` | `T` | `"c" = ?n` | 値のない行（`NULL`）は、どの値にも合わない |
| `T?` | `T?` | `"c" IS ?n` | 型が等しい。引数に値がなければ、値のない行に合う（SQLite の `IS` は、両辺が `NULL` のとき真） |
| `T` | `T?` | — | GOSQL-9（列より広い） |

- 「等しい」は `docs/types.md`「等しい」。scalar は名前で比べる（`type.Token` の列に `string` の引数は渡せない）。
- 今、列にできる union は `T?` だけ（アームを持つ union は列にできない。GOSQL-3）。
- 引数に値がないとき、問い合わせをやめて「ない」を返すことはしない（その規則は、なくした）。値がないときにどうするかは、呼ぶ側の配線が、呼ぶ前に決める（`match … by nullable` か、場合に名前を付けた分類。`docs/requirements.md`「書き方の指針」）。

### トランザクション

`@db.effects` に効果を二つ以上並べた op は、**一つのトランザクションで、書いた順に**文を実行する。どれかが失敗すれば、どれも残らない。

```go
// PlaceOrder は op store.placeOrder（@db.effects）: 一つのトランザクションで、書いた順に行う。効果 store.createOrder（@db.insert）で、表 "orders" に、引数 order の行を足す。効果 store.notifyUser（@db.insert）で、表 "notifications" に、引数 notification の行を足す。どれかが失敗すれば、どれも残らない。
func (t SharedTable) PlaceOrder(ctx context.Context, order pkgtype.Order, notification pkgtype.Notification) error {
	args1, err := dbArgsOrder(order)
	if err != nil {
		return err
	}
	args2, err := dbArgsNotification(notification)
	if err != nil {
		return err
	}
	tx, err := t.db.BeginTx(ctx, nil)
	if err != nil {
		return err
	}
	defer tx.Rollback()
	if _, err := tx.ExecContext(ctx,
		`INSERT INTO "orders" ("id", "userId", "lines", "placedAt") VALUES (?1, ?2, ?3, ?4)`, args1...); err != nil {
		return err
	}
	if _, err := tx.ExecContext(ctx,
		`INSERT INTO "notifications" ("userId", "message") VALUES (?1, ?2)`, args2...); err != nil {
		return err
	}
	return tx.Commit()
}
```

メソッドの本体は、この順:

1. 行を受け取る効果（`@db.insert`、`@db.update`）ごとに、効果の順で、`args<i>, err := dbArgs<Model>(<引数>)` と、その `err` の確認。`<i>` は、効果が何番目か（1 始まり）。値を列の形にできなければ、トランザクションを始めない。
2. `tx, err := t.db.BeginTx(ctx, nil)` と、その `err` の確認。
3. `defer tx.Rollback()`。途中で返れば取り消す。確定した後の `Rollback` は何もしない（その戻り値は見ない）。
4. 効果ごとに、効果の順で、`if _, err := tx.ExecContext(ctx, <文>, <値>); err != nil { return err }`。`<値>` は、行を受け取る効果なら `args<i>...`、`@db.delete` なら、引数の「書く値」。
5. `return tx.Commit()`。

- どの単位の型のメソッドでも同じ形（宛先の単位が一つなら `<状態>Table`、分かれれば `SharedTable`、述語で決まる状態の分類なら `<C>Table`）。型が持つのは `*sql.DB` だけで、トランザクションは、メソッドの中で始めて終える。
- 複数の op にまたがるトランザクション（配線の二つの呼び出しを一つにする）は、ない: 一緒に行うものは、一つの op の `@db.effects` に並べる。

### 補助

使うものだけを、この順で、ファイルの末尾に出す。

| 名前 | 中身 |
|---|---|
| `dbArgs<Model>(row <Model>) ([]any, error)` | model を、列の順の値にする |
| `dbScan<Model>(r dbRow) (<Model>, error)` | 列の順の値を model に読む |
| `dbRow` | `*sql.Row` と `*sql.Rows` が共に持つ `Scan(dest ...any) error` |
| `dbTimeLayout`、`dbTime`、`dbParseTime` | `Time` の列の形（`"2006-01-02T15:04:05.000000000Z07:00"`、UTC）と、その読み書き（読むのは `time.RFC3339Nano`） |
| `dbOpt`、`dbOptTime` | 省略可能な列の値（`nil` なら `nil`） |
| `dbExec` | 行を返さない文を実行する |
| `dbIsEmpty` | 行の数を返す問い合わせの結果が 0 かどうか |
| `dbGet[R]` | 問い合わせの一行を読む。行がなければ（`sql.ErrNoRows`）`nil` |
| `dbList[R]` | 問い合わせのすべての行を読む |

メソッドの引数の名前は、基底と同じ規則で仕様の引数名から作る。このファイルが使う名前（レシーバの `t`、`ctx`、`args`、`args<数>`、`tx`、`err`、import するパッケージの名前、このファイルの非公開の名前）と当たれば、末尾に `_` を付ける。`dbArgs<Model>` と `dbScan<Model>` の中の変数（`Time` と JSON の列の値。名前はフィールドの名前）も同じ。`<Model>` は model の Go の型の名前で、別の名前空間の同じ名前の model と当たれば、後の方に `2`、`3`、… を付ける。

### メソッドの形とコメント

```go
// FindUser は op store.findUser（@db.find）: 表 "users" から、"email"（@db.unique）が引数 email と同じ行を引く。なければ nil。
func (t UsersTable) FindUser(ctx context.Context, email pkgtype.Email) (*pkgtype.User, error) {
	return dbGet(ctx, t.db, dbScanUser,
		`SELECT "id", "email", "name", "hash" FROM "users" WHERE "email" = ?1`, string(email))
}

// AddUser は op store.addUser（@db.effects）: 効果 store.createUser（@db.insert）で、表 "users" に、引数 user の行を足す。
func (t UsersTable) AddUser(ctx context.Context, user pkgtype.User) error {
	args, err := dbArgsUser(user)
	if err != nil {
		return err
	}
	return dbExec(ctx, t.db,
		`INSERT INTO "users" ("id", "email", "name", "hash") VALUES (?1, ?2, ?3, ?4)`, args...)
}

// RemoveSession は op store.removeSession（@db.effects）: 効果 store.deleteSession（@db.delete）で、表 "sessions" から、"token" が引数 token と同じ行を消す。行がなければ何もしない。
func (t SessionsTable) RemoveSession(ctx context.Context, token pkgtype.Token) error {
	return dbExec(ctx, t.db, `DELETE FROM "sessions" WHERE "token" = ?1`, string(token))
}
```

- `SELECT`（`COUNT` を除く）、`INSERT`、`UPDATE` の文は、呼び出しの二行目に書く。`SELECT COUNT(*)` と `DELETE` の文は、呼び出しと同じ行に書く。トランザクションの中の `tx.ExecContext` も同じ。
- 効果が一つの op の、行の値の変数は `args`。二つ以上なら `args<i>`（「トランザクション」）。
- コメントは、宣言ごとに一行（単位の型は二行）。途中で折り返さない。

| 宣言 | コメント |
|---|---|
| `Schema` | `// Schema は @db の状態の表を作る SQL（SQLite）。状態ごとに表一つ、要素の model のフィールドごとに列一つ。` |
| `CreateTables` | `// CreateTables は db に、@db の状態の表を作る（Schema を実行する）。すでにある表には触れない。` |
| `<状態>Table` | `// <状態>Table は状態 <FQN> の単位（<状態>State）の、表 "<表>" の上の実装。` と `// メソッドは、形で決まる問い合わせ（IsEmpty、Get）と、この単位の葉の op のうち、db の語彙のデコレータを付けたもの（<句>）。`。句は、すべてに付いていれば（op が一つもないときを含む）`この単位では、すべて`、そうでなければ `付けていない op: <op 名を「、」で>` |
| `New<状態>Table` | `// New<状態>Table は db の表 "<表>" の上の <状態>Table を返す。表は CreateTables が作る。` |
| `SharedTable` | `// SharedTable は、複数の状態にまたがる葉の op（SharedState）の、db の上の実装。` と `// メソッドは、SharedState の op のうち、db の語彙のデコレータを付けたもの（<句>）。`。句は `<状態>Table` と同じ |
| `NewSharedTable` | `// NewSharedTable は db の上の SharedTable を返す。表は CreateTables が作る。` |
| `<C>Table` | `// <C>Table は状態の分類 <FQN> の単位（<C>State）の命令の、db の上の実装。` と `// メソッドは、<C>State の命令のうち、db の語彙のデコレータを付けたもの（<句>）。ケースの述語は、埋め込んで書き足す。`。句は同じ |
| `New<C>Table` | `// New<C>Table は db の上の <C>Table を返す。表は CreateTables が作る。` |
| `IsEmpty` | `// IsEmpty は形で決まる問い合わせ: 表 "<表>" に行が一つもなければ true。` |
| `Get` | `// Get は形で決まる問い合わせ: 表 "<表>" の行を、足した順にすべて引く。` |
| `@db.find` の op | `// <メソッド名> は op <FQN>（@db.find）: 表 "<表>" から、"<列>"（<@db.key か @db.unique>）が引数 <引数名> と同じ行を引く。なければ nil。` |
| `@db.list` の op | `// <メソッド名> は op <FQN>（@db.list）: 表 "<表>" から、"<列>" が引数 <引数名> と同じ行を、足した順にすべて引く。`。列がなければ `// <メソッド名> は op <FQN>（@db.list）: 表 "<表>" の行を、足した順にすべて引く。` |
| `@db.effects` の op（効果が一つ） | `// <メソッド名> は op <FQN>（@db.effects）: <効果の句>` |
| `@db.effects` の op（効果が二つ以上） | `// <メソッド名> は op <FQN>（@db.effects）: 一つのトランザクションで、書いた順に行う。<効果の句を、効果の順に、区切りなしで>どれかが失敗すれば、どれも残らない。` |
| `dbArgs<Model>` / `dbScan<Model>` | `// dbArgs<Model> は <model の FQN> を、表 "<表>" の列の順の値にする。` / `// dbScan<Model> は、表 "<表>" の列の順の値を <model の FQN> に読む。`（表は、その model を要素に持つ最初の表の状態） |

効果の句は、効果のデコレータごとに一文:

| 効果のデコレータ | 効果の句 |
|---|---|
| `@db.insert` | `効果 <効果の FQN>（@db.insert）で、表 "<表>" に、引数 <引数名> の行を足す。` |
| `@db.update` | `効果 <効果の FQN>（@db.update）で、表 "<表>" の、キーが引数 <引数名> と同じ行を書き換える。行がなければ何もしない。` |
| `@db.delete` | `効果 <効果の FQN>（@db.delete）で、表 "<表>" から、"<列>" が引数 <引数名> と同じ行を消す。行がなければ何もしない。` |

補助のコメントは、サンプルの通り。

## 診断

`emit` の応答の `errors` で返す。

| ID | 重さ | 意味 |
|---|---|---|
| GOSQL-1 | error | `@db` の状態の要素が model でない。位置は状態 |
| GOSQL-2 | error | `@db` の状態の形が `list` でない（`nullable`、`single`）。位置は状態 |
| GOSQL-3 | error | 列にできない型のフィールドがある（union と、union を中に持つ型）。位置は model |
| GOSQL-4 | error | このトランスパイラの公開の名前（`Schema`、`CreateTables`、`<状態>Table`、`New<状態>Table`、出すなら `SharedTable`、`NewSharedTable`、`<C>Table`、`New<C>Table`）が、N の定義のパッケージの名前（型、`New<Model>` など。`docs/plugin-go.md`「名前」）と当たる。位置は当たった宣言。このトランスパイラの公開の名前どうし（状態 `users` の `NewUsersTable` と、状態 `newUsers` の `NewUsersTable`。状態 `shared` の `SharedTable` と、`SharedState` の `SharedTable`）も同じで、位置は後ろの宣言 |
| GOSQL-6 | error | `[emit.options.go-sqlite]` に、知らないキーがある。位置なし |
| GOSQL-7 | error | `db` の語彙のデコレータ（`@db.find`、`@db.list`、`@db.insert`、`@db.update`、`@db.delete`）の引数の状態が、N の表の状態でない（`@db` が付いていない、別の名前空間の状態）。位置はデコレータを付けた宣言 |
| GOSQL-8 | error | デコレータの引数の列の名前が、その表の要素の model のフィールドにない。位置はデコレータを付けた宣言 |
| GOSQL-9 | error | op の引数が、デコレータの言うものと合わない（「op の中身」「列と引数の型」）: `@db.find` と、列を渡した `@db.list` は、引数が一つで、型が列に合う。列のない `@db.list` は、引数がない。`@db.effects` は、引数の数が並べた効果の数と同じで、n 番目の型が、n 番目の効果の受け取るもの（`@db.insert` / `@db.update` は表の要素の model、`@db.delete` は列に合う型）。位置は op |
| GOSQL-10 | error | op の戻り値が、デコレータの言うものと合わない: `@db.find` は `M?`、`@db.list` は `M[]`（M は表の要素の model）、`@db.effects` は戻り値なし。位置は op |
| GOSQL-11 | error | 効果のデコレータが、効果の宛先と合わない（「op の中身」）: 宛先が組み込みの効果なのに、状態がデコレータの表でないか、操作が合わない（`@db.insert` は `post`、`@db.update` は `put`、`@db.delete` は `delete`）。宛先が遷移なのに、デコレータの表が、その効果の書き込む状態（`Effect.writes`）にない。位置は効果 |
| GOSQL-12 | error | `@db.effects` に並べた効果が、`@db.insert` / `@db.update` / `@db.delete` のどれも持たない（位置は op）。または、一つの効果が、その三つのうち二つ以上を持つ（位置は効果） |
| GOSQL-13 | error | `@db.find` の列が、一行に決まる列でない（表の要素の model のただ一つの `@db.key` でも、`@db.unique` でもない）。位置は op |
| GOSQL-14 | error | op が、`db` の op のデコレータ（`@db.find`、`@db.list`、`@db.effects`）の言う以外のものを読み書きする: そのデコレータを二つ以上持つ。op が直に読む状態か直に持つ効果に、そのデコレータが運ぶもの以外がある。`@db.effects` に効果が一つもない。位置は op |
| GOSQL-15 | error | `@db.update` の表の要素の model が、`@db.key` を一つも持たないか、キーでない列を一つも持たない。位置は効果 |

- GOSQL-5 は欠番。「状態の単位のメソッドの名前が、このファイルの型のフィールド `db` と当たる（op `db`）」という規則だったが、起きない: メソッドの名前は op 名の先頭を大文字にしたもの（`Db`。`docs/plugin-go.md`「名前」）で、フィールド `db` とは別の名前。そのうえ、op `db` を持つ名前空間では、`@db` がその op を指すので（RES-4）、表の状態を書けない。番号は別の意味に使い回さない（欠番の一覧は `docs/requirements.md`「検査の規則の一覧」）。
- GOSQL-7〜GOSQL-15 は、書いたものの整合の検査: デコレータが言ったことと、状態・model・op・効果の宣言が食い違っていれば、出力を推し量らずに error にする（`docs/requirements.md`「出力を推論しない」）。`db` の op のデコレータを配線の op に付けたときは、hozoc が先に DEC-17 を返す（`docs/check.md`「デコレータ」）。
- warning（コードは `PLUGIN`）は一つ: 表の状態が一つもない。`db` の語彙のデコレータを付けていない op には、warning を出さない（「状態ごとの型」）。
- Dir(U, N) の上に `go.mod` がないことは、基底が報告する（GO-1。`docs/plugin-go.md`「診断」）。このトランスパイラは、型のパッケージの import パスを求められないので、ファイルも診断も返さない。
- `@db` は、どの保存先かを言わない。同じ `@db` の状態を別の保存先にするのは、別のトランスパイラを並べた別の単位（か、人が書く実装）。`@db.key` / `@db.unique` / `@db.ref` の意味（重なれば失敗する、など）は、このトランスパイラの出力にしかなく、ほかの実装が同じ振る舞いをすることは、仕様からは言えない。
