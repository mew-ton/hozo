# 型

## この文書が決めること

値がどの位置に渡せるか（互換）、形の語と型の対応、継承した model、分類のケースでの絞り込み、式の型の決め方、呼び出しの引数の照合。`docs/ir.md` の `Type` の上で定義する。違反はこの文書の「診断」の `TYPE-*`。

## 型の種類

`docs/ir.md`「型」の通り。加えて、式にだけある型が四つある。IR の `Type` にはならない。

| 式の型 | 中身 |
|---|---|
| `none` の型 | `none` の型。どの `optional` にも入る |
| レコードリテラルの型 | フィールド名と値の型の組の列。model に照合して初めて型が決まる |
| 「値がない」 | 値を返さない（`void` の）op の呼び出しと、効果の呼び出し（`createOrder(order)`、`orders.post(order)`）の型 |
| 「返らない」 | 決して値を返さない式の型: `never` を返す op の呼び出し、アームの本体の `throw`、すべてのアームが返らない `match`（「式の型」） |

`never` は値の型ではない。IR では `Op.returns` にだけ現れる（`docs/ir.md`「型」）。

## 形の書き方

形の語（`docs/grammar.md`「型」）は、型の別の書き方。どの `Type` の位置でも同じ型になり、IR には一つの形だけが残る（`docs/ir.md`「正規化」）。

| 形の語 | 同じ型 | IR |
|---|---|---|
| `nullable<T>` | `T?` | `optional(T)` |
| `list<T>` | `T[]` | `array(T)` |
| `single<T>` | `T` | T そのもの |

- 入れ子も同じ規則で読む: `single<T?>` は `T?`、`nullable<T?>` は `T??` で、`T?` に正規化される（`optional` は入れ子にしない）。`list<T>?` と `nullable<list<T>>` は同じ `optional(array(T))`。
- 状態の型（`state 名前: Type;` の `Type`）も同じ。状態の形（`list` / `nullable` / `single`）は、この型の最も外側から決まる（`docs/check.md`「状態の形」）。
- 型の表示（診断、ホバー）は `T?` と `T[]` で書く。状態の宣言の見出しだけは形の語で書く（`docs/lsp.md`「ホバー」）。

## 等しい

二つの `Type` は、構造が等しければ等しい。`ref` は FQN が等しいとき。`case` は `classify` と `cases` の集合と `of` が等しいとき。

## 互換

S の値を T の位置に渡せるのは、次のどれかを満たすとき。再帰的に適用する。

1. S と T が等しい。
2. T が `optional(T')` で、S が T' に渡せる。
3. S が `none` の型で、T が `optional`。
4. S が `case(C, cases, of)` で、T が `of`（絞り込みを捨てる）。
5. S が `case(C, s, of)`、T が `case(C, t, of)` で、s ⊆ t（§10.2「まとめたアームではケースの和の型」。狭い方は広い方に渡せる）。
6. S が `array(S')`、T が `array(T')` で、S' が T' に渡せる。
7. S が `record(K1, V1)`、T が `record(K2, V2)` で、K1 = K2 かつ V1 が V2 に渡せる。
8. （欠番。model から model への射影の規則だった。なくした。下の「渡せないもの」）
9. S がレコードリテラルで、T が model への `ref`（または model の `optional`）で、リテラルが T に**当てはまる**（下）。
10. S がリテラルの型で、T が対応する核の型（`string`→`string`、`int`→`int` または `float`、`float`→`float`、`boolean`→`boolean`、`duration`→`Duration`）。
11. S が `scalar` への `ref` で、S の `base` が T に渡せる（`Email` を `string` に。値の型は元の型の部分集合）。

規則の番号は使い回さない（ほかの文書とコードが番号で引くため）。

渡せないもの（明示）:

- model の値を、別の model の位置に渡す。フィールドが同じでも、一方がもう一方を継承していても（「継承した model」）、別の型で、どちらの向きにも渡せない（引数なら TYPE-4、`return` なら TYPE-3）。設計書 §7.1「出力は宣言した型に自動で射影される」はやめた（`docs/decisions.md`「設計書から離れた決定」S22）。別の model の値が要るところでは、写す op を呼ぶ: 仕様の上では普通の葉の op（`op toPublicUser(user: User): PublicUser;`）で、人が中身を書く。
- 核の型の値を `scalar` の位置に渡す（TYPE-1。§6.5「元の型の値を値の型の位置に渡すには、検証を通す必要がある」）。配線でその手段になるのは、述語の要る絞り込み（「絞り込み」。`string` の対象を `Email` にするケース）だけで、それ以外の位置では常にエラー。
- `scalar` の値を別の `scalar` の位置に渡す（`Token` を `UserId` に）。元の型が同じでも別の型。
- `union`（`arms`）に、アームの型の値を直接渡す。配線にユニオンの値を作る手段はなく、ユニオンを返すのは葉の op（§11.2 の VM 関数）。
- `union`（`set`）は値の型ではない。型の位置に書いたら RES-4。

### 当てはまる（レコードリテラルを model T に）

- リテラルの各フィールドが T にあり、値の型が T のフィールドの型に渡せる。T にないフィールドがあれば TYPE-5。
- T の必須のフィールド（`optional` でない）が、リテラルにあるか、`bind` で埋まる位置（`Call.bound` のパス）である。なければ BIND-4（`docs/check.md`）。
- 同じフィールドが二度あれば TYPE-6。

## 継承した model

`model D extends B { ... }`（`docs/grammar.md`「model」）の D を**継承した model**、B を D の**元の model**と呼ぶ。D は B とは別の型で、D と B の間に互換はない（「互換」の「渡せないもの」）。元の model になれるのは `model` の宣言（別の名前空間のもの、語彙のもの、継承した model でもよい）。その場で書いた model は名前で書けないので、元の model になれない。

型 X が型 Y を**継承している**とは、次のどちらか。X と Y が等しいときは含まない。

- X と Y が model で、X の元の model を一回以上辿ると Y に着く。
- X が `scalar` で、X の `extends` を一回以上辿ると Y（`scalar` か核の型）に着く。

### フィールド

D のフィールド（`Model.fields`）は、次の順に作る。IR には作った後の並びだけが残る（`docs/ir.md`「正規化」）。

1. B のフィールドを B の並びのまま写す（B が継承した model なら、B の作った後の並び）。
2. D の本体の `Override` を当てる: なくす（`never`）ならそのフィールドを除く。型を書いていれば、その位置のまま型を差し替える。デコレータは、その位置のフィールドに足す。説明は、`Override` に書いたものに置き換える（書いていなければ、説明なしになる）。
3. D の本体の `Field`（足すフィールド）を、書かれた順に末尾に足す。

受け継ぐもの:

| もの | 扱い |
|---|---|
| フィールドの名前と型 | 受け継ぐ |
| フィールドのデコレータ | 受け継ぐ。外せない。`Override` に付けたデコレータは、受け継いだものの後ろに、書かれた順に足す（同じデコレータを重ねれば DEC-13） |
| フィールドの説明（`DocComment`） | `Override` していないフィールドだけが受け継ぐ。`Override` したフィールドは受け継がない: `Override` に `DocComment` があればそれが説明になり、なければ説明なし。説明だけを変える `Override` は書けない（TYPE-16） |
| model の説明、model に付いたデコレータ | 受け継がない。D に書いたものだけ |

### 本体に書けるもの

| 書いたもの | 条件 | 満たさないとき |
|---|---|---|
| `Field`（`f: T;`） | f が B のフィールドにない（足すフィールド） | TYPE-14（元と同じ名前は `override` を書く） |
| `Override`（どの形でも） | f が B のフィールドにある。D の本体で f への `Override` は一度だけ | B にない（`extends` のない model、その場で書いた model を含む）なら TYPE-10。二度目は TYPE-16 |
| `override f;`（型を書かない） | デコレータが一つ以上付いている | TYPE-16（何も変えない。説明だけを変えるのも、ここに当たる） |
| `override f: T;` | T が、f の元の型から「変えられる型」（下）。T が元の型と等しいなら、デコレータが一つ以上付いている | 変えられない型は TYPE-15。等しい型で何も足さなければ TYPE-16 |
| `override f: never;` | デコレータも `DocComment` も付いていない | TYPE-16（なくすフィールドには何も足せない） |

「B のフィールド」は、B の作った後の並び。B がなくしたフィールドは B にないので、D で同じ名前の `Field` を足せる。

### 変えられる型

元の型 O を N に変えられるのは、次のどれか。4〜6 は再帰的に適用する。

1. N が O と等しい（型は変わらない。デコレータを足すために型も書いた場合）。
2. **広げる**: N が union（`arms`）への `ref` で、そのアームのどれかの型が O と等しい。
3. **差し替える**: N が O を継承している（上の定義。N と O が model への `ref`、または N が `scalar` への `ref` で O が `scalar` への `ref` か核の型）。
4. O が `optional(O')`、N が `optional(N')` で、O' を N' に 2〜6 で変えられる。
5. O が `array(O')`、N が `array(N')` で、O' を N' に 2〜6 で変えられる。
6. O が `record(K, V)`、N が `record(K, V')` で、V を V' に 2〜6 で変えられる。

これ以外の変更（必須を省略可能にする、省略可能を必須にする、関係のない型にする、union から元の型に戻す、など）は TYPE-15。

### 循環

`extends` を辿って自分に戻れば TYPE-10（位置は `extends` の後ろの名前）。循環に入った model は、元の model を持たないものとして残りの検査を続け、その本体の `Override` は重ねて報告しない。

## 絞り込み

分類のケースが `対象 as T`（`docs/grammar.md`「classify / condition」の `CaseTyping`）を持つとき、そのケースのアームの中で、対象は T の型になる。分類の側の規則（どの対象に書けるか、ケースがどう判定されるか）は `docs/check.md`「分類」。ここは型の規則。

### 絞り込める型

対象の型を S とする: 値の分類なら `subject` の型、op の分類ならその op の `returns`、状態の分類ならその状態の型（`State.type`）。`as` に書ける T は、次のどちらか。どちらでもなければ CLS-6（`docs/check.md`「classify / match」）。

1. T が S に渡せる（「互換」）。
2. S から `optional` を外した型が union（`arms`）への `ref` で、T がそのアームのどれかの型と等しい。アームの型は union の位置に渡せない（「互換」の「渡せないもの」）ので、絞り込みに限って認める。

### 型で決まる絞り込み

S を T に絞り込むとき、当たっているかを値の型だけで判定できるものを**型で決まる絞り込み**と呼ぶ。次の二つ。

| 名前（`CaseTyping.by`） | 条件 | 当たるとき |
|---|---|---|
| `presence` | S が `optional(T)` | 値がある |
| `variant` | S が union（`arms`）への `ref` で、T がそのアームのどれかの型と等しい | 値が、型 T のアーム |

それ以外（`string` を `Email` に、`string?` を `Email` に、`Item` を `Kind.Yamada<Item>` に、対象と同じ型に、など）は**述語の要る絞り込み**（`by` は `predicate`）: 型からは判定できず、そのケースの述語が真であることが根拠になる。

### アームの中の対象の型

`match` のアーム（ケースの並びを Ks とする）の中での対象の型。対象は、値を対象にした `match`（値の分類、op の分類、標準の分類）ならその `Atom`、状態の分類での `match by C` なら C の対象の状態のそれぞれ。対象の、アームの外での型を X とする。上から順に、最初に当たるもの。

1. `default` のアーム → X のまま。
2. 標準の分類で、`by nullable` の Ks が `HasItems` だけ → X が `optional(T)` なら T。それ以外（`Empty` のアーム、二つのケースを並べたアーム、`by list`）→ X のまま（空でない並びの型はない）。
3. Ks のすべてのケースがその対象の `as` を持ち、書いた型がすべて等しい（T とする）→ T。ただし X が T に渡せるなら X のまま（既に同じか、より狭い）。
4. 値の分類か op の分類で、3 に当たらない → `case(C, Ks, X)`（X が既に `case` なら、その `of` を使う）。型を書かないケースの、今までの絞り込み。
5. 状態の分類で、3 に当たらない → X のまま。

- 3 で絞り込んだ型は T そのもので、`case` にはならない。`C.K<…>` の位置（規則 5）には渡せず、T の位置に渡す。型を書いたケースと `C.Case<T>` は、どちらか一方で書く。
- 絞り込みが掛かるのは、アームの本体の中の、対象と同じ `Atom`（同じ束縛・引数・状態を指し、パスが等しいもの）と、それを先頭に持つ、より長いパス（`session.token`）。より長いパスの型は、絞り込まれた型から「式の型」の規則で辿る（`case` は `of` に戻してから）。呼び出しの引数のレコードリテラルの中の値にも掛かる。
- 対象が名前でない `Atom`（リテラル、レコードリテラル、`none`）なら、絞り込みは何にも掛からない。
- `bind` で埋まる位置（`Call.bound`）には掛からない。
- 状態を対象にした絞り込み（対象の `Atom` が状態、または `match by C`）では、アームの中のその状態の名前は、`match` が読んだ値を指す。
- 絞り込まれた型は `Match.arms[].narrowed`（`docs/ir.md`「配線」）に置く。

## 式の型

| 式 | 型 |
|---|---|
| 束縛名 | 束縛した式の型 |
| 引数名 | 引数の型 |
| 状態の名前（今の名前空間の状態。`docs/resolve.md`「手続き」） | その状態の型（`State.type`）: `list<T>` は `T[]`、`nullable<T>` は `T?`、`single<T>` は `T` |
| フィールド参照 `x.f` | x の型が model への `ref` なら、そのフィールドの型。x の型が `optional(model)` なら `optional(フィールドの型)`。それ以外は RES-3。x は束縛・引数・状態のどれでもよい |
| リテラル | リテラルの型 |
| `none` | `none` の型 |
| レコードリテラル | 当てはめる先が決まるまで未定。引数の位置、`return` の位置、`match` のアーム（下の「match の型」の 5・6）で決まる。位置が決まらない（`const x = { ... }`）なら TYPE-7 |
| op の呼び出し | 呼び出した op の `returns`。`null`（void）なら「値がない」（WIRE-2 で区別する）。`never` なら「返らない」 |
| `read` の呼び出し（`userByEmail(email)`） | その `read` の結果の型（`Read.returns`） |
| 効果の呼び出し（`effect` の宣言、直に呼ぶ `状態.操作(…)`） | 「値がない」 |
| `throw E`、`throw E(…)`（アームの本体） | 「返らない」 |
| `match` | 下の「match の型」 |

アームの中では、対象の型は「絞り込み」の「アームの中の対象の型」。

「返らない」式は、どの型の位置の `return` にも書ける（`return unauthorized();`、すべてのアームが `throw` の `return match ...`）。束縛はできず、文として書けるのは本体の最後だけ（WIRE-2、WIRE-9。`docs/check.md`「配線」）。

### match の型

1. アームごとに本体の型を決める: `Call` は呼び出しの型（op、`read`、効果のどれでも、上の表）、`Atom` はその型（そのアームの絞り込みを掛けた後）、`Throw` は「返らない」。
2. 「返らない」アームを除く。一つも残らなければ、`match` の型は「返らない」。
3. 残りに値のある本体（値のある呼び出し、`none` 以外の `Atom`）が一つもなければ（「値がない」と `none` だけなら）、`match` の型は「値がない」。
4. 値のある本体と「値がない」が混ざれば TYPE-8。
5. そろえる型 T を決める。上から順に、最初に当たるもの。
   1. 型の決まった本体（値のある呼び出し、名前の `Atom`）があれば、それらの型のうち、ほかのすべてが渡せる型（「互換」。等しい型は一つと数え、複数あればアームの順で最初のもの）。そういう型がなければ TYPE-8。
   2. リテラルの本体があり、リテラルの種類がすべて同じなら、対応する核の型（`string` / `int` / `float` / `boolean` / `Duration`）。種類が混ざれば TYPE-8（`int` と `float` も別の種類）。
   3. レコードリテラルと `none` しかなく、`match` が `return` の式なら、op の `returns` から `optional` を外した型。`return` の式でなければ TYPE-7。
6. リテラルとレコードリテラルの本体は、T に渡せること（規則 9・10。レコードリテラルは T に当てはめる）。渡せなければ、そのアームの位置に TYPE-8（T が `scalar` でリテラルを渡したなら TYPE-1）。
7. `match` の型は、`none` の本体があれば `optional(T)`（T が既に `optional` なら T）、なければ T。

5.1 は、すべての型が等しければその型になる（今までの規則と同じ結果）。`T` と `T?` のアームは `T?` に、絞り込んだ `case(C, [A], T)` と `T` のアームは `T` にそろう。

## 呼び出しの引数

配線の呼び出し（`docs/grammar.md`「配線」の `Call`）と、アームの本体の `throw E(…)` の引数は、呼び出し先の引数の並びに、位置で対応付ける。呼び出し先と、その引数の並び:

| 呼び出し先 | 引数の並び |
|---|---|
| op | `Op.params` |
| `read` | `Read.params` |
| 効果（`effect` の宣言） | `Effect.params` |
| 直に呼ぶ組み込みの効果（`状態.操作(…)`） | `docs/check.md`「直に呼ぶ組み込みの効果」の表: 値を取る操作は、型が状態の要素の型（`State.element`）の引数一つ（IR での名前は `value`）。`nullable` の `delete` は引数なし |
| `throw E(…)` | `Exception.params` |

どの呼び出し先でも、同じ規則で確かめる。

- 渡した値の数が引数の数を超えれば TYPE-4（位置は、超えた最初の値）。
- 値の型が、対応する引数の型に渡せなければ TYPE-4（「互換」。`scalar` の位置に核の型の値なら TYPE-1。アームの中の対象をそのまま渡していれば MATCH-4。`docs/check.md`「classify / match」）。
- 省略可能でない引数に値が渡されていなければ BIND-4（`docs/check.md`「必須の入力」）。`bind` で埋まるのは op の引数だけ。
- レコードリテラルは、引数の型の model に当てはめる（「当てはまる」）。

## デコレータの引数

`Application.args` の値が `Param.type` に合うかの規則。`docs/resolve.md` で種類が決まった後に適用する。

| `ParamType` | 受け付ける `ArgValue` |
|---|---|
| `type` の `Type` | `literal` で、リテラルの型が渡せるもの（`scalar` の位置には渡せない。TYPE-1）。`list` は `array` の位置に。`ref` で op の引数（`$param:`。`docs/resolve.md`「手続き」1.3）なら、その引数の型が渡せること |
| `any exception` | `ref`（例外）、`refs`（例外の集合）、`ref`（`set` のユニオンで要素が例外。展開して `refs` にする） |
| `any effect` | `ref`（効果）、`refs`、ユニオン（同上） |
| `any effect on s.op` | 上のうち、すべての効果の宛先（`Effect.target`）が組み込みの効果で、その `state` が `s`、`operation` が `op` のもの。遷移の効果や、違う状態・操作なら DEC-7 |
| `any state` | `ref`（状態） |
| `any op` | `ref`（op） |
| `any model` | `ref`（model） |
| `any variant` | `variant` |
| ユニオンへの `ref`（`error: ApiError`） | `ref` で、そのユニオンの `members` に含まれる例外か効果。`refs` なら全要素が含まれる。含まれなければ DEC-7 |

引数の数と名前:

- 必須の `Param` が渡されていなければ DEC-11。
- 宣言にない引数名、または位置で渡した引数が `Param` の数を超えれば DEC-11。
- 宣言が**残りの引数**（`Param.rest`。`docs/grammar.md`「decorator の宣言」の `RestParam`）を持てば、ほかの `Param` の数を超えて位置で渡した値は、書いた順に、残りの引数の値になる（0 個でもよい。`Application.args` では一つの `list`。`docs/ir.md`「デコレータの適用」）。値は一つずつ、残りの引数の `ParamType` で上の表を当てる。残りの引数に名前で渡せば DEC-11。
- 同じ引数に二度渡せば DEC-11。

## 診断

| ID | 重さ | 意味 |
|---|---|---|
| TYPE-1 | error | 核の型（リテラルを含む）の値を `scalar` の位置に渡した |
| TYPE-2 | — | `valid` の制約を `scalar` とフィールド以外に付けた（DEC-1 で検出されるので、ID は索引として残す） |
| TYPE-3 | error | `return` の値の型が op の `returns` に渡せない。「返らない」式は渡せる（「式の型」） |
| TYPE-4 | error | 引数の値の型が引数の型に渡せない（どの規則で失敗したかを示す）。または、渡した値の数が引数の数を超える。op、`read`、効果の呼び出しと、`throw` の引数（「呼び出しの引数」）、デコレータの引数の値（「デコレータの引数」） |
| TYPE-5 | error | レコードリテラルに、当てはめる model にないフィールドがある |
| TYPE-6 | error | レコードリテラルに同じフィールドが二度ある |
| TYPE-7 | error | レコードリテラルの当てはめる先が決まらない |
| TYPE-8 | error | `match` のアームの型がそろわない（「match の型」の 4〜6） |
| TYPE-9 | error | `scalar X extends B` の `B` が核の型でも `scalar` でもない。または `scalar` の継承が循環している |
| TYPE-10 | error | `override f` の `f` が元の model のフィールドにない（元の model を持たない model に書いた `override` を含む）。または model の `extends` が循環している（「継承した model」。`model P is U omit f` をなくす前は、`omit` の名前が元にないことと `is` の循環だった。同じ規則の、今の書き方での形） |
| TYPE-11 | error | `Record<K, V>` の `K` が `string` でも、元が `string` の `scalar` でもない |
| TYPE-12 | error | `C.Case<T>` の `T` が `C` の対象の型（値の分類は `subject` の型、op の分類はその op の `returns`）に渡せない |
| TYPE-14 | error | 継承した model の本体に、元の model のフィールドと同じ名前のフィールドを `override` なしで書いた（「本体に書けるもの」） |
| TYPE-15 | error | `override f: T` の T が、元の型から変えられる型でない（「変えられる型」）。元の型と、変えられる形をメッセージに示す |
| TYPE-16 | error | `override` の形が合わない: 何も変えない（型を書かないか元と等しい型で、デコレータを足していない。説明だけを変えるのも含む）、`never` にデコレータか説明を付けた、同じフィールドへの `override` が二度ある（「本体に書けるもの」） |
| LIT-1 | error | 整数リテラルが 64 ビット符号付きの範囲を超える。`Duration` がナノ秒で同じ範囲を超える |

TYPE-13 は欠番。「既定値のリテラルがフィールドの型（`scalar` なら元の型）に渡せない」という規則で、フィールドの既定値を言語からなくした（`docs/grammar.md`「決めたこと」）ときになくなった。番号は別の意味に使い回さない（欠番の一覧は `docs/requirements.md`「検査の規則の一覧」）。
