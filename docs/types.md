# 型

## この文書が決めること

値がどの位置に渡せるか（互換）、形の語と型の対応、継承した model、値を有限に作れない型、分類のケースでの絞り込み、式の型の決め方、呼び出しの引数の照合。`docs/ir.md` の `Type` の上で定義する。違反はこの文書の「診断」の `TYPE-*`。

## 型の種類

`docs/ir.md`「型」の通り。加えて、式にだけある型が四つある。IR の `Type` にはならない。

| 式の型 | 中身 |
|---|---|
| `none` の型 | `none` の型。どの `optional` にも入る |
| レコードリテラルの型 | フィールド名と値の型の組の列。model に照合して初めて型が決まる |
| 「値がない」 | 値を返さない（`void` の）op の呼び出しと、効果の呼び出し（`createOrder(order)`、`orders.post(order)`）の型。デコレータの本体の、包んだ関数の呼び出し（`next()`）も、「値がない」: 包んだ op が値を返しても、本体からは、受け取れない（`docs/grammar.md`「デコレータの本体」） |
| 「返らない」 | 決して値を返さない式の型: `never` を返す op の呼び出し、アームの本体の `throw`、すべてのアームが返らない `match`（「式の型」） |

この節の細部は、決定 D621 が決めた。

### never

`never` は、値が一つもない型。意味は、これ一つ（決定 D363）。書ける所は、四つで、どれも、この意味から読む。

| 書く所 | 読み方 | 決まりの持ち主 |
|---|---|---|
| 戻り値（`fn denied(): never throws Unauthorized;`） | 返る値がない: 返らない | `docs/check.md`「never を返す op」 |
| `override f: never;` | そのフィールドに入る値がない: フィールドがない | 「継承した model」の「フィールド」「本体に書けるもの」 |
| `classify C of never { … }` | 分類する値がない: 対象のない分類 | `docs/check.md`「分類」の「対象のない分類」 |
| `case of never` | 対象のない分類の、ケース | `docs/grammar.md`「decorator の宣言」 |

ほかの型の位置（フィールド、引数、`val`、`as` など）には、書けない。IR に現れる所は `docs/ir.md`「型」。

### 絞り込んだ型

`T on C.K` は、分類のケースで絞り込んだ型: 「`T` で、分類 `C` の、ケース `K` にあるもの」（決定 D368。綴りは `docs/grammar.md`「型」の `OnType`）。いくつかのケースを `|` で並べた `T on C.K1 | C.K2` は、「`K1` か `K2` にあるもの」。IR では `case(C, Ks, T)`（`docs/ir.md`「型」）。

- 型は、`T` のまま。絞り込みは、検査のための情報で、出力する言語では、ただの `T` になる。
- 並べるケースは、どれも、同じ分類 `C` のもので、同じケースを、二度は書かない。`C` は、値の分類か、op の分類（`docs/check.md`「分類」の「対象」。状態の分類と、対象のない分類は RES-4）。`T` は、`C` の対象の型（値の分類は `subject` の型、op の分類はその op の `returns`）に渡せること。どれかが合わなければ TYPE-12。
- 渡し方は「互換」の 4 と 5: 絞り込みを捨てて `T` の位置に渡せ、ケースが収まるなら、同じ分類の、より広い絞り込みの位置に渡せる。`T` の値は、`T on C.K` の位置に渡せない。
- この型の値が作られるのは、`match (x by C)` のアームの中の対象（「絞り込み」の「アームの中の対象の型」）。引数、`val`、`for` の変数、戻り値、フィールドに、この型を書けば、その先へ運べる。
- 診断のメッセージと、ホバーは、この型を、仕様の綴りで出す（`Order on Stage.Draft | Stage.Accepted`。診断は、分類を FQN で）。`optional` と `array` の中にあるときは、`nullable<T on C.K>`、`list<T on C.K>`（`on` の後ろに `?` と `[]` を続けられないため。`docs/grammar.md`「型」）。

この節の細部は、決定 D621 が決めた。

### リテラルの型

リテラルの型は、値が、そのリテラル一つだけの型（`docs/ir.md`「型」の `literal`。決定 D482）。リテラルの式の型（「式の型」）と、型の位置に書いたリテラル（`docs/grammar.md`「型」の `LiteralType`）は、同じ型。

- **種類は四つ**: 文字列（`"error"`）、整数（`0`、`-1`）、小数（`1.5`）、真偽（`true`、`false`）。`duration` のリテラル（`5m`）の型は、式にだけあり、型の位置には書けない（`docs/grammar.md`「決めたこと」）。
- **対応する核の型**: 文字列は `string`、整数は `int`、小数は `float`、真偽は `boolean`、`duration` のリテラルは `duration`。
- **書ける所**: `Type` を書けるどの位置にも（フィールド、引数、戻り値、union のアーム、`T?` と `T[]` の中）。`scalar X extends "a"` は書けない（TYPE-9: `scalar` の元は、核の型か `scalar`）。
- **値の集まり**は、リテラルの型をアームに持つ union（`arms`）で書く（`union Severity { Error: "error"; Warning: "warning"; }`）。一つの union の、二つのアームが、等しいリテラルの型を持てば UNION-2: 値から、どちらのアームかを、決められない。
- **閉じた型**: `boolean`（値は `true` と `false` の二つ）と、union（`arms`）は、値の種類が、宣言で尽きる。リテラルの型で分類できるのは、閉じた型だけ（`docs/check.md`「ケースの型」の CLS-11）。
- 値が、そのリテラルであることを、どこで確かめるかは、出力する側が決める（Go は `docs/plugin-go.md`「型」）。

この節の細部は、決定 D764 が決めた。

## 形の書き方

型の、もとの形は、形の語（`docs/grammar.md`「型」）で書いた `single<T>`、`nullable<T>`、`list<T>`。`T`、`T?`、`T[]` は、その省略形（決定 D355、D361）。どの `Type` の位置にも、どちらでも書け、同じ型になり、IR には一つの形だけが残る（`docs/ir.md`「正規化」）。

| もとの形 | 省略形 | IR |
|---|---|---|
| `single<T>` | `T` | T そのもの |
| `nullable<T>` | `T?` | `optional(T)` |
| `list<T>` | `T[]` | `array(T)` |

- その場で書く union（`T | null`、`T | none`）は、ない: 値がないことは、`nullable<T>` か、その省略の `T?` で言う。
- デコレータの引数の、省ける印の `?`（`docs/grammar.md`「decorator の宣言」の `ParamType`）も、同じ省略: `who: any case of Order?` は、引数の型の全体を、`nullable` で包んだ形。

- 入れ子も同じ規則で読む: `single<T?>` は `T?`、`nullable<T?>` は `T??` で、`T?` に正規化される（`optional` は入れ子にしない）。`list<T>?` と `nullable<list<T>>` は同じ `optional(array(T))`。
- 状態の型（`state 名前: Type;` の `Type`）も同じ。状態の形（`list` / `nullable` / `single`）は、この型の最も外側から決まる（`docs/check.md`「状態の形」）。
- 型の表示（診断、ホバー）は `T?` と `T[]` で書く。状態の宣言の見出しだけは形の語で書く（`docs/lsp.md`「ホバー」）。

## 等しい

二つの `Type` は、構造が等しければ等しい。`ref` は FQN が等しいとき。`case` は `classify` と `cases` の集合と `of` が等しいとき。`literal` は、リテラルの種類と値が等しいとき（整数の `1` と、小数の `1.0` は、等しくない）。

この節の細部は、決定 D765 が決めた。

## 互換

S の値を T の位置に渡せるのは、次のどれかを満たすとき。再帰的に適用する。

1. S と T が等しい。
2. T が `optional(T')` で、S が T' に渡せる。
3. S が `none` の型で、T が `optional`。
4. S が `case(C, cases, of)` で、T が `of`（絞り込みを捨てる）。
5. S が `case(C, s, of)`、T が `case(C, t, of)` で、s ⊆ t（§10.2「まとめたアームではケースの和の型」。狭い方は広い方に渡せる）。
6. S が `array(S')`、T が `array(T')` で、S' が T' に渡せる。
7. （欠番。`Record<K, V>` どうしの規則だった。なくした: キーが決まっていない構造は、インデックスの model で、ほかの model と同じに、名前で比べる。「インデックスの model」）
8. （欠番。model から model への射影の規則だった。なくした。下の「渡せないもの」）
9. S がレコードリテラルで、T が model への `ref`（または model の `optional`）で、リテラルが T に**当てはまる**（下）。
10. S がリテラルの型（「リテラルの型」）で、T が対応する核の型（`string`→`string`、`int`→`int` または `float`、`float`→`float`、`boolean`→`boolean`、`duration`→`duration`）。リテラルの式を渡すときも、リテラルの型の値（`severity: "error"` のフィールドの値）を渡すときも、同じ。`datetime`、`date`、`time` には、リテラルがない（`docs/grammar.md`「決めたこと」）。
11. S が `scalar` への `ref` で、S の `base` が T に渡せる（`Email` を `string` に。値の型は元の型の部分集合）。
12. S が `optional(S')`、T が `optional(T')` で、S' が T' に渡せる（6 と同じことを、`optional` に。`nullable<Order on Stage.Draft>` を `Order?` に: 型を書いたケースのアームと `none` のアームを持つ `match` の値を、`T?` の位置に渡せる。「match の型」の 7）。
13. S が整数のリテラルの型で、T が、同じ値の、小数のリテラルの型（`1` を `1.0` の位置に。10 の `int`→`float` と同じ向き）。種類も値も同じリテラルの型は、等しい（1）ので、リテラルの式 `"error"` は、型 `"error"` の位置に渡せる。
14. **union に入れる**（決定 D484）: T（か、`optional(T)` の中の型）が、アームを持つ union（`arms`）への `ref` で、S が、そのアームの**ちょうど一つ**の型に、規則 1〜13 で渡せる（`union Severity { Error: "error"; Warning: "warning"; }` の位置に、リテラルの式 `"error"`。`union Pet { D: Dog; C: Cat; }` の位置に、`Dog` の値と、`Dog` に当てはまるレコードリテラル）。どのアームに入るかは、値の型から決まる（下の「union に入れる」）。

規則の番号は使い回さない（ほかの文書とコードが番号で引くため）。

渡せないもの（明示）:

- model の値を、別の model の位置に渡す。フィールドが同じでも、一方がもう一方を継承していても（「継承した model」）、別の型で、どちらの向きにも渡せない（引数なら TYPE-4、`return` なら TYPE-3）。設計書 §7.1「出力は宣言した型に自動で射影される」はやめた（決定 S22）。別の model の値が要るところでは、写す op を呼ぶ: 仕様の上では普通の葉の op（`fn toPublicUser(user: User): PublicUser;`）で、人が中身を書く。
- 核の型の値を `scalar` の位置に渡す（TYPE-1。§6.5「元の型の値を値の型の位置に渡すには、検証を通す必要がある」）。配線でその手段になるのは、述語の要る絞り込み（「絞り込み」。`string` の対象を `Email` にするケース）だけで、それ以外の位置では常にエラー。
- 核の型の値を、リテラルの型の位置に渡す（`string` の値を `"error"` の位置に）。値が違うリテラルの型どうしも、渡せない（`"warning"` を `"error"` の位置に）。引数なら TYPE-4、`return` なら TYPE-3。
- リテラルの型の値を `scalar` の位置に渡す（TYPE-1。核の型の値と同じ）。
- `scalar` の値を別の `scalar` の位置に渡す（`Token` を `UserId` に）。元の型が同じでも別の型。
- `union`（`arms`）の位置に、アームの**二つ以上**の型に渡せる値を渡す（TYPE-20。下の「union に入れる」）。アームの、どの型にも渡せない値は、ほかの型と同じ（引数なら TYPE-4、`return` なら TYPE-3）。前は、アームの型の値を、union の位置に、直接は渡せなかった（配線に、union の値を作る手段がなかった）: 決定 D484 が、置き換えた。
- `union`（`set`）は値の型ではない。型の位置に書いたら RES-4。

この節の細部は、決定 D765 が決めた。

### union に入れる

規則 14 の細部（決定 D484）。

- **入れられる位置**は、値を、型の決まった位置に置く所: 呼び出しの引数（op、`read`、効果、`throw` の例外の引数）、`return` の式、レコードリテラルのフィールドの値、型を書いた `val` に入れる式（宣言の式と、値を入れる文）、型を書いた `val` に集める式、デコレータの引数。
- **入れない所**: `match` のアームの本体を、`match` の型にそろえるとき（「match の型」の 5 と 6）と、型を書いていない `val` の型を、入れる式からそろえるとき（「val の型」）は、規則 14 を使わない。`match` の型が決まった後、その値を、上の位置に置くときには、使う（`return match (…) { … };` の `match` の型が `Dog` で、戻り値の型が `Pet` なら、入る）。絞り込みの検査（「絞り込める型」）、分類の対象の型の検査（MATCH-6、TYPE-12）にも、使わない。
- **アームの決め方**: union のアームを、宣言の順に見て、S が、規則 1〜13 で渡せる型のアームを数える。レコードリテラルは、アームの型（`optional` を外した型）が model で、その model に当てはまる（下の「当てはまる」の 1 と 3: フィールドがあり、値が渡せる。必須のフィールドが埋まっているかは、アームが決まった後に見る: BIND-4）ものを数える。
  - ちょうど一つなら、そのアームに入る。
  - 二つ以上なら TYPE-20（位置は、渡した値。メッセージに、当たったアームの名前を並べる）。`union U { A: string; B: "x"; }` の位置の `"x"` は、`A` にも `B` にも渡せるので、TYPE-20。
  - 一つもなければ、渡せない（今までの診断: TYPE-4、TYPE-3、TYPE-17、DEC-7 など）。
- **重ねない**: アームの型に渡せるかは、規則 1〜13 だけで見る（規則 14 を、もう一度は使わない）。アームの型が、別の union でも、その中のアームまでは、辿らない（`Dog` は、`union Pet { A: Animal; }`、`union Animal { D: Dog; }` の `Pet` の位置には、渡せない）。`array` の要素（`Dog[]` を `Pet[]` に）と、`optional` どうし（`Dog?` を `Pet?` に）にも、広げない: 規則 6 と 12 の中では、規則 14 を使わない。`Dog` を `Pet?` の位置に渡すのは、規則 14 の「`optional(T)` の中の型」で、入る。
- **IR**: 入れた位置は、どのアームに入るかを、`arm`（`docs/ir.md`「配線」の `ArmRef`）で持つ。プラグインは、型から、アームを計算し直さない。デコレータの引数（`Application.args`）は、値だけを持ち、`arm` を持たない。
- 逆の向き（union の値を、アームの型に絞る）は、今までどおり、`match` の絞り込みだけ（「絞り込める型」）。

この節の細部は、決定 D772、D773、D774 が決めた。

### 当てはまる（レコードリテラルを model T に）

- リテラルの各フィールドが T にあり、値の型が T のフィールドの型に渡せる。T にないフィールドがあれば TYPE-5。
- T の必須のフィールド（`optional` でない）が、リテラルにあるか、`bind` で埋まる位置（`Call.bound` のパス）である。なければ BIND-4（`docs/check.md`）。
- 同じフィールドが二度あれば TYPE-6。

## 継承した model

`model D extends B { ... }`（`docs/grammar.md`「model」）の D を**継承した model**、B を D の**元の model**と呼ぶ。D は B とは別の型で、D と B の間に互換はない（「互換」の「渡せないもの」）。元の model になれるのは `model` の宣言（別の名前空間のもの、語彙のもの、継承した model でもよい）。その場で書いた model は名前で書けないので、元の model になれない。

型 X が型 Y を**継承している**とは、次のどちらか。X と Y が等しいときは含まない。

- X と Y が model で、X の元の model を一回以上辿ると Y に着く。
- X が `scalar` で、X の `extends` を一回以上辿ると Y（`scalar` か核の型）に着く。

### フィールド

D のフィールド（`Model.fields`）は、次の順に作る。IR には作った後の並びだけが残る（`docs/ir.md`「正規化」）。

1. B のフィールドを B の並びのまま写す（B が継承した model なら、B の作った後の並び）。
2. D の本体の `Override` を当てる: なくす（`never`）ならそのフィールドを除く。型を書いていれば、その位置のまま型を差し替える。デコレータは、その位置のフィールドに足す。説明は、`Override` に書いたものに置き換える（書いていなければ、説明なしになる）。
3. D の本体の `Field`（足すフィールド）を、書かれた順に末尾に足す。

受け継ぐもの:

| もの | 扱い |
|---|---|
| フィールドの名前と型 | 受け継ぐ |
| フィールドのデコレータ | 受け継ぐ。外せない。`Override` に付けたデコレータは、受け継いだものの後ろに、書かれた順に足す（同じデコレータを重ねれば DEC-13） |
| フィールドの説明（`DocComment`） | `Override` していないフィールドだけが受け継ぐ。`Override` したフィールドは受け継がない: `Override` に `DocComment` があればそれが説明になり、なければ説明なし。説明だけを変える `Override` は書けない（TYPE-16） |
| model の説明、model に付いたデコレータ | 受け継がない。D に書いたものだけ |

### 本体に書けるもの

| 書いたもの | 条件 | 満たさないとき |
|---|---|---|
| `Field`（`f: T;`） | f が B のフィールドにない（足すフィールド） | TYPE-14（元と同じ名前は `override` を書く） |
| `Override`（どの形でも） | f が B のフィールドにある。D の本体で f への `Override` は一度だけ | B にない（`extends` のない model、その場で書いた model を含む）なら TYPE-10。二度目は TYPE-16 |
| `override f;`（型を書かない） | デコレータが一つ以上付いている | TYPE-16（何も変えない。説明だけを変えるのも、ここに当たる） |
| `override f: T;` | T が、f の元の型から「変えられる型」（下）。T が元の型と等しいなら、デコレータが一つ以上付いている | 変えられない型は TYPE-15。等しい型で何も足さなければ TYPE-16 |
| `override f: never;` | デコレータも `DocComment` も付いていない | TYPE-16（なくすフィールドには何も足せない） |

「B のフィールド」は、B の作った後の並び。B がなくしたフィールドは B にないので、D で同じ名前の `Field` を足せる。

### 変えられる型

元の型 O を N に変えられるのは、次のどれか。4 と 5 は再帰的に適用する。

1. N が O と等しい（型は変わらない。デコレータを足すために型も書いた場合）。
2. **広げる**: N が union（`arms`）への `ref` で、そのアームのどれかの型が O と等しい。
3. **差し替える**: N が O を継承している（上の定義。N と O が model への `ref`、または N が `scalar` への `ref` で O が `scalar` への `ref` か核の型）。
4. O が `optional(O')`、N が `optional(N')` で、O' を N' に 2〜5 で変えられる。
5. O が `array(O')`、N が `array(N')` で、O' を N' に 2〜5 で変えられる。
6. （欠番。`Record<K, V>` の値の型を変える規則だった。なくした: 「インデックスの model」）

これ以外の変更（必須を省略可能にする、省略可能を必須にする、関係のない型にする、union から元の型に戻す、など）は TYPE-15。

### 循環

`extends` を辿って自分に戻れば TYPE-10（位置は `extends` の後ろの名前）。循環に入った model は、元の model を持たないものとして残りの検査を続け、その本体の `Override` は重ねて報告しない。

## インデックスの model

本体にインデックスを書いた model（`model Attrs { [name: string]: string[]; }`。`docs/grammar.md`「model」）は、キーが決まっていない構造: キーから、値を引く。`Record<K, V>` の置き換え（決定 D360）。

- **キーの型**は、`string` か、元が `string` の `scalar`。違えば TYPE-11。**値の型**は、どの型でもよい（`[sku: Sku]: int?;`）。入れ子にするときは、値の型に、別のインデックスの model の名前を書く。
- **フィールドを持たない。** `x.f` のパス（「式の型」）は、インデックスの model の値の先には、書けない（RES-3: そのフィールドは、ない）。`for` の並びにも、`match (x by list)` の対象にも、ならない（並びではない: TYPE-17、MATCH-7）。配線に、キーで値を引く書き方は、ない: 引くのは、葉の op の中身。
- **ほかの model と同じに、名前で比べる。** 別の model の位置には、キーと値の型が同じでも、渡せない（「互換」の「渡せないもの」）。
- **レコードリテラルは、空（`{}`）だけが、当てはまる**（空の構造）。フィールドを書いたリテラルは、T にないフィールドなので、TYPE-5（「当てはまる」）。
- **継承できない。** インデックスの model を、`extends` の元にすれば、TYPE-10。`extends` を持つ model の本体に、インデックスは書けない（SYNTAX。`docs/grammar.md`「model」）。
- デコレータは、model の宣言に付ける（`for model`）。インデックスそのものには、付けられない。

この節の細部は、決定 D601 が決めた。

## 値を、有限に作れない型

決定 D403。値を、有限に作れない型の宣言は、TYPE-19。`model A { a: A; }` の値は、必ず、もう一つの `A` を持つので、終わりがない。どの言語に出すかに、よらない。

**有限の値を持てるか**は、型ごとに、次の表で決まる。

| 型 | 有限の値を、持てるか |
|---|---|
| 核の型、scalar | 持てる |
| `T?`、`T[]` | 持てる（値がない。空の並び） |
| インデックスの model（「インデックスの model」） | 持てる（空の構造） |
| model（その場で書いた合成 model を含む） | 省略できないフィールドの型が、どれも持てれば、持てる |
| アームを持つ union | アームの型の、どれか一つが持てれば、持てる |
| 絞り込んだ型 `T on C.Ks` | `T` が持てれば、持てる |

- **決め方**: はじめは、どの model と union も、「持てない」とする。上の表で、「持てる」と決まるものを、変わるものがなくなるまで、「持てる」に移す。残った model と union が、有限の値を持てない型。辿る回数の上限は、置かない: 型は、宣言したものだけなので、辿る先は、宣言の数で止まる。
- **名前空間を、またぐかは、見ない**（`a.X { y: b.Y; }` と `b.Y { x: a.X; }` も、同じ理由で、持てない）。
- **有限に作れる型は、輪があっても、書ける**: `model A { a: A?; }`、`model Node { children: Node[]; }`、`union Tree { Leaf: {}; Fork: { left: Tree; right: Tree; }; }`（`Leaf` で終われる）。そういう型を、扱えないプラグインは、自分の診断で止める（基底 `go` は、型どうしが、名前空間をまたいで輪になると、GO-3: `docs/plugin-go.md`「パッケージと import パス」）。
- **報告は、互いに辿り合える宣言のまとまりごとに、一つ。** 持てない型が、省略できないフィールドと、アームを辿って、互いに行き着けるまとまり（輪が、いくつ重なっていても、一つ）ごとに、TYPE-19 を一つ出す。位置は、そのまとまりの中で、最初に現れる宣言の名前（その場で書いた model なら、その本体）。メッセージは、そこから、自分に戻る、いちばん短い道（フィールドとアームの名前）を示し、`Related` に、その道の上の宣言を並べる。輪に入らず、持てない型を、省略できないフィールドに持つだけの宣言（`model B { a: A; }`）には、重ねて出さない。
- **見ないもの**: 例外や効果の集合の union（値の型でない）、アームを一つも持たない union、解決できなかった型の参照（RES-* が出ている）、`extends` の循環（TYPE-10。「継承した model」の「循環」）。

この節の細部は、決定 D676 が決めた。

## 絞り込み

分類のケースが `対象 as T`（`docs/grammar.md`「classify」の `CaseTyping`）を持つとき、そのケースのアームの中で、対象は T の型になる。分類の側の規則（どの対象に書けるか、ケースがどう判定されるか）は `docs/check.md`「分類」。ここは型の規則。

### 絞り込める型

対象の型を S とする: 値の分類なら `subject` の型、op の分類ならその op の `returns`、状態の分類ならその状態の型（`State.type`）。`as` に書ける T は、次のどちらか。どちらでもなければ CLS-6（`docs/check.md`「classify / match」）。

1. T が S に渡せる（「互換」）。
2. S から `optional` を外した型が union（`arms`）への `ref` で、T がそのアームのどれかの型と等しい。アームの型は union の位置に渡せない（「互換」の「渡せないもの」）ので、絞り込みに限って認める。

T がリテラルの型のときは、加えて、S が、その型で分けられる型でなければならない（CLS-11。`docs/check.md`「ケースの型」）。

### 型で決まる絞り込み

S を T に絞り込むとき、当たっているかを値の型だけで判定できるものを**型で決まる絞り込み**と呼ぶ。次の三つ。

| 名前（`CaseTyping.by`） | 条件 | 当たるとき |
|---|---|---|
| `presence` | S が `optional(T)` | 値がある |
| `variant` | S が union（`arms`）への `ref` で、T がそのアームのどれかの型と等しい（T が、リテラルの型のアームでも、同じ） | 値が、型 T のアーム |
| `literal` | S から `optional` を外した型が `boolean` で、T が `true` か `false`（「リテラルの型」） | 値が、そのリテラル |

それ以外（`string` を `Email` に、`string?` を `Email` に、`Item` を `Item on Kind.Yamada` に、対象と同じ型に、など）は**述語の要る絞り込み**（`by` は `predicate`）: 型からは判定できず、そのケースの述語が真であることが根拠になる。

型の代わりに `else` を書いた `対象 as else`（残りのケース。`docs/check.md`「残りのケース」）は、絞り込む先の型を書かない。`by` は `else` で、当たるのは、値が、ほかのケースの型で決まる絞り込みのどれにも当たらないとき。

型の代わりに `none` を書いた `対象 as none`（ない側のケース。`docs/check.md`「ない側のケース」）も、絞り込む先の型を書かない。`by` は `none` で、当たるのは、値がないとき。

この節の細部は、決定 D768 が決めた。

### 残りのケースでの対象の型

残りのケース（`docs/check.md`「残りのケース」）と、`as none` のケース（同「ない側のケース」）が成り立つときの、対象の型（`CaseTyping.type`）。S は対象の型で、絞り込みは、その分類のほかのケースのもの。

| 絞り込み | 型 |
|---|---|
| `presence`（`as none` のケースは、いつもこの行） | S のまま。値がないことを表す型はない（標準の分類 `nullable` の `None` と同じ） |
| `variant` で、残りのアームがちょうど一つ | そのアームの型 |
| `variant` で、残りのアームが二つ以上 | S のまま。union の一部のアームだけを表す型はない |
| `literal` | S のまま（残りが、もう一方の真偽の値だけでも） |

残りのアームは、型が、ほかのケースが `as` に書いた型のどれとも等しくないアーム（`docs/check.md`「残りのケース」）。

この節の細部は、決定 D768 が決めた。

### アームの中の対象の型

`match` のアームの中での対象の型。アームが受けるケースの並びを Ks とする: 名前で並べたアームなら並べたケース、`else` のアームなら、ほかのアームが並べなかったケース（`docs/check.md`「アームが受けるケース」）。対象は、値を対象にした `match`（値の分類、op の分類、標準の分類）ならその `Atom`、状態の分類での `match (by C)` なら C の対象の状態のそれぞれ。対象の、アームの外での型を X とする。上から順に、最初に当たるもの。

1. 標準の分類で、`by nullable` の Ks が `Some` だけ → X が `optional(T)` なら T。それ以外（`None` のアーム、二つのケースを並べたアーム、`by list`）→ X のまま（空でない並びの型はない）。
2. 状態の分類で、Ks のすべてのケースがその状態の `as` を持ち、その型がすべて等しい（T とする）→ T。ただし X が T に渡せるなら X のまま。そうでなければ X のまま。`as` の型は、型を書いたケースなら書いた型、残りのケース（`as else`）と `as none` のケースなら「残りのケースでの対象の型」。
3. 値の分類か op の分類 → `case(C, Ks, B)`（`B on C.Ks`。「型の種類」の「絞り込んだ型」。決定 D370）。もとの型 B は、X から絞り込みを捨てた型を X′ として:
   1. `else` のアームで、Ks が二つ以上 → X′。
   2. Ks のすべてのケースが対象の `as` を持ち、その型がすべて等しい（T とする）→ T。ただし X′ が T に渡せるなら X′（既に同じか、より狭い）。`as` の型の決め方は、2 と同じ。T が、もう、絞り込んだ型（`Passed: Order as Order on Stage.Accepted;`）なら、アームの中の対象の型は、`case(C, Ks, …)` にせず、T そのもの。
   3. それ以外 → X′。

- 3 は、型を書いたケース（`Draft: Order? as Order;`）のアームにも掛かる: 対象は `Order on Life.Draft`。絞り込みを捨てて、`Order` の位置にも渡せる（「互換」の 4）。
- Ks がちょうど一つの `else` のアームは、そのケースを名前で書いたアームと同じ（3.2、3.3）: `match (user by Registration) { Unregistered => throw NotFound; else => greet(user); }` の `else` は `Registered` だけを受け、`user` は、`Registered` のアームと同じ型。
- 3.1 の `else` のアームは、Ks のすべてが同じ型の `as` を持っていても、もとの型を変えない: `else` は、どのケースかを書いていないので、ケースを足したときに、アームの中の、もとの型が黙って変わらないようにする。変わるのは、受けるケースの並びだけで、分類にケースを足せば、並びが広がり、足りていた呼び出しが、渡せなくなる（TYPE-4、MATCH-4。黙って通ることはない）。
- X が、もう、別の分類で絞り込んだ型のとき、前の絞り込みは、残らない（3 は、絞り込みを捨てた X′ から作る）。二つの分類の絞り込みを、同時に持つ型は、ない: `order: Order on Stage.Accepted` を、`match (order by Urgency)` のアームの中で、`Order on Stage.Accepted` の引数に、渡せない（MATCH-4）。渡すなら、`match` の外で渡すか、別の `val` に受けてから `match` する（`docs/open.md`「言語」）。
- 残りのケースだけのアームは、3.2 の `as` の型が、絞り込みが `presence` なら X のまま、`variant` で残りのアームがちょうど一つなら、そのアームの型になる（「残りのケースでの対象の型」）。
- 絞り込みが掛かるのは、アームの本体の中の、対象と同じ `Atom`（同じ `val`・`for` の変数・引数・状態を指し、パスが等しいもの）と、それを先頭に持つ、より長いパス（`session.token`）。より長いパスの型は、絞り込まれた型から「式の型」の規則で辿る（`case` は `of` に戻してから）。呼び出しの引数のレコードリテラルの中の値にも掛かる。
- 対象が名前でない `Atom`（リテラル、レコードリテラル、`none`）なら、絞り込みは何にも掛からない。
- `bind` で埋まる位置（`Call.bound`）には掛からない。
- 状態を対象にした絞り込み（対象の `Atom` が状態、または `match (by C)`）では、アームの中のその状態の名前は、`match` が読んだ値を指す。
- 絞り込まれた型は `Match.arms[].narrowed`（`docs/ir.md`「配線」）に置く。

この節の細部は、決定 D620 が決めた。

### ケースが分かっている値

配線の値（`Atom`）が、分類 C の**ケース Ks にあると分かっている**のは、その値の型が `case(C, Ks, …)` のとき。道は、型の一つだけ（決定 D370）。行の引数を絞り込んだ効果を呼べるかも、これで決まる（`docs/check.md`「行の遷移」の「呼ぶ側」）。

- その型を持つのは、`match (x by C)` のアームの中の対象（「アームの中の対象の型」の 3）と、その型を書いた `val`、`for` の変数、引数（`fn f(order: Order on Stage.Accepted)`）。
- より長いパス（`shipment.order`）や、対象から作った別の値（葉の op の戻り値）は、型が `case(C, …)` でなければ、分かっていない。検査器は、配線の行をまたいで値を追わない。
- アームは入れ子にならない（アームの本体は、呼び出し一つ。`docs/grammar.md`「配線」）ので、アームの中の対象に掛かる絞り込みは、その呼び出しを本体に持つアーム一つの分。

## 式の型

| 式 | 型 |
|---|---|
| `val` の名前 | 下の「val の型」 |
| `for` の変数（`for (val v of 並び)`） | 並びの型が `list<T>` なら `T`。`list` でなければ（`optional` の並びを含む）TYPE-17 |
| 引数名 | 引数の型 |
| 状態の名前（今の名前空間の状態。`docs/resolve.md`「手続き」） | その状態の型（`State.type`）: `list<T>` は `T[]`、`nullable<T>` は `T?`、`single<T>` は `T` |
| フィールド参照 `x.f` | x の型が model への `ref` なら、そのフィールドの型。x の型が `optional(model)` なら `optional(フィールドの型)`。それ以外は RES-3。x は `val`・`for` の変数・引数・状態のどれでもよい |
| リテラル | リテラルの型 |
| `none` | `none` の型 |
| レコードリテラル | 当てはめる先が決まるまで未定。引数の位置、`return` の位置、型を書いた `val` に入れる位置（`val x: T = { … }`、`x = { … }`、`xs collect { … }`。当てはめる先は、「val の型」の 1）、`match` のアーム（下の「match の型」の 5・6）で決まる。位置が決まらない（型を書かない `val x = { ... }`）なら TYPE-7 |
| op の呼び出し | 呼び出した op の `returns`。`null`（void）なら「値がない」（WIRE-2 で区別する）。`never` なら「返らない」 |
| `read` の呼び出し（`userByEmail(email)`） | その `read` の結果の型（`Read.returns`） |
| 効果の呼び出し（`effect` の宣言、直に呼ぶ `状態.操作(…)`） | 「値がない」 |
| `throw E`、`throw E(…)`（アームの本体） | 「返らない」 |
| `match` | 下の「match の型」 |

アームの中では、対象の型は「絞り込み」の「アームの中の対象の型」。

「返らない」式は、どの型の位置の `return` にも書ける（`return unauthorized();`、すべてのアームが `throw` の `return match ...`）。`val` には受けられず（`=`、`collect` も）、文として書けるのは、本体（いちばん外のブロック）の最後だけ（WIRE-2、WIRE-9。`docs/check.md`「配線」）。

### val の型

`val`（`docs/check.md`「値の入れ物」）の型は、宣言に書いた型か、入れる式から導いた型。合わなければ TYPE-17。

1. **型を書いた `val`**（`val x: T;`、`val x: T = 式;`）の型は、T。
   - 値と一緒の宣言と、値を入れる文（`x = 式;`）の式の型は、T に渡せる（「互換」）。レコードリテラルは、T に当てはめる。
   - 集める文（`x collect 式;`）があれば、T は `list<U>` で、式の型は、U に渡せる。レコードリテラルは、U に当てはめる。
2. **型を書かない `val`** の型は、入れる式から導く。
   - 値と一緒の宣言（`val x = 式;`）と、値を入れる文なら、その式の型。レコードリテラルは、当てはめる先がないので TYPE-7。
   - 集める文なら、`list<U>`。U は、その `val` に集める文の式の型のうち、ほかのすべてが渡せる型（「match の型」の 5.1 と同じ決め方）。そういう型がなければ TYPE-17。レコードリテラルは TYPE-7。
3. 値を入れる文も、集める文もない、空の `val` は、型が決まらない（WIRE-12）。

- `val` を読めるのは、代入が済んだ後（WIRE-10）なので、読む所では、型は、決まっている。
- 絞り込んだ型（`case(C, Ks, T)`）の式を入れた `val` は、その型を持つ（「ケースが分かっている値」）。

この節の細部は、決定 D583 が決めた。

### match の型

1. アームごとに本体の型を決める: `Call` は呼び出しの型（op、`read`、効果のどれでも、上の表）、`Atom` はその型（そのアームの絞り込みを掛けた後）、`Throw` は「返らない」。
2. 「返らない」アームを除く。一つも残らなければ、`match` の型は「返らない」。
3. 残りに値のある本体（値のある呼び出し、`none` 以外の `Atom`）が一つもなければ（「値がない」と `none` だけなら）、`match` の型は「値がない」。
4. 値のある本体と「値がない」が混ざれば TYPE-8。
5. そろえる型 T を決める。上から順に、最初に当たるもの。
   1. 型の決まった本体（値のある呼び出し、名前の `Atom`）があれば、それらの型のうち、ほかのすべてが渡せる型（「互換」。等しい型は一つと数え、複数あればアームの順で最初のもの）。そういう型がなければ、それぞれの型から絞り込みを捨てた型で、同じことをする（`T on C.A` と `T on C.B` のアームは `T` にそろう）。それでもなければ TYPE-8。
   2. リテラルの本体があり、リテラルの種類がすべて同じなら、対応する核の型（`string` / `int` / `float` / `boolean` / `duration`）。種類が混ざれば TYPE-8（`int` と `float` も別の種類）。
   3. レコードリテラルと `none` しかなく、`match` が `return` の式なら、op の `returns` から `optional` を外した型。型を書いた `val` に入れる式（「val の型」の 1）なら、その当てはめる先の型から `optional` を外した型。どちらでもなければ TYPE-7。
6. リテラルとレコードリテラルの本体は、T に渡せること（規則 9・10。レコードリテラルは T に当てはめる）。渡せなければ、そのアームの位置に TYPE-8（T が `scalar` でリテラルを渡したなら TYPE-1）。
7. `match` の型は、`none` の本体があれば `optional(T)`（T が既に `optional` なら T）、なければ T。

5.1 は、すべての型が等しければその型になる（今までの規則と同じ結果）。`T` と `T?` のアームは `T?` に、絞り込んだ `case(C, [A], T)` と `T` のアームは `T` にそろう。

## 呼び出しの引数

配線の呼び出し（`docs/grammar.md`「配線」の `Call`）と、アームの本体の `throw E(…)` の引数は、呼び出し先の引数の並びに、位置で対応付ける。呼び出し先と、その引数の並び:

| 呼び出し先 | 引数の並び |
|---|---|
| op | `Op.params` |
| `read` | `Read.params` |
| 効果（`effect` の宣言） | `Effect.params` |
| 直に呼ぶ組み込みの効果（`状態.操作(…)`） | `docs/check.md`「直に呼ぶ組み込みの効果」の表: 値を取る操作は、型が状態の要素の型（`State.element`）の引数一つ（IR での名前は `value`）。`nullable` の `delete` は引数なし |
| `throw E(…)` | `Exception.params` |

どの呼び出し先でも、同じ規則で確かめる。

- 渡した値の数が引数の数を超えれば TYPE-4（位置は、超えた最初の値）。
- 値の型が、対応する引数の型に渡せなければ TYPE-4（「互換」。`scalar` の位置に核の型の値なら TYPE-1。アームの中の対象をそのまま渡していれば MATCH-4。`docs/check.md`「classify / match」）。
- 省略可能でない引数に値が渡されていなければ BIND-4（`docs/check.md`「必須の入力」）。`bind` で埋まるのは op の引数だけ。
- レコードリテラルは、引数の型の model に当てはめる（「当てはまる」）。

## デコレータの引数

`Application.args` の値が `Param.type` に合うかの規則。`docs/resolve.md` で種類が決まった後に適用する。

- `any <種類>` は、その種類の宣言なら、どれでも、を受ける型（`any` は「どれでも」。`docs/grammar.md`「decorator の宣言」）。
- 一つの引数に `A | B` と渡した値（`refs`）は、その場で書いた union で、「A か B」（`docs/grammar.md`「デコレータの適用」）。名前を付けた union を渡したときと、同じに数える: どちらも、要素の並びに開く。

| `ParamType` | 受け付ける `ArgValue` |
|---|---|
| `type` の `Type` | `literal` で、リテラルの型が渡せるもの（`scalar` の位置には渡せない。TYPE-1）。`list` は `array` の位置に。`ref` で op の引数（`$param:`。`docs/resolve.md`「手続き」1.3）なら、その引数の型が渡せること |
| `any exception` | `ref`（例外）、`refs`（その場で書いた、例外の union）、`ref`（`set` のユニオンで要素が例外。展開して `refs` にする） |
| `any effect` | `ref`（効果）、`refs`、ユニオン（同上） |
| `any effect on s.op` | 上のうち、すべての効果の宛先（`Effect.target`）が組み込みの効果で、その `state` が `s`、`operation` が `op` のもの。遷移の効果や、違う状態・操作なら DEC-7 |
| `any state` | `ref`（状態） |
| `any op` | `ref`（op） |
| `any model` | `ref`（model） |
| `any variant` | `variant` |
| `any` の後ろの、分類のケース（`docs/grammar.md`「decorator の宣言」の `CaseKind`） | `case`（分類のケース。`Actor.Customer`）。絞りは、`of` の後ろ（`docs/grammar.md`「decorator の宣言」）。分類の名前（`any case of Actor`）なら、その分類のケース。型（`any case of Order`、`any case of never`）なら、値の分類で、対象の型が、その型と等しいもの（「型」の「等しい」）のケース: `of never` は、対象のない分類（`docs/check.md`「分類」の「対象のない分類」）。`any case` と `any case of any` は、どの分類のケースでも。合わなければ DEC-7 |
| ユニオンへの `ref`（`error: ApiError`） | `ref` で、そのユニオンの `members` に含まれる例外か効果。`refs` なら全要素が含まれる。含まれなければ DEC-7 |

引数の数と名前:

- 必須の `Param` が渡されていなければ DEC-11。
- 宣言にない引数名、または位置で渡した引数が `Param` の数を超えれば DEC-11。
- 宣言が**残りの引数**（`Param.rest`。`docs/grammar.md`「decorator の宣言」の `RestParam`）を持てば、ほかの `Param` の数を超えて位置で渡した値は、書いた順に、残りの引数の値になる（0 個でもよい。`Application.args` では一つの `list`。`docs/ir.md`「デコレータの適用」）。値は一つずつ、残りの引数の `ParamType` で上の表を当てる。残りの引数に名前で渡せば DEC-11。
- 同じ引数に二度渡せば DEC-11。

この節の細部は、決定 D589 が決めた。

## 診断

この見出しの診断の、ID と条件と重さの持ち主は、`spec/diagnostics/rule.hozo` の分類 `hozo.diagnostics.Rule` のケース。

TYPE-13 は欠番。「既定値のリテラルがフィールドの型（`scalar` なら元の型）に渡せない」という規則で、フィールドの既定値を言語からなくした（`docs/grammar.md`「決めたこと」）ときになくなった。番号は別の意味に使い回さない（欠番は、`spec/diagnostics/` のケースの `@retired`）。

この節の細部は、決定 D590、D617、D766、D774 が決めた。
