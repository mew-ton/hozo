# IDE の画面の構成

## この文書が決めること

IDE の設計の段 3（`tools.md`「IDE の設計の段階」）: 段 2 の情報と操作（`ide-needs.md`）を、IDE の場に割り当てたもの。設計の場であるノート、ノートに置けるもの、ノートのほかの場、場の間の移り方。次の段（画面の見本）は、ここに並ぶものの見本を作る。

決まっていること（`decisions.md`「決めたこと」192〜200、204〜311）は、「決まっている前提」の節。**そのほかは、案**で、利用者が確かめていない（`open.md`「聞かずに決めて、確かめていない決定」）。

この文書は、見た目と、細かい配置を、決めない（段 4）。今の Hozo と `hozoc` で出せるかどうかは、構成に影響させない（`ide-needs.md`「原則」）。

## 決まっている前提

- **詳細に設計する単位は、コンテキスト。** アプリの全体は、粗く俯瞰する。コンテキストは、仕様の名前空間（境界は、言語が守っている: 状態は、持ち主の名前空間の中でしか読めず、外からは、外に出した op を通す。`check.md`「export」「状態の参照」）。
- **設計の場は、ノート。** ノートは、自由なキャンバス。設計の図形は、ノートに作った領域の中に置き、線でつなぐ。領域は、設計図の種類を、一つ持つ。単体の表と、矩形、ラベル、付箋は、領域の外に置ける（「領域」）。図の種類ごとに、画面を分けない。
- **ノートは、コンテキストごとと、全体とで、作るのがよい。ただし、仕組みは、それを縛らない。** どのノートにも、どの要素でも置ける。ノートに、種類はない。
- **ノートは、専用のファイルとして保存する。** 置いた図形は、設計（仕様）に連動する。
- **図形は、プラグインが作る**（`ide-shapes.md`）。IDE は、図形を、自由に置き、つなぐ仕組みを持つ。
- **付箋には、ラベル（後で決める、など）を付けられる。付けなくてもよい。**
- **設計の結果、どんなハーネスになるかを、前もって見られる**（「ハーネスのプレビュー」）。
- **仕様（`.hozo`）そのものを、目で見て直すエディタがある。** 仕様は、各種の設計（ノートに置いた、手法ごとの図）から作られる。置き場は、ノートとは別の場（「仕様の図」）と、ノートの、両方。
- **ハーネスのプレビューは、仕様そのものの図の上に出す。** op、効果、read の一つずつに、強度を二つ（中身の強度、設計を守る強度）出す。入口を選ぶと、そこから末端までの経路と節が浮き上がり、強度と穴を探れる（「ハーネスのプレビュー」）。
- **フロントエンド、バックエンド、DB は、名前空間の区切りで表す。** 言語に、新しい概念は足さない。
- **図形は、仕様の要素を、名前で指す。名前は、基本的に、変わらない。** 図形の上で名前を変えるときは、一括で変えるか、分離するかを、選ぶ（「図形と要素の結び付き」）。
- **アウトラインのパネルがある。** 仕様の要素を、コードのアウトラインのように並べる。そこから、ノートへ引いて、図形として置く。または、ノートの図形に引いて、関連付ける（「アウトライン」）。
- **ノートの上で支えるのは、置く、関連付ける、図形の欄を直して設計の詳細を詰める、まで。手順（配線）の中身も、ノートの上で直せる形で進める。** 試して、難しければ、手順は、見るだけに下げる。
- **手順を直す図も、その図を提供するプラグインの役目。** IDE の本体は、手順の図を、特別には持たない。
- **仕様にあって、どのノートにも置いていない要素を、特別には扱わない。** 仕様の要素は、アウトラインに、すべて並ぶ。
- **ユースケース図の領域では、担い手とユースケースを、規格どおり、線で結ぶ。担い手を囲み（レーン）にするのは、業務フロー図の領域。** 259 より前は、どこでも、担い手は、入口を入れる囲みだった（`decisions.md`「決めたこと」195。273 が、ユースケース図について、置き換えた）。
- **ノートの上で、図形を描くこと、線を引くことは、仕様を直すこと。** 仕様に結ばれた図形を描けば、宣言が足され、線を引けば、関係が足される。矩形、ラベル、付箋は、仕様に入らない。

## 図形の二つの種類

ノートに置くものは、二つの種類に分かれる。この分けが、ただ一つの正（`requirements.md`「ただ一つの正」）を守る。

| 種類 | 例 | 仕様との関係 | ノートが持つもの |
|---|---|---|---|
| **結ばれた図形** | 担い手、ユースケース、状態、クラス。単体の表（「塊」）も、こちら | 仕様の要素そのもの。名前、説明、つながりは、仕様にある | どの要素を、どこに置いたか、だけ |
| **自由な図形** | 矩形（囲み）、ラベル、付箋、自由な線 | 仕様に入らない。検査も、コードの枠も、これを見ない | 中身のすべて |

- **ノートは、設計を持たない。** 持つのは、結ばれた図形の配置と、自由な図形。ノートを消しても、仕様は変わらない。
- **結ばれた図形は、領域の中に置く。** 自由な図形は、どこにでも置ける。単体の表は、領域の外に置く（「領域」）。
- 同じ要素を、いくつものノートに置ける。どのノートで直しても、同じ仕様が変わる。
- ノートは、ウィンドウより大きくなる。拡大、縮小と、ノートの全体の中の、今の位置を出す。
- **「ノートから外す」と「仕様から消す」は、別の操作。**
- 自由な図形に書いたことを、仕様にしたいときは、それを選んで、AI に頼む（「AI とのやり取り」）。ざっと描いてから、仕様に起こす使い方は、これで受け持つ。
- 自由な線は、結ばれた線と、見て分かる違いを持たせる（段 4）。

## ノート

### ノートの作り方

ノートに、種類はない。どのノートも、同じ、自由なキャンバスで、どの種類の領域でも、作れる。次の三つは、IDE が用意する、作り方（はじめの中身の決め方）で、できたノートを、縛らない。はじめの中身は、案。

| 作り方 | 対象 | はじめの中身（案） |
|---|---|---|
| 全体から作る | アプリの全体。粗く俯瞰する | ユースケース図の領域（担い手と、ユースケース）、業務フロー図の領域（フローの op ごと）、コンポーネント図の領域（いちばん外の見え方）、要求トレーサビリティマトリクス、入口の一覧 |
| コンテキストから作る | 一つのコンテキスト（名前空間）。詳細に設計する | クラス図の領域（その名前空間の model）、ER 図の領域（表になる状態）、ステートマシン図の領域（状態の分類ごと）、CRUD 表 |
| 空から作る | 決まっていない。コンテキストをまたぐ検討（一本の流れ、「取り消しを入れる」）のため | 空。領域を作って、置いていく。ユースケースか、op から作ると、その手順の図の領域が、置かれる |

- **プロジェクトを、はじめて開いたとき、IDE は、全体のノートと、コンテキストごとのノートを作る。** 4,300 行の下書きを、はじめて読む人（`ide-scenarios.md` の筋書き 1）が、置くところから始めなくて済む。人が動かした後は、その配置を覚える。作ったノートは、消しても、作り直しても、まとめても、よい。
- ほかのコンテキストの要素も、置ける。どのノートからでも、直せる（同じ仕様が変わる）。要素には、持ち主のコンテキストの札が付く。
- ノートの名前と、まとめ方（どのノートを、どの見出しの下に並べるか）は、人が決める。IDE が作ったノートは、はじめ、コンテキストの種類（概念、入口、アプリの画面、外の仕組み）でまとめてある。

### 領域

`decisions.md`「決めたこと」258〜260。

- **ノートに、領域を作る。** 領域は、作るときに、設計図の種類（ユースケース図、ステートマシン図、など）を、一つ決める。
- **領域には、その設計図の図形しか、置けない。**
- **領域の外には、自由な図形（矩形、ラベル、付箋。「自由な図形」）を置ける。設計には、関与しない**（仕様に入らない）。
- **表は、単体で完結するなら、領域にしない。作図になりうるもの（図形を置いて、つなぐもの）は、領域にする。** 単体の表は、領域の外に、そのまま置く（「塊」）。表は、ほかの図形と、関連付けられない。
- **図形の関連付け（線）は、領域の中だけ**（`ide-shapes.md`「線の定義」）。領域の境が、そのまま、決まりになる。
- 狙い: 設計図ごとに、図形と、つなげる相手を、閉じて決められること。設計図の組み合わせごとに、作用を決めなくて済む。
- 一つのノートに、領域は、いくつでも、並べられる。図の種類ごとに、画面を分けない、という前提（`decisions.md`「決めたこと」192）は、保つ。
- 同じ仕様の要素を指す図形が、いくつもの領域に、あってよい。図形は、要素を、名前で指す（`decisions.md`「決めたこと」204）。

領域の種類。図形と線の列は、案。部品が、仕様の何に当たり、どんなハーネスが生まれるかの持ち主は、`ide-chain.md`「図ごとの設計」の、同じ名前の見出し。

| 領域の種類 | 置く図形 | 人が引く線（引くと、仕様に足される） | 自動で出る線 |
|---|---|---|---|
| ユースケース図 | 担い手、ユースケース | 担い手 — ユースケース（ユースケースのデコレータの引数に、その担い手を入れる）。ユースケース → ユースケース（含む） | — |
| 業務フロー図（サービスブループリントを含む） | レーン（担い手）、ステップ（ユースケース） | ステップ → ステップ（フローの op の、呼ぶ順） | — |
| 手順の図（アクティビティ図、ユースケース記述） | 一歩（作業）、分かれ道、終わり | 一歩の順。線ではなく、並べ方で直す | — |
| シーケンス図 | ライフライン、メッセージ | メッセージ（直せるなら。`ide-chain.md`「シーケンス図」） | — |
| ステートマシン図 | 状態、開始、終了 | 遷移（行の遷移を持つ効果を足す。名前を付ける） | — |
| クラス図 | クラス（属性は、中に出す） | 関連（別の model を型に持つフィールドを足す） | — |
| ER 図 | エンティティ（属性は、中に出す） | 関係（`@db.ref`） | — |
| 画面遷移図 | 画面、ダイアログ（語彙 `page` のプラグインが足す） | 遷移（操作と、その行き先を足す） | — |
| コンポーネント図（C4 のコンテキスト図を含む） | コンポーネント、外の仕組み | なし | 依存の線（名前空間をまたぐ op の呼び出し） |
| 仕様の図（「仕様の図」を、ノートにも置く。`decisions.md`「決めたこと」210） | op、効果、read の節 | なし | 呼び出し（手順から出る） |

手順の図と、シーケンス図の領域は、中身が、仕様から出る:

| 領域の種類 | 対象 | 中身 | 中で直せること |
|---|---|---|---|
| 手順の図 | ユースケースの op か、op | 前提、流れ（一歩ごとに、読む、書く、外に頼む、別の手順、中身に任せる、の別）、分かれ道、終わった後、例外と、そのとき変わっているもの。例外の枝と、別の手順の中は、はじめは畳んである | 一歩を、足す、消す、入れ替える。分かれ道の、場合ごとにすること。前提。例外 |
| シーケンス図 | ユースケースの op か、op | ライフライン（関わる名前空間）と、メッセージ（呼び出しと、応答）と、その順 | 呼び出しを、足す、消す、入れ替える。試して、難しければ、見るだけにする |

領域にしないもの:

| 分け | 設計図 |
|---|---|
| 単体の表（「塊」） | CRUD 表、受け入れ条件、要求トレーサビリティマトリクス、入口の一覧 |
| 後回し（例外の設計の目的と、一緒に決める。`ide-chain.md`「決定表」「状態の表」） | 状態の表（状態遷移表）、状態の決め方（決定表） |
| 「仕様の図」の見え方 | ロバストネス図、イベントストーミング |
| 支えない | DFD、外部インタフェース一覧、バッチ一覧、エラー一覧 |

**領域をまたぐつながりは、線では、出さない。** ユースケースが、どの状態を変えるか、のようなつながりは、「仕様の図」、CRUD 表、「詳しく見るところ」で見る。同じ要素を指す、ほかの領域の図形へは、移れる（「移り方」）。

決めていないこと（`open.md`「次の段」に置いた）:

- 上の表の、領域の種類と、図形と線（案）の、確かめ。
- 領域の主題（どの分類のステートマシン図か、どの op の手順の図か）と、名前の、持ち方。
- 領域の外に、自由な図形で描いたものを、後で、領域の図形にする道。
- 自動で出る線（導いた線）を、領域の中だけにするか（案: 中だけ）。

### ノートのファイル

- ノートは、一つにつき、一つのファイル。プロジェクトのルートの `.hozo/` の下に置く。`hozoc ide` でプロジェクトを開くと、`.hozo/` と、その下のノートのファイルが、作られる。
- 置き場は、プロジェクトの設定（`hozo.toml`）で変えられる。既定は `.hozo/`。
- **設計（`.hozo` の仕様のファイル）は、`.hozo/` の外に置く。** `.hozo/` に入るのは、ノートと、IDE が使う、設計ではないもの。
- ノートのファイルが持つのは、結ばれた図形の配置（どの要素を、どの図形で、どこに置いたか）と、自由な図形の中身。設計は、持たない（「図形の二つの種類」）。
- ノートのファイルは、仕様と一緒に、版の管理（git）に入れて、共有できる形にする。ファイルの形は、決めていない（段 6）。

### ノートに置いていない要素

仕様にあって、どのノートにも置いていない要素を、特別には扱わない: 数を出したり、置くように促したりは、しない。仕様の要素は、アウトラインに、すべて並び（「アウトライン」）、文面でも読める。「仕様にあるものは、すべて見える」（`decisions.md`「決めたこと」184）は、それで満たす。

- AI や、ほかの人が、仕様に足したものは、アウトラインに現れる。置きたければ、そこから引く。
- 仕様からなくなった要素の図形は、なくなったことが分かる形で残り、人が片づける。

### 図形と要素の結び付き

- **結ばれた図形は、仕様の要素を、名前で指す**（`payment.Standing` の `Held`）。ノートのファイルに書くのも、名前。仕様に、変わらない番号のようなものは、足さない。
- **名前は、基本的に、変わらない。** 変えるのは、まれなこととして扱う。
- 図形の上で、名前の欄を打ち直したら、IDE は、どちらにするかを尋ねる（図形のメニューからも、選べる）:

| 選ぶもの | 起きること |
|---|---|
| 一括で変える | その要素の名前を、仕様の全体で変える（宣言と、それを指すすべての場所）。同じ要素を置いた、すべてのノートの図形が、新しい名前を指す |
| 分離する | この図形だけを、もとの要素から離す。図形は、新しい名前の要素を指す（その名前の要素がなければ、新しく足す）。もとの要素は、仕様に、そのまま残る |

- IDE の外（AI、エディタ）で、文面の名前が変わると、図形は、指していた要素を見失う。見失った図形は、そうと分かる形で残り、アウトラインから、要素を引いて、関連付け直す（「アウトライン」）。
- 「分離する」の中身（もとの要素の何を、新しい要素に写すか）は、決めていない。

### アウトライン

仕様の要素を、コードのアウトラインのように、木として並べるパネル。

- 並べ方は、コンテキスト（名前空間）ごと、その中に、宣言の種類ごと。ファイルごとの並べ方にも、切り替えられる。
- 仕様の要素は、ここに、すべて並ぶ。ノートに置いてあるかどうかで、扱いを変えない。
- **ノートへ引く**: 要素を、ノートの空いたところへ引くと、その要素の図形が置かれる。当たる図形が、いくつもあるとき（プラグインが、同じ要素に、別々の図形を定義している）は、選ぶ。
- **図形へ引く**: 要素を、ノートの図形の上へ引くと、その図形を、その要素に関連付ける。自由に描いた図形や、要素を見失った図形を、仕様の要素に結ぶ道。
- 要素を選ぶと、それを置いてあるノートへ移れる。名前と説明で、探せる。

### ノートの上で、支える範囲

ノートの上で、できること:

| できること | 中身 |
|---|---|
| 置く | アウトラインから引く。または、置くものを選んで、新しく描く（新しい要素が、仕様に足される） |
| 関連付ける | 図形を、仕様の要素に結ぶ。線を引いて、要素どうしを結ぶ |
| 欄を直す | 図形の欄（名前、説明、項目、など）を直して、設計の詳細を詰める |

手順（配線）の中の、一歩ごとの書き換え（一歩を、足す、消す、入れ替える。分かれ道の、場合ごとにすることを変える）も、ノートの上で直せる形で進める。手順の図の領域（「領域」）の中で直すこととして扱い、その図を提供するプラグインが、直したときの仕様の変化を決める。試して、難しければ、手順は、ノートの上では見るだけにして、直すのは、AI に頼むか、文面で行う。

### 結ばれた図形

図形は、設計図（領域の種類）ごとに、その設計図のプラグインが定義する（`ide-shapes.md`）。領域の種類ごとの図形は、「領域」の表。図形が、仕様の何に当たるかの持ち主は、`ide-chain.md`「図ごとの設計」。

- 図形は、名前と、説明の一行目を出す。名前と説明は、その場で打ち直せる。線の文と図形に、仕様の名前を出すか、説明を出すかを、選べる（仕様の名前は、設計する人には読みにくいことがある: `ide-mock.md`「仕様の書き方に返ること」）。
- クラスと、エンティティの図形は、項目を、中に出せる（開く、畳む）。項目は、その場で、足す、消す、直す。
- 同じ要素を指す図形が、設計図ごとに、ある。例: クラス図のクラスと、ER 図のエンティティは、別の図形で、同じ model を指す。

259 より前の、標準の図形の、行き先:

| 前の図形 | 今 |
|---|---|
| 担い手、ユースケース | ユースケース図の領域の図形。担い手は、業務フロー図の、レーン |
| 入口 | 業務フロー図のステップは、ユースケース（`ide-chain.md`「業務フロー図」）。ユースケースのない仕様の入口は、入口の一覧（「塊」） |
| 手順、書き込み、読み出し | 仕様の図の節 |
| もの、データ | クラス図のクラス、ER 図のエンティティ |
| 状態 | ステートマシン図の状態 |
| コンテキスト、外の仕組み | コンポーネント図のコンポーネント、外の仕組み |
| アプリの画面 | 画面遷移図の画面 |
| 約束 | 図形としては、置かない。要求トレーサビリティマトリクスの行（「塊」）。要求の書き方は、`ide-chain.md`「要求の文書」 |
| 例外 | 図形としては、置かない。手順の図の、終わり。仕様の図の、節の欄。例外の設計は、後回し（`ide-chain.md`「例外を設計する図」） |

### 結ばれた線

線も、プラグインが定義する: 何と何を結べるか、見た目、結んだとき、仕様が、どう変わるか（`ide-shapes.md`「線の定義」）。線は、領域の中だけ（「領域」）。領域の種類ごとの線は、「領域」の表。

線には、二つの種類がある。

| 種類 | 人が | 仕様との関係 |
|---|---|---|
| **宣言の線** | 引ける。消せる | 引くと、仕様に足される。消すと、仕様から消える |
| **導いた線** | 引けず、消せない。隠すことは、できる | 置いてある二つの図形の間に、仕様の上のつながりがあれば、自動で出る |

導いた線を直したいときは、線を選ぶと、もとの宣言（効果、手順の一歩）へ移る道が出る。

### 塊

塊は、単体の表: 一つの対象を、一つの手法で見せる、大きさを持った図形で、単体で完結するもの（`decisions.md`「決めたこと」260）。領域の外に、そのまま置く。プラグインが提供する（`ide-shapes.md`「塊」）。中身は、仕様から出る。結ばれた図形と同じく、ノートが持つのは、配置だけ。259 より前に、塊だった、手順と、やり取りは、領域にした（「領域」）。

| 塊 | 対象 | 中身 | 中で直せること | 当たる手法 |
|---|---|---|---|---|
| 入口の一覧 | 担い手か、コンテキスト | 入口を、名前と説明の行として、まとめて出す | 名前と説明 | 機能の一覧 |
| 操作とデータの表 | コンテキストか、全体 | 行は、ユースケースの op か、入口。列は、データ。作る、読む、変える、消す。誰も作らないデータ | なし（導いたもの。書き込めるようにするかは、後で判断する: `ide-chain.md`「CRUD 表」） | CRUD 表 |
| 確かめ | ユースケース、要求、コンテキスト | 書かなければならないテスト（`ide-chain.md`「テストの規約」）の表: ラベル、実装されているか、守られているか、カバレッジ | なし。行から、テストコードへ飛ぶ | 受け入れ条件 |
| 要求と、守る役の表 | 全体か、コンテキスト | 行は、要求。列は、それを守る役の op と、書かなければならないテスト。守る役のない要求 | なし（導いたもの） | 要求トレーサビリティマトリクス |

後回しにした塊（例外の設計の目的と、一緒に決める。`ide-chain.md`「決定表」「状態の表」）:

| 塊 | 対象 | 中身 | 当たる手法 |
|---|---|---|---|
| 状態の表 | もの（分類） | 行は、その分類で分かれる op、列は、ケース。ますは、そのケースで、すること: 進む先と後の状態、例外、何もしない。決めていないますは、空き | 状態遷移表 |
| 状態の決め方 | もの | 条件と、その状態 | 決定表 |

### 自由な図形

| 図形 | 使い道 |
|---|---|
| 矩形（囲み） | まとまりを示す。担い手ごとのレーン、段階、検討中の範囲 |
| ラベル | 見出し、注 |
| 付箋 | 書きとめる。ラベルを付けられる（気づいたこと、後で決める、今回は作らない、など）。付けなくてもよい。図形に付けると、その図形と一緒に動く |
| 自由な線 | 意味を持たない矢印。仕様にするなら、AI に頼む |

ラベルの付いた付箋は、「欠けと決めごと」（「ノートのほかの場」）に、ラベルごとに集まる: `ide-needs.md`「設計ではないが、設計する人の仕事に要るもの」の置き場になる。ラベルのない付箋は、ノートの上にだけ、ある。

### 重ね

ノートの図形と線と塊の上に、重ねて出せる印。

| 重ね | 出すもの |
|---|---|
| 欠け | 検査の誤りと、目を通すところ。機械的に埋まるものには、足す操作 |
| 差 | 基準の版から、足された、なくなった、変わった。足されたものが、ノートに置かれていなければ、差を出している間だけ、関わる図形の近くに、仮に置く |
| 確かめ | その要素についての、確かめた結果 |
| ハーネス | op、効果、read ごとの、二つの強度（「ハーネスのプレビュー」） |
| 出どころ | 設計する人が話したことか、AI が補ったことか |
| 目を通した印 | 設計する人が、読んだ、と記したもの |

## ノートのほかの場

| 場 | 中身 | いつも出ているか |
|---|---|---|
| ノートの一覧 | プロジェクトのノート。人が決めた、まとめ方で並ぶ。ノートごとの、欠けの数 | いつも |
| 詳しく見るところ | 選んでいるものの、すべて: 名前、説明、項目、つながり（逆に引いたもの: これを使う入口、これを起こす入口、これを読み書きする入口）、当たる文面。入口なら、手順の図と同じ中身。選んでいる間だけ見るところで、残したいものは、ここから、領域か、塊として、ノートに置く | 選んでいるものがあれば |
| AI とのやり取り | 言葉で頼む。選んでいるもの（図形、付箋、囲みの中）を添える。AI の聞き返しに答える。AI の案を、書き換える前に見る。AI が書いている途中かが分かる。書き換えたら、「変更」への道が出る | いつも |
| 状況 | 検査の誤りの数、目を通すところの数、枠が今の仕様のものか、中身の欠けの数、確かめの結果の数 | いつも |
| アウトライン | 仕様の要素の木。ノートへ引いて置く、図形へ引いて関連付ける。名前と説明で探す（「アウトライン」） | いつも |
| 変更 | 基準の版からの差の一覧。頼んだことに関わる変更と、関わらない変更。受け入れる、戻す、一部だけ戻す。選ぶと、その要素のあるノートを、差の重ねを出して開く | 呼び出したとき |
| 欠けと決めごと | 検査の誤り（機械的に埋まるものと、判断が要るもの）、目を通すところ、ラベルの付いた付箋（ラベルごと）、目を通していない範囲 | 呼び出したとき |
| 仕様の図 | 仕様の全体を、op と、その依存の図として、漏れなく出す。節の欄、手順の中身、デコレータを直す（「仕様の図」）。節ごとの、二つの強度（「ハーネスのプレビュー」） | 呼び出したとき |
| 中身の状況 | コードの枠が、今の仕様のものか。まだない中身。確かめた結果の、コンテキストごと、要求ごとの集計。枠を出し直す、AI に中身を書かせる、確かめを走らせる | 呼び出したとき |
| 文面 | `.hozo` と `hozo.toml` のファイルと、文面。直に直せる | 呼び出したとき |

ノートに置いていない要素も、「アウトライン」と「文面」と「仕様の図」からは、必ず届く。

## 仕様の図

仕様（`.hozo`）そのものを、目で見て直す場。「文面」が、仕様を、文字で出すのに対して、こちらは、図で出す。

### 決まっていること

`decisions.md`「決めたこと」207、210、211、214、254〜257。

- **op と、その依存を、節と線にした図（ノードグラフ）。** 節は、op、効果、read。
- **仕様の全体を、漏れなく出す。** 並べ方は、IDE が決める。
- **仕様は、各種の設計（ノートに置いた、手法ごとの図）から作られる。**
- **入口を選ぶと、そこから辿れる、末端までの経路と節が、浮き上がる。** 入口は、システムの一つのイベントの入口で、ユースケースなどで決まる。
- **op、効果、read は、ノートにも、図形として置ける**（「領域」の、仕様の図の領域）。
- **見え方に、ロバストネス図と、イベントストーミングがある**（`ide-chain.md`「ロバストネス図」「イベントストーミング」）。

### 直せること

| 直せること | 中身 |
|---|---|
| 節の欄 | 名前、説明、引数、例外。節を、足す、消す |
| 手順の中身 | 節を開いて、直す。ノートの、手順の図（「領域」）を、そのまま使う |
| デコレータ | 節と、節の欄に出る宣言（例外など）に付いたデコレータを、足す、外す、引数を直す |

- 線（依存）は、手順から出る。人は、引かない。
- **デコレータを直せるようにする理由**: 設計から生まれる概念は、デコレータにある。ただし、すべてを、デコレータで書くことには、固執しない: 要求の形式は、コメントブロックのタグで書く手段がある（`ide-chain.md`「要求の文書」。`decisions.md`「決めたこと」267）。デコレータを直すことで、節を、設計の概念に関連付け（例: 約束の `@prd.promise`）、設計の図に出ない設定（例: 例外のときの応答を決める `@http.status`）を、直す。

### 決めていないこと

`open.md`「次の段」に置いた。

- 並べ方の決め方。
- デコレータを直す欄の、作り方（デコレータの宣言から、IDE が作るのか、語彙のプラグインが、見た目を用意するのか）。

## ハーネスのプレビュー

設計の結果、どんなハーネス（`requirements.md`「ハーネス」）になるかを、中身を書く前に、見るところ。「中身の状況」が、今ある中身を確かめた結果なのに対して、こちらは、設計そのものが、何を縛り、何を縛らないかを見せる。

サンプル `order-app` に当てて、数えた記録は `ide-harness-trial.md`。

### 決まっていること

`decisions.md`「決めたこと」207〜213。

- **土台は、「仕様の図」。** 節ごとの強度は、ノートに置いた op、効果、read にも、出る。
- **節ごとに、強度を、二つ出す**（「二つの強度」）。
- **入口を選んで、浮き上がった経路と節の上で、ハーネスが保てる品質の強度と、穴を探る。**
- **節の強度は、節の見た目（大きさ、派手さ）で見せる**（「節の見た目」）。絞ったときの、まとめた数や、穴の一覧は、決めていない: 探すのは、図の上。
- **フロントエンド、バックエンド、DB は、名前空間の区切りで表す。** 言語に、新しい概念は足さない。名前空間を区切るのは、エンジニアか、要件を聞いた AI（AI が補う）。入口から末端までの依存は、この区切りをまたぐ。

### 二つの強度

| 強度 | 言うこと | 出し方 |
|---|---|---|
| 中身の強度 | ハーネスが、その節の中身を、どれほど縛るか | ハーネスの段の数字（「中身の強度の段」） |
| 設計を守る強度 | その節と、その節から作るテストが、設計を、どれほど守っているか | その節に、直に依る設計の数と、そのうち、テストで覆えている割合 |

二つは、別のことを言う: 中身が仕様から作られる節（中身の強度は、段 4）でも、その節に依る設計が、テストで覆えていなければ、設計を守る強度は、低い。

### 直に依る設計

設計を守る強度で数える設計は、図形と線として描ける、設計の要素（要求、状態の向き、例外、前提、画面の操作、ユースケースなど）のうち、その節を、直に指すもの。

- どの要素が、どの節を指すかは、図形と線の定義が言う、「その図形が、仕様の何に当たるか」から決まる（`ide-shapes.md`「図形の定義」「線の定義」）。
- 手法の部品ごとに、仕様の何に反映され、どの節を指すかの案は、`ide-chain.md`「対応」。
- ノートに置いてあるかどうかは、数え方に関わらない（「ノートに置いていない要素」）。

### テストで覆えている

設計の一つが、テストで覆えている、とは、その設計が破られたら落ちるテストを、ハーネスが、仕様から作れること。

- 中身を書く前に、決まる。
- そのテストが、今、通っているかは、「ノートのほかの場」の「中身の状況」が見せる。
- 人や AI が書いたテストは、設計に結び付けてあっても、数えない: そのテストが、その設計を確かめていることを、ハーネスは、確かめられない。

### 中身の強度の段

中身の強度は、ハーネスの段の数字で出す（`decisions.md`「決めたこと」305）。段の意味の持ち主は、`requirements.md`「もとの考えと、Hozo が守るもの」。節への当て方は、次のとおり。決め手は、中身を誰が書くかと、仕様が、その振る舞いを言っているか。

| 段 | 当たる節 | 例 |
|---|---|---|
| 4 | 中身が、仕様から作られる節（人は、書かない）。人か AI が書くが、仕様が、振る舞いを言っていて、中身を確かめるテストを作れる節 | 配線の op。`@db.insert` の効果、`@db.find` の read。行の遷移を宣言した効果（`as Held -> Captured`）で、ケースの判定が、Hozo の中にあるもの |
| 3 | 書かなければならないテストが、決まる節 | ユースケースの op。行の遷移を宣言した効果で、ケースの判定を、人か AI が書くもの（`ide-chain.md`「テストの規約」） |
| 2 | 人か AI が書き、仕様が言うのは、形（型、返す例外、触れるデータ）だけの節 | 葉の op |
| 1 | 仕様が、何も約束していない節 | `as any -> else` の効果、外の仕組み |

- 段 0（書けない）は、節に出ない: 仕様に書けないものは、節にならない。
- 図の部品ごとの段は、`ide-chain.md`「図ごとの、ハーネスの段」。

### 節の見た目

| 見た目 | 表すもの |
|---|---|
| 大きさ | 重み: その節に、直に依る設計の数。多いほど、大きい |
| 派手さ | 弱さ: 中身の強度が低いほど、また、テストで覆えていない設計があるほど、目立つ。強い節は、静か |

- 穴は、入口から末端までの道の上の、派手な節: 中身の強度が、段 2 以下の節と、覆えていない設計がある節。
- 大きくて、派手な節が、いちばんの穴: 多くの設計が乗っているのに、守れていない。
- 派手さを、何で出すか（色、形、動き）は、見本の段（段 4）で決める。

### 決めていないこと

`open.md`「次の段」に置いた。

- DB を、名前空間として区切っていない仕様で、DB の端を、どう見せるか。サンプル `order-app` では、データ（状態）と、その効果と read が、業務の名前空間（`payment` など）の中にある。

### 207 より前の案

207 より前は、見せるものを、次の四つにしていた。節の強度の内訳として残すかは、決めていない。

| 見せるもの | 中身 | 例（支払いのコンテキスト） |
|---|---|---|
| 枠 | その設計から作られる、コードの枠（型、関数の形、実装を受け取る口） | `Payment` の型。外に出す手順 5 の、関数の形 |
| 中身に求めること | 人か AI が書かなければならないもの。書かなければ、コンパイルエラーになるもの | 額を決める関数、状態の述語 5、読み書き 12 |
| 確かめること | その設計から作られる、テストの条件: 進んでよい向き、進んではいけない向き、例外のとき変わっていないもの | 進んでよい向き 7、いけない向き 23 |
| 縛らないもの | 仕様に書いてあるが、ハーネスが、何も守らないもの | 要求「請求は、同意した額を超えない」は、印だけ。額の規則は、中身 |

### 今の Hozo で、出せるもの

出せないことは、構成を縛らない（`ide-needs.md`「原則」）。出せないものは、`open.md`「Hozo の側の改善する点」に置いた。

| 要るもの | 今 |
|---|---|
| op、効果、read の、依存の図（入口から末端まで） | 出せる: 配線の呼び出し（`ir.md`「配線」）と、検査が計算した効果と read（`ir.md`「op」） |
| 名前空間の区切り | 出せる（`ir.md`「Program」） |
| 中身の強度 | 一部だけ、出せる。配線の op か、葉の op か、行の遷移を宣言しているかは、仕様から分かる。効果と read の中身を、プラグインが作るのか、人が書くのかを、`hozoc` は返さない |
| 設計を守る強度 | 出せない。設計から節への依存の計算と、テストの生成が、ない（`requirements.md`「ハーネス」） |

## 移り方

| 移り方 | 例 |
|---|---|
| 領域の中で、線を辿る | ステートマシン図の、状態 → 遷移 → 次の状態 |
| 同じ要素を指す、ほかの領域の図形へ（案） | ユースケース図のユースケース → 業務フロー図のステップ、その手順の図の領域 |
| 全体のノートから、コンテキストのノートへ | 全体のノートの、コンポーネント図のコンポーネント → そのコンテキストのノート |
| コンテキストのノートから、ほかのコンテキストのノートへ | 置いてある、ほかのコンテキストの要素 → その持ち主のノート |
| 選んでいるものの、つながりを辿る | 「詳しく見るところ」の、これを使う入口 → その入口のあるノート |
| 一覧から、ノートへ | 「変更」「欠けと決めごと」「アウトライン」の行 → その要素のあるノート |

- 移っても、選んでいるものは変わらない。移った先は、選んでいるものが見えるように開く。
- 同じ要素が、いくつものノートにあるときは、対象のノート（その要素のコンテキストのノート）を、先に開く。
- 移る前のところへ、戻れる。

## 手法との対応

設計の手法は、画面ではなく、ノートに置くものとして現れる: 領域か、単体の表。一つのノートに、いくつもの手法を、並べて置ける。手法ごとの置き場は、「領域」の表。

## 割り当ての確かめ

### 情報

`ide-needs.md`「情報」のまとまりごとに、受け持つところ。

| 情報のまとまり | 受け持つところ |
|---|---|
| アプリの全体 | 全体のノート（ユースケース図の領域、コンポーネント図の領域、入口の一覧） |
| 業務の流れ | 全体のノート（業務フロー図の領域） |
| 一つの入口 | 手順の図の領域、シーケンス図の領域、「詳しく見るところ」 |
| ものの一生 | コンテキストのノート（ステートマシン図の領域）。状態の表と、状態の決め方は、後回し |

### 操作

| 操作のまとまり | 受け持つところ |
|---|---|
| 読むための操作 | 「ノートの一覧」「アウトライン」「詳しく見るところ」「移り方」。絞る代わりに、ノートに置くものを選ぶ。比べるは「変更」 |
| AI との操作 | 「AI とのやり取り」。受け入れる、戻すは「変更」 |
| 直すための操作 | 領域の中で、図形を描く、線を引く、その場で打ち直す。順のあるものは、手順の図の領域の中。足りない宣言を足すは、重ねの「欠け」。文面を直に直すは「文面」 |
| 仕事のための操作 | 付箋、目を通した印 |
| ハーネスのための操作 | 「仕様の図」で、入口を選ぶ。穴については、直すための操作と、付箋 |
| 中身のための操作 | 「中身の状況」 |

### 筋書き

筋書き（`ide-scenarios.md`）の歩みを、なぞる。

| 筋書き | 歩み → ところ |
|---|---|
| 1 はじめて読む | 開くと、全体のノート（IDE が置いたもの）。1 → ユースケース図の領域（担い手と、ユースケース）。2 → 要求と、守る役の表。3 → 業務フロー図の領域 → コンテキストのノートの、ステートマシン図の領域。4 → ユースケースを選び、「詳しく見るところ」（例外の枝は畳んだまま）。5 → 要求と、守る役の表の行 → 守る役 →「仕様の図」で、それを通る入口。6 → 付箋（気づいたこと）。7 → 目を通した印、「欠けと決めごと」の、まだの範囲 |
| 2 約束を追う | 自由なノートを作り、要求と、守る役の表を置く。1 → その行の、守る役。2 →「仕様の図」で、守る役を通る入口。3 → 支払いの、ステートマシン図の領域を置く。4 → 受け持つものが、ない（決定表は、後回し。規則は、仕様にない）。5〜6 → 入口の、手順の図の領域の、例外。7 → 確かめの表。置いた領域と表が、一枚のノートに残る |
| 3 AI に頼む | 1 → 注文と支払いのコンテキストのノート。2〜3 → ステートマシン図の領域の状態を選び、「AI とのやり取り」。4 →「変更」。足された状態は、アウトラインに現れる。差の重ねを出すと、当たる領域に、仮に置かれる。5 →「変更」の、関わらない変更。6 → ステートマシン図の領域に、差の重ね。7 → 手順の図の領域。8 →「変更」で、受け入れる |
| 4 抜けを決める | 1 → 操作とデータの表。2 → 空きに、付箋（今回は作らない）。3 → ステートマシン図の領域（入る向き、出る向き）。4 → 受け持つものが、ない（宣言していない向きの一覧は、状態の表が要る。後回し）。5 →「アウトライン」（説明のないもの）。6 →「欠けと決めごと」 |
| 5 小さく直す | 1〜2 → 図形の名前と説明を、その場で。3 → ステートマシン図の領域で、状態を描き、遷移を引く。4 → 手順の図の領域の中。5 → 重ねの「差」。6 → 一つ前に戻す |
| 6 中身を知る | 1〜2 →「中身の状況」。3〜4 → 重ねの「確かめ」、確かめの表。5 → 確かめの表の、誤りの分け |
| 7 何もないところから | 1 →「AI とのやり取り」。または、全体のノートの、領域の外に、自由な図形で、ざっと描いて、AI に仕様にさせる。2 → ユースケース図の領域に現れた、担い手とユースケース（重ねの「出どころ」）。3 → 要求を書く（場は、決めていない）。4 → 業務フロー図の領域、コンテキストのノート。5〜6 → 付箋（後で決める、今回は作らない）。7 →「AI とのやり取り」→「変更」。8 →「欠けと決めごと」、「状況」 |
| 8 ハーネスを知る | 1〜2 →「仕様の図」で、入口を選ぶ。浮き上がった経路と節、名前空間のまとまり。3〜5 → 節の見た目（大きさ、派手さ）。6 → 穴の節から、ノートへ移って、設計を足す。または、付箋（後で決める） |

なぞって、分かったこと:

- **追った跡は、領域と表の並びとして、残る。** 筋書き 2（約束を追う）は、図ごとの画面では、画面を渡り歩くだけだった。ノートでは、関わる領域と表を置いていくと、その約束についての一枚ができる。259 より前は、線を辿って、図形を置いていけた。領域をまたぐ線は、ないので、今は、辿るのに、「仕様の図」と、同じ要素を指すほかの領域へ移る道を使う。
- **状態の表と、決定表を後回しにした分、受け持つものがない歩みが、ある。** 筋書き 2 の歩み 4（額を決める規則）と、筋書き 4 の歩み 4（宣言していない向きの一覧）。
- **付箋が、段 2 で置き場のなかったものを受け持つ。** 気づいたこと、後で決める、今回は作らない。
- **AI の書き換えと、人の配置がぶつかる。** AI が足したものは、勝手には置かれず、アウトラインに現れる（「ノートに置いていない要素」）。AI が名前を変えると、図形は、要素を見失う（下の「残る問い」）。
- **はじめの配置の質が、はじめて読む体験を決める。** IDE が置く、はじめの中身（どれを、どう並べるか）は、段 4 で、見本として詰める。
