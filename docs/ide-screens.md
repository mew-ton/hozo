# IDE の画面の構成

## この文書が決めること

IDE の設計の段 3（`tools.md`「IDE の設計の段階」）: 段 2 の情報と操作（`ide-needs.md`）を、IDE の場に割り当てたもの。設計の場であるノート、ノートに置けるもの、ノートのほかの場、場の間の移り方。次の段（画面の見本）は、ここに並ぶものの見本を作る。

決まっていること（`decisions.md`「決めたこと」192〜200、204〜231）は、「決まっている前提」の節。**そのほかは、案**で、利用者が確かめていない（`open.md`「聞かずに決めて、確かめていない決定」）。

この文書は、見た目と、細かい配置を、決めない（段 4）。今の Hozo と `hozoc` で出せるかどうかは、構成に影響させない（`ide-needs.md`「原則」）。

## 決まっている前提

- **詳細に設計する単位は、コンテキスト。** アプリの全体は、粗く俯瞰する。コンテキストは、仕様の名前空間（境界は、言語が守っている: 状態は、持ち主の名前空間の中でしか読めず、外からは、外に出した op を通す。`check.md`「export」「状態の参照」）。
- **設計の場は、ノート。** ノートは、自由なキャンバス: 設計の図形を、好きなところに置き、線でつなぎ、矩形、ラベル、付箋を、好きに足せる。図の種類ごとに、画面を分けない。
- **ノートは、コンテキストごとと、全体とで、作るのがよい。ただし、仕組みは、それを縛らない。** どのノートにも、どの要素でも置ける。ノートに、種類はない。
- **ノートは、専用のファイルとして保存する。** 置いた図形は、設計（仕様）に連動する。
- **図形は、プラグインが作る**（`ide-shapes.md`）。IDE は、図形を、自由に置き、つなぐ仕組みを持つ。
- **付箋には、ラベル（後で決める、など）を付けられる。付けなくてもよい。**
- **設計の結果、どんなハーネスになるかを、前もって見られる**（「ハーネスのプレビュー」）。
- **仕様（`.hozo`）そのものを、目で見て直すエディタがある。** 仕様は、各種の設計（ノートに置いた、手法ごとの図）から作られる。置き場は、ノートとは別の場（「仕様の図」）と、ノートの、両方。
- **ハーネスのプレビューは、仕様そのものの図の上に出す。** op、効果、read の一つずつに、強度を二つ（中身の強度、設計を守る強度）出す。入口を選ぶと、そこから末端までの経路と節が浮き上がり、強度と穴を探れる（「ハーネスのプレビュー」）。
- **フロントエンド、バックエンド、DB は、名前空間の区切りで表す。** 言語に、新しい概念は足さない。
- **図形は、仕様の要素を、名前で指す。名前は、基本的に、変わらない。** 図形の上で名前を変えるときは、一括で変えるか、分離するかを、選ぶ（「図形と要素の結び付き」）。
- **アウトラインのパネルがある。** 仕様の要素を、コードのアウトラインのように並べる。そこから、ノートへ引いて、図形として置く。または、ノートの図形に引いて、関連付ける（「アウトライン」）。
- **ノートの上で支えるのは、置く、関連付ける、図形の欄を直して設計の詳細を詰める、まで。手順（配線）の中身も、ノートの上で直せる形で進める。** 試して、難しければ、手順は、見るだけに下げる。
- **手順を直す図も、その図を提供するプラグインの役目。** IDE の本体は、手順の図を、特別には持たない。
- **仕様にあって、どのノートにも置いていない要素を、特別には扱わない。** 仕様の要素は、アウトラインに、すべて並ぶ。
- **担い手は、入口を入れる囲み。** 担い手と入口は、線ではなく、入れることで結ぶ（業務フロー図のレーンと同じ）。
- **ノートの上で、図形を描くこと、線を引くことは、仕様を直すこと。** 仕様に結ばれた図形を描けば、宣言が足され、線を引けば、関係が足される。矩形、ラベル、付箋は、仕様に入らない。

## 図形の二つの種類

ノートに置くものは、二つの種類に分かれる。この分けが、ただ一つの正（`requirements.md`「ただ一つの正」）を守る。

| 種類 | 例 | 仕様との関係 | ノートが持つもの |
|---|---|---|---|
| **結ばれた図形** | 担い手、入口、状態、もの、約束 | 仕様の要素そのもの。名前、説明、つながりは、仕様にある | どの要素を、どこに置いたか、だけ |
| **自由な図形** | 矩形（囲み）、ラベル、付箋、自由な線 | 仕様に入らない。検査も、コードの枠も、これを見ない | 中身のすべて |

- **ノートは、設計を持たない。** 持つのは、結ばれた図形の配置と、自由な図形。ノートを消しても、仕様は変わらない。
- 同じ要素を、いくつものノートに置ける。どのノートで直しても、同じ仕様が変わる。
- ノートは、ウィンドウより大きくなる。拡大、縮小と、ノートの全体の中の、今の位置を出す。
- **「ノートから外す」と「仕様から消す」は、別の操作。**
- 自由な図形に書いたことを、仕様にしたいときは、それを選んで、AI に頼む（「AI とのやり取り」）。ざっと描いてから、仕様に起こす使い方は、これで受け持つ。
- 自由な線は、結ばれた線と、見て分かる違いを持たせる（段 4）。

## ノート

### ノートの作り方

ノートに、種類はない。どのノートも、同じ、自由なキャンバスで、どの要素でも置ける。次の三つは、IDE が用意する、作り方（はじめの中身の決め方）で、できたノートを、縛らない。

| 作り方 | 対象 | はじめの中身 |
|---|---|---|
| 全体から作る | アプリの全体。粗く俯瞰する | 担い手、入口、入口から入口への受け渡し、コンテキスト、外の仕組み、約束 |
| コンテキストから作る | 一つのコンテキスト（名前空間）。詳細に設計する | そのコンテキストが外に出す手順、もの、ものの状態と向き、データ、例外、守っている約束 |
| 空から作る | 決まっていない。コンテキストをまたぐ検討（一本の流れ、「取り消しを入れる」）のため | 空。入口から作ると、その入口の手順と、関わるものが置かれる |

- **プロジェクトを、はじめて開いたとき、IDE は、全体のノートと、コンテキストごとのノートを作る。** 4,300 行の下書きを、はじめて読む人（`ide-scenarios.md` の筋書き 1）が、置くところから始めなくて済む。人が動かした後は、その配置を覚える。作ったノートは、消しても、作り直しても、まとめても、よい。
- ほかのコンテキストの要素も、置ける。どのノートからでも、直せる（同じ仕様が変わる）。要素には、持ち主のコンテキストの札が付く。
- ノートの名前と、まとめ方（どのノートを、どの見出しの下に並べるか）は、人が決める。IDE が作ったノートは、はじめ、コンテキストの種類（概念、入口、アプリの画面、外の仕組み）でまとめてある。

### ノートのファイル

- ノートは、一つにつき、一つのファイル。プロジェクトのルートの `.hozo/` の下に置く。`hozoc ide` でプロジェクトを開くと、`.hozo/` と、その下のノートのファイルが、作られる。
- 置き場は、プロジェクトの設定（`hozo.toml`）で変えられる。既定は `.hozo/`。
- **設計（`.hozo` の仕様のファイル）は、`.hozo/` の外に置く。** `.hozo/` に入るのは、ノートと、IDE が使う、設計ではないもの。
- ノートのファイルが持つのは、結ばれた図形の配置（どの要素を、どの図形で、どこに置いたか）と、自由な図形の中身。設計は、持たない（「図形の二つの種類」）。
- ノートのファイルは、仕様と一緒に、版の管理（git）に入れて、共有できる形にする。ファイルの形は、決めていない（段 6）。

### ノートに置いていない要素

仕様にあって、どのノートにも置いていない要素を、特別には扱わない: 数を出したり、置くように促したりは、しない。仕様の要素は、アウトラインに、すべて並び（「アウトライン」）、文面でも読める。「仕様にあるものは、すべて見える」（`decisions.md`「決めたこと」184）は、それで満たす。

- AI や、ほかの人が、仕様に足したものは、アウトラインに現れる。置きたければ、そこから引く。
- 仕様からなくなった要素の図形は、なくなったことが分かる形で残り、人が片づける。

### 図形と要素の結び付き

- **結ばれた図形は、仕様の要素を、名前で指す**（`payment.Standing` の `Held`）。ノートのファイルに書くのも、名前。仕様に、変わらない番号のようなものは、足さない。
- **名前は、基本的に、変わらない。** 変えるのは、まれなこととして扱う。
- 図形の上で、名前の欄を打ち直したら、IDE は、どちらにするかを尋ねる（図形のメニューからも、選べる）:

| 選ぶもの | 起きること |
|---|---|
| 一括で変える | その要素の名前を、仕様の全体で変える（宣言と、それを指すすべての場所）。同じ要素を置いた、すべてのノートの図形が、新しい名前を指す |
| 分離する | この図形だけを、もとの要素から離す。図形は、新しい名前の要素を指す（その名前の要素がなければ、新しく足す）。もとの要素は、仕様に、そのまま残る |

- IDE の外（AI、エディタ）で、文面の名前が変わると、図形は、指していた要素を見失う。見失った図形は、そうと分かる形で残り、アウトラインから、要素を引いて、関連付け直す（「アウトライン」）。
- 「分離する」の中身（もとの要素の何を、新しい要素に写すか）は、決めていない。

### アウトライン

仕様の要素を、コードのアウトラインのように、木として並べるパネル。

- 並べ方は、コンテキスト（名前空間）ごと、その中に、宣言の種類ごと。ファイルごとの並べ方にも、切り替えられる。
- 仕様の要素は、ここに、すべて並ぶ。ノートに置いてあるかどうかで、扱いを変えない。
- **ノートへ引く**: 要素を、ノートの空いたところへ引くと、その要素の図形が置かれる。当たる図形が、いくつもあるとき（プラグインが、同じ要素に、別々の図形を定義している）は、選ぶ。
- **図形へ引く**: 要素を、ノートの図形の上へ引くと、その図形を、その要素に関連付ける。自由に描いた図形や、要素を見失った図形を、仕様の要素に結ぶ道。
- 要素を選ぶと、それを置いてあるノートへ移れる。名前と説明で、探せる。

### ノートの上で、支える範囲

ノートの上で、できること:

| できること | 中身 |
|---|---|
| 置く | アウトラインから引く。または、置くものを選んで、新しく描く（新しい要素が、仕様に足される） |
| 関連付ける | 図形を、仕様の要素に結ぶ。線を引いて、要素どうしを結ぶ |
| 欄を直す | 図形の欄（名前、説明、項目、など）を直して、設計の詳細を詰める |

手順（配線）の中の、一歩ごとの書き換え（一歩を、足す、消す、入れ替える。分かれ道の、場合ごとにすることを変える）も、ノートの上で直せる形で進める。手順の図（「塊」の、手順）の欄を直すこととして扱い、その図を提供するプラグインが、直したときの仕様の変化を決める。試して、難しければ、手順は、ノートの上では見るだけにして、直すのは、AI に頼むか、文面で行う。

### 結ばれた図形

図形は、プラグインが定義する（`ide-shapes.md`）。下の表は、`hozoc` に同梱する、標準の図形。語彙のプラグインは、その語彙の図形を足す（アプリの画面は、語彙 `page` のプラグインが足す図形の例）。

| 図形 | 当たる仕様の要素 | 描くと（仕様に足されるもの） | 当たる手法の部品 |
|---|---|---|---|
| 担い手 | 担い手 | 担い手。**入口を入れる囲み**: 入口を中に入れると、その担い手の入口になる。外に出すと、外れる | ユースケース図のアクター、業務フロー図のレーン |
| ユースケース | ユースケースのデコレータが付いた op（`ide-chain.md`「ユースケース図」） | ユースケースの op と、そのデコレータ。コードは、作らない | ユースケース図のユースケース |
| 入口 | 誰からも呼ばれない op | 手順のない、骨組みの入口 | 業務フロー図の作業 |
| 手順 | op（外に出すもの、中だけのもの） | 骨組みの op | コンポーネントの口、アクティビティ |
| 書き込み | 効果 | 効果の宣言 | — |
| 読み出し | read | read の宣言 | — |
| もの | model | model | クラス、エンティティ |
| 状態 | 値の分類のケース | ケース。ものに付けて描く | ステートマシン図の状態 |
| データ | 状態（`state`） | 状態の宣言 | データの置き場、表 |
| 例外 | 例外 | 例外 | — |
| コンテキスト | 名前空間 | 名前空間。そのノートも、できる | コンポーネント、境界づけられたコンテキスト |
| 外の仕組み | こちらが作らないコンテキスト | 外の仕組み | コンテキスト図の外部 |
| 約束 | 約束 | 約束 | 要求 |
| アプリの画面 | 画面と、その状態 | 画面 | 画面遷移図の画面 |

- 図形は、名前と、説明の一行目を出す。名前と説明は、その場で打ち直せる。線の文と図形に、仕様の名前を出すか、説明を出すかを、選べる（仕様の名前は、設計する人には読みにくいことがある: `ide-mock.md`「仕様の書き方に返ること」）。
- 担い手の囲みは、意味を持つ。意味を持たない自由な囲み（矩形）とは、見て分かる違いを持たせる。
- ものの図形は、項目を、中に出せる（開く、畳む）。項目は、その場で、足す、消す、直す。

### 結ばれた線

線も、プラグインが定義する: 何と何を結べるか、見た目、結んだとき、仕様が、どう変わるか（`ide-shapes.md`「線の定義」）。下は、標準の線。

置いてある二つの結ばれた図形の間に、仕様の上のつながりがあれば、線は、自動で出る。線にも、二つの種類がある。

**宣言の線**（人が引ける。引くと、仕様に足される。消すと、仕様から消える）:

| 線 | 引くと |
|---|---|
| 状態 → 状態 | 進んでよい向き（効果の行の遷移）を足す。名前を付ける |
| もの — もの | 項目（関連）を足す |
| 約束 — 手順 | その手順を、守る役にする |
| アプリの画面 → アプリの画面 | 操作と、その行き先を足す |

**導いた線**（自動で出る。人は、引けず、消せない。隠すことは、できる）:

| 線 | もと |
|---|---|
| 入口 → 入口（受け渡し。何が、どの状態で渡るか） | 行の遷移の、後のケースと前のケース（`ide-methods.md`「入口をまたぐ流れ」） |
| 入口 → 状態の向き（起こす） | 入口の、検査が計算した効果 |
| 入口、手順 → 手順（呼ぶ） | 配線。順があるので、線では直さず、手順の塊で直す |
| 入口 → データ（読む、作る、変える、消す） | 検査の計算 |
| 入口、手順 → 書き込み、読み出し（呼ぶ） | 配線 |
| 書き込み、読み出し → データ | 効果と read の宛先（`check.md`「効果の宛先」「read の宛先」） |
| コンテキスト → コンテキスト（依る） | 配線の呼び出し |
| 入口 → 例外（出す） | 検査の計算 |

導いた線を直したいときは、線を選ぶと、もとの宣言（効果、手順の一歩）へ移る道が出る。

### 塊

塊も、図形の一つで、プラグインが提供する（`ide-shapes.md`「塊」）。手順の塊も、同じ: 見た目と、中で直したときの仕様の変化は、その図を提供するプラグインが決める。下は、標準の塊。

図形と線では、表せないもの（順のあるもの、表）は、**塊**として、ノートに置く。塊は、一つの対象を、一つの手法で見せる、大きさを持った図形。中身は、仕様から出る。結ばれた図形と同じく、ノートが持つのは、配置だけ。

| 塊 | 対象 | 中身 | 中で直せること | 当たる手法 |
|---|---|---|---|---|
| 手順 | 入口か、手順 | 前提、流れ（一歩ごとに、読む、書く、外に頼む、別の手順、中身に任せる、の別）、分かれ道、終わった後、例外と、そのとき変わっているもの。例外の枝と、別の手順の中は、はじめは畳んである | 一歩を、足す、消す、入れ替える。分かれ道の、場合ごとにすること。前提。例外 | ユースケース記述、アクティビティ図 |
| やり取り | 入口か、ユースケース | 関わるコンテキストの帯、呼ぶ順。例外での戻りを見せるかは、決めていない（`ide-chain.md`「シーケンス図」） | 呼び出しを、足す、消す、入れ替える。試して、難しければ、見るだけにする（`ide-chain.md`「シーケンス図」） | シーケンス図 |
| 入口の一覧 | 担い手か、コンテキスト | 入口を、名前と説明の行として、まとめて出す。流れに出ない入口（見るだけの入口）を、一つずつ置かずに済ませる | 名前と説明。行を、図形として取り出す | 機能の一覧 |
| 状態の表 | もの（分類） | 行は、その分類で分かれる op（起こすこと）、列は、ケース（今の状態）。ますは、そのケースで、すること: 進む先と後の状態、例外、何もしない。決めていないますは、空き（`ide-chain.md`「状態の表」） | ますを埋める（向きを足す、例外を置く）、空ける | 状態遷移表 |
| 状態の決め方 | もの | 条件と、その状態 | 条件 | 決定表 |
| 操作とデータの表 | コンテキストか、全体 | 行は入口、列はデータ。作る、読む、変える、消す。誰も作らないデータ | なし（導いたもの） | CRUD 表 |
| 確かめ | 入口、もの、約束 | 確かめる条件と、確かめた結果 | なし（導いたもの） | 受け入れ条件 |

### 自由な図形

| 図形 | 使い道 |
|---|---|
| 矩形（囲み） | まとまりを示す。担い手ごとのレーン、段階、検討中の範囲 |
| ラベル | 見出し、注 |
| 付箋 | 書きとめる。ラベルを付けられる（気づいたこと、後で決める、今回は作らない、など）。付けなくてもよい。図形に付けると、その図形と一緒に動く |
| 自由な線 | 意味を持たない矢印。仕様にするなら、AI に頼む |

ラベルの付いた付箋は、「欠けと決めごと」（「ノートのほかの場」）に、ラベルごとに集まる: `ide-needs.md`「設計ではないが、設計する人の仕事に要るもの」の置き場になる。ラベルのない付箋は、ノートの上にだけ、ある。

### 重ね

ノートの図形と線と塊の上に、重ねて出せる印。

| 重ね | 出すもの |
|---|---|
| 欠け | 検査の誤りと、目を通すところ。機械的に埋まるものには、足す操作 |
| 差 | 基準の版から、足された、なくなった、変わった。足されたものが、ノートに置かれていなければ、差を出している間だけ、関わる図形の近くに、仮に置く |
| 確かめ | その要素についての、確かめた結果 |
| ハーネス | op、効果、read ごとの、二つの強度（「ハーネスのプレビュー」） |
| 出どころ | 設計する人が話したことか、AI が補ったことか |
| 目を通した印 | 設計する人が、読んだ、と記したもの |

## ノートのほかの場

| 場 | 中身 | いつも出ているか |
|---|---|---|
| ノートの一覧 | プロジェクトのノート。人が決めた、まとめ方で並ぶ。ノートごとの、欠けの数 | いつも |
| 詳しく見るところ | 選んでいるものの、すべて: 名前、説明、項目、つながり（逆に引いたもの: これを使う入口、これを起こす入口、これを読み書きする入口）、当たる文面。入口なら、手順の塊と同じ中身。選んでいる間だけ見るところで、残したいものは、ここから、塊としてノートに置く | 選んでいるものがあれば |
| AI とのやり取り | 言葉で頼む。選んでいるもの（図形、付箋、囲みの中）を添える。AI の聞き返しに答える。AI の案を、書き換える前に見る。AI が書いている途中かが分かる。書き換えたら、「変更」への道が出る | いつも |
| 状況 | 検査の誤りの数、目を通すところの数、枠が今の仕様のものか、中身の欠けの数、確かめの結果の数 | いつも |
| アウトライン | 仕様の要素の木。ノートへ引いて置く、図形へ引いて関連付ける。名前と説明で探す（「アウトライン」） | いつも |
| 変更 | 基準の版からの差の一覧。頼んだことに関わる変更と、関わらない変更。受け入れる、戻す、一部だけ戻す。選ぶと、その要素のあるノートを、差の重ねを出して開く | 呼び出したとき |
| 欠けと決めごと | 検査の誤り（機械的に埋まるものと、判断が要るもの）、目を通すところ、ラベルの付いた付箋（ラベルごと）、目を通していない範囲 | 呼び出したとき |
| 仕様の図 | 仕様の全体を、op と、その依存の図として、漏れなく出す。節の欄、手順の中身、デコレータを直す（「仕様の図」）。節ごとの、二つの強度（「ハーネスのプレビュー」） | 呼び出したとき |
| 中身の状況 | コードの枠が、今の仕様のものか。まだない中身。確かめた結果の、コンテキストごと、約束ごとの集計。枠を出し直す、AI に中身を書かせる、確かめを走らせる | 呼び出したとき |
| 文面 | `.hozo` と `hozo.toml` のファイルと、文面。直に直せる | 呼び出したとき |

ノートに置いていない要素も、「アウトライン」と「文面」と「仕様の図」からは、必ず届く。

## 仕様の図

仕様（`.hozo`）そのものを、目で見て直す場。「文面」が、仕様を、文字で出すのに対して、こちらは、図で出す。

### 決まっていること

`decisions.md`「決めたこと」207、210、211、214。

- **op と、その依存を、節と線にした図（ノードグラフ）。** 節は、op、効果、read。
- **仕様の全体を、漏れなく出す。** 並べ方は、IDE が決める。
- **仕様は、各種の設計（ノートに置いた、手法ごとの図）から作られる。**
- **入口を選ぶと、そこから辿れる、末端までの経路と節が、浮き上がる。** 入口は、システムの一つのイベントの入口で、ユースケースなどで決まる。
- **op、効果、read は、ノートにも、図形として置ける**（「結ばれた図形」）。

### 直せること

| 直せること | 中身 |
|---|---|
| 節の欄 | 名前、説明、引数、例外。節を、足す、消す |
| 手順の中身 | 節を開いて、直す。ノートの、手順の図（「塊」）を、そのまま使う |
| デコレータ | 節と、節の欄に出る宣言（例外など）に付いたデコレータを、足す、外す、引数を直す |

- 線（依存）は、手順から出る。人は、引かない。
- **デコレータを直せるようにする理由**: 設計から生まれる概念は、すべて、デコレータにある。デコレータを直すことで、節を、設計の概念に関連付け（例: 約束の `@prd.promise`）、設計の図に出ない設定（例: 例外のときの応答を決める `@http.status`）を、直す。

### 決めていないこと

`open.md`「次の段」に置いた。

- 並べ方の決め方。
- デコレータを直す欄の、作り方（デコレータの宣言から、IDE が作るのか、語彙のプラグインが、見た目を用意するのか）。

## ハーネスのプレビュー

設計の結果、どんなハーネス（`requirements.md`「ハーネス」）になるかを、中身を書く前に、見るところ。「中身の状況」が、今ある中身を確かめた結果なのに対して、こちらは、設計そのものが、何を縛り、何を縛らないかを見せる。

サンプル `order-app` に当てて、数えた記録は `ide-harness-trial.md`。

### 決まっていること

`decisions.md`「決めたこと」207〜213。

- **土台は、「仕様の図」。** 節ごとの強度は、ノートに置いた op、効果、read にも、出る。
- **節ごとに、強度を、二つ出す**（「二つの強度」）。
- **入口を選んで、浮き上がった経路と節の上で、ハーネスが保てる品質の強度と、穴を探る。**
- **節の強度は、節の見た目（大きさ、派手さ）で見せる**（「節の見た目」）。絞ったときの、まとめた数や、穴の一覧は、決めていない: 探すのは、図の上。
- **フロントエンド、バックエンド、DB は、名前空間の区切りで表す。** 言語に、新しい概念は足さない。名前空間を区切るのは、エンジニアか、要件を聞いた AI（AI が補う）。入口から末端までの依存は、この区切りをまたぐ。

### 二つの強度

| 強度 | 言うこと | 出し方 |
|---|---|---|
| 中身の強度 | ハーネスが、その節の中身を、どれほど縛るか | 四つの段（「中身の強度の段」） |
| 設計を守る強度 | その節と、その節から作るテストが、設計を、どれほど守っているか | その節に、直に依る設計の数と、そのうち、テストで覆えている割合 |

二つは、別のことを言う: 中身が仕様から作られる節（中身の強度は、いちばん上）でも、その節に依る設計が、テストで覆えていなければ、設計を守る強度は、低い。

### 直に依る設計

設計を守る強度で数える設計は、図形と線として描ける、設計の要素（約束、状態の向き、例外、前提、画面の操作、ユースケースなど）のうち、その節を、直に指すもの。

- どの要素が、どの節を指すかは、図形と線の定義が言う、「その図形が、仕様の何に当たるか」から決まる（`ide-shapes.md`「図形の定義」「線の定義」）。
- 手法の部品ごとに、仕様の何に反映され、どの節を指すかの案は、`ide-chain.md`「対応」。
- ノートに置いてあるかどうかは、数え方に関わらない（「ノートに置いていない要素」）。

### テストで覆えている

設計の一つが、テストで覆えている、とは、その設計が破られたら落ちるテストを、ハーネスが、仕様から作れること。

- 中身を書く前に、決まる。
- そのテストが、今、通っているかは、「ノートのほかの場」の「中身の状況」が見せる。
- 人や AI が書いたテストは、設計に結び付けてあっても、数えない: そのテストが、その設計を確かめていることを、ハーネスは、確かめられない。

### 中身の強度の段

決め手は、中身を誰が書くかと、仕様が、その振る舞いを言っているか。

| 段 | 意味 | 例 |
|---|---|---|
| 作られる | 中身が、仕様から作られる。人は、書かない | 配線の op。`@db.insert` の効果、`@db.find` の read |
| 確かめられる | 人か AI が書く。仕様が、振る舞いを言っていて、テストを作れる | 行の遷移を宣言した効果（`as Held -> Captured`） |
| 形だけ | 人か AI が書く。仕様が言うのは、形（型、返す例外、触れるデータ）だけ | 葉の op |
| 約束なし | 仕様が、何も約束していない | `as any -> else` の効果、外の仕組み |

### 節の見た目

| 見た目 | 表すもの |
|---|---|
| 大きさ | 重み: その節に、直に依る設計の数。多いほど、大きい |
| 派手さ | 弱さ: 中身の強度が低いほど、また、テストで覆えていない設計があるほど、目立つ。強い節は、静か |

- 穴は、入口から末端までの道の上の、派手な節: 中身の強度が「形だけ」「約束なし」の節と、覆えていない設計がある節。
- 大きくて、派手な節が、いちばんの穴: 多くの設計が乗っているのに、守れていない。
- 派手さを、何で出すか（色、形、動き）は、見本の段（段 4）で決める。

### 決めていないこと

`open.md`「次の段」に置いた。

- DB を、名前空間として区切っていない仕様で、DB の端を、どう見せるか。サンプル `order-app` では、データ（状態）と、その効果と read が、業務の名前空間（`payment` など）の中にある。

### 207 より前の案

207 より前は、見せるものを、次の四つにしていた。節の強度の内訳として残すかは、決めていない。

| 見せるもの | 中身 | 例（支払いのコンテキスト） |
|---|---|---|
| 枠 | その設計から作られる、コードの枠（型、関数の形、実装を受け取る口） | `Payment` の型。外に出す手順 5 の、関数の形 |
| 中身に求めること | 人か AI が書かなければならないもの。書かなければ、コンパイルエラーになるもの | 額を決める関数、状態の述語 5、読み書き 12 |
| 確かめること | その設計から作られる、テストの条件: 進んでよい向き、進んではいけない向き、例外のとき変わっていないもの | 進んでよい向き 7、いけない向き 23 |
| 縛らないもの | 仕様に書いてあるが、ハーネスが、何も守らないもの | 約束「請求は、同意した額を超えない」は、印だけ。額の規則は、中身 |

### 今の Hozo で、出せるもの

出せないことは、構成を縛らない（`ide-needs.md`「原則」）。出せないものは、`open.md`「Hozo の側の改善する点」に置いた。

| 要るもの | 今 |
|---|---|
| op、効果、read の、依存の図（入口から末端まで） | 出せる: 配線の呼び出し（`ir.md`「配線」）と、検査が計算した効果と read（`ir.md`「op」） |
| 名前空間の区切り | 出せる（`ir.md`「Program」） |
| 中身の強度 | 一部だけ、出せる。配線の op か、葉の op か、行の遷移を宣言しているかは、仕様から分かる。効果と read の中身を、プラグインが作るのか、人が書くのかを、`hozoc` は返さない |
| 設計を守る強度 | 出せない。設計から節への依存の計算と、テストの生成が、ない（`requirements.md`「ハーネス」） |

## 移り方

| 移り方 | 例 |
|---|---|
| ノートの中で、線を辿る | 約束 → 守る役 → それを通る入口 |
| 全体のノートから、コンテキストのノートへ | 全体のノートの、受け渡しの「支払いが Held」→ 支払いのコンテキストのノートの、その状態 |
| コンテキストのノートから、ほかのコンテキストのノートへ | 置いてある、ほかのコンテキストの手順 → その持ち主のノート |
| 選んでいるものの、つながりを辿る | 「詳しく見るところ」の、これを使う入口 → その入口のあるノート |
| 一覧から、ノートへ | 「変更」「欠けと決めごと」「アウトライン」の行 → その要素のあるノート |

- 移っても、選んでいるものは変わらない。移った先は、選んでいるものが見えるように開く。
- 同じ要素が、いくつものノートにあるときは、対象のノート（その要素のコンテキストのノート）を、先に開く。
- 移る前のところへ、戻れる。

## 手法との対応

設計の手法は、画面ではなく、ノートに置くものの組として現れる。同じノートに、いくつもの手法の部品を、混ぜて置ける。

| 手法 | ノートの上では |
|---|---|
| ユースケース図 | 担い手と入口の図形、その間の線 |
| 業務フロー図、BPMN、サービスブループリント、イベントストーミング | 入口の図形と、受け渡しの線。担い手ごとの囲み |
| コンテキスト図、コンポーネント図、C4、DFD の一段目 | コンテキストと、外の仕組みの図形、依る線 |
| ステートマシン図 | 状態の図形と、向きの線 |
| ドメインモデル図（クラス図、ER 図） | ものと、データの図形、関連の線 |
| 画面遷移図 | アプリの画面の図形と、操作の線 |
| 要求との対応表 | 約束の図形と、守る役への線。一覧は「アウトライン」 |
| ユースケース記述、アクティビティ図 | 手順の塊 |
| シーケンス図 | やり取りの塊 |
| 状態遷移表、決定表、CRUD 表、受け入れ条件 | それぞれの塊 |
| ロバストネス図 | 置かない: 制御が多すぎて、図として読めなかった（`ide-methods.md`「手法ごとの結果」） |

### 筋書き

筋書き（`ide-scenarios.md`）の歩みを、なぞる。

| 筋書き | 歩み → ところ |
|---|---|
| 1 はじめて読む | 開くと、全体のノート（IDE が置いたもの）。1 → 担い手と入口。2 → 約束の図形、「アウトライン」の約束の一覧。3 → 受け渡しの線 → コンテキストのノートの状態。4 → 入口を選び、「詳しく見るところ」（例外の枝は畳んだまま）。5 → 約束 → 守る役 → 入口。6 → 付箋（気づいたこと）。7 → 目を通した印、「欠けと決めごと」の、まだの範囲 |
| 2 約束を追う | 自由なノートを作り、約束を置く。1〜2 → 守る役と、通る入口を、線を辿って置いていく。3 → 支払いの状態の表の塊を置く。4 → 状態の決め方の塊。5〜6 → 入口の手順の塊の、例外。7 → 確かめの塊。追った跡が、一枚のノートに残る |
| 3 AI に頼む | 1 → 注文と支払いのコンテキストのノート。2〜3 → 状態を選び、「AI とのやり取り」。4 →「変更」。足された状態は、アウトラインに現れる。差の重ねを出すと、ノートに、仮に置かれる。5 →「変更」の、関わらない変更。6 → 状態の表の塊に、差の重ね。7 → 手順の塊。8 →「変更」で、受け入れる |
| 4 抜けを決める | 1 → 操作とデータの表の塊。2 → 空きに、付箋（今回は作らない）。3〜4 → 状態の表の塊、確かめの塊。5 →「アウトライン」（説明のないもの）。6 →「欠けと決めごと」 |
| 5 小さく直す | 1〜2 → 図形の名前と説明を、その場で。3 → 状態を描き、向きを引く。4 → 手順の塊の中。5 → 重ねの「差」。6 → 一つ前に戻す |
| 6 中身を知る | 1〜2 →「中身の状況」。3〜4 → 重ねの「確かめ」、確かめの塊。5 → 確かめの塊の、誤りの分け |
| 7 何もないところから | 1 →「AI とのやり取り」。または、全体のノートに、自由な図形で、ざっと描いて、AI に仕様にさせる。2 → 全体のノートに現れた担い手と入口（重ねの「出どころ」）。3 → 約束を描く。4 → 受け渡しの線、コンテキストのノート。5〜6 → 付箋（後で決める、今回は作らない）。7 →「AI とのやり取り」→「変更」。8 →「欠けと決めごと」、「状況」 |

なぞって、分かったこと:

- **追った跡が残る。** 筋書き 2（約束を追う）は、図ごとの画面では、画面を渡り歩くだけだった。ノートでは、辿ったものを置いていくと、その約束についての一枚ができる。
- **付箋が、段 2 で置き場のなかったものを受け持つ。** 気づいたこと、後で決める、今回は作らない。
- **AI の書き換えと、人の配置がぶつかる。** AI が足したものは、勝手には置かれず、アウトラインに現れる（「ノートに置いていない要素」）。AI が名前を変えると、図形は、要素を見失う（下の「残る問い」）。
- **はじめの配置の質が、はじめて読む体験を決める。** IDE が置く、はじめの中身（どれを、どう並べるか）は、段 4 で、見本として詰める。
