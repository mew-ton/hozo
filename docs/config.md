# hozo.toml

## この文書が決めること

プロジェクトの設定ファイル `hozo.toml` の形と読み方、設定に関わる検査（CFG-*）。設計書 §4.5 の名前空間ごとの設定を、出力の単位の一覧に変えたもの（`docs/decisions.md`「設計書から離れた決定」S14）。読むのは `internal/config`。

hozoc 本体は、特定の言語を知らない。どの言語のコードも、単位に書いたトランスパイラが出す（`docs/plugin-protocol.md`「この文書が決めること」）。この文書が決めるのは、どのトランスパイラを、どの名前空間に、どのオプションで起動するかと、その組み合わせが成り立つための規則（基底と相乗り、継ぎ目、型の置き場）。

## 置き場と探し方

- `hozoc` は `--config <path>` か環境変数 `HOZO_CONFIG` で指定されたファイルを読む。どちらもなければ、作業ディレクトリから親へ向かって最初に見つかる `hozo.toml`。指定されたファイルが読めなければ CFG-7（`ConfigInvalid`。`docs/diagnostics.md`「終了コード」）。指定がなく、どこにも見つからなければ「設定なし」で、何も出力せず、設定の検査（CFG-*）もプラグインの探索も行わない。`hozoc check` と `hozoc lsp` は設定なしで動き、`hozoc emit` は書き出すものがないので CFG-7。設計だけの段階で検査できるようにするため（`docs/requirements.md`「モデルが先」）。
- `hozo.toml` のあるディレクトリが**プロジェクトのルート**。`.hozo` の探索、`in`、`out`、プラグインの探索の起点。

## 形

```toml
[hozo]                              # 全体の設定。省略できる
sources      = ["**/*.hozo"]        # ルートからの glob。既定はこの一つ。各単位の out の下と、plugin_dirs の下は常に除く（隠しディレクトリは除かない）
plugin_dirs  = ["plugins"]          # プラグインを探すディレクトリ（docs/plugin-protocol.md「探索」）。ルートからの相対パス。既定は []
max_bindings = 5                    # WIRE-6 の閾値（docs/check.md「配線」）。既定はそこに書いた値

[options.go]                        # トランスパイラ go への、プロジェクト全体のオプション（「オプション」）
module = "example.com/shop-server"

[[emit]]                            # 出力の単位。いくつでも書ける。書いた順が「設定の順」
namespace   = "type"                # 必須。視点の名前空間（FQN）
transpilers = ["go", "go-valid"]    # 必須。一つ以上。トランスパイラの名前（docs/plugin-protocol.md「探索」）。基底を一つと、それに相乗りするもの（「基底と相乗り」）
out         = "gen/type"            # 必須。ルートの下のディレクトリを、ルートからの相対パスで

[[emit]]
in          = ["api/**/*.hozo"]     # 省略できる。ルートからの glob。既定は読み込んだすべてのファイル
namespace   = "server"
transpilers = ["go", "go-valid", "go-http"]
out         = "gen/server"

[emit.options.go-http]              # 直前の [[emit]] の単位の、トランスパイラ go-http へのオプション（「オプション」）
validate = true

[[emit]]
namespace   = "server"              # 同じ名前空間を複数の単位に書ける
transpilers = ["go", "go-valid", "go-cli"]
out         = "cmd/gen"
```

- TOML の読み込みは `github.com/BurntSushi/toml`（`docs/packages.md`「依存の向き」）。
- トップレベルに書けるのは `[hozo]` と `[[emit]]` だけ。ほかのキーは CFG-7。名前空間ごとのテーブル（`[server]`）はない。名前空間の名前に使えない名前もない。
- 単位に書けるキーは `in` / `namespace` / `transpilers` / `out` / `options`。知らないキー、値の型違いは CFG-7。`emit` はテーブルの配列（`[[emit]]`）で、テーブル一つ（`[emit]`）は CFG-7。CFG-7 か CFG-12 のあった単位は使わない（ほかの単位はそのまま読む）。
- `out` はプロジェクトのルートの下のディレクトリ。絶対パス、ルートの外へ出るパス（`../gen`。`./` や `..` を畳んだ後で見る）、ルートそのもの（`.`）は CFG-7。ルートの外を許さないのは、hozoc が書いて消すファイルをプロジェクトの中に限るため（`docs/cli.md`「emit」）。ルートそのものを許さないのは、`out` の下が `sources` から常に除かれ、何も読めなくなるため。
- `[[emit]]` を一つも書かなければ、何も出力しない（検査はできる）。

## 単位

`[[emit]]` の一つが**単位**。一つの単位は、どのファイルを（`in`）、どの名前空間から見て（`namespace`）、どのトランスパイラで（`transpilers`）、どのオプションで（`options`）、どこへ書き出すか（`out`）の組。

- 設定が選ぶのはトランスパイラで、プラグインではない（二つの言葉の定義は `docs/plugin-protocol.md`「この文書が決めること」）。プラグインを入れるとトランスパイラが増え、設定はその中から使うものを名前で選ぶ。
- 名前空間ごとのテーブルに `language` と `plugins` を書き、子の名前空間が継ぐ形（§4.5）をやめた理由: 「プラグインが処理を決める」形は、どの設定がどの出力を作るのかが読み取りにくい。単位にすれば、入力・視点・変換・出力先が一か所に並ぶ（Vite の「プラグインを入れる」と「設定で使う」の分け方と同じ）。同じ名前空間から、トランスパイラごとに別の出力先へ書き出すこともできる。
- `transpilers` の名前からトランスパイラを探す手続き（どのプラグインのものか、見つからないとき、二つ以上あるとき）は `docs/plugin-protocol.md`「探索」。
- `transpilers` に書く順は、起動の順（`docs/plugin-protocol.md`「起動」）と診断の並びにだけ効く。書いた順を入れ替えても、書き出すファイルは変わらない（依存しているものを先に書く必要はない）。

## 基底と相乗り

トランスパイラは、マニフェストの `requires`（`docs/plugin-protocol.md`「マニフェスト」）で二つに分かれる。

| 言葉 | 定義 | すること |
|---|---|---|
| **基底** | `requires` が空のトランスパイラ | その言語で、語彙を知らなくても仕様だけから決まるものをすべて出す（型、op の形、配線の本体。Go なら `docs/plugin-go.md`） |
| **相乗り** | `requires` が空でないトランスパイラ | `requires` に書いたトランスパイラの出力の形を前提に、語彙に固有のファイルだけを足す（`docs/plugin-go-http.md` など） |

- **一つの単位は、基底をちょうど一つ持つ。** 一つもない、または二つ以上なら CFG-20。型と op の形を出すのは基底だけで、二つあれば同じものを二度出す。基底を持たない出力（図や文書だけ）が要るなら、それ自身を基底（`requires` が空）として書いたトランスパイラを、別の単位に置く。
- **単位の基底**は、その単位のただ一つの基底。**単位の言語**は、単位の基底の `language`（マニフェストが持つ）。設定に `language` は書かない。相乗りの `language` は、単位の基底のものと同じでなければならない（CFG-16）。言語の名前は基底が決める文字列で、hozoc は中身を見ない（新しい言語は、基底を入れれば使える）。
- **依存は、すべて `transpilers` に書く。** 単位のトランスパイラ T の `requires` にある名前が、同じ単位の `transpilers` になければ CFG-19。メッセージに、足りない名前と、それを要るトランスパイラを示す（`go-http は go-valid を要るが、transpilers にない`）。hozoc が黙って足すことはしない: 暗黙に加わる依存は、何が動いているかを設定から読めなくする。足した名前のトランスパイラが入っていなければ、今度は CFG-14 になる。
- `requires` は、単位のオプションによらない。オプションで使わなくなる依存（`validate = false` のときの `go-valid`）も、書かなければ CFG-19（オプションごとに要るものが変わると、設定を一行変えただけで単位が読めなくなる）。
- 依存は一方向。`requires` を辿って元に戻る輪は、その単位に基底がないことになり、CFG-20 で分かる。

## オプション

単位ごとに、トランスパイラへオプションを渡せる。汎用のトランスパイラにプロジェクトの事情を伝える、ただ一つの方法。

```toml
[[emit]]
namespace   = "server"
transpilers = ["go", "go-valid", "go-http"]
out         = "gen/server"

[emit.options.go-http]
validate = true
```

- `options` は、トランスパイラの名前をキーにしたテーブルで、値はそのトランスパイラへのオプションのテーブル。`[emit.options.<名前>]` は、TOML の規則で、直前の `[[emit]]` の単位に付く。
- `<名前>` は、その単位の `transpilers` に書いた名前でなければならない。そうでなければ CFG-21（書き間違えたオプションが、黙って捨てられないように）。
- オプションの値に書けるのは、文字列、整数、小数、真偽値、それらの配列とテーブル（JSON にそのまま写せるもの）。日時は書けない（CFG-7）。`options` や `options.<名前>` がテーブルでなければ CFG-7。
- **中身（キーと値の型）を確かめるのは、そのトランスパイラ。** hozoc は中身を見ずに渡す（`View.config.options`。`docs/ir.md`「その名前空間から見た IR」）。トランスパイラは、知らないキーと型の違う値を `emit` の応答の `errors` で返す（それぞれのプラグインの文書の「オプション」と「診断」）。オプションを書かなかったトランスパイラには、空のテーブルが渡る。
- 同じ単位のほかのトランスパイラのオプションと、ほかの単位のオプションも `View` に載る。相乗りが、基底のオプションで変わる形を再現できるようにするため。

### プロジェクト全体のオプション

`docs/decisions.md`「決めたこと」425。どの単位でも同じ値を、一度だけ書く所。

```toml
[options.go]
module = "example.com/shop-server"
```

- `[options.<名前>]` は、設定のいちばん外のテーブル（`[[emit]]` の中ではない）。`<名前>` は、トランスパイラの名前。
- **そのトランスパイラを並べた、どの単位にも、渡る。** 単位が `[emit.options.<名前>]` に、同じキーを書いていれば、単位の値が、効く（キーごと。値がテーブルでも、中を合わせず、丸ごと、単位の値にする）。`View.config.options` に載るのは、合わせた後のもの。トランスパイラからは、どちらに書かれたかは、見えない。
- `<名前>` が、どの単位の `transpilers` にもなければ CFG-24（単位の CFG-21 と、同じ理由）。単位のない設定に書いても、CFG-24。
- 値に書けるものと、形の決まりは、単位のオプションと同じ（CFG-7）。中身を確かめるのも、そのトランスパイラ。
- 使い道の一つ目は、Go のモジュールの名前（`docs/plugin-go.md`「パッケージと import パス」）: プラグインは、プロジェクトのファイルを、何も、受け取らないので、`go.mod` に書いてある名前を、ここに、もう一度、書く。

## 継ぎ目

デコレータの適用が何を出力するかは、そのデコレータを読むトランスパイラが決める（言語ごとの持ち主は基底の文書。Go なら `docs/plugin-go.md`「デコレータ」）。たいていは、相乗りが自分のファイルの中だけで形にできる（入口を作る、実装を出す、材料にする）。できないのは、**op の中身の前後に処理を置く**こと（頻度の制限、計測、キャッシュ、再試行）: op が呼ばれる道は、同じ名前空間の配線からの呼び出しを含めて、基底の出力の中にある。そのために、トランスパイラは、デコレータが**継ぎ目**を要ると宣言できる。

| 言葉 | 定義 |
|---|---|
| **継ぎ目** | op の中身の前と後に、何でも置ける口。基底が、そのデコレータの付いた op を二層で出す: op の**中身**（生成した配線の本体か、葉の実装）と、継ぎ目に制御を渡す**外側**。継ぎ目の中身（前後に置くもの）は、その継ぎ目を宣言したトランスパイラが出す |
| **単位の継ぎ目** | 単位のトランスパイラの、マニフェストの `seams`（`docs/plugin-protocol.md`「マニフェスト」）を合わせたもの: デコレータの FQN と、それを宣言したトランスパイラの組の集まり |

- **継ぎ目を持つのは、本体のないデコレータ。** 本体のないデコレータを、プラグインが、op を包む処理として解釈するなら、継ぎ目を宣言する。語彙として読むだけなら、宣言しない。どちらかは、プラグインが決め、仕様の宣言では、言い分けない（`docs/decisions.md`「決めたこと」393）。本体のあるデコレータ（`docs/grammar.md`「デコレータの本体」）は、包み方が、仕様にあるので、基底が、本体から外側を作り、継ぎ目を持たない（Go なら `docs/plugin-go.md`「本体のあるデコレータ」。継ぎ目を宣言していれば、基底の診断 GO-7）。
- **宣言は静的。** 単位の継ぎ目は、`hozo.toml`（単位の `transpilers`）とマニフェストだけで決まり、仕様にも、オプションにも、トランスパイラの応答にもよらない（`requires` と同じ）。基底は、ほかのトランスパイラの応答を見ずに、どの op を二層で出すかを決められる。hozoc は、単位の継ぎ目を `View.config.seams` で、単位のすべてのトランスパイラに渡す（`docs/ir.md`「その名前空間から見た IR」）。
- **口を出すのは基底、中身を出すのは宣言したトランスパイラ。** 基底は、単位の対象の op（「in」）のうち、単位の継ぎ目にあるデコレータが付いたものを二層で出す。口の形は、基底の文書が決める（Go なら `docs/plugin-go.md`「継ぎ目」）。宣言したトランスパイラは、その口を満たすコードを、op ごとに出す。
- **基底は、デコレータの宣言の節を見ない。** `throws`、`catches … recovers` / `halts` / `ignores` は検査のためのもので（`docs/check.md`「計算」）、基底は、そこから決まった形（例外を捕まえる、投げる）を生成しない。節が言うことを実際に起こすのは、継ぎ目の中身。
- デコレータは FQN で書く。照らす相手は、適用の `Application.decorator`（名前付きデコレータは、汎用のデコレータに展開済み。`docs/ir.md`「デコレータの適用」）なので、書くのは汎用のデコレータの FQN。op 以外の宣言への適用は、継ぎ目を持たない。
- **同じ単位の二つのトランスパイラが、同じデコレータの継ぎ目を宣言していれば CFG-23。** 継ぎ目の中身を出す者を、一人に決めるため（同じファイルを二人が出す CFG-5 と同じ向き）。単位に並べただけで出る（そのデコレータが付いているかは見ない）。別の単位でなら、同じデコレータを別のトランスパイラが宣言していてよい。
- **読む者がなければ、何も出ない。** 単位の継ぎ目にないデコレータの適用に、基底は継ぎ目を出さない。単位のどのトランスパイラも読まないデコレータは、何も生成せず、warning もない: 何も生成しないデコレータは、その言語のために用意されたものではないデコレータと区別がつかない。逆に、単位の継ぎ目にあるデコレータが、単位の対象のどの op にも付いていなくても、何も出ず、診断もない。`seams` に書いた FQN のデコレータが宣言されているかも、確かめない（その語彙を読み込まないプロジェクトで、そのプラグインのほかのトランスパイラが使えなくならないように）。
- **プロジェクトの中のプラグイン。** プロジェクトが自分で宣言したデコレータに継ぎ目が要るなら、それを宣言するプラグインをプロジェクトの `plugin_dirs`（`docs/plugin-protocol.md`「探索」の 1）に置き、単位の `transpilers` に、そのトランスパイラを書く。設定だけで継ぎ目を足す方法（`hozo.toml` に書く、など）はない: 継ぎ目には、中身を出す者が要る。プラグインを置かないなら、そのデコレータは印で、処理は配線の中の op の呼び出しとして書く。
- **継ぎ目が掛かるのは、op を持つ名前空間の出力。** 継ぎ目は単位ごとのもので、同じ名前空間の二つの単位でも、宣言したトランスパイラを並べた単位の出力にだけある。単位を置かない名前空間の op には、基底の出力がないので、継ぎ目もない。別の名前空間の op を呼ぶ側の出力は、相手の op の継ぎ目について何も持たない（Go なら `docs/plugin-go.md`「内側のフォルダと、別の名前空間」）。
- 基底が自分の `seams` を宣言してもよい（口も中身も、自分で出す）。継ぎ目を宣言する相乗りは、継ぎ目を支える基底を `requires` に書く（継ぎ目を知らない基底の単位では、宣言しても口が出ない）。

## 単位の対象

名前空間 N（FQN）を**対象にする単位**は、次の手続き（CFG-13）で決まる。単位 U から見れば、U が対象にする名前空間が **U の対象の名前空間**（単に「単位の対象」と言えばこれ）。

1. A(N) は、N とその祖先のうち、どれかの単位の `namespace` に書かれている最も近いもの（N 自身が書かれていれば N）。どれも書かれていなければ、N を対象にする単位はない。
2. N を対象にする単位は、`namespace` が A(N) であるすべての単位（設定の順）。

つまり、単位はその `namespace` とすべての子孫を対象にする。ただし、別の単位が子孫の名前空間を `namespace` に書いていれば、その子孫と、その下のすべては、祖先の単位の対象から外れる。

- どの単位の対象にもならない名前空間は出力せず、エラーにもしない（人の操作や外部のシステムのように、コードを生成しない部分をモデルに含められる。`docs/requirements.md`「モデルが先」）。検査は出力しない名前空間にも同じに掛かる。
- **単位の `namespace` には、宣言を持つどの名前空間も書ける。** `state` も `op` も持たない、型だけの名前空間（共有の型）も、語彙の名前空間（`docs/vocab.md`「語彙の名前空間」）も書ける。型だけの名前空間の単位は、基底がその型を出すだけの単位になる（`transpilers = ["go"]`）。書けない名前空間を定めていた CFG-8 は欠番（「診断」）。
- 単位 U での名前空間 N の出力先 Dir(U, N) は、`U.out` に、`U.namespace` から N までのセグメントをパスにして足したもの（N が `U.namespace` 自身なら `U.out`、`namespace = "server"` の単位での `server.admin` なら `<out>/admin`）。トランスパイラは、U での N のファイルを Dir(U, N) の下に置く（そこでないパスを返せば PLG-1。`docs/plugin-protocol.md`「emit」）。
- 単位の出力先は `out` とその下のすべて。二つの単位の `out` が同じか、一方が他方の下にあれば CFG-17（比べるのは、`./` や余分な `/` を取り除いたパス。「形」の CFG-7 で使えなかった単位は比べない）。出力先ごとの記録（`docs/cli.md`「emit」の `.hozoc-outputs.json`）と、Dir(U, N) の持ち主を一つに決めるため。
- 同じ名前空間を対象にする複数の単位は、互いに独立。それぞれが自分の `out` に、自分のトランスパイラの出力をすべて持つ。

## in

- `in` は、単位が出力する範囲をファイルで絞る。glob の書き方は `sources` と同じで、照らす相手は読み込んだユーザーのファイル（`sources` に合い、除かれなかったもの）。`in` はファイルを読み足さない。省略すれば、読み込んだすべてのファイル。
- 語彙のファイル（`Span.file` が `hozo:` で始まるもの。`docs/ir.md`「Program」）は、`in` によらず、いつも合ったものとして扱う。語彙の名前空間の単位が、`in` を書かなくても、書いても、その宣言を出力できるようにするため。
- **単位の対象の宣言**は、単位の対象の名前空間の宣言のうち、`in` に合うファイル（と語彙のファイル）に書かれたもの。対象の名前空間が、そういう宣言を一つも持たなければ、その単位はその名前空間を出力しない（トランスパイラも起動しない）。
- 単位 U と、U が出力する名前空間 N（U の対象の名前空間のうち、単位の対象の宣言を一つでも持つもの）の組 (U, N) を**出力**と呼ぶ。出力ごとにトランスパイラを起動し（`docs/plugin-protocol.md`「起動」）、Dir(U, N) に書き出す（`docs/cli.md`「emit」）。「対象」と付く言葉はほかに二つあり、どれも別のもの: 基底が一つの出力に何の宣言を出すかが**出力の対象**（Go なら `docs/plugin-go.md`「出力の対象」）、一度の `hozoc emit` がどの出力を書き出すかが **emit の対象**（`docs/cli.md`「emit」）。
- 検査は変わらない。`sources` の全体を一つのプログラムとして読み、検査する。`in` が絞るのは出力だけ。
- `in` の外の宣言が出力にどう現れるかは、基底が決める（Go なら `docs/plugin-go.md`「出力の対象」: 型と状態は `in` によらずすべて出し、op は `in` に合うものだけを出す）。
- `in` の glob が、読み込んだファイルのどれにも合わなければ CFG-18。

単位の設定と Dir(U, N)、`in` に合ったファイルは、`View.config`、`View.namespaces`、`View.files` としてトランスパイラに渡す（`docs/ir.md`「その名前空間から見た IR」）。

## 型の置き場

型（model、scalar、union、exception）は、基底ごとに一度だけ出力し、使う側は import する。使う側の出力に複製しない（`docs/decisions.md`「決めたこと」67）。

- **名前空間 M が基底 B の出力を持つ**とは、基底が B である単位のどれかが M を出力すること（「in」の出力）。基底は、出力する名前空間の型をすべて出す（Go なら `docs/plugin-go.md`「出力の対象」）ので、M の型がどこにあるかは、設定だけで決まる。
- **型の置き場**: 基底が B の単位 U から見た、名前空間 M の型の置き場は、U が M を出力するなら U 自身の出力 (U, M)、そうでなければ、基底が B で M を出力する単位のうち、設定の順で最初のものの出力。同じ単位の中で閉じられる依存を、別の単位へ向けないため。
- **使う型の名前空間は、同じ基底の出力を持たなければならない。** 出力 (U, N) が、別の名前空間 M の宣言を使っていて（下の表）、M が U の基底の出力を持たなければ CFG-22。メッセージに、使っている宣言の一つと、足す単位の形を示す（`3 番目の [[emit]]（namespace = "server"）は type.User を使うが、type を出力する go の単位がない。[[emit]] namespace = "type"、transpilers = ["go"] の単位を足す`）。
- 語彙の名前空間の型（`http` や `proc` の例外、プロジェクトが宣言した語彙の型）も同じ規則で、使うなら、その名前空間の単位を置く（`namespace = "proc"`、`transpilers = ["go"]`）。型を持たない語彙（デコレータだけの `valid`、`db` など）は、使っても置き場は要らない。
- グローバルの名前空間（`namespace` の外）は、単位の `namespace` に書けず、出力を持てない。そこに宣言した型を出力が使えば、いつも CFG-22 になる。出力が使う型は、名前のある名前空間に置く。

出力 (U, N) が「使う」宣言:

| # | 使うもの | 数える参照 |
|---|---|---|
| 1 | N のすべての model / scalar / union / exception | フィールドの型、インデックスのキーと値の型（`Model.index`）、scalar の元の型、アームの型、例外の引数の型（例外が運ぶ値。`Exception.params`） |
| 2 | N のすべての状態、分類、`read`、効果 | 状態の型、分類の対象の型、ケースの `as` の型、`read` と効果の引数の型、`read` の結果の型、効果の `throws` の例外（`Effect.throws`） |
| 3 | 単位の対象の op | 引数と戻り値の型、`Op.signature.exceptions` の例外 |
| 4 | 単位の対象の配線が呼ぶ op（別の名前空間のものを含む） | 引数と戻り値の型 |
| 5 | 単位の対象の配線の `match` | 述語で決まる分類（`Classify.decidedBy` が `predicate`。`docs/check.md`「ケースの判定」）のうち、別の名前空間のもの |
| 6 | N の効果の引数のうち、型が、そのまま、絞り込んだ型（`T on C.K`）のもの | その分類 C が、述語で決まり、別の名前空間のものなら、C（基底が、効果の入口で、判定関数を呼ぶ: Go なら `docs/plugin-go.md`「効果の入口の確かめ」） |
| 7 | 単位の対象の、本体のない op の戻り値のうち、型が、そのまま、絞り込んだ型のもの | 6 と同じ分類（基底が、単体テストを走らせる側で、判定関数を呼ぶ: Go なら `docs/plugin-go.md`「単体テストの口」） |

- 数えるのは、型（`ref`）、例外、5〜7 の分類が指す宣言の名前空間が N でないもの。型の中の型（`array`、`optional`）は辿るが、参照先の宣言の中までは辿らない（参照先の名前空間の単位が、自分の分を同じ規則で確かめる）。
- デコレータの適用とその引数、別の名前空間の効果と `read` の宣言そのもの（配線の op の `effects` / `reads` の節に書いたもの）、別の名前空間の op そのもの（呼び出し先は、型ではなく、実装を受け取る口になる）、型で決まる分類は数えない。
- Go の基底は、名前空間どうしが、互いの型を使えるように、型だけのパッケージを分けて出す（`docs/plugin-go.md`「型のパッケージ」）。輪になって、出せないのは、表の 1 と、2 の分類の分（型どうし）が、互いを使うときだけ。
- この表は、どの言語の基底と相乗りにも共通の約束: トランスパイラが別の名前空間の宣言を import してよいのは、この表が数えるものだけ。数えないものを import する形が要るようになったら、この表を広げる。

エラーにする理由は三つ。置き場が設定だけから決まり、どのトランスパイラも、ほかのトランスパイラの出力を見ずに正しい参照を書ける。同じ型が二つの出力に複製されて、別の型になることがない。何が出力されるかが設定に書いてあり、hozoc が黙って出力を足さない（依存を `transpilers` にすべて書かせるのと同じ向き）。

## 診断

| ID | 重さ | 手続き |
|---|---|---|
| CFG-5 | error | 書き出すファイルのパス（ルートからの相対パスに正規化したもの）が、二つ以上のトランスパイラから出た。出どころを `Related` 相当としてメッセージに示す。何も書き出さない。例外は `OutputConflict` |
| CFG-6 | warning | 単位のトランスパイラのマニフェストの `unsupported` にあるデコレータの FQN が、その単位の対象の宣言に付いている。付いた位置に出す |
| CFG-7 | error | 知らないキー（`hozo` と `emit` 以外のトップレベルのキーを含む）、値の型違い（`options` がテーブルのテーブルでない、オプションの値が日時、を含む）、TOML の構文エラー、一つの単位の `transpilers` に同じ名前が二度ある、単位の `out` がルートの下のディレクトリでない（絶対パス、ルートの外、ルートそのもの。「形」）。`--config` か `HOZO_CONFIG` で指定されたファイルが読めないとき（「置き場と探し方」）と、設定なしで `hozoc emit` したとき（`docs/cli.md`「手で書くもの」）も CFG-7 |
| CFG-10 | error | 単位の `namespace` の名前空間も、その子孫も `.hozo` にない（語彙のファイルにもない） |
| CFG-12 | error | 単位に `namespace` / `transpilers` / `out` のどれかがない、または空（空の文字列、空の配列）。その単位は使わない |
| CFG-13 | — | 対象の手続き（「単位の対象」）。診断なし |
| CFG-14 | error | `transpilers` の名前のトランスパイラを、入っているどのプラグインも提供していない（探し方は `docs/plugin-protocol.md`「探索」） |
| CFG-15 | error | `transpilers` の名前のトランスパイラを、二つ以上のプラグインが提供している（同上）。どのプラグインかをメッセージに示す |
| CFG-16 | error | 一つの単位のトランスパイラの `language` がそろっていない。例外は `LanguageMismatch` |
| CFG-17 | error | 二つの単位の `out` が同じか、一方が他方の下にある |
| CFG-18 | error | 単位の `in` の glob が、読み込んだファイルのどれにも合わない |
| CFG-19 | error | 単位のトランスパイラの `requires` にある名前が、その単位の `transpilers` にない（「基底と相乗り」）。足りない名前ごとに一つ。解決できなかった（CFG-14 / CFG-15 の）トランスパイラの `requires` は見ない |
| CFG-20 | error | 単位の `transpilers` のうち、基底（`requires` が空のトランスパイラ）がちょうど一つでない（「基底と相乗り」）。CFG-14 / CFG-15 のある単位では出さない（解決できなかった名前が基底かもしれない） |
| CFG-21 | error | `[emit.options.<名前>]` の `<名前>` が、その単位の `transpilers` にない（「オプション」） |
| CFG-22 | error | 出力が使う宣言の名前空間が、その単位の基底の出力を持たない（「型の置き場」）。単位と、足りない名前空間の組ごとに一つ。CFG-20 のある単位では出さない（基底が決まらない） |
| CFG-23 | error | 一つの単位の二つ以上のトランスパイラが、マニフェストの `seams` に同じデコレータを書いている（「継ぎ目」）。デコレータと、宣言したトランスパイラをメッセージに示す。単位とデコレータの組ごとに一つ。解決できなかった（CFG-14 / CFG-15 の）トランスパイラの `seams` は見ない |
| CFG-24 | error | `[options.<名前>]` の `<名前>` が、どの単位の `transpilers` にもない（「プロジェクト全体のオプション」） |

- CFG-1〜CFG-4 と CFG-9 は欠番。名前空間ごとのテーブル、使えない名前、継承、名前空間の `language` とプラグインの照合、`plugins` の名前の探索は、単位の一覧に変えたときになくなった。
- CFG-8 は欠番。「単位の `namespace` が語彙の名前空間である、または、その名前空間と子孫のどれも `state` と `op` を持たない」という規則で、型を基底ごとに一度だけ出力して import する形（「型の置き場」）にしたときになくなった: 型だけの名前空間にも、語彙の名前空間にも、型の置き場として単位が要る。
- CFG-11 は欠番。「単位の言語が `"ts"` だが、TS の既定の出力はまだない」という規則で、出力をすべてトランスパイラに任せたときになくなった（hozoc は言語を知らない。TS の基底がなければ、その名前は CFG-14 になる）。
- 番号は別の意味に使い回さない（欠番の一覧は `docs/requirements.md`「検査の規則の一覧」）。
- `hozo.toml` の診断は位置を持たない（ファイルだけ）。単位を指すときは、何番目の `[[emit]]` か（1 始まり）と、その `namespace` と `out` をメッセージに書く。
- CFG-16 と CFG-5 以外の error は `ConfigInvalid`。終了コードは `docs/diagnostics.md`「終了コード」。
