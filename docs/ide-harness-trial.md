# ハーネスのプレビューを、サンプルに当てた記録

## この文書が決めること

何も決めない。ハーネスのプレビューについて決めたこと（決定 D207〜D214。中身は `ide-screens.md`「仕様の図」「ハーネスのプレビュー」）を、サンプル `order-app`（`tests/samples/order-app/`。`main` の `618740b`）に当てて、数えた記録。

- 見本（`tools.md`「IDE の設計の段階」の段 4）ではない: 図は、描いていない。
- 当てるために、文書が決めていない点を、仮に決めた（「当て方」）。**仮の決めは、案**で、利用者が確かめていない（決定 D566）。
- 分かったことから出た、決める点は、`open.md`「次の段」「Hozo の側の改善する点」に置いた。

## 当て方

この節の細部は、決定 D566 が決めた。

### 節と線

| もの | 取り方 |
|---|---|
| 節 | 仕様の、op、効果、read のすべて |
| 線（呼ぶ） | 配線の呼び出し（`ir.md`「配線」） |
| 線（デコレータが指す） | デコレータの引数が、op を指しているもの（例: `@browser.page.interaction(openLogin, …)`、`@backoffice.recover(…, sayWrongCredentials)`） |
| 入口 | 誰からも呼ばれず、どのデコレータからも指されない op |
| 入口から辿れる節 | 入口から、二つの線を、末端まで辿ったもの |

### 中身の強度

この記録は、ハーネスの段より前の、四つの段（作られる、確かめられる、形だけ、約束なし）で数えた。今の物差しは、ハーネスの段の数字（`ide-screens.md`「中身の強度の段」）。当て方: 作られると、確かめられるは、段 4。形だけは、段 2。約束なしは、段 1。数え直しては、いない。どの節が、どの段かを、次のとおりに決めた。

| 節 | 段 | 仮に決めた理由 |
|---|---|---|
| 配線の op | 作られる | 中身は、仕様の配線 |
| 葉の op（外の仕組みの名前空間のもの、`clock.now`） | 約束なし | 中身は、こちらが作らない |
| 葉の op（そのほか） | 形だけ | 仕様が言うのは、型と、返す例外だけ |
| `@db.insert`、`@db.delete` の付いた効果。`@db.find`、`@db.list`、`@db.where` の付いた read | 作られる | 中身は、プラグインが作る（`plugin-go-sqlite.md`「read の中身」「効果の中身」） |
| 行の遷移が、後のケースを言う効果。状態の分類の遷移を言う効果。`as` のない `put` で、その表に行の分類があるもの | 確かめられる | テストで確かめる、と決めてある（`check.md`「検査器が確かめないこと」） |
| 行の遷移が、後のケースを言わない効果 | 約束なし | — |
| そのほかの効果と read | 形だけ | 仕様が言うのは、宛先と型だけ |

### 設計を守る強度

数える設計の決まりは `ide-screens.md`「直に依る設計」、覆えているかの決まりは同「テストで覆えている」。図形の定義（`ide-shapes.md`）は、まだないので、節を直に指す設計を、次のとおりに取った。

| 設計の種類 | 取り方 | 覆えるか（仮の決め） |
|---|---|---|
| 入口 | その op が、入口であること | 判定できない: 入口が「破られる」とは何かを、決めていない |
| 例外 | op が宣言した例外の、一つずつ | 配線の op は、覆える（どの場合に出るかが、手順にある）。葉の op は、覆えない（いつ出すかを、仕様は言わない） |
| 例外のとき変わらないもの | op が宣言した関係（`prevents effects`）の、一つずつ | 例外に同じ |
| 向き | 効果の、行の遷移と、状態の分類の遷移の、前のケース一つにつき、一つ | 覆える |
| 約束 | `@pact.promise` の、一つずつ | 覆えない（印だけ。`requirements.md`「PRD の水準の記述」） |
| 語彙のデコレータ（約束のほか） | 節に付いたデコレータの、一つずつ | `@db.*` と、配線の op の `@http.*` は、覆える（プラグインが作る）。そのほかは、判定できない（その語彙のプラグインが、ない） |

中身が作られる節に乗った設計は、テストを作るまでもなく、破れない。これも、「覆える」に数えた。

## 分かったこと

- **依存の図は、今の仕様から、出せた。** 入口 27 から、末端まで、辿れる。入口ごとに、節の数（5〜68）と、強度の内訳が、はっきり違う: `hooks.trackingEvent` は、「形だけ」「約束なし」の節が 0、`storefront.onPlaceOrder` は、30。
- **入口の多くは、画面の操作だった。** 27 のうち、23 が `web`（残りは、届く通知 2、定期の仕事 2）。フロントエンドを仕様に書いてあると、入口は、API の op ではなく、それを呼ぶ画面の op になる。
- **デコレータが指す op を、線に入れないと、図が切れる。** 10 の op（画面を開く op）は、配線からは呼ばれず、デコレータの引数からだけ、指される。どのデコレータの、どの引数が、依存かは、語彙の意味。
- **まとまり（`web`、`api`、`domain`、`external`）は、フォルダにあって、名前空間には、ない。** 名前空間は、平らに 21 並ぶ。`storefront` がフロントエンドで、`ordering` がバックエンドであることは、仕様からは、読めない。
- **DB の端は、名前空間ではなく、語彙に現れた。** `@db.*` の付いた効果と read（36）が、DB に触れる節。業務の名前空間の中にある。
- **op の中身の強度は、二つに割れた。** 作られる（184）か、形だけ・約束なし（78）で、「確かめられる」の op は、0。葉の op の振る舞いを、確かめられる形で言う書き方が、言語にない。
- **「形だけ」の効果は、ほとんどが、画面の状態の効果。** 35 のうち、27 が `web`。
- **二つの強度は、別のことを言った。** 約束 11 のうち、10 は、配線の op（中身の強度は、いちばん上）に付いていて、どれも、覆えない。中身の強度だけでは、ここは、穴に見えない。
- **割合は、例外の数に、引っぱられた。** 設計 581 のうち、例外が 323。同じ例外（44 種類）を、道の上の op が、一つずつ宣言するので、数が増える。そのほとんどは、配線の op のもので、覆える。`storefront.onPlaceOrder` は、109 のうち 84 が覆えるが、覆えない 9 が、いちばん大事な約束を含む。
- **約束の重みは、それを決める葉には、乗らなかった。** 約束は、配線の op（`ordering.place`）を直に指す。約束が守られるかを決めるのは、その下の葉だが、葉の op 78 のうち、52 は、直に依る設計が 0（多くて 4）。「大きくて、派手」（`ide-screens.md`「節の見た目」）になるのは、約束の付いた配線の op で、葉は、「小さくて、派手」になる。
- **入口という設計は、覆えているかを、決められなかった。** 入口が「破られる」とは、何かが、決まっていない。
- **語彙のデコレータの 6 割は、判定できなかった。** 194 のうち、120。その語彙のプラグインが、何を作り、何を確かめるかを言わないと、決まらない（サンプルの `page`、`nav`、`webhook`、`clock`、`outside` などは、プラグインが、ない）。
- **図形の定義がないので、「直に依る設計」は、仮の取り方で数えた。** 図形と線の定義（`ide-shapes.md`「図形の定義」「線の定義」）が決まると、数え方も、決まる。
