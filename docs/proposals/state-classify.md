# 提案: 状態を分類で表し、効果をその変化として宣言する

## この文書が決めること

言語の仕様の変更の提案。状態の「場合」を `classify` で名付け、`effect` がその変化を言えるようにし、配線が状態の場合で分岐できるようにする。まだ決定ではなく、決まったら設計書（`mew-ton/drafts` の `hozo/README.md`。「§n」はその節）の §5.2・§6.2・§10・§12 と、このリポジトリの `docs/grammar.md`・`docs/ir.md`・`docs/resolve.md`・`docs/check.md`・`docs/emit-go.md` に移してこの文書は消す。「決めること」に残っている項目が決まるまで実装しない。

## 動機

値については §10.1 が「結果の種類で名付けた排他なケース」を徹底しているが、状態の場合分けは名前を持たずに三か所へ漏れている。

- 例外の名前: §7.1 の `AlreadyLoggedIn`、§5.2 の `UserHasOrders` は「呼ばれた時点で状態がどの場合だったか」だが、どの状態のどの場合かは宣言にない。
- 効果の説明文: §6.2 の `effect removeToken on token.put; // none を入れる` は、どの場合からどの場合になるかをコメントに逃がしている。
- 配線: §10.2 の `match` が分類できるのは値だけで、状態の場合では分岐できない。

## モデル

1. **根底はリスト型の状態**。`list<T>` は組み込みの効果と組み込みの分類を持つ。
2. **組み込みの効果は相対的な変化**。`post` は列数が増える、`put` は列数が変わらない、`delete` は列数が減る。リストが空かどうかは問わない。
3. **組み込みの分類は `Empty` と `HasItems`**。リストが持つ絶対的な場合。
4. **`single<T>` は列数が 1 で固定のリスト**。列数を変える `post` / `delete` は書けず（今の STATE-1）、組み込みの分類も持たない（常に一列）。
5. **ユーザーは状態を対象に `classify` を宣言できる**。値の分類（§10.1）と同じく、名前と説明だけを宣言し、判定は述語として人が実装する。
6. **`effect` は、組み込みの効果の上に名前と説明を付けたもの**（今のまま）。加えて、分類の上でどの場合からどの場合になるかを宣言できる。

組み込みの効果（相対）と分類の場合（絶対）は別のものなので、宣言として競合しない。`post` は `Empty` でも `HasItems` でも「増える」で、場合を知らなくても定義できる。

## 書き方

```ts
namespace browser {
  @localStorage
  state token: single<server.Token?>;

  /** ログインしているかどうか */
  classify Auth of token {
    LoggedIn;
    LoggedOut;
  }

  /** 手元のトークンを消す */
  effect removeToken on token.put: Auth.LoggedIn -> Auth.LoggedOut;

  op openHome(): HomePage {
    return match token by Auth {
      LoggedIn  => loadHome();
      LoggedOut => guestHome();
    };
  }
}

namespace server {
  @db
  state carts: list<CartLine>;

  /** カートに一行足す。組み込みの効果から、後は HasItems と分かる */
  effect addCartLine on carts.post;

  /** カートを空にする */
  effect clearCart on carts.delete: list.HasItems -> list.Empty;

  op showCart(): CartView {
    return match carts by list {
      Empty    => emptyCartView();
      HasItems => cartView();
    };
  }
}
```

- 状態を対象にした分類は `classify C of <状態>`。対象が型か状態かは名前の解決で決まる。
- 組み込みの分類は `list` という名前で指す（`match carts by list`、`list.Empty`）。
- 効果の場合の変化は `: <分類>.<前> -> <分類>.<後>`。省略できる（今の書き方はそのまま通る）。
- `match <状態> by <分類>` の対象は、今の名前空間の状態だけ。持ち主が自分の状態を読むので §5.1 に反しない。

## 意味

### 状態の分類

- 排他と全集合は値の分類と同じ（§10.1）。`default` も同じ。
- 宣言した名前空間（＝状態の持ち主）の中でだけ使える。§3.2 の「`classify` は宣言した名前空間の中でだけ使える」と、§5.1 の「状態は持ち主の外には出ない」が同じ結論になる。
- 述語は状態を読む判定関数に訳される（`carts` の `Empty` なら `isCartsEmpty` に当たるもの）。値の分類の述語が純粋な関数なのに対し、状態の述語は保存先への問い合わせで、人が実装する。
- 判定関数は二つの場面で呼ばれる。配線の `match` の実行時と、テストで効果の結果を確かめるとき（「検証」）。配線で使われない分類でも、テストのために宣言する意味がある。

### 効果の場合の変化

`effect e on s.op: C.A -> C.B` は「e が起きたなら、起きる前の s は C の A で、起きた後は B」。

- 前と後はどちらも同じ分類のケース。ケースの和（`A | B`）と `any`（どのケースでも）も書ける。
- 組み込みの効果と組み込みの分類の間には、言語が知っている関係がある。宣言がこれと食い違えばエラー。

  | 組み込みの効果 | 前 | 後 |
  |---|---|---|
  | `post` | `any` | `HasItems` |
  | `put` | `HasItems` | `HasItems` |
  | `delete` | `HasItems` | `Empty` か `HasItems` |

- `list` の状態の効果で、組み込みの分類について何も書かなければ、この表の通りとみなす。
- ユーザーの分類については、書かなければ「不明」。§7.3 の「宣言がなければ不明」と同じ扱い。

### 検証

§12.1 の「設計どおりかのアサーション」に、効果の結果を足す。

| 対象 | アサーション |
|---|---|
| 効果（場合の変化を宣言したもの） | op の呼び出しの前に判定関数で前の場合を、後に後の場合を確かめる。効果が起きた（成功、または `keeps`）なら宣言どおりの変化。起きていない（`prevents`）なら場合は変わっていない |

これにより、§7.3 の `prevents` / `keeps` が実行時に確かめられる意味を持つ。§12.2 が「Hozo の外」としている「効果の観測（状態がどう変わったかの検証）」のうち、分類の場合で言える範囲は Hozo の中に入る。値そのものの検証（何がセットされたか）は外のまま。

## 既定の出力（Go）

- 状態の分類ごとに、人が実装する述語のインターフェースと判定関数を出す。述語は `func(ctx context.Context) (bool, error)`。値の分類（`docs/emit-go.md`「classify」）との違いは、引数に値を取らず、失敗しうること。
- 組み込みの分類は `Empty` の述語一つで足りる（`HasItems` はその否定）。`States` に `<状態>IsEmpty(ctx) (bool, error)` を足す。
- `match <状態> by <分類>` は、判定関数を呼んで `switch` する（`docs/emit-go.md`「match」と同じ形）。

## 決めること

1. **組み込みの分類の名前**。ケースは `Empty` / `HasItems` でよいか。分類そのものを `list` で指す書き方（`by list`、`list.Empty`）でよいか。
2. **`single<T?>` に組み込みの分類を持たせるか**。リストの `Empty` / `HasItems` に当たるものとして「値がある / ない」を組み込みにするか、常にユーザーの分類（`Auth` のように意味で名付ける）にするか。提案は後者（§16 の「空になりうるかは値の型（`T?`）だけで表す」と同じ考え方で、意味のある名前を強制できる）。
3. **一つの効果が言える変化の数**。リストの効果は組み込みの分類とユーザーの分類の両方で変化を持ちうる。提案は「分類ごとに高々一つ、`,` で並べる」。
4. **検査器が変化をどこまで使うか**。提案は、所属と組み込みの関係の確認、IR への搭載、「検証」のアサーションまで。配線の行をまたぐ追跡（効果の後の `match` で到達しないアームの検出など）は、§7.3 の「不明」と絡むので後で別に決める。
5. **例外と場合の結びつけ**。`AlreadyLoggedIn` のような例外が「前の場合が合わなかった」ことを表す、と書けるようにするか。§16 の「状態 × 入力の表で分岐を網羅させる」に近づくので、この提案には含めない。
6. **リストの一部を対象にした分類**。`carts` の全体ではなく「このユーザーのカート」の場合を言いたいとき、述語は引数（どのユーザーか）を要る。提案の範囲は全体の分類だけで、部分は葉の op で値を取ってから値の分類で書く（今のまま）。
