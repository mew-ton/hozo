# Hozo の実装の要件

## この文書が決めること

Hozo の実装（`hozoc`、言語サーバー、エディタの対応、プラグイン）を作るために、設計書から導いた要件と、設計書にはなく実装のために決めることを一覧にする。言語の意味（何が正しい Hozo か）はこの文書では決めない。設計書が持ち主で、この文書はそれを使う側。

設計書は `mew-ton/drafts` の `hozo/README.md`（https://github.com/mew-ton/drafts/blob/main/hozo/README.md ）。この文書の「§n」はその節番号。導出の元にしたのはコミット `19e0820` 時点の内容で、設計書が変わったらこの文書を見直す。

## 作るもの

このリポジトリはモノレポで、Hozo の実装をすべて持つ。

## 自己展開

hozoc は自分自身の境界（コマンド、ファイル、プラグインとのやり取り）を `.hozo` で書き、そこから Go の CLI の骨組みを生成する。設計書の `examples/hozoc.hozo` がその叩き台で、§14「合わないものは境界（入力・出力・所有する状態）だけをこの型で書き、中身は別の仕様手段に任せる」に従って、解析や検査の中身は書かない。

進め方は三つ:

1. **仮の CLI**: 手で書いた Go で、`.hozo` を解析・検査し、Go の既定の出力（§4.3）を書き出せるところまで作る。`cli` の語彙（`examples/hozoc.hozo` の `cli.command` / `cli.arg` / `cli.flag` / `cli.env` / `cli.exitCode`）を Go の CLI の骨組み（サブコマンドの振り分け、フラグと環境変数の読み取り、終了コード）にするプラグイン `plugins/go-cli/` もここで作る。
2. **hozoc を `.hozo` で書く**: `examples/hozoc.hozo` を元に、リポジトリ直下の `cli.hozo` と `hozo.toml` を書く。`lsp` サブコマンドもここに op として入れる。仮の CLI の `check` を通す。
3. **置き換え**: 仮の CLI が `cli.hozo` から Go を生成し、`cmd/hozoc` の手書きの骨組みをそれで置き換える。葉の op（解析、検査、展開、プラグインの呼び出し、言語サーバー）の中身は手で書いたものをつなぐ。以降、CLI の骨組みの変更は `cli.hozo` を変えて生成し直す。

この順番にする理由は、最初の利用者を hozoc 自身にして、既定の出力とプラグインのプロトコルを本物の入力で確かめるため。`examples/hozoc.hozo` が「書けなかったもの」として挙げた三つ（「決まっていない数値と強さ」）は、2 の時点で設計書と一緒に解く。

## プラグインの書き方

プラグインは展開先の言語で書く。TS のコードを出すプラグインは TS（Node）で、Go のコードを出すプラグインは Go で書く。§4.6「どの言語で書いてもよく」の範囲で、プラグインの実行環境の要求を利用者の手元にあるもの（TS のプロジェクトには Node、Go のプロジェクトには Go）に一致させるため。protoc の `protoc-gen-go` と `ts-proto` と同じ分かれ方。

プラグインの側で IR を扱うための SDK（IR の型と、標準入出力の JSON の読み書き）を言語ごとに用意する。Go はこのリポジトリの `ir` パッケージと `plugin` パッケージをそのまま import する。TS は `sdk/ts/` を npm パッケージとして出す。npm のパッケージ名は未確認で、出す前に確かめる。

IR の JSON の形の持ち主は Go の `ir` パッケージ（手で書く）。JSON スキーマ `schema/ir.schema.json` はそこから生成し、TS の型はスキーマから生成する。生成物が元から遅れていないことをテストで確かめる（「シンタックスハイライト」のキーワードの一覧と同じ考え方）。IR の意味（何をどう正規化するか）は `docs/ir.md` が持ち主で、`ir` パッケージはその形。

## リポジトリの構成

一つの Go モジュール `github.com/mew-ton/hozo` に、役割ごとのパッケージとディレクトリを置く。

```
go.mod                 module github.com/mew-ton/hozo
hozo.toml, cli.hozo    hozoc 自身の仕様と設定（「自己展開」）
cmd/hozoc/             CLI の main。骨組みは cli.hozo から生成し、葉の op の実装をつなぐ
ir/                    IR の型（公開。Go のプラグインが import する）
plugin/                Go 向けプラグイン SDK（公開。標準入出力の JSON の読み書き）
internal/syntax/       字句・構文解析と構文木
internal/check/        検査器
internal/emit/         既定の出力
internal/config/       hozo.toml
internal/lsp/          言語サーバー（hozoc lsp の中身）
plugins/<name>/        プラグイン。一つのディレクトリが一つの実行ファイルと hozo-plugin.toml（§4.6）。Go なら main パッケージ、TS なら npm パッケージ
sdk/ts/                TS 向けプラグイン SDK（IR の型はスキーマから生成）
schema/                IR の JSON スキーマ（ir パッケージから生成）
vocab/                 標準の語彙の .hozo
editors/vscode/        VS Code 拡張（ハイライトの文法、hozoc lsp のクライアント）
tests/corpus/          設計書の例を集めたテストの入力
docs/                  設計書、文法、IR、この文書
```

`internal/` の下は `hozoc` と言語サーバーだけが使う。プラグインが依存してよいのは `ir` と `plugin` だけ（§4.3「どのプラグインも既定のインターフェースに依存する」と同じく、依存先を約束した形だけにするため）。

## 段階

| 段階 | 入口 | 終わったと言える条件 |
|---|---|---|
| 1 | 仮の CLI（「自己展開」の 1） | `docs/grammar.md` と `docs/ir.md` がある。設計書の例と `examples/hozoc.hozo` をすべて解析でき、「検査の規則の一覧」のうち語彙に固有でない規則がすべて実装され、各規則に成功と失敗のテストがある。`hozo.toml`（§4.5）を読み、Go の既定の出力（§4.3）を書き出せる。§4.6 のプロトコルで `plugins/go-cli/` を呼べる |
| 2 | hozoc を `.hozo` で書く（「自己展開」の 2） | `cli.hozo` が仮の CLI の `check` を通る |
| 3 | 置き換え（「自己展開」の 3） | `cmd/hozoc` の骨組みが `cli.hozo` から生成したもので、`hozoc check` と `hozoc emit` が生成後も同じ結果を返す。生成物が `cli.hozo` から遅れていないことをテストで確かめる |
| 4 | `hozoc lsp`、シンタックスハイライト | VS Code で、診断がその場で出て、定義へジャンプでき、ホバーで説明（§3.4）が読め、`.hozo` に色が付く |

| 6 | `hozoc import` / `hozoc extract`、§12 のアサーションとカバレッジ | 段階 5 が終わってから要件を書く |

段階 1 に入る前に、「最初に決めること」の全部を済ませる。段階 1 の最初の成果物は「文法」と「IR の形」の文書で、パーサーと `ir` パッケージはそこから書く。

## 最初に決めること

### 実装言語

決定（2026-11-09）: 本体と言語サーバーは **Go**。

§4.4「`hozoc` は特定の実行環境に依存しない」と、§16 で TypeSpec を廃案にした理由「Node.js の上で動き、特定の実行環境に依存しない方針と合わない」から、本体は実行環境を要求しない単一のバイナリにする。候補は Rust と Go で、どちらも満たす。

Go にした理由は「プラグインの書き方」に依る。設計書の例は最初から `browser` が TS、`server` が Go（§4.5）で、Go 向けの一次プラグインを初期から持つ。本体が Go なら、Go のプラグインは IR の型を本体から直接 import でき、SDK の生成は TS 向けだけで済み、モノレポのツールチェーンは Go と Node の二つで済む。Rust なら SDK を TS と Go の両方に生成し、ツールチェーンは三つになる。Rust の利点（WASM / napi で Node のプロセス内に本体を載せやすい）は、今は必要になっていない。

言語に関わるもの（解析、検査、展開、言語サーバー）はすべて Go の `hozoc` に集約する。VS Code 拡張だけは TypeScript で書くが、`hozoc lsp` を起動して接続する薄いクライアントにとどめ、言語の知識を持たせない。エディタの実行環境が決めることで、言語サーバーの側には実行環境を持ち込まない。クライアントの側に Volar などの道具を使うかは、拡張を作るときに決める。

### 設計書の置き場

設計書を `drafts` に置いたまま実装を進めると、実装から見つかった修正が二つのリポジトリに分かれる。`drafts` の README の運用方針「育っていったアイデアが実装フェーズに入ったら、別リポジトリに切り出すことを検討する」に従い、設計書をこのリポジトリの `docs/design.md` に移し、`drafts/hozo` はここへのリンクだけにすることを推奨する。移すまで、この文書は `drafts` を参照する。

## 設計書にない、実装に要るもの

### 文法

設計書は例で書かれていて、文法の定義がない。パーサーは文法から作るので、段階 1 の最初に `docs/grammar.md` を書く。例から拾った、文法が形を決めるべきもの:

- 型: `string` / `boolean` / `int` / `float` / `Time` / `Duration`、`T[]`、`T?`、`Record<K, V>`（§4.1）。状態の形 `list<T>` / `single<T>`（§5.2）。デコレータの引数の型 `any exception` / `any effect` / `any state` / `any op` / `any model` / `any variant`、`any effect on location.put`、ユニオン名（§8.2）、`int | float`（§4.2 の `valid.min`）。絞り込まれた型 `WarrantyKind.Yamada<server.Item>`（§10.2）。`void`（§7.1）。その場で書く model `{ ... }`（§6.1、§11.2）。
- 宣言: `model`（フィールド、`?`、既定値 `= 1`、`is X omit y`）、`scalar X extends B`、`union`（`A: { ... }`、`B: M`、`member;` の三つの書き方）、`state`、`op`（`effects A | B`、複数行の `throws`、`prevents` / `keeps`）、`exception X: M`、`effect e on s.op`、`classify` / `condition`、`decorator`（引数、`for`、`throws` / `catches` と `recovers` / `halts` / `ignores`、別名 `= generic(args)`、`@external`）、`bind s to ns.*` / `ns.**`、`namespace`（ブロックの入れ子とドットの書き方）。
- 配線（§9、§10.2）: `const`、`return`、値を返さない呼び出しの行、`match x by C { A | B => call(); default => none; }`、引数に書けるもの（名前、フィールド参照、リテラル、レコードの組み立て `{ page: query.page }`）、`none`。
- リテラル: 文字列、整数、小数、真偽、`Duration`（`5m` / `30s`）。デコレータの引数の位置指定 `@http.status(401)` と名前指定 `@http.header(name: "Authorization")`。
- コメント: `/** */`、`//`、`/* */` と、タグ `@param` / `@throws` / `@see`（§3.4）。

### IR の形

§2「IR（中間表現）を正とする」、§4.6 で IR を JSON でプラグインに渡す、とあるが IR の形は定義されていない。段階 1 で意味を `docs/ir.md` に、形を `ir` パッケージに定義し（「プラグインの書き方」）、JSON にはプロトコルの版を入れる。IR には設計書が求める正規化を反映する: 名前空間の併合（§3.2）、`condition` を `default` 付きの `classify` にする（§10.1）、`void` と省略の同一視（§7.1）、名前付きデコレータを汎用デコレータと引数に展開（§8.2）、デコレータの入れ子への正規化（§8.2）、op の引数は書かれたまま（§7.1）、ドキュメンテーションコメントの説明（§3.4）。

### 「その名前空間から見た IR」

§4.6「プラグインが受け取るのは、その名前空間から見た IR だけ」の中身が定義されていない。`docs/ir.md` で決める。含めるべきもの: その名前空間の宣言。使っている別の名前空間の型（§4.5「その型は使う側の名前空間の言語でも型として出力する」）。呼んでいる別の名前空間の op の、その名前空間から見た関数の型。関数の型には `bind` を反映し（§4.3「`bind` で埋まる位置は入力から消える」）、`@external` の例外を足す（§8.2「型はどの名前空間から見るかで変わる」）。

### 語彙プラグインの読み込み

§4.2 の語彙プラグインは `namespace http { ... }` のように Hozo の構文で宣言を提供するが、§4.6 のマニフェストにその宣言のファイルを指す項目がなく、§4.5 では「語彙の名前空間（`http` / `db` / `page` / `valid` など）は実行環境を持たないので書かない」とある。hozoc が `http` や `valid` の宣言をどこから読むかが決まっていない。案: マニフェストに `vocabulary = ["vocab/*.hozo"]` を足す。標準の `valid` は §6.5「`valid` の標準の制約の中身は展開器が持ち」に合わせて hozoc 本体に同梱する。設計書に返す。

### プラグインの探索

`hozo.toml` はプラグインを名前（`"react-router"`）で書き（§4.5）、マニフェストは `command` を持つ（§4.6）が、名前からマニフェストのファイルに至る方法が決まっていない。案: `hozo.toml` の `[hozo]` テーブルの `plugin_dirs` の中と、`PATH` 上の `hozoc-plugin-<name>` の隣の `hozo-plugin.toml` を探す。段階 3 の前に決める。

### 既定の出力の担い手と言語

§4.3「展開器は、仕様の宣言をその言語の既定の形で出力する。プラグインがなくても、これだけで生成できる」から、言語ごとの既定の出力は hozoc 本体が持つ。§6.5 の標準の制約の中身も同じ。対象の言語は決まっていない。設計書の例は TS と Go。決定: 最初は Go（「自己展開」で hozoc 自身を生成するため）、TS は段階 5。

### 語彙に固有の検査

§11.2 に「`view` は、そのアームの型でなければならない（検査器が確かめる）」と、ルーティングを「検査だけする（キャッチオールの有無、パターンの重複）」とあるが、どちらも `page` の語彙に固有の検査で、§4.1「`http`・`db`・`page`・`valid` などは一つも組み込まない」と両立しない。誰が検査するかが決まっていない。案は二つ: デコレータの引数の型で制約を書けるようにする（`view` を「付けた op の出力のアーム」に限る型）か、プラグインのプロトコルに `"direction": "check"` を足す。決まるまで、この二つは段階 1 に含めない。設計書に返す。

### 診断の形

`examples/hozoc.hozo` の `Diagnostic` は `at: string` と `message` だけで、終了コードは `CheckFailed` が 1、`ConfigInvalid` / `LanguageMismatch` が 2、`OutputConflict` が 3。hozoc の診断には次を持たせる: 重さ（error / warning）、位置（ファイル、行、列の範囲）、メッセージ、規則の ID（「検査の規則の一覧」の ID）。終了コードは `hozoc.hozo` の値を使う。エディタと CI のために `--format json` で同じ内容を出す。一度の実行で見つかる誤りはすべて報告し、最初の一つで止めない。

### 決まっていない数値と強さ

- §9「束縛の数が一定を超えたら『op に切り出す候補』として警告する」の「一定」が決まっていない。案: 既定 5、`hozo.toml` の `[hozo]` で変えられる。
- §3.3 の命名規則（型は UpperCamelCase、実行・適用されるものは lowerCamelCase）に違反したときが error か warning か決まっていない。案: warning。
- `examples/hozoc.hozo` の「書けなかったもの」三つ（状態の宣言から設定の値 `{out}` を参照する書き方、名前空間ごと・プラグインごとの繰り返し、デコレータの引数に実行時の値 `{plugin.command}` を入れる書き方）は設計の未決事項だが、§15「未決事項」は「なし」になっている。設計書に返す。

### 検査の規則の一覧

設計書の検査の規則は節ごとに散っている。実装とテストが規則を一つずつ指せるように、ここで ID を振る。規則の意味は設計書の節が持ち主で、この表は引くための索引。実装の中のコメントとテストの名前はこの ID を書き、この表は実装を列挙しない。

| SYN-2 | ドキュメンテーションコメントはデコレータより上（文法で閉じる。同上） | §3.4 |
| NS-1 | 別の名前空間の宣言は常に修飾して参照。外側を自動で探さない | §3.2 |

## 言語サーバー

`hozoc lsp` が Language Server Protocol のサーバーとして標準入出力で動く。別のバイナリにしないのは、配布物を一つにし、CLI と言語サーバーで解析・検査の実装がずれる余地をなくすため。エディタは選ばない。VS Code は最初のクライアントで、拡張は `hozoc lsp` を起動して接続するだけ。`lsp` も `cli.hozo` の op として宣言する（長く動くプロセスだが、§14 に従って境界だけを書く）。

提供する機能と、それが本体のライブラリに求めること:

| 機能 | 元になるもの | 本体への要求 |
|---|---|---|
| 診断 | 「検査の規則の一覧」の規則。`hozoc check` と同じ結果、同じ ID | 検査器は一つで、CLI とサーバーの両方から呼ぶ。結果の違いは許さない |
| 定義へジャンプ、参照の検索 | 名前の解決（§3.2） | 解決した参照先を、宣言の位置とともに保持する。語彙プラグインと標準の語彙の宣言にも飛べる |
| ホバー | ドキュメンテーションコメントの説明（§3.4）と、宣言の形（op なら引数・出力・`throws` / `effects`） | 説明は IR に入る（§3.4）ので、IR から引く |
| ドキュメントのシンボル | 宣言の一覧と入れ子（名前空間） | 構文木から引く |
| 補完 | 参照できる名前。別の名前空間は修飾した形（§3.2） | 名前の解決と同じ表 |
| コードアクション | THROWS-1 の「どれが漏れているか」を `throws` に足す、など、診断が名指しするものを機械的に直せるもの | 診断は、直し方に要る名前を構造化して持つ（メッセージの文字列だけにしない） |

段階 4 で作るのは診断・定義へジャンプ・ホバー・ドキュメントのシンボル。補完とコードアクションは段階 4 の後。

本体のライブラリへの前提条件:

- パーサーは誤りに耐える。構文の誤りがある箇所だけを飛ばし、残りの宣言は解析して検査する。IDE では書きかけの文書が常に入力になるため。
- すべての構文木と IR の節は元の位置（ファイル、バイトの範囲）を持つ。LSP は行と UTF-16 の列で位置を表すので、変換はサーバーの側で行う。
- 解析の単位はプロジェクト全体（`hozo.toml` のあるディレクトリ以下の `**/*.hozo`、`examples/hozoc.hozo` の `sources` と同じ）。一つのファイルの変更で全体を解析し直してよいが、エディタの一打ごとに体感できる遅れが出ない速さにする。差分の解析は、遅れが出てから考える。
- 開いているが保存していない文書の内容を、ディスクの内容より優先して解析する。

## シンタックスハイライト

TextMate の文法（`editors/vscode/syntaxes/hozo.tmLanguage.json`）で色を付ける。VS Code のほかに GitHub の表示（linguist）など、言語サーバーがない場所でも使える形だから。言語サーバーの semantic tokens による色分けは、段階 4 の後に足してよいが、TextMate の文法を置き換えるものではない。

色を分けるもの: 予約語と文脈キーワード（`docs/grammar.md`「予約語」）、デコレータ（`@` から名前まで。名前空間の修飾を含む）、型の位置の名前と値・実行の位置の名前（§3.3 の命名規則に沿う）、リテラル（`docs/grammar.md`「リテラル」）、コメントとドキュメンテーションコメント（中の `@param` / `@throws` / `@see` も分ける）。文脈キーワードは、その位置（`for` の後ろ、`any` の後ろ、`on 状態.` の後ろ）でだけ色を付ける。

予約語と文脈キーワードの一覧は `docs/grammar.md`「予約語」が持ち主。パーサーの字句解析器と TextMate の文法は両方ともそこから書き写すので、二つの一覧が一致することをテストで確かめる（どちらかを変えたとき、もう一方の変え忘れを検出するため）。

## 品質の要件

- 配布: OS ごとの単一のバイナリ `hozoc`。実行環境（Node.js、JVM など）を要求しない（§4.4）。VS Code 拡張は、対応する OS のバイナリを同梱するか、初回に取得する。
- 共有: `hozoc check` と `hozoc lsp` の診断は同じ検査器の同じ呼び出しで作る。同じ入力に対する診断が二つの入口で食い違わないため。
- 決定性: 同じ入力から同じバイトの出力を作る。出力の並びは宣言の並びに従い、ハッシュの順序に依存しない。生成物の差分がレビューできるため。
- 診断: 漏れを指摘するときは何が漏れているかを名指しする（§7.2「どれが漏れているかまで示す」）。
- テスト: 「検査の規則の一覧」の各 ID に、通る例と落ちる例が少なくとも一つずつある。設計書と `examples/hozoc.hozo` の例をテストの入力（`tests/corpus/`）にし、すべて `hozoc check` を通す。同じ入力を言語サーバーの診断にも通し、`hozoc check` と同じ結果になることを確かめる。
- 追跡: 規則を実装するコードとテストは ID を書く。設計書が変わったとき、ID の表から変える場所を引けるようにするため。
