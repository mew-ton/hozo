# Hozo の実装の要件

## この文書が決めること

Hozo の実装（`hozoc`、言語サーバー、エディタの対応、プラグイン）を作るための要件と、実装のために決めることを一覧にする。言語の意味（何が正しい Hozo か）はこの文書では決めない。持ち主は、`docs/README.md`「読む順」に並ぶ、それぞれの文書（文法は `docs/grammar.md`、検査は `docs/check.md` など）。

この文書の「設計書」と「§n」は、出発点のアイデア集と、その節番号（`docs/README.md`「設計書という呼び名」）。考えの出どころを指すだけで、仕様の持ち主ではない。

## 価値と位置づけ

**Hozo は、アプリの設計の、ただ一つの正（SSOT）になる言語。**

- 要件や設計を AI が書いても、**人が UI でレビューし、手直しできる**。
- レビューしたものが、**そのままコードの枠とハーネスになる**。
- それによって、**アプリ開発で人が責任を持つ範囲**を、はっきりさせる。人が責任を持つのは仕様で、中身は AI に任せられる。

コードの品質を軽んじるわけではない。生成するコードは、その言語の作法に従う。中身が仕様から外れないことは、ハーネスが確かめる（「ハーネス」）。

決定の番号は、`docs/decisions.md`「決めたこと」174。

この価値にした理由: 要件定義や設計の手法が、今どれだけ実際に行われているかは、はっきりしない。その多くは、AI に任されるようになっている。今すぐ要るのは、そうして書かれた設計を、UI でレビュー（と手直し）しやすくし、そのままコードとハーネスにする仕組み。

人が責任を持つ範囲の線（どこまでを仕様に書くか）は、まだ決めていない（「仕様に書く範囲」）。

### もとの考えと、Hozo が守るもの

`docs/decisions.md`「決めたこと」275〜277、282、283、287、289〜291、293。

もとの考え（仮説）:

- **世の中のシステムは、極端に抽象化すれば、関数の組み合わせで、末端に、状態への読み書きを持つ。**
- **設計を、システムが認識できれば、抽象度の高い、関数としての全体像を、作り出せる。** そこから、実装を、どこまで言い当てられるか。Hozo は、その実験。
- 今の Hozo は、AI が先に立つ開発の起点で、設計を、ハーネスにすることを、主にしている。根本は、変わっていない。

Hozo が守るもの:

- **設計によって作れるハーネスの、段を、示すこと。** 段に、数字を付ける。最大は、テストを、完全に作れる状態。その下に、枠だけ、何もなし、などの段がある。
- 段を示すことで、**設計の手法ごとに、どれだけ効果があるか**を、出せる。
- **Hozo が守る品質と、人が持つ責任を、それぞれ、明言する。** 一つの言い方に、まとめない。

op の配線は、概念的な流れ（`docs/decisions.md`「決めたこと」282、283、287、289〜291、293、326）:

- **op の中で、別の op を呼び、その結果を、別の op に渡し、分類で分かれる、という記述（配線）は、実体のコードではなく、おおまかな、呼ぶ順などの、設計。** 概念的な、処理の流れを示す。
- **実際のコードは、流れは同じでも、細かいところで、手直しが出る。** 処理の順と、依存関係は、テストになる: 何を、どの順に呼び、何を渡して、何が返ったかを、テストから追える。
- **条件は、流れではなく、中身。** 「どの場合に、何をするか」は、配線が言う。「どうやって、その場合だと分かるか」は、言わない。配線にも、言語の核にも、条件の式は、書かない。
- **配線の op のコードは、既定では、仕様から、そのまま作る。op ごとに、手で書くことを、選べる。**
  - 手で書いた範囲を、どう示して、どう残すかの仕組み（下の、`generated` と `slot`）は、**後で、考え直す**（326）。トランスパイルの上での課題が、多い（`docs/open.md`「Hozo の側の改善する点」の、手で書く道の行）。下の箇条と例は、考え直す前の、今の案。
  - hozoc が作った範囲は、関数ごとに、対のコメントで囲む: `// <hozoc: generated>` から、`// </hozoc: generated>` まで。
  - 人が、手で直したい範囲は、その中の、`// <hozoc: slot>` から、`// </hozoc: slot>` までの対で囲む。範囲は、関数の中身の、一部でよい。
  - `slot` の中は、作り直しの対象にしない。`slot` の外は、作り直す。
  - `slot` を置けるのは、op の処理を写した部分だけ。デコレータを写した部分は、いつも、上書きし、そこに `slot` があれば、エラーにする。今の基底 `go` では、op の処理を写した部分が、中身（`<op>Body`）で、デコレータを写した部分が、外側の関数の全体。
  - 仕様が変わって、`slot` の周りを作り直すときは、`slot` の前後の、作った行を、手がかりにして、同じ間に戻す: 新しく作った中身と、今のファイルの、`slot` の外の行を、並びで突き合わせる。突き合わせられなければ、エラーにして、人が、置き直す。`slot` のコメントに、手がかりは、書かない。
  - 作ったままのコードに、`slot` の対は、ない。手で書いた op は、`slot` の対のある op。
  - hozoc が作るはずの関数に、`generated` の対が、揃っていなければ（外れている。開きか、閉じの、片方だけ）、エラーにして、止める。`slot` の対が、片方だけのときも、同じ。
  - 手で書いた op は、流れのテストで確かめる。

  op `login` の例（Go。今の基底の形）。デコレータ（`@rate.limited`）を写すのは、外側の `Login`。op の処理を写すのは、中身の `loginBody` で、その一部を、手で直している（`slot` の中の `…` は、人が書いたコード）:

  ```go
  // <hozoc: generated>
  func (o *ops) Login(ctx context.Context, in LoginInput) (LoginOk, error) {
  	return o.seams.LoginRateLimited(ctx, in, o.loginBody)
  }
  // </hozoc: generated>
  ```

  ```go
  // <hozoc: generated>
  func (o *ops) loginBody(ctx context.Context, in LoginInput) (LoginOk, error) {
  	user, err := o.store.FindUser(ctx, in.Body.Email)
  	if err != nil {
  		return LoginOk{}, err
  	}
  	// match (user by store.Registration)
  	if user != nil {
  		// Registered: user は type.User
  		return o.IssueSession(ctx, *user, in.Body.Password)
  	}
  	// <hozoc: slot>
  	// Unregistered
  	…
  	// </hozoc: slot>
  }
  // </hozoc: generated>
  ```

- 作る場合も、流れのテストを、完全に作る場合も、ハーネスの段は、4。

Hozo が、約束しないもの:

- **完全なハーネス。**
- **すべての開発の現場に合う設計。**

そのうえでの、位置づけ: 設計そのものを、プラグインにし、共通の言語にする。AI が先に立つ開発で、人が持つべき責任を、どこまで、設計の段階に引き寄せられるかの、実験の場。

ハーネスの段（`docs/decisions.md`「決めたこと」277）。分けるのは、人の責任が、どこに残るか:

| 段 | 名前 | Hozo が守ること | 人に残る責任 |
|---|---|---|---|
| 4 | 作られる | 中身そのものか、中身を確かめるテストが、仕様から、完全に作られる | 設計だけ |
| 3 | テストの規約 | 書かなければならないテストが決まり、書かれていて、通っていること | 設計と、テストの中身。テストが、設計を確かめているか |
| 2 | 枠 | コードの形。欠ければ、コンパイルエラー | 中身の正しさの、すべて |
| 1 | 印だけ | 何も縛らない。設計の文書としては、残る | すべて |
| 0 | 書けない | 仕様に、書く場所がない | すべて。設計も、仕様の外 |

- 中身が作られる場合と、テストが、完全に作られる場合は、同じ段。どちらも、人に残る責任は、設計だけ。
- **仕様の中のつながりの検査**（例外と効果の伝播、状態の持ち主、など。「ハーネス」）は、段に入れない。中身ではなく、設計そのものの整合を守るもので、どの段にも、同じように掛かる。
- 段が言うのは、設計から、何が作れるか。今の `hozoc` が、それを作っているかは、別（テストの生成は、まだない。「ハーネス」）。
- 図の部品ごとの段は、`docs/ide-chain.md`「図ごとの、ハーネスの段」。画面での見せ方は、`docs/ide-screens.md`「ハーネスのプレビュー」。

### ただ一つの正

要件: 設計を言うものは、仕様（`.hozo`）だけ。レビューで見せる形（図を含む。「レビューで見せる形」）、生成するコードの枠、テストは、どれも仕様から作る。設計を言うものを、仕様の横に、手で保守しない（`docs/decisions.md`「決めたこと」175）。

今の状態: 仕様から作っているのは、コードだけ（`hozoc emit`。`docs/cli.md`「emit」）。レビューで見せる形と、テストは、まだ作っていない（「段階」）。

### 書く人と、読む人

`.hozo` の文面を書くのは、主に AI（と、エンジニア）。人は、UI で読み、手直しする（「UI での手直し」）。だから、文面は、長く、厳密でよい: 手で書きやすいことより、検査が、曖昧なく確かめられることを取る（`docs/decisions.md`「決めたこと」176）。

### 検査が求める完全さ

検査は、仕様に完全さを求める: 配線の `throws` は、呼び出し先の例外をすべて書かせる（THROWS-1）。この明示は緩めない（配線の op の `throws` を省略して推論する形は、採らない。出どころは設計書 §7.2、§16）。

完全さが摩擦になる場面は、二つ（`docs/decisions.md`「決めたこと」176）。

| 場面 | 摩擦 | 今の状態 |
|---|---|---|
| AI が下書きした仕様を、検査に掛ける | 下書きは、分かっていることだけを先に宣言したもの（§2「設計は分かっていることだけを先に宣言する」）で、不完全。足りない宣言は、どれも error になる | 足りない宣言は、道具の側で埋める: 診断が持つ `Data`（`docs/check.md`「Data」）から、足りない宣言を自動で足す操作を、言語サーバーと UI が提供する。言語サーバーの操作（コードアクション）は、段階 4 の後で、まだない（「言語サーバー」）。不完全な仕様を、不完全なまま受け付ける方法は、**ない。決めてもいない** |
| 人が、仕様をレビューする | 完全に書いた文面は、長い（「書く人と、読む人」）。そのまま見せれば、検査のために書いた宣言のすべてを、レビューする人が読むことになる | レビューする人に、そのうちの何を見せるかは、**決めていない**。見せる形そのものが、まだない（「レビューで見せる形」） |

### レビューで見せる形

設計の手法や図に合わせることは、目的ではない。図は、仕様を、レビューする人に見せる形の候補（`docs/decisions.md`「決めたこと」177）。

候補にする図と、その材料になる仕様の記述:

| 見せる形の候補（UML の図） | 材料になる仕様の記述 |
|---|---|
| クラス図 | `model` / `scalar` / `union` |
| コンポーネント図 | 名前空間と、状態の持ち主（§5.1） |
| ステートマシン図 | 状態の分類と、効果の遷移（`docs/check.md`「状態の形」）。表の一行（注文、支払いなど）の進み具合は、値の分類と、効果の行の遷移（同「行の遷移」） |
| アクティビティ図 | 配線と `match`（§9、§10.2） |
| シーケンス図 | 名前空間をまたぐ op の呼び出しと、例外の伝播（§7.2） |
| ユースケース図 | 人の操作を表す op（「モデルが先」） |

この表が言うのは、どの記述が、どの図の材料になりうるかだけ。図を実際に出して確かめたものではなく、仕様が、それぞれの図をどこまで表せるかは、言っていない。

今の状態: 仕様を、レビューのために表示するものは、まだ何もない（図も、画面も）。見せるのは、IDE（`docs/tools.md`「道具」）。静的なページや図を出すだけの仕組みは、作らない: レビューは、見る、欠けを知る、直す、の繰り返しで、一度出した写しでは回らない（`docs/decisions.md`「決めたこと」185。177 の「仕様から図を出すことは、プラグインの展開先の一つとして扱う」を置き換える）。見せるものは選ばず、仕様にあるものをすべて見せる（同 184。`docs/tools.md`「見るものの決まり」）。作る順は `docs/tools.md`「作る順」。

### UI での手直し

要件: 人は、UI で仕様を手直しでき、その結果を、`.hozo` の文面に書き戻す。段階の外に置く将来の目標ではなく、価値から導く要件（`docs/decisions.md`「決めたこと」178）。

UI が変えるのは、文面と同じ IR（`docs/ir.md`「この文書が決めること」の「IR を正とし」: 文面は、IR の表し方の一つ）。書き戻しは、変えた IR から `.hozo` の文面を作ること。書き戻しについて決めてあること（書き換える範囲、UI で編集している間の文面の扱い）は、「モデルが先」の「決まったこと」。

今の状態: UI も、書き戻しも、ない。`//` のコメントは IR に入らない（§3.4）ので、書き戻しでの扱いが要る（決めた扱いは、「モデルが先」の「決まったこと」）。作る段階は、割り当てていない（「段階」）。

### ハーネス

価値の言うハーネスは、中身（op の中身のコード）が仕様から外れないことを確かめる仕組みの全体。次の部分から成り、それぞれの中身は、持ち主の文書と見出しが持つ（`docs/decisions.md`「決めたこと」179）。

| 部分 | 持ち主 |
|---|---|
| 仕様の中のつながりの検査（例外と効果の伝播、状態の持ち主、`bind`） | `docs/check.md`「計算」「診断」 |
| op の中身に立ち入らない: 守るのは、仕様に書いたこと | 「op の中身に立ち入らない」 |
| 出力を推論しない: op から作るのは関数の枠だけで、デコレータは包むだけ | 「出力を推論しない」 |
| 実装の漏れは、コンパイルエラーになる | `docs/plugin-go.md`「実装を受け取る口」（Go の基底） |
| 閉じた分類: 宣言したケースの外の値は、誤り | `docs/check.md`「閉じた分類」 |
| 行の遷移: 宣言と、呼ぶ側の検査 | `docs/check.md`「行の遷移」 |
| テストの生成（行の遷移の保証、アサーション）。**まだない** | 「段階」 |

### PRD の水準の記述

目指す向き（要件ではない）: PRD の水準の記述（誰に、何を約束するか）も、Hozo の中に書けるようにする。ここで言う約束は、要求と、同じもの（`docs/decisions.md`「決めたこと」278）。書き方の見込みは、`docs/ide-chain.md`「要求の文書」。ただ一つの正であること（「ただ一つの正」）と、向きが合う（`docs/decisions.md`「決めたこと」181）。

今、書けるもの:

- op と、概念を表す宣言（名前空間、model、状態など）の、名前と説明（`docs/grammar.md`「ドキュメンテーションコメント」）。
- 印のデコレータ（「モデルが先」の「何も生成しないデコレータ」）。サンプル `order-app` の `@prd.promise(whom, what)` は、約束を、それを守る op に結ぶ（`tests/samples/order-app/README.md`「語彙」）。

**まだ決めていない**: 約束の中身を、確かめられる形で言う書き方は、ない。印は、約束と op を結ぶだけで、検査器は、中身を確かめない（`tests/samples/order-app/README.md`「分かったこと」の F11、「利用者への問い」の Q10）。PRD の取り込みと、PRD の文と仕様の要素を結ぶ仕組みも、ない（「段階」）。

## モデルが先

仕様は、コードを生成しない部分を含んでよい。設計のただ一つの正（「価値と位置づけ」）は、人の操作や外部の仕組みのような、コードにしない部分も持つため。設計書（§1「一つの定義から…生成・検証できるようにする」）が生成を前提に書いている点を広げる。

| 要件 | 中身 | 今の状態 |
|---|---|---|
| 出力しない op | op は、どの言語にも出力されなくてよい。ブラウザを操作する利用者の行動のような、人の操作を op として書ける | 書ける。出力するのは、単位の対象の op だけ（単位を置かない名前空間の op と、`in` で外した op は出力しない。`docs/config.md`「単位の対象」「in」）。人そのものを担い手とする名前空間は、`hozo.toml` のどの単位の対象にもしなければ出力されない（「決まったこと」） |
| 出力しない名前空間 | 名前空間は、出力先を持たなくてよい。検査は出力する名前空間と同じに掛かる | 「決まったこと」 |
| 何も生成しないデコレータ | どのトランスパイラからも読まれないデコレータを、印として付けられる。要求（PRD）、ドメイン、分かれた文脈（境界づけられたコンテキスト）の管理に使う | 書ける。基底はデコレータについて何も生成せず、意味を形にするのは、それを読む相乗りだけ（`docs/plugin-go.md`「デコレータ」）。付ける先は宣言で、名前空間には付けられない（「決まったこと」） |
| 設定なしの検査 | 設計だけの段階では、`hozo.toml` がなくても `hozoc check` できる | できる（`docs/config.md`。`hozoc emit` は CFG-7）。言語サーバーも設定なしで動く（`docs/lsp.md`「プロジェクト」） |

### 決まったこと

| 決めたこと | 持ち主 |
|---|---|
| `hozo.toml` は出力の単位（`[[emit]]`）の一覧で、単位はトランスパイラを名前で選ぶ。プラグインは入れるもので、トランスパイラを提供する | `docs/config.md`「単位」、`docs/plugin-protocol.md`「この文書が決めること」「マニフェスト」 |
| どの単位の対象でもない名前空間は出力しない。エラーにもしない | `docs/config.md`「単位の対象」 |
| 出力するものは、設定だけで決まる。基底は、出力する名前空間の型のすべてと、単位の対象の op のすべてを出す。コードにしたくない op は、単位を置かない名前空間に書くか、`in` で外す | `docs/config.md`「in」「型の置き場」、`docs/plugin-go.md`「出力の対象」 |
| どのトランスパイラも読まないデコレータは印で、何も生成しない。`throws` / `catches` を宣言していても同じ | `docs/plugin-go.md`「デコレータ」 |
| デコレータは名前空間には付けられない。印は中の宣言（op、model など）に付ける（理由は持ち主の文書） | `docs/grammar.md`「ファイルと宣言」「決めたこと」 |
| 人の操作を、担い手ごとの名前空間として書くか、op に印を付けて書くかは、言語が決めない。書いてみて分かりやすい方を選ぶ | — |
| `hozo.toml` がなくても `hozoc check` できる | `docs/config.md`「置き場と探し方」 |
| 書き戻しは、変えた宣言の範囲だけを書き換え、ほかの文面には触れない。それができない場合は、ファイル全体を IR から作り直してよい（`//` のコメントは失われる）。UI で編集している間は、文面を手で直していないものとみなす | —（書き戻しを作るときに持ち主の文書を決める） |

## 書き方の指針

仕様の書き方についての勧め。言語の規則ではなく、検査はしない。

| 指針 | 理由 |
|---|---|
| DB の状態は、それを使う名前空間とは別の名前空間に切り出す | 状態を名前で読めるのは持ち主の名前空間の中だけ（`docs/check.md`「状態の参照」）なので、切り出せば、ほかの名前空間はその op を通すしかなくなる |
| 分岐には標準の分類（`by nullable`、`by list`）を使えるが、場合に業務の名前を付けた分類を、その都度宣言する方がよい（`classify Registration of findUser { Registered: findUser as User; Unregistered: findUser as else; }`） | 「値がある」ではなく「登録済み」と読める。判定は同じ（`docs/check.md`「ケースの判定」） |
| 分類のケースには、仕様が使う場合だけを宣言し、どのケースにも、その場合の名前を付ける。仕様が使わない場合（相手が送ってくる、ほかの種類の通知など）は、宣言しない: 宣言したケースの外の値は、分類の誤りになる（`docs/check.md`「閉じた分類」）。残りが意味のある状態なら、名前を付ける: 述語で決まる分類は、もう一つのケースを宣言し（`classify Gathered of Shipment { Complete; Awaiting; }`）、型で決まる分類は、残りのケースを書く（`Unregistered: findUser as else;`。同「残りのケース」） | 二つに分かれる分類は、たいてい、どちらの側も状態（そろった / 待っている、登録済み / 未登録）で、名前がなければ、`match` のアームと遷移を読んでも、何の場合かが分からない。使わない場合を「その他」のケースで受けると、来るはずのない値が来たときに、黙って「その他」の扱いになる。宣言しなければ、その値は誤りとして見える（`docs/decisions.md`「決めたこと」154、161）。当たらない値に対して何かをしたい（無視する、定義した例外を投げる）なら、それは分類できるということなので、ケースとして宣言して、枝に書く。分類の誤りは、仕様が扱わない、ありえないことが起きた誤り（同 171） |
| `match` の `else` のアームは、多くのケースから一つ（か、少し）を取り出して、ほかをまとめて同じに扱うときに使う（五つのケースが「1 : 4」に分かれる: `Pending => replaceSession(order, payment, returnTo); else => throw AlreadySecured;`）。ケースがいくつかの組に分かれるとき（「1 : 2 : 2」）は、`else` を使わず、どのアームにもケースを名前で並べる（`Held => capture(payment, fee); Prepaid, Settled => none; Pending, Released => throw NotSecured;`） | `else` は「取り出したもの以外」と読める。組が二つ以上あるのに、その一つを `else` にすると、その組がどの場合かを、分類の宣言から引き算しないと読めない。名前で並べてあれば、分類にケースを足したときに、MATCH-2 が、どの組に入れるかを尋ねる（`docs/check.md`「アームが受けるケース」。`docs/decisions.md`「決めたこと」161） |
| 表の一行の進み具合（注文、支払い、仕事、出荷）は、その行の型の分類と、効果の行の遷移で書く（`effect fn startProduction(order: Order on Stage.Accepted): effects orders.put as Stage.InProduction;`。`docs/check.md`「行の遷移」）。行の状態を変えない書き換えは、`as` を書かない `put`。`as else` は、後のケースを本当に約束できない効果にだけ使う | どの効果が、どのケースからどのケースへ進めるかが、効果の宣言から読める。`put` は、`as` がなければ行のケースを変えないので、行のケースが変わる道は、宣言した行の遷移だけになる。`-> else` を逃げ道にすると、その約束が消える |
| 履歴や記録が要るものは、消さない: 消す代わりに、ケースを持たせる（取り消した注文は `Cancelled`）。消す（`delete` の効果）のは、なくなることそのものが意味であるもの（下書き、期限の切れたセッション、カートの行）。なくなることを名前のある状態として扱うときだけ、`T?` を対象にした分類に、ない側のケースを書く（`Absent: Order? as none;`。`docs/check.md`「行がないこと」） | 消した行は、後から、あったことも、なぜなくなったかも言えない。ケースなら、遷移として宣言でき、読める。消すものまでケースにすると、もう意味のない行が残り、どの `read` も、それを除く条件を持つことになる（`docs/decisions.md`「決めたこと」171） |
| 語彙のデコレータ（`@db.key` など）は、複数の担い手が共有する型のフィールドに書いてよい。どこに何を書くかは設計する人が決める。別の名前空間でだけ注釈を足したいときは、型を継承して足す（`docs/types.md`「継承した model」） | 言語は注釈の置き場を縛らない |
| 別のプロセスや外部の仕組みを使う op には、その仕組みの語彙のデコレータを付ける（外部のサービスならそのサービスの語彙、SMTP なら `@smtp.sendMail` のように） | デコレータの付いた op は純粋でなくなり（`docs/check.md`「純粋」）、その op が外部に触れることが仕様から読める |
| デコレータは、原則として、op の入力と出力の値を変えない。デコレータが足すのは、op の前後の処理（確かめる、数える、記録する、待つ、やり直す）と、宣言した例外。値を変えたいなら、その変換を op として書き、配線で呼ぶ | op の引数と戻り値の型は、op の宣言に書いたもので、デコレータを読んでも変わらない。値が途中で変わると、配線を読んでも流れる値が分からなくなる。デコレータを読むトランスパイラ（継ぎ目の中身を出すもの。`docs/config.md`「継ぎ目」）を書く人への勧めでもある。継ぎ目の中で何をするかは、そのトランスパイラが決め、hozoc も基底も確かめない |
| 失敗しうる呼び出しを、`for`（R6 で入る。`docs/check.md`「繰り返し」）の中で繰り返すと、一つの失敗が、残りの回を止める。止めては困るもの（外の仕組みを、並びの一つずつに呼ぶ op）は、失敗した事項と、その理由を、状態に残す: 繰り返しの中で呼ぶ op が、想定した失敗を、受けて、効果で残す（デコレータの `catches … halts …`）。後で、やり直すか、人に見直させる。握りつぶすのは、呼ぶ人のいない op（時計や、届いた通知で動く op）だけにし、人が呼ぶ op は、例外を、そのまま返す。受けた後も、出る例外は、想定していない失敗なので、止まってよい。前の回の効果を、残すか、すべて破棄するかも、設計で決める | 配線は、例外を受けて、次へ進む書き方を、持たない（`docs/decisions.md`「決めたこと」323）。例外を受ける所は、op のデコレータ（同 345）。例は、サンプル `order-app` の `payment.prepayExpiring` と `payment.prepay`。確かめた記録は、`docs/wiring-trial.md`「分かったこと」の W5 |

## 仕様に書く範囲

仕様が、どこまでを書くかの指針（`docs/decisions.md`「決めたこと」151、180）。言語の規則ではなく、検査はしない。

仕様に書いたことは、人がレビューして、責任を持つ。書かなかったことは、中身で、AI に任せられる（「価値と位置づけ」）。だから、どこまでを書くかの線は、**人が責任を持たなければならないこと**として決める。

- 仕様は、最低限、PRD の水準の概念と、その境界を定める。
- それより先は、要るようになったときにだけ足す。
- **その線をどこに引くかの規則は、まだ決めていない。** 探すために、仕様だけのサンプル `tests/samples/order-app/` を書いている。決まるまで、この節が言うのは、線を何として決めるかと、この二つの指針だけ。

## 自己展開

hozoc は自分自身の境界（コマンド、ファイル、プラグインとのやり取り）を `.hozo` で書き、そこから Go の CLI の骨組みを生成する。設計書の `examples/hozoc.hozo` がその叩き台で、§14「合わないものは境界（入力・出力・所有する状態）だけをこの型で書き、中身は別の仕様手段に任せる」の考えで、解析や検査の中身は書かない。

進め方は三つ:

1. **仮の CLI**: 手で書いた Go で、`.hozo` を解析・検査し、Go のコード（§4.3 の、言語ごとの既定の出力。今は基底のプラグイン `plugins/go/` が出す）を書き出せるところまで作る。`cli` の語彙（`examples/hozoc.hozo` の `cli.command` / `cli.arg` / `cli.flag` / `cli.env` / `cli.exitCode`）を Go の CLI の骨組み（サブコマンドの振り分け、フラグと環境変数の読み取り、終了コード）にするプラグイン `plugins/go-cli/` もここで作る。
2. **hozoc を `.hozo` で書く**: `examples/hozoc.hozo` を元に、リポジトリ直下の `cli.hozo` と `hozo.toml` を書く。`lsp` サブコマンドもここに op として入れる。仮の CLI の `check` を通す。
3. **置き換え**: 仮の CLI が `cli.hozo` から Go を生成し、`cmd/hozoc` の手書きの骨組みをそれで置き換える。葉の op（解析、検査、展開、プラグインの呼び出し、言語サーバー）の中身は手で書いたものをつなぐ。以降、CLI の骨組みの変更は `cli.hozo` を変えて生成し直す。

この順番にする理由は、最初の利用者を hozoc 自身にして、基底の出力とプラグインのプロトコルを本物の入力で確かめるため。`examples/hozoc.hozo` が「書けなかったもの」として挙げた三つの解き方は `docs/cli.md`「cli.hozo」。

## プラグインの書き方

当面の展開先は Go と TS の二つ。プラグインは展開先の言語で書く。TS のコードを出すプラグインは TS（Node）で、Go のコードを出すプラグインは Go で書く。§4.6「どの言語で書いてもよく」の範囲で、プラグインの実行環境の要求を利用者の手元にあるもの（TS のプロジェクトには Node、Go のプロジェクトには Go）に一致させるため。protoc の `protoc-gen-go` と `ts-proto` と同じ分かれ方。

プラグインの側で IR を扱うための SDK（IR の型と、標準入出力の JSON の読み書き）を言語ごとに用意する。Go はこのリポジトリの `ir` パッケージと `plugin` パッケージをそのまま import する。TS は `sdk/ts/` を npm パッケージとして出す。npm のパッケージ名は未確認で、出す前に確かめる。

IR の構造と JSON の形は `docs/ir.md` が持ち主。Go の `ir` パッケージはそれを手で写し、JSON スキーマ `schema/ir.schema.json` は `ir` パッケージから、TS の型はスキーマから生成する（`docs/packages.md`「生成するもの」）。生成物が元から遅れていないことは `docs/testing.md`「生成物の一致」で確かめる。

### 出力を推論しない

プラグインが従う原則（`docs/decisions.md`「決めたこと」132。91、103 の、当てはまる範囲を決め直したもの）。仕様の書き方の指針（「書き方の指針」）ではなく、プラグインを書く側の決まり。付ける先が op か、op でないかで、二つに分かれる。

| | op | op 以外（`read`、効果、例外、状態、model とそのフィールド、scalar） |
|---|---|---|
| 宣言から作るもの | **関数の枠だけ**（名前、引数、戻り値）。中身は、配線の本体か、人が書く葉 | **宣言の全体から、プラグインが、そのものを作る**: 型と、引数と、宛先（`reads` の状態、`effects` の宛先）を使ってよい |
| デコレータのすること | **包む**: op の中身の前後に処理を足す。中身は決めず、置き換えない | **宣言が言っていないことだけを、足して言う**。宣言に書いてあること（表は `reads` の状態か `effects` の宛先の状態、列は引数の名前、値がなくてよいかは型の `?`）を、引数でもう一度言わせない |
| 出すコードと型 | **型に依らない**: デコレータの引数だけから作る。型は、書いたものが食い違っていないかを確かめるのにだけ使う | 型で決まってよい。ただし、型に書いていないことを、型から当てない |
| 例 | `@http.get` と `@cli.command`（と、その入口が読むフィールドと例外のデコレータ: `@http.header`、`@http.status`、`@cli.flag`）、`@rate.limited`、`@db.transaction` | `@db.table`、`@db.text`、`@db.find`、`@db.insert`、`@valid.min` |

**op のデコレータが出すコードを、型に依らなくする**のは、デコレータが op の中身に手を出さないことを、形で守るため: 型を見て中身を組み立てる余地がなければ、デコレータは、op の前後にしか居られない。二つ重ねても、互いの中身を知らずに済む。

次のことは、別の規則ではなく、この原則を当てはめたもの。

- **人が書くコードを、できるだけ減らす。** 状態に触れるのは `read` と効果だけ（`docs/check.md`「状態に触れるもの」）で、その二つは、プラグインが宣言から作れるように書ける（`docs/vocab.md`「`db` の read と効果」）。op は、それを呼ぶ配線か、状態に触れない葉。
- **op のデコレータは、始端と終端に処理を足すだけ。** 足した処理が状態に触れるなら、デコレータの宣言の `reads` / `effects` の節がそれを言い、葉でも配線でも、付いた op の関数の型に加わる（`docs/check.md`「デコレータが運ぶ reads と effects」）。型に加わっても、包むものであることは変わらない: op の中身は、配線の本体か、人が書く葉のまま。
- **op のデコレータは、op の中身を出さない。** op の中身の全体を、op に付けたデコレータで言う形（「この op は、この `read` を行う」）は、取らない: 包むものと違って、二つ重ねられず、型（引数と戻り値）を見ないと作れない。中身を持つのは、`read` と効果の宣言。
- **op のデコレータで、値によって変わる振る舞いは、共通のコードが、実行時に決める。** トランスパイラは、型を見て、出すコードの形を切り替えない。op ごと、入力のフィールドごとに出すコードは、どの型でも同じ形（同じ補助の呼び出し）で、違い（値があるかないか、文字列をどう読むか）は、補助の中にある。補助は、型引数と制約で書いても、実行時に値の型を見て（Go なら `reflect`）書いてもよい。書き忘れがコンパイルエラーになる形にできるなら、そちらを取る。op の入口が読む入力の model のフィールド（`@http.header`、`@cli.flag`）と、入口が応答にする例外（`@http.status`、`@cli.exitCode`）のデコレータも、op を包むコードの材料なので、同じに扱う。
- **op の入口で、値がないときの扱いは、型からは決めない。** フィールドが省略可能かどうかから、「なければ誤り」を決めない。なければ誤りか（`@http.required`、`@cli.required`）、何を入れるか（`@http.default`、`@cli.default`）は、デコレータが言い、型は、それと食い違っていないかを確かめる側（省略可能なフィールドに `@http.required` は error）。型の宣言に書く既定値は、言語にない: 誰が値を入れるかは、境界の振る舞い（`docs/decisions.md`「設計書から離れた決定」S24）。
- **op 以外でも、型に書いていないことは、当てない。** 列のしまい方は、フィールドの型からは選ばない（`string` を、文字列の列にも JSON の列にもしまえる。`@db.text` を書く）。引数の型と等しい型のフィールドを探して列に結ぶこともしない（列は、引数の名前）。当たらなかったときに黙って何も出さない（か warning にする）形も取らない: 書いた人は、どの規則に当たったか（当たらなかったか）を、出力を見るまで知れない。食い違いは、トランスパイラの error。
- **デコレータを付けていない宣言には、何も生成しない。** warning も出さない: 付けないのは、中身を人が書くと、仕様を書いた人が選んだこと。デコレータのない `read` と効果は、口（メソッド）だけが出て、足りない実装は、コンパイルエラーで分かる。
- **例外、効果、`read` に付けたデコレータは、それを投げる、行う、読む op の実装に働く。** 例外の `@http.status(401)` は、その例外を投げる op のハンドラの応答を決める。効果の `@db.insert` と、`read` の `@db.find` は、その効果と `read` の中身になり、それを呼ぶ配線の op が、その中身を通る（`docs/decisions.md`「決めたこと」127 の（a））。
- 言語が形から決めている約束（状態の形ごとの組み込みの分類と、形で決まる問い合わせと命令。`docs/check.md`「状態の形」）を出力にするのは、デコレータが言うことではない。型そのものを出す基底（`docs/plugin-go.md`「型」）も同じ。
- 相乗りが、基底の出したものを名指しする（op のメソッドを呼ぶ、型の名前を書く）のは、型で出力を決めることではない。名前と形は、基底の規則の写し（`docs/plugin-protocol.md`「相乗りが基底の形を知る方法」）から求める。

当てはめたプラグイン: op を包む側は `go-http`（`docs/plugin-go-http.md`「出力」）、`go-cli`（`docs/plugin-go-cli.md`「コマンドごとの関数」）、`go-sqlite` の `@db.transaction`（`docs/plugin-go-sqlite.md`「トランザクション」）と、継ぎ目の中身を出す相乗り。宣言から作る側は `go-sqlite` の表と `read` と効果（同「表」「read の中身」「効果の中身」）、`go-valid`（`docs/plugin-go-valid.md`「Validate を持つ型」: `Validate` を持つ型を、型の構造から決める）、基底 `go`（`docs/plugin-go.md`）。

### op の中身に立ち入らない

基底のトランスパイラが従う原則（`docs/decisions.md`「決めたこと」145）。

**Hozo は、プログラミング言語として書いた仕様で、同時に、ハーネスでもある。仕様が守られている限り、op の中身には立ち入らない。** 中身は AI が書いてもよく、壊れたら作り直せばよい。Hozo が守るのは、仕様に書いたこと: op の名前、引数、戻り値、例外・読む状態・効果と、それらのつながり。

そこから、基底は、op の中身に何が要るかを判定しない。出力する言語の作法で関数に付くもの（Go なら `context.Context` と `error`）は、仕様ではない。基底は、それが「この op には要る、この op には要らない」を、仕様から当てず、**仕様の宣言を写した関数のすべてに、同じ形で与える**。中身を書き直した結果、中断を見るようになった、失敗を返すようになった、というだけで、関数の形と、それを呼ぶコードが変わらないようにするため。

- 当てはめた基底: `go`（`docs/plugin-go.md`「op の形」: どの関数も、最初の引数に `ctx context.Context` を取り、最後の戻り値に `error` を返す）。
- op が純粋かどうか（`docs/check.md`「純粋」）は、言語が仕様から割り出す事実として残る。基底が、それで関数の形を分けないだけ。

### 出力に、Hozo の概念の名前を出さない

プラグインの出力の、方針。考え中の、見込みで、原則としては、まだ、決めていない（`docs/decisions.md`「決めたこと」288）。

**実体のコードに、`seams`、`leaves` のような、Hozo の概念の名前を、出さない。** そういう名前が出ると、出力を使う人に、Hozo というフレームワークを、押し付けることになる。

- 当てる範囲は、出力の全体。人が書くコードだけでなく、作ったコードも含む。
- 今の出力で、この方針に合っていない所と、決めていないこと（どの名前が当たるか、代わりの形）は、`docs/open.md`「出力のコードに出る、Hozo の概念の名前」。
- TS の基底（「段階」の 5。まだない）は、op のデコレータを、関数を包む式で写す（`docs/decisions.md`「決めたこと」292）。op の処理は、別の関数に写す。TS のデコレータの構文（`@…`）は、使わない。

  ```ts
  export const login = decorate(rateLimit, …)(loginBody);
  ```

## 最初に決めること

### 実装言語

決定（2026-11-09）: 本体と言語サーバーは **Go**。

§4.4「`hozoc` は特定の実行環境に依存しない」と、§16 で TypeSpec を廃案にした理由「Node.js の上で動き、特定の実行環境に依存しない方針と合わない」から、本体は実行環境を要求しない単一のバイナリにする。候補は Rust と Go で、どちらも満たす。

Go にした理由は「プラグインの書き方」に依る。設計書の例は最初から `browser` が TS、`server` が Go（§4.5）で、Go 向けの一次プラグインを初期から持つ。本体が Go なら、Go のプラグインは IR の型を本体から直接 import でき、SDK の生成は TS 向けだけで済み、モノレポのツールチェーンは Go と Node の二つで済む。Rust なら SDK を TS と Go の両方に生成し、ツールチェーンは三つになる。Rust の利点（WASM / napi で Node のプロセス内に本体を載せやすい）は、今は必要になっていない。

言語に関わるもの（解析、検査、展開、言語サーバー）はすべて Go の `hozoc` に集約する。エディタの対応は、そのエディタの拡張が要求する言語で書き、`hozoc lsp` を起動して接続する薄いクライアントにとどめて言語の知識を持たせない。初期は VS Code 拡張（TypeScript）だけ（`docs/editors.md`「VS Code 拡張」）。

## 言語サーバー

`hozoc lsp` が Language Server Protocol のサーバーとして標準入出力で動く。別のバイナリにしないのは、配布物を一つにし、CLI と言語サーバーで解析・検査の実装がずれる余地をなくすため。エディタは選ばない。VS Code は最初のクライアントで、拡張は `hozoc lsp` を起動して接続するだけ。

提供する機能と、それが本体のライブラリに求めること:

| 機能 | 元になるもの | 本体への要求 |
|---|---|---|
| 診断 | 「検査の規則の一覧」の規則。`hozoc check` と同じ結果、同じ ID | 「品質の要件」の共有 |
| 定義へジャンプ、参照の検索 | 名前の解決（§3.2） | 解決した参照先を、宣言の位置とともに保持する。語彙プラグインと標準の語彙の宣言にも飛べる |
| ホバー | ドキュメンテーションコメントの説明（§3.4）と、宣言の形（op なら引数・出力・`throws` / `effects` / `reads`） | 説明は IR に入る（§3.4）ので、IR から引く |
| ドキュメントのシンボル | 宣言の一覧と入れ子（名前空間） | 構文木から引く |
| 補完 | 参照できる名前。別の名前空間は修飾した形（§3.2） | 名前の解決と同じ表 |
| コードアクション | THROWS-1 の「どれが漏れているか」を `throws` に足す、など、診断が名指しするものを機械的に直せるもの | 診断は、直し方に要る名前を構造化して持つ（メッセージの文字列だけにしない） |

段階 4 で作るのは診断・定義へジャンプ・ホバー・ドキュメントのシンボル。補完とコードアクションは段階 4 の後。

本体のライブラリへの前提条件:

- パーサーは誤りに耐える。構文の誤りがある箇所だけを飛ばし、残りの宣言は解析して検査する。エディタでは書きかけの文書が常に入力になるため。
- すべての構文木と IR の節は元の位置を持つ（形は `docs/ir.md`「Program」の `Span` と `docs/packages.md`「internal/source」）。エディタの位置の表し方への変換はサーバーの側で行う（`docs/lsp.md`「通信」）。
- 解析の単位はプロジェクト全体（`docs/config.md`「形」の `sources`）。一つのファイルの変更で全体を解析し直してよいが、エディタの一打ごとに体感できる遅れが出ない速さにする。差分の解析は、遅れが出てから考える。
- 開いているが保存していない文書の内容を、ディスクの内容より優先して解析する。

## シンタックスハイライト

TextMate の文法（`editors/vscode/syntaxes/hozo.tmLanguage.json`）で色を付ける。VS Code のほかに GitHub の表示（linguist）など、言語サーバーがない場所でも使える形だから。言語サーバーの semantic tokens による色分けは、段階 4 の後に足してよいが、TextMate の文法を置き換えるものではない。

色を分けるもの: 予約語と文脈キーワード（`docs/grammar.md`「予約語」）、デコレータ（`@` から名前まで。名前空間の修飾を含む）、型の位置の名前と値・実行の位置の名前（§3.3 の命名規則に沿う）、リテラル（`docs/grammar.md`「リテラル」）、コメントとドキュメンテーションコメント（中の `@param` / `@throws` / `@see` も分ける）。文脈キーワードは、その位置（`for` の後ろ、`any` の後ろ、`on 状態.` の後ろ、`effects` の節の要素の最後の `.` の後ろ）でだけ色を付ける。

予約語と文脈キーワードの一覧は `docs/grammar.md`「予約語」が持ち主。字句解析器はそこから書き写し、TextMate の文法の予約語の部分は字句解析器の一覧から生成する（`docs/packages.md`「生成するもの」）。一覧の一致は `docs/testing.md`「予約語の一致」で確かめる。

## 品質の要件

- 配布: OS ごとの単一のバイナリ `hozoc`。実行環境（Node.js、JVM など）を要求しない（§4.4）。VS Code 拡張は、対応する OS のバイナリを同梱するか、初回に取得する。
- 共有: `hozoc check` と `hozoc lsp` の診断は同じ検査器の同じ呼び出しで作る。同じ入力に対する診断が二つの入口で食い違わないため。
- 決定性: 同じ入力から同じバイトの出力を作る。出力の並びは宣言の並びに従い、ハッシュの順序に依存しない。生成物の差分がレビューできるため。
- 診断: 漏れを指摘するときは何が漏れているかを名指しする（§7.2「どれが漏れているかまで示す」）。
- テスト: 規則ごとに通る例と落ちる例があり、設計書の例が `hozoc check` を通り、言語サーバーの診断が `hozoc check` と一致する。置き場と書き方は `docs/testing.md`。
- 追跡: 規則を実装するコードとテストは ID を書く。規則が変わったとき、ID の表から変える場所を引けるようにするため。
