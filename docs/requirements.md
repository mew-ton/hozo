# Hozo の実装の要件

## この文書が決めること

Hozo の実装（`hozoc`、言語サーバー、エディタの対応、プラグイン）を作るために、設計書から導いた要件と、設計書にはなく実装のために決めることを一覧にする。言語の意味（何が正しい Hozo か）はこの文書では決めない。設計書が持ち主で、この文書はそれを使う側。

設計書は `mew-ton/drafts` の `hozo/README.md`（https://github.com/mew-ton/drafts/blob/main/hozo/README.md ）。この文書の「§n」はその節番号。導出の元にしたのはコミット `19e0820` 時点の内容で、設計書が変わったらこの文書を見直す。

## 価値と位置づけ

Hozo の価値は、**エンジニアでなくても設計できること**。UML に当たる設計の記述を、図ではなく検査できる仕様として持ち、そこからバックエンド・フロントエンド・ネイティブアプリのコードを生む。

UML の各図に当たるものは、言語の中に既にある。

| UML | Hozo |
|---|---|
| クラス図 | `model` / `scalar` / `union` |
| コンポーネント図 | 名前空間と、状態の持ち主（§5.1） |
| ステートマシン図 | 状態の分類と、効果の遷移（`docs/check.md`「状態の形」） |
| アクティビティ図 | 配線と `match`（§9、§10.2） |
| シーケンス図 | 名前空間をまたぐ op の呼び出しと、例外の伝播（§7.2） |
| ユースケース図 | 人の操作を表す op（下の「モデルが先」） |

UML に足しているのは、つながりの整合（例外と効果の伝播、状態の持ち主、`bind`）を機械が検査すること、そこからコードとアサーションが出ること。

将来の目標は **UI での編集**。仕様の正は IR（§2）で、文面はその一つの表し方。図や画面から同じ IR を編集できるようにする。

## モデルが先

仕様は、コードを生成しない部分を含んでよい。この節の要件は、上の価値から導いたもので、設計書（§1「一つの定義から…生成・検証できるようにする」）が生成を前提に書いている点を広げる。設計書へ返す（`docs/decisions.md`）。

| 要件 | 中身 | 今の状態 |
|---|---|---|
| 出力しない op | op は、どの言語にも出力されなくてよい。ブラウザを操作する利用者の行動のような、人の操作を op として書ける | 書ける。出力するのは、単位の対象の op だけ（単位を置かない名前空間の op と、`in` で外した op は出力しない。`docs/config.md`「単位の対象」「in」）。人そのものを担い手とする名前空間は、`hozo.toml` のどの単位の対象にもしなければ出力されない（「決まったこと」） |
| 出力しない名前空間 | 名前空間は、出力先を持たなくてよい。検査は出力する名前空間と同じに掛かる | 「決まったこと」 |
| 何も生成しないデコレータ | どのトランスパイラからも読まれないデコレータを、印として付けられる。要求（PRD）、ドメイン、分かれた文脈（境界づけられたコンテキスト）の管理に使う | 書ける。基底はデコレータについて何も生成せず、意味を形にするのは、それを読む相乗りだけ（`docs/plugin-go.md`「デコレータ」）。付ける先は宣言で、名前空間には付けられない（「決まったこと」） |
| 設定なしの検査 | 設計だけの段階では、`hozo.toml` がなくても `hozoc check` できる | できる（`docs/config.md`。`hozoc emit` は CFG-7）。言語サーバーも設定なしで動く（`docs/lsp.md`「プロジェクト」） |
| 図への展開 | 仕様から図（ステートマシン、シーケンス、アクティビティ、ユースケース）を出す。プラグインの展開先の一つとして扱う | ない |
| 文面への書き戻し | IR から `.hozo` の文面を作れる。UI での編集は IR を変えて文面に書き戻す | ない。`//` のコメントは IR に入らない（§3.4）。扱いは「決まったこと」 |

### 決まったこと

| 決めたこと | 持ち主 |
|---|---|
| `hozo.toml` は出力の単位（`[[emit]]`）の一覧で、単位はトランスパイラを名前で選ぶ。プラグインは入れるもので、トランスパイラを提供する | `docs/config.md`「単位」、`docs/plugin-protocol.md`「この文書が決めること」「マニフェスト」 |
| どの単位の対象でもない名前空間は出力しない。エラーにもしない | `docs/config.md`「単位の対象」 |
| 出力するものは、設定だけで決まる。基底は、出力する名前空間の型のすべてと、単位の対象の op のすべてを出す。コードにしたくない op は、単位を置かない名前空間に書くか、`in` で外す | `docs/config.md`「in」「型の置き場」、`docs/plugin-go.md`「出力の対象」 |
| どのトランスパイラも読まないデコレータは印で、何も生成しない。`throws` / `catches` を宣言していても同じ | `docs/plugin-go.md`「デコレータ」 |
| デコレータは名前空間には付けられない。印は中の宣言（op、model など）に付ける（理由は持ち主の文書） | `docs/grammar.md`「ファイルと宣言」「決めたこと」 |
| 人の操作を、担い手ごとの名前空間として書くか、op に印を付けて書くかは、言語が決めない。書いてみて分かりやすい方を選ぶ | — |
| `hozo.toml` がなくても `hozoc check` できる | `docs/config.md`「置き場と探し方」 |
| 書き戻しは、変えた宣言の範囲だけを書き換え、ほかの文面には触れない。それができない場合は、ファイル全体を IR から作り直してよい（`//` のコメントは失われる）。UI で編集している間は、文面を手で直していないものとみなす | —（書き戻しを作るときに持ち主の文書を決める） |


### エンジニアでない人が設計するときの摩擦

設計は一人で完成させるものではない。画面の水準で分かる範囲の効果と例外をプロダクトの担当者が用意し、残りをエンジニアや AI が補う（§2「設計は分かっていることだけを先に宣言する」）。

それでも、価値を「エンジニアでなくても設計できる」に置くと、今の検査の厳しさが摩擦になる。配線の `throws` は呼び出し先の例外をすべて書かせる（THROWS-1）。この明示は設計書の方針（§7.2、§16「配線の op は `throws` を省略して推論」の廃案）なので緩めず、道具の側で埋める: 診断が持つ `Data`（`docs/check.md`「Data」）から、足りない宣言を自動で足す操作を言語サーバーと UI が提供する。

## 書き方の指針

仕様の書き方についての勧め。言語の規則ではなく、検査はしない。

| 指針 | 理由 |
|---|---|
| DB の状態は、それを使う名前空間とは別の名前空間に切り出す | 状態を名前で読めるのは持ち主の名前空間の中だけ（`docs/check.md`「状態の参照」）なので、切り出せば、ほかの名前空間はその op を通すしかなくなる |
| 分岐には標準の分類（`by nullable`、`by list`）を使えるが、場合に業務の名前を付けた分類を、その都度宣言する方がよい（`classify Registration of findUser { Registered: findUser as User; default; }`） | 「値がある」ではなく「登録済み」と読める。判定は同じ（`docs/check.md`「ケースの判定」） |
| 語彙のデコレータ（`@db.key` など）は、複数の担い手が共有する型のフィールドに書いてよい。どこに何を書くかは設計する人が決める。別の名前空間でだけ注釈を足したいときは、型を継承して足す（`docs/types.md`「継承した model」） | 言語は注釈の置き場を縛らない |
| 別のプロセスや外部の仕組みを使う op には、その仕組みの語彙のデコレータを付ける（外部のサービスならそのサービスの語彙、SMTP なら `@smtp.sendMail` のように） | デコレータの付いた op は純粋でなくなり（`docs/check.md`「純粋」）、その op が外部に触れることが仕様から読める。付け忘れは実装を書く時点で分かるので、そこで仕様を直す |
| デコレータは、原則として、op の入力と出力の値を変えない。デコレータが足すのは、op の前後の処理（確かめる、数える、記録する、待つ、やり直す）と、宣言した例外。値を変えたいなら、その変換を op として書き、配線で呼ぶ | op の引数と戻り値の型は、op の宣言に書いたもので、デコレータを読んでも変わらない。値が途中で変わると、配線を読んでも流れる値が分からなくなる。デコレータを読むトランスパイラ（継ぎ目の中身を出すもの。`docs/config.md`「継ぎ目」）を書く人への勧めでもある。継ぎ目の中で何をするかは、そのトランスパイラが決め、hozoc も基底も確かめない |

## 自己展開

hozoc は自分自身の境界（コマンド、ファイル、プラグインとのやり取り）を `.hozo` で書き、そこから Go の CLI の骨組みを生成する。設計書の `examples/hozoc.hozo` がその叩き台で、§14「合わないものは境界（入力・出力・所有する状態）だけをこの型で書き、中身は別の仕様手段に任せる」に従って、解析や検査の中身は書かない。

進め方は三つ:

1. **仮の CLI**: 手で書いた Go で、`.hozo` を解析・検査し、Go のコード（§4.3 の、言語ごとの既定の出力。今は基底のプラグイン `plugins/go/` が出す）を書き出せるところまで作る。`cli` の語彙（`examples/hozoc.hozo` の `cli.command` / `cli.arg` / `cli.flag` / `cli.env` / `cli.exitCode`）を Go の CLI の骨組み（サブコマンドの振り分け、フラグと環境変数の読み取り、終了コード）にするプラグイン `plugins/go-cli/` もここで作る。
2. **hozoc を `.hozo` で書く**: `examples/hozoc.hozo` を元に、リポジトリ直下の `cli.hozo` と `hozo.toml` を書く。`lsp` サブコマンドもここに op として入れる。仮の CLI の `check` を通す。
3. **置き換え**: 仮の CLI が `cli.hozo` から Go を生成し、`cmd/hozoc` の手書きの骨組みをそれで置き換える。葉の op（解析、検査、展開、プラグインの呼び出し、言語サーバー）の中身は手で書いたものをつなぐ。以降、CLI の骨組みの変更は `cli.hozo` を変えて生成し直す。

この順番にする理由は、最初の利用者を hozoc 自身にして、基底の出力とプラグインのプロトコルを本物の入力で確かめるため。`examples/hozoc.hozo` が「書けなかったもの」として挙げた三つの解き方は `docs/cli.md`「cli.hozo」。

## プラグインの書き方

当面の展開先は Go と TS の二つ。プラグインは展開先の言語で書く。TS のコードを出すプラグインは TS（Node）で、Go のコードを出すプラグインは Go で書く。§4.6「どの言語で書いてもよく」の範囲で、プラグインの実行環境の要求を利用者の手元にあるもの（TS のプロジェクトには Node、Go のプロジェクトには Go）に一致させるため。protoc の `protoc-gen-go` と `ts-proto` と同じ分かれ方。

プラグインの側で IR を扱うための SDK（IR の型と、標準入出力の JSON の読み書き）を言語ごとに用意する。Go はこのリポジトリの `ir` パッケージと `plugin` パッケージをそのまま import する。TS は `sdk/ts/` を npm パッケージとして出す。npm のパッケージ名は未確認で、出す前に確かめる。

IR の構造と JSON の形は `docs/ir.md` が持ち主。Go の `ir` パッケージはそれを手で写し、JSON スキーマ `schema/ir.schema.json` は `ir` パッケージから、TS の型はスキーマから生成する（`docs/packages.md`「生成するもの」）。生成物が元から遅れていないことは `docs/testing.md`「生成物の一致」で確かめる。

## リポジトリの構成

一つの Go モジュール `github.com/mew-ton/hozo` に、役割ごとのパッケージとディレクトリを置く。一覧と依存の向きは `docs/packages.md`「ディレクトリ」「依存の向き」。

## 最初に決めること

### 実装言語

決定（2026-11-09）: 本体と言語サーバーは **Go**。

§4.4「`hozoc` は特定の実行環境に依存しない」と、§16 で TypeSpec を廃案にした理由「Node.js の上で動き、特定の実行環境に依存しない方針と合わない」から、本体は実行環境を要求しない単一のバイナリにする。候補は Rust と Go で、どちらも満たす。

Go にした理由は「プラグインの書き方」に依る。設計書の例は最初から `browser` が TS、`server` が Go（§4.5）で、Go 向けの一次プラグインを初期から持つ。本体が Go なら、Go のプラグインは IR の型を本体から直接 import でき、SDK の生成は TS 向けだけで済み、モノレポのツールチェーンは Go と Node の二つで済む。Rust なら SDK を TS と Go の両方に生成し、ツールチェーンは三つになる。Rust の利点（WASM / napi で Node のプロセス内に本体を載せやすい）は、今は必要になっていない。

言語に関わるもの（解析、検査、展開、言語サーバー）はすべて Go の `hozoc` に集約する。IDE の対応は、その IDE の拡張が要求する言語で書き、`hozoc lsp` を起動して接続する薄いクライアントにとどめて言語の知識を持たせない。初期は VS Code 拡張（TypeScript）だけ（`docs/editors.md`「VS Code 拡張」）。

### 設計書の置き場

設計書を `drafts` に置いたまま実装を進めると、実装から見つかった修正が二つのリポジトリに分かれる。`drafts` の README の運用方針「育っていったアイデアが実装フェーズに入ったら、別リポジトリに切り出すことを検討する」に従い、設計書をこのリポジトリの `docs/design.md` に移し、`drafts/hozo` はここへのリンクだけにすることを推奨する。移すまで、この文書は `drafts` を参照する。

## 言語サーバー

`hozoc lsp` が Language Server Protocol のサーバーとして標準入出力で動く。別のバイナリにしないのは、配布物を一つにし、CLI と言語サーバーで解析・検査の実装がずれる余地をなくすため。エディタは選ばない。VS Code は最初のクライアントで、拡張は `hozoc lsp` を起動して接続するだけ。

提供する機能と、それが本体のライブラリに求めること:

| 機能 | 元になるもの | 本体への要求 |
|---|---|---|
| 診断 | 「検査の規則の一覧」の規則。`hozoc check` と同じ結果、同じ ID | 「品質の要件」の共有 |
| 定義へジャンプ、参照の検索 | 名前の解決（§3.2） | 解決した参照先を、宣言の位置とともに保持する。語彙プラグインと標準の語彙の宣言にも飛べる |
| ホバー | ドキュメンテーションコメントの説明（§3.4）と、宣言の形（op なら引数・出力・`throws` / `effects` / `reads`） | 説明は IR に入る（§3.4）ので、IR から引く |
| ドキュメントのシンボル | 宣言の一覧と入れ子（名前空間） | 構文木から引く |
| 補完 | 参照できる名前。別の名前空間は修飾した形（§3.2） | 名前の解決と同じ表 |
| コードアクション | THROWS-1 の「どれが漏れているか」を `throws` に足す、など、診断が名指しするものを機械的に直せるもの | 診断は、直し方に要る名前を構造化して持つ（メッセージの文字列だけにしない） |

段階 4 で作るのは診断・定義へジャンプ・ホバー・ドキュメントのシンボル。補完とコードアクションは段階 4 の後。

本体のライブラリへの前提条件:

- パーサーは誤りに耐える。構文の誤りがある箇所だけを飛ばし、残りの宣言は解析して検査する。IDE では書きかけの文書が常に入力になるため。
- すべての構文木と IR の節は元の位置を持つ（形は `docs/ir.md`「Program」の `Span` と `docs/packages.md`「internal/source」）。エディタの位置の表し方への変換はサーバーの側で行う（`docs/lsp.md`「通信」）。
- 解析の単位はプロジェクト全体（`docs/config.md`「形」の `sources`）。一つのファイルの変更で全体を解析し直してよいが、エディタの一打ごとに体感できる遅れが出ない速さにする。差分の解析は、遅れが出てから考える。
- 開いているが保存していない文書の内容を、ディスクの内容より優先して解析する。

## シンタックスハイライト

TextMate の文法（`editors/vscode/syntaxes/hozo.tmLanguage.json`）で色を付ける。VS Code のほかに GitHub の表示（linguist）など、言語サーバーがない場所でも使える形だから。言語サーバーの semantic tokens による色分けは、段階 4 の後に足してよいが、TextMate の文法を置き換えるものではない。

色を分けるもの: 予約語と文脈キーワード（`docs/grammar.md`「予約語」）、デコレータ（`@` から名前まで。名前空間の修飾を含む）、型の位置の名前と値・実行の位置の名前（§3.3 の命名規則に沿う）、リテラル（`docs/grammar.md`「リテラル」）、コメントとドキュメンテーションコメント（中の `@param` / `@throws` / `@see` も分ける）。文脈キーワードは、その位置（`for` の後ろ、`any` の後ろ、`on 状態.` の後ろ）でだけ色を付ける。

予約語と文脈キーワードの一覧は `docs/grammar.md`「予約語」が持ち主。字句解析器はそこから書き写し、TextMate の文法の予約語の部分は字句解析器の一覧から生成する（`docs/packages.md`「生成するもの」）。一覧の一致は `docs/testing.md`「予約語の一致」で確かめる。

## 品質の要件

- 配布: OS ごとの単一のバイナリ `hozoc`。実行環境（Node.js、JVM など）を要求しない（§4.4）。VS Code 拡張は、対応する OS のバイナリを同梱するか、初回に取得する。
- 共有: `hozoc check` と `hozoc lsp` の診断は同じ検査器の同じ呼び出しで作る。同じ入力に対する診断が二つの入口で食い違わないため。
- 決定性: 同じ入力から同じバイトの出力を作る。出力の並びは宣言の並びに従い、ハッシュの順序に依存しない。生成物の差分がレビューできるため。
- 診断: 漏れを指摘するときは何が漏れているかを名指しする（§7.2「どれが漏れているかまで示す」）。
- テスト: 規則ごとに通る例と落ちる例があり、設計書の例が `hozoc check` を通り、言語サーバーの診断が `hozoc check` と一致する。置き場と書き方は `docs/testing.md`。
- 追跡: 規則を実装するコードとテストは ID を書く。設計書が変わったとき、ID の表から変える場所を引けるようにするため。
