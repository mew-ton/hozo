# 設計の手法への写し

## この文書が決めること

サンプル `order-app`（`tests/samples/order-app/`）の仕様を、設計の手法ごとの図と表に、機械的に写した結果: 手法ごとに、仕様から何が出て、何が出ないか。IDE の設計の段 1（`tools.md`「IDE の設計の段階」）の材料で、筋書き（`ide-scenarios.md`）と組にして使う。

**この文書は、調べの記録で、画面の要件ではない。** どの手法を IDE の画面にするか、画面に何を置くかは、ここでは決めない（段 3）。写した図と表そのものは、リポジトリに置かない: 仕様から作れるものを、仕様の横に、手で保守しない（`requirements.md`「ただ一つの正」）。

調べたのは、`main` の `2cec431` の `order-app`（IR の版 0.9）。数字は、そのときのもの。

## 写し方

- IR（`ir.md`）だけを読む小さな道具で、手法ごとに、図（Mermaid）か表を出した。
- **入口**は、仕様の中の、誰からも呼ばれない op（`tools.md`「試作で分かったこと」）。37 ある。
- 語彙の意味を読まないと写せなかった手法には、「語彙」の列に、読んだ語彙を書いた。書いていない手法は、言語の宣言と、検査の計算（`check.md`「計算」）だけから写せた。

## 手法ごとの結果

「答える問い」は、その手法が、設計を読む人の、どの問いに答えるものか。

写さなかった手法（材料の当たりだけを付けた）:

| 手法 | 材料になりそうなもの | 足りないもの |
|---|---|---|
| DFD | 処理（op）、データの置き場（状態）、流れ（読む、書く、呼ぶ） | 外部の主体（担い手）。CRUD 表と、同じ材料 |
| イベントストーミング、イベントモデリング | コマンド（入口）、起きた事実（効果）、読むモデル（`read`）、外部の仕組み | 「事実が起きたら、別の処理を動かす」反応（言語に、ない） |
| BPMN | アクティビティ図と同じ。時計と通知の入口が、開始イベント | 開始イベントの種類は、語彙（`clock`、`webhook`）にしかない。補償、繰り返し |
| DMN（決定表） | 分類のケース | 述語で決まる分類（36 のうち 15）は、条件を仕様に書いていない（人か AI が書く述語）ので、表のますが埋まらない。型で決まる分類は、型が条件 |
| ロバストネス図 | 境界（画面と API の入口）、制御（配線の op）、実体（状態） | 境界か、制御かは、語彙（`page`、`http`）にしかない |

## 手法をまたいで分かったこと

### 仕様にあって、どの手法の図にもないもの

- **失敗したとき、何が変わっているか。** 検査は、入口ごと、失敗ごとに、どの効果が「起きていない」「起きている」「分からない」かを計算している（`Signature.relations`）。これを書く場所は、UML の図にない。ユースケース記述の「例外の流れ」に、文で書くことはできる。`order-app` の入口のうち、失敗を外に出すのは 7 で、「分からない」が 7 組ある。
- **どの入口が、どの遷移を起こすか。** ステートマシン図の引き金として書けるが、ふつうは、人が書き足すもの。仕様からは、計算で出る。
- **約束と、その守り手。** 対応表として出せるが、設計の図の中には、置き場がない。

### 手法が求めて、仕様にないもの

| ないもの | 求める手法 | 今、近いもの |
|---|---|---|
| 担い手（誰が、その入口を使うか） | ユースケース図、業務フロー図、DFD | 入口の名前空間の名前、語彙のデコレータ |
| 事前条件 | ユースケース記述、受け入れ条件 | 分かれ道の、失敗を投げるアーム。効果の行の遷移の「前のケース」 |
| 遷移の条件（ガード） | ステートマシン図 | 遷移の前の分かれ道（別の分類のケース） |
| 操作の行き先の画面 | 画面遷移図 | 操作が変える状態 |
| 表の間の関連 | ER 図 | `@db.ref`（ほとんど使っていない）。識別子の型の名前 |
| こちらと、外の境 | コンポーネント図、C4 | `hozo.toml` の単位（設計だけの段階では、ない）。`@external` の付いた op |
| 値についての条件 | 受け入れ条件、決定表 | 葉の op のコメント、印 `@prd.promise` |

どれを、言語か語彙で言えるようにするかは、決めていない。値についての条件は、すでに未決の点にある（`open.md`「言語」の、不変条件の点）。担い手は、担い手ごとの名前空間として書くか、op に印を付けて書くかを、言語が決めない、と決めてある（`requirements.md`「モデルが先」の「決まったこと」）: 仕様の書き方で、出せるようになる。

### 入口をまたぐ流れ

業務の全体の流れ（注文する → 支払いに同意する → 作る、そろえる → 梱包する → 送る）は、一つの入口の中にない: 別々の担い手が、別々のときに起こす、いくつもの入口にまたがる。アクティビティ図も、シーケンス図も、一つの入口の中しか描けなかった。

入口をつなぐのは、**ものの一生**。遷移ごとに、それを起こす入口を並べると、入口をまたぐ流れになる:

| `payment.Standing` の遷移 | 起こす入口 | 担い手 |
|---|---|---|
| （入る）→ Pending | `storefront.onPlaceOrder`、`storefront.onPay` | 客 |
| Pending → Held、Pending → Settled、Held → Released | `hooks.paymentEvent` | 外部の仕組み（支払い） |
| Held → Prepaid | `payment.prepayExpiring` | 時計 |
| Held、Prepaid → Settled | `backoffice.onBuyLabel` | 担当者 |

業務フロー図の、担い手のレーンと、時間の順は、この表から作れる。ただし、いくつかの「もの」（注文、支払い、仕事、出荷）の一生が、どう絡むか（支払いが Held になったら、注文が Accepted になり、出荷が作られる）は、同じ入口が、いくつかの遷移を起こすことからしか、分からない。

### 大きさと、読みやすさ

- **一枚に入るもの**: ステートマシン図（最大でケース 5）、状態遷移表、クラス図（名前空間一つ）、ユースケース図（担い手一人ぶん）。
- **一枚に入らないもの**: クラス図の全体（model 95）、CRUD 表の全体（37 × 25）、ユースケース図の全体（37）。絞る軸（名前空間、担い手）が要る。
- **入口によって、大きさが大きく違うもの**: ユースケース記述（19 行から 87 行）、アクティビティ図（13 個から 50 個）、シーケンス図。大きい入口では、失敗の枝が、主な流れを埋める: 配線のアーム 153 のうち、失敗を投げるものが 37 あり、入口の頭の「いなければ失敗」「権限がなければ失敗」が、図の上半分を占める。失敗の枝を畳む見せ方が要る。
- **手順の一歩の文**は、呼ぶ相手の説明の一行目。説明が、その op の失敗まで書いていると、箱の文が長くなる。説明のない op は、名前だけになる。

### 表の形が、図より抜けを見せる

- 状態遷移表は、宣言していない向きを、すべて「×」として見せる。図では、線がないことは、目に入らない。
- CRUD 表は、どの入口からも書かれない状態（10）と、読まれない状態（3）を見せた。書かれない 10 は、管理の画面を書いていないことによる（`tests/samples/order-app/README.md`「書けたが、書かなかったもの」の G4）。読まれない 3 は、外部の仕組みの内側の状態。
- 「書いていないのは、わざと」と言う方法が、仕様にない。表の空きが、抜けなのか、範囲の外なのかは、表からは分からない。

### 語彙に依るもの

言語の宣言だけから写せなかったのは、担い手、画面遷移、ER 図、要求との対応の四つ。どれも、語彙のデコレータ（`clock`、`webhook`、`page`、`nav`、`db`、`prd`）を、その意味を知って読んだ。IDE が語彙の意味を読むか（読むなら、語彙ごとの読み方を、誰が持つか）は、決めていない（`open.md`「次の段」）。
