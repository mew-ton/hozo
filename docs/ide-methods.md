# 設計の手法への写し

## この文書が決めること

サンプル `order-app`（`tests/samples/order-app/`）の仕様を、設計の手法ごとの図と表に、機械的に写した結果: 手法ごとに、仕様から何が出て、何が出ないか。IDE の設計の段 1（`tools.md`「IDE の設計の段階」）の材料で、筋書き（`ide-scenarios.md`）と組にして使う。

**この文書は、調べの記録で、画面の要件ではない。** どの手法を IDE の画面にするか、画面に何を置くかは、ここでは決めない（段 3）。写した図と表そのものは、リポジトリに置かない: 仕様から作れるものを、仕様の横に、手で保守しない（`requirements.md`「ただ一つの正」）。

調べたのは、`main` の `2cec431` の `order-app`（IR の版 0.9）。数字は、そのときのもの。

## 写し方

- IR（`ir.md`）だけを読む小さな道具で、手法ごとに、図（Mermaid）か表を出した。
- **入口**は、仕様の中の、誰からも呼ばれない op（`tools.md`「試作で分かったこと」）。37 ある。
- 語彙の意味を読まないと写せなかった手法には、「語彙」の列に、読んだ語彙を書いた。書いていない手法は、言語の宣言と、検査の計算（`check.md`「計算」）だけから写せた。

## 手法をまたいで分かったこと

### 仕様にあって、どの手法の図にもないもの

- **例外が出たとき、何が変わっているか。** 検査は、入口ごと、例外ごとに、どの効果が「起きていない」「起きている」「分からない」かを計算している（`Signature.relations`）。これを書く場所は、UML の図にない。ユースケース記述の「例外の流れ」に、文で書くことはできる。`order-app` の入口のうち、例外を外に出すのは 7 で、「分からない」が 7 組ある。
- **どの入口が、どの遷移を起こすか。** ステートマシン図の引き金として書けるが、ふつうは、人が書き足すもの。仕様からは、計算で出る。
- **約束と、その守り手。** 要求トレーサビリティマトリクスとして出せるが、設計の図の中には、置き場がない。
- **例外が、外まで出るか。** エラーの一覧は、ふつう、名前と文面を並べる。仕様からは、例外ごとに、中で起きうる入口の数と、外（画面、応答）まで出る入口の数が、計算で出る。`order-app` の 42 の例外のうち、外まで出るのは 7。

### 手法が求めて、仕様にないもの

| ないもの | 求める手法 | 今、近いもの |
|---|---|---|
| 担い手（誰が、その入口を使うか） | ユースケース図、業務フロー図、DFD | 入口の名前空間の名前、語彙のデコレータ |
| 事前条件 | ユースケース記述、受け入れ条件 | 分かれ道の、例外を投げるアーム。効果の行の遷移の「前のケース」 |
| 遷移の条件（ガード） | ステートマシン図 | 遷移の前の分かれ道（別の分類のケース） |
| 操作の行き先の画面 | 画面遷移図 | 操作が変える状態 |
| 表の間の関連 | ER 図 | `@db.ref`（ほとんど使っていない）。識別子の型の名前 |
| こちらと、外の境 | コンポーネント図、C4 | `hozo.toml` の単位（設計だけの段階では、ない）。入口のデコレータ（`@entry` の印を持つデコレータ）の付いた op |
| 値についての条件 | 受け入れ条件、決定表 | 葉の op のコメント、印 `@pact.promise` |
| 入口が要る前提のうち、行の遷移に書いていないもの（「荷物がある」） | 業務フロー図 | 分かれ道の、例外を投げないアームのケース |
| 事実が起きたら、次を動かす方針 | イベントストーミング、BPMN | 時計で動く op、外からの通知の入口 |
| 分類の条件（何が、その場合を決めるか） | 決定表 | 型で決まる分類の型。述語で決まる分類では、ケースの説明の文 |

**これらは、Hozo の側の改善する点で、画面の設計の制約ではない**（決定 D191）: 画面の設計は、手法が求めるものが、あるものとして行う。一覧の持ち主は `open.md`「Hozo の側の改善する点」。どれを、言語か語彙で言えるようにするかは、決めていない。値についての条件は、すでに未決の点にある（`open.md`「言語」の、不変条件の点）。担い手は、担い手ごとの名前空間として書くか、op に印を付けて書くかを、言語が決めない、と決めてある（`requirements.md`「モデルが先」の「決まったこと」）: 仕様の書き方で、出せるようになる。

### 入口をまたぐ流れ

業務の全体の流れ（注文する → 支払いに同意する → 作る、そろえる → 梱包する → 送る）は、一つの入口の中にない: 別々の担い手が、別々のときに起こす、いくつもの入口にまたがる。アクティビティ図も、シーケンス図も、一つの入口の中しか描けなかった。

入口をつなぐのは、**ものの一生**。前の入口が、ものを、あるケースにし、次の入口が、そのケースから進める（行の遷移の、後のケースと、前のケースが合う）とき、二つの入口は、受け渡しでつながる。これを計算すると、業務フロー図になった:

| 前の入口（担い手） | 受け渡すもの | 次の入口（担い手） |
|---|---|---|
| 注文する（客） | 注文が AwaitingPayment、支払いが Pending | 支払いの通知（支払いの仕組み）、期限切れにする（時計） |
| 支払いの通知（支払いの仕組み） | 支払いが Held、出荷が InHouse | 送り状を買う（担当者）、先に請求を確定する（時計）、配送業者に渡した（担当者） |
| 先に請求を確定する（時計） | 支払いが Prepaid | 送り状を買う（担当者） |
| 配送業者に渡した（担当者） | 出荷が WithCarrier | 荷物の動きの通知（配送の仕組み） |

- 状態を変える入口は 14 で、受け渡しは 10 本。
- **つながらなかった順がある。** 「梱包した」と「棚から出した」は、どの受け渡しにも入らなかった: 梱包は、荷物を「新しく作る」効果で、送り状を買う側は、「荷物があること」を、分かれ道で確かめているだけ（行の遷移の「前のケース」として、宣言していない）。分かれ道の、例外を投げないアームのケースを、「その入口が要る前提」として読めば、つなげられる。
- いくつかの「もの」（注文、支払い、仕事、出荷）の一生が、どう絡むかは、同じ入口が、いくつかの遷移を起こすこととして、出る（支払いの通知が、支払いを Held に、注文を Accepted に、出荷を InHouse にする）。

### 大きさと、読みやすさ

- **一枚に入るもの**: ステートマシン図（最大でケース 5）、状態遷移表、クラス図（名前空間一つ）、ユースケース図（担い手一人ぶん）。
- **一枚に入らないもの**: クラス図の全体（model 95）、CRUD 表の全体（37 × 25）、ユースケース図の全体（37）。絞る軸（名前空間、担い手）が要る。
- **入口によって、大きさが大きく違うもの**: ユースケース記述（19 行から 87 行）、アクティビティ図（13 個から 50 個）、シーケンス図。大きい入口では、例外の枝が、主な流れを埋める: 配線のアーム 153 のうち、例外を投げるものが 37 あり、入口の頭の「いなければ例外」「権限がなければ例外」が、図の上半分を占める。例外の枝を畳む見せ方が要る。
- **手順の一歩の文**は、呼ぶ相手の説明の一行目。説明が、その op の例外まで書いていると、箱の文が長くなる。説明のない op は、名前だけになる。

### 表の形が、図より抜けを見せる

- 状態遷移表は、宣言していない向きを、すべて「×」として見せる。図では、線がないことは、目に入らない。
- CRUD 表は、どの入口からも書かれない状態（10）と、読まれない状態（3）を見せた。書かれない 10 は、管理の画面を書いていないことによる（`tests/samples/order-app/README.md`「書けたが、書かなかったもの」の G4）。読まれない 3 は、外部の仕組みの内側の状態。
- 「書いていないのは、わざと」と言う方法が、仕様にない。表の空きが、抜けなのか、範囲の外なのかは、表からは分からない。

### 語彙に依るもの

言語の宣言だけから写せなかったのは、担い手、開始の種類、境界、画面遷移、ER 図、要求との対応、一覧の中の間隔と HTTP の状態。どれも、語彙のデコレータ（`clock`、`webhook`、`page`、`nav`、`http`、`db`、`prd`）を、その意味を知って読んだ。IDE が語彙の意味を読むか（読むなら、語彙ごとの読み方を、誰が持つか）は、決めていない（`open.md`「次の段」）。
