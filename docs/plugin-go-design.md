# go-design プラグイン

## この文書が決めること

設計の図の語彙（`docs/vocab.md`「設計の図の語彙」）のうち、`prd.business.flow`、`prd.usecase.of`、`prd.ref` を読んで、テストを受け取る口を出すトランスパイラ `go-design`。Go の基底 `go`（`docs/plugin-go.md`）に相乗りする。プラグインは `plugins/go-design/`。期待する出力の実物は、サンプル `tests/samples/shop-server/` の `gen/flows/flowstest/design.go`。

この文書は二つを決める: フローごとの E2E テストを受け取る口（「E2E テストの口」）と、要求ごとの、テストの入れ物を受け取る口（「要求の、テストの入れ物の口」）。言語によらない決まり（何を担保するか、誰が何を書くか）の持ち主は `docs/ide-chain.md`「テストの規約」の「E2E テスト」「要求のテスト」で、この文書は、その Go の形。

出すのは、口と、それを走らせる関数だけ。フローの配線のコードは、基底が作る（フローの op は、ふつうの配線の op）。テストの中身（`Given`、`Then`、要求の入れ物の中）は、人か AI が書く。

人が書くのは、口を満たす型と、それを走らせる関数に渡す、一行のテスト:

```go
func TestFlows(t *testing.T)        { flowstest.RunFlows(t, ops, flowCases{}) }
func TestRequirements(t *testing.T) { flowstest.RunRequirements(t, requirements{}) }
```

## マニフェスト

```toml
name     = "go-design"
wasm     = "plugin.wasm"
protocol = "0.26"

[[transpiler]]
name     = "go-design"
language = "go"
requires = ["go"]
interprets = [
  "prd.business.flow", "prd.usecase.of", "prd.ref",
]
```

- `interprets`（`docs/plugin-protocol.md`「マニフェスト `hozo-plugin.toml`」）は、読む三つ。三つとも `@hint` を持つので、このトランスパイラを並べなくても、CFG-26 は出ない（`docs/vocab.md`「解釈されなくてよいデコレータ」）。
- 読む語彙は、標準の `prd.business`（op の `@prd.business.flow`）、`prd.usecase`（op の `@prd.usecase.of`）、`prd`（`@prd.ref`）。`prd.actor` の語彙（担い手の種類）は、読まない（印のまま）。マニフェストの `interprets` は、読む三つ（`prd.business.flow`、`prd.usecase.of`、`prd.ref`）。語彙は提供しない。
- 継ぎ目は宣言しない。基底の出力（配線、`Ops`、`New`）は、変えない。

## オプション

| キー | 型 | 既定 | 意味 |
|---|---|---|---|
| `requirements` | 文字列の配列 | `[]` | 要求の分類の FQN。並べた分類のケースの一つずつが、要求（「要求の、テストの入れ物の口」の「要求の分類」） |

```toml
[[emit]]
namespace   = "flows"
transpilers = ["go", "go-design"]
out         = "gen/flows"

[emit.options.go-design]
requirements = ["design.Requirement"]
```

知らないキー、型の違う値、対象のない分類でない FQN、同じ FQN の二度書きは GODESIGN-5。

## 対象

- **フロー**は、出力 (U, N) の、単位の対象の op（`View.files` にあるファイルの op。`docs/config.md`「in」）のうち、`@prd.business.flow` の付いたもの。宣言順。
- **要求**は、オプション `requirements` に並べた分類のケース。分類は、どの名前空間のものでもよい（単位を置かない名前空間のものも）。N のものである必要はない。
- フローも、要求もない単位（`@prd.business.flow` の op がなく、`requirements` が空）は、ファイルを出さず、warning を一つ返す。
- フローの名前空間は、テスト用の単位だけの対象にする（`docs/ide-chain.md`「業務フロー図」）。`go-design` を並べる単位が、そのテスト用の単位。

## 出力

- 口は、N の**テストのパッケージ**（`docs/plugin-go.md`「単体テストの口」の「テストのパッケージ」。`gen/flows/flowstest`）に、`design.go` を一つ。先頭は `// Code generated by hozoc go-design <版>; DO NOT EDIT.`。基底が、そのパッケージを作らない出力（葉の op も、判定の口を出す分類もない）でも、出す（パッケージのファイルは、これ一つになる）。
- 同じディレクトリに、`RunFlows` と `RunRequirements` のテストの、**テストの対応表** `hozo-tests.go-design.json` を出す。形と、行の取り方は、基底と同じ（`docs/plugin-go.md`「テストの対応表」。`golang.TestMap` で作る）: `name` は、フローの FQN（`flows.signInAndOrder`）と、要求の名前（`design.Requirement.PRD_001`）。並びは、`design.go` の行の順。
- 中身は、この順: フローごとの `<Op>FlowCase`（宣言順）、まとめの `FlowCases`、走らせる `RunFlows`（ここまでは、フローが一つでもあるとき）、`Requirements`、走らせる `RunRequirements`（この二つは、`requirements` に、分類が一つでもあるとき）。
- 公開の名前は、上の五つ。`<Op>` は、op のメソッドの名前（`docs/plugin-go.md`「名前」）。非公開の名前は、出さない（足すなら、`design` で始める）。
- 公開の名前が、テストのパッケージの、基底の公開の名前（`golang.PublicTestNames`。`docs/packages.md`「`plugin/golang`（公開）」）か、自分のほかの名前と当たれば、GODESIGN-6（葉 `flow` の `FlowCases`。分類 `Flows` の `RunFlows`）。一つの `<Op>FlowCase` のフィールドの名前どうしが当たるときも（引数 `id` と `Id`。引数 `given` と `given_`）。`Requirements` のメソッドの名前どうしが当たるときも（二つの分類の、同じ名前のケース）。フローの op の名前か、要求のケースの名前が `_` で始まるときも（Go の公開の名前にならず、口を、別のパッケージから満たせない）。
- 同じ単位が、子の名前空間 `N.<N のパッケージ名>test` を出力するなら、GODESIGN-7（基底が、同じことを GO-4 で返す出力では、重ねて返さない。`docs/plugin-go.md`「診断」）。
- import の名前の決まりは、テストのパッケージのもの（`docs/plugin-go.md`「単体テストの口」の「テストのパッケージ」: N の入口のパッケージは、いつも、名前を書いて import する）。import の名前に使わないのは、このファイルの関数の本体が、決まった名前で使う識別子: `t`、`c`、`k`、`ops`、`ctx`、`got`、`err`。
- 失敗の文面（`t.Fatalf`）は、英語で書く（基底と同じ）。
- 出すコードは、宣言だけから作る（`docs/requirements.md`「出力を推論しない」）: フローの op の引数と戻り値の型、名前、説明。要求のケースの名前と説明、`@prd.ref` の引数。型で、形を変えるのは、フローが値を返すかどうかだけ。

## E2E テストの口

`@prd.business.flow` の付いた op（フロー）ごとに、E2E テストのケースを一つ受け取る口と、それを走らせる関数を出す（`docs/decisions.md`「決めたこと」366、367）。Hozo が担保するのは、フローごとに、ケースが用意されていて、通っていること（確かめる所は `docs/ide-chain.md`「テストの規約」の「担保すること」）。

### 口の形

```ts
/** ログインして、注文し、自分の注文の一覧を見る */
@prd.business.flow
export fn signInAndOrder(email: type.Email, password: type.Password, lines: type.OrderLine[]): Ordered
  throws type.InvalidCredentials, rate.LimitExceeded, type.Unauthorized, type.NotificationFailed, http.ServerError, http.NetworkError
{
  val token = client.signIn(email, password);
  val placed = client.order(token, lines);
  val listed = client.viewOrders(token);
  return { placed: placed, listed: listed };
}
```

```go
// SignInAndOrderFlowCase は、フロー flows.signInAndOrder の、E2E テストのケース: フローの引数と、今の状態の用意と、足りない確かめ。
// フロー: ログインして、注文し、自分の注文の一覧を見る
type SignInAndOrderFlowCase struct {
	Email    pkgtype.Email
	Password pkgtype.Password
	Lines    []pkgtype.OrderLine
	// Given は、フローを呼ぶ前に、今の状態を用意する（nil なら、呼ばない）。
	Given func(ctx context.Context) error
	// Then は、フローが、正常に終わったと確かめた後に、呼ばれる（nil なら、呼ばない）。got は、フローが返した値。後の状態は、ここで確かめる。
	Then func(t *testing.T, got flows.Ordered)
}

// FlowCases は、@prd.business.flow の付いた op の、E2E テストのケース。フローごとに、メソッド一つ（宣言順）。
// メソッドが一つでも足りない値は、RunFlows に渡すところでコンパイルできない。
type FlowCases interface {
	SignInAndOrder() SignInAndOrderFlowCase
}

// RunFlows は、フローごとに、テストを一つ走らせる。テストの名前は、フローの FQN。
// Given を呼んでから、ops のフロー（配線は、基底が作る）を呼び、正常に終わったことを確かめてから、Then を呼ぶ。
func RunFlows(t *testing.T, ops flows.Ops, c FlowCases) {
	t.Run("flows.signInAndOrder", func(t *testing.T) {
		k := c.SignInAndOrder()
		ctx := context.Background()
		if k.Given != nil {
			if err := k.Given(ctx); err != nil {
				t.Fatalf("given: %v", err)
			}
		}
		got, err := ops.SignInAndOrder(ctx, k.Email, k.Password, k.Lines)
		if err != nil {
			t.Fatalf("want no error, got %v", err)
		}
		if k.Then != nil {
			k.Then(t, got)
		}
	})
}
```

- **必要なケースは、フロー一つに、一本**（ハッピーパス）。フローを足して、`FlowCases` のメソッドを書かなければ、`RunFlows` に渡すところで、コンパイルできない。
- **テストの名前**（ラベル）は、フローの FQN（`flows.signInAndOrder`）。
- **`<Op>FlowCase` のコメント**は、一行目が上の形。フローの op に説明があれば、二行目から、`// フロー: <説明>`（説明が二行以上なら、二行目から先は、行ごとに `// ` を付けて続ける）。
- **`<Op>FlowCase` のフィールド**は、この順: フローの引数（`Op.params` の順。名前は、フィールド名と同じ決まりで、`Given`、`Then` と当たれば、末尾に `_`。型は、引数の型）、`Given`、`Then`。
- **`Given`** は、今の状態を用意する。走らせる側は、フローを呼ぶ前に、呼ぶ。失敗を返せば、そのテストは、そこで失敗する。状態には、テストを書く側が持っている道具（差し替えた状態の単位）で、触れる。
- **走らせる側は、フローが、正常に終わったことを確かめる。** フローが失敗を返せば（仕様の例外でも、そうでなくても）、そのテストは、そこで失敗する。例外の道は、ここでは確かめない: 入口ごとの、結果ごとのケース（`docs/plugin-go-http.md`「インテグレーションテストの口」）が、確かめる。
- **`Then`** は、値を返すフローなら `func(t *testing.T, got <結果の型>)`、返さないフローなら `func(t *testing.T)`。後の状態と、返り値が、要件どおりであることを、ここで確かめる。
- **`RunFlows` の引数**は、`t`、`ops`（N の入口の `Ops`。`New` の戻り値）、`c`（`FlowCases`）。`ops` を、すべてのフローで使う: フローの間で、状態は、引き継がれる（前のフローの状態に依らないようにするのは、`Given` の役目）。`ops` を、どう組み立てるか（操作の op の名前空間と、機能入口の名前空間を、どうつなぐか）は、人が書く。
- ケースを取り出すメソッド（`c.SignInAndOrder()`）は、そのテストの中で、呼ぶ。

### フローの op の決まり

フローの op が、次のどれかに当たれば、error（「診断」）。どれも、書いたものの整合の検査で、出力を、黙って変えない。

- **`export` が要る**（GODESIGN-1）。走らせる側は、入口の `Ops` のメソッドとして、フローを呼ぶ。
- **配線で、値か、何も返さないもの**（GODESIGN-2）。本体のない op（葉）は、順を持たない。`never` を返す op は、正常に終わる道を持たない。
- **呼べるのは、操作の op だけ**（GODESIGN-3。`docs/ide-chain.md`「業務フロー図」）: 配線の呼び出し（`Call.callee`）の先は、どれも、`@prd.usecase.of` の付いた op。`@prd.usecase.of` のない op（同じ名前空間のものも、別のフローも）、`read`、効果（直に呼ぶ組み込みの効果を含む）は、呼べない。`match` のアームの本体の呼び出しと、`for`、`disjoint` の中の呼び出しも、見る。
- **操作の op とは、別の名前空間**（GODESIGN-4）: フローを持つ名前空間 N に、`@prd.usecase.of` の付いた op があれば、その op に、error。

`@prd.usecase.of` の引数（担い手）は、見ない。引数のない `@prd.usecase.of()` も、操作の op の印として数える。

## 要求の、テストの入れ物の口

要求ごとに、テストの入れ物を一つ受け取る口と、それを走らせる関数を出す（`docs/decisions.md`「決めたこと」377）。Hozo が担保するのは、要求を足したら、入れ物が要ることと、その中のテストが、通っていること（確かめる所は `docs/ide-chain.md`「テストの規約」の「担保すること」）。

### 要求の分類

- **どの分類のケースが、要求かは、設定で言う**: オプション `requirements` に、分類の FQN を並べる（「オプション」）。並べられるのは、対象のない分類（`classify … of never`。`docs/check.md`「分類」の「対象のない分類」）だけ。
- 語彙の印（ケースか、分類に付けるデコレータ）にしないのは、同じ、対象のない分類のケースでも、担い手（`design.Actor`）は、要求でないから: `@prd.ref` が指した分類を、要求と見なす決め方では、どこからも指されていない要求の分類が、見えなくなる。要求かどうかは、出力の話なので、出力の設定に置く。
- 口は、オプションを書いた単位の、N のテストのパッケージに出る。要求の分類の名前空間が、単位を持つ必要は、ない。

### 口の形

```ts
namespace design {
  /** 要求 */
  classify Requirement of never {
    /** ログインしていない人は、注文できない */
    PRD_001;
    /** 注文したら、その注文が、自分の注文の一覧に出る */
    PRD_002;
  }
}
```

```go
// Requirements は、要求ごとの、テストの入れ物。要求（design.Requirement のケース）ごとに、メソッド一つ（宣言順）。中身は、人か AI が書く。
// メソッドが一つでも足りない値は、RunRequirements に渡すところでコンパイルできない。
type Requirements interface {
	// PRD_001 は、要求 design.Requirement.PRD_001: ログインしていない人は、注文できない
	// 指している設計: server.authenticate、server.placeOrder
	PRD_001(t *testing.T)
	// PRD_002 は、要求 design.Requirement.PRD_002: 注文したら、その注文が、自分の注文の一覧に出る
	// 指している設計: server.getOrders、server.placeOrder
	PRD_002(t *testing.T)
}

// RunRequirements は、要求ごとに、入れ物を一つ走らせる。テストの名前は、要求の名前（<分類の FQN>.<ケース>）。
func RunRequirements(t *testing.T, c Requirements) {
	t.Run("design.Requirement.PRD_001", func(t *testing.T) {
		c.PRD_001(t)
	})
	t.Run("design.Requirement.PRD_002", func(t *testing.T) {
		c.PRD_002(t)
	})
}
```

- **入れ物は、要求ごとのメソッド。** 中に、サブテスト（`t.Run`）を、いくつでも書ける。中のケースの数は、決めない。要求を足して、メソッドを書かなければ、`RunRequirements` に渡すところで、コンパイルできない。
- **テストの名前**（ラベル）は、要求の名前: `<分類の FQN>.<ケース>`（`design.Requirement.PRD_001`）。
- **走らせる側は、入れ物を、その場の関数で包んで呼ぶ**（`t.Run(<名前>, func(t *testing.T) { c.<メソッド>(t) })`）。メソッドを、そのまま渡さない（`t.Run(<名前>, c.<メソッド>)`）のは、`RunRequirements` の中に、要求ごとの行を持つため: メソッドの中身は、人のコードで、`design.go` の行ではないので、包まなければ、テストの対応表（「出力」）が、要求ごとの行を指せない。
- **メソッドの名前**は、ケースの名前の、先頭を大文字にしたもの（`PRD_001`、`prd1` → `Prd1`）。並びは、`requirements` に書いた分類の順、その中は、ケースの宣言順。
- **`Requirements` のコメント**の括弧の中は、`requirements` の分類の FQN を、書いた順に「、」でつないだもの。
- **メソッドのコメント**の一行目は、`// <メソッド名> は、要求 <要求の名前>: <説明>`（説明が二行以上なら、二行目から先は、行ごとに `// ` を付けて続ける）。説明がなければ、`// <メソッド名> は、要求 <要求の名前>。`。その後ろに、指している設計の一行。
- **`RunRequirements` の引数**は、`t` と、`c`（`Requirements`）。どの設計（入口、フロー）を通して確かめるかは、書く人が、要求ごとに選ぶので、走らせる側は、アプリの口を、受け取らない。

### 指している設計

- 要求を**指している設計**は、`@prd.ref` の引数に、その要求（`CaseValue` の、分類とケース）を持つ宣言（op、model、状態、効果、`read`）。仕様の全体（`View.program`）から集める: 単位の対象かどうかにも、名前空間が単位を持つかどうかにも、依らない。
- コメントの一行は、`// 指している設計: <宣言の FQN を「、」で>`。並びは、名前空間の FQN の辞書順、その中は、宣言順。同じ宣言は、一度だけ。
- **どこからも指されていない要求**は、コメントの一行が `// 指している設計: なし` になり、warning を一つ返す（要求ごとに。位置は、その分類）。辿る先のない要求は、穴（`docs/ide-chain.md`「テストの規約」の「要求のテスト」）。error にしないのは、要求を先に書いて、設計を後から足す順を、止めないため。入れ物の口は、指されていなくても、出す。
- `@prd.ref` は、辿るための印で、テストの中身は、そこから作らない（同）。

## 診断

| ID | 重さ | 条件 |
|---|---|---|
| GODESIGN-1 | error | `@prd.business.flow` の付いた op に `export` がない（「フローの op の決まり」）。位置は、その op |
| GODESIGN-2 | error | `@prd.business.flow` の付いた op が、本体を持たない（葉）、または `never` を返す。位置は、その op |
| GODESIGN-3 | error | フローの op の配線が、操作の op（`@prd.usecase.of` の付いた op）でないものを呼ぶ: `@prd.usecase.of` のない op、`read`、効果。位置は、フローの op。呼んだ先ごとに、一つ |
| GODESIGN-4 | error | フローを持つ名前空間 N に、`@prd.usecase.of` の付いた op がある。位置は、その op |
| GODESIGN-5 | error | `[emit.options.go-design]` に、知らないキーがある。`requirements` が、文字列の配列でない。`requirements` の項目が、対象のない分類の FQN でない（宣言がない、分類でない、対象を持つ分類）。同じ FQN を、二度書いた。位置なし |
| GODESIGN-6 | error | テストのパッケージに足す公開の名前（`<Op>FlowCase`、`FlowCases`、`RunFlows`、`Requirements`、`RunRequirements`）が、そのパッケージの、基底の公開の名前か、自分のほかの名前と当たる。一つの `<Op>FlowCase` のフィールドの名前どうしが当たる。`Requirements` のメソッドの名前どうしが当たる。フローの op の名前か、要求のケースの名前が `_` で始まる（「出力」）。位置は、当たった自分の名前を生んだフローの op か、要求の分類。決まった名前が当たったなら、相手の名前を生んだ宣言 |

warning（コードは `PLUGIN`）は二つ: フローも、要求もない（「対象」）。どこからも指されていない要求（「指している設計」）。

- error が一つでもあれば、ファイルも warning も返さない。
- 基底のオプション `module` がないとき（同じ単位の基底が GO-8 を返し、何も書き出されない。`docs/plugin-go.md`「診断」）は、ファイルを返さず、GO-8 も重ねて返さない。上の診断は、GODESIGN-7 のほかは、そのときも返す。warning も、返す。
- 生成器の不具合（`View` が欠けている、生成したコードを `go/format` で整形できない）は、診断にせず、異常終了する（`Crashed`。`docs/plugin-protocol.md`「起動」）。
