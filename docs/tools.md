# 道具とユースケース

## この文書が決めること

誰が、何のために、どの道具で、何をするか。道具は四つ: CLI（`hozoc check` など）、言語サーバー（`hozoc lsp`）、VS Code 拡張、IDE。この文書が持つのは、担い手、ユースケース、道具の境目、道具が共有する操作。道具ごとの中身の持ち主は、CLI が `cli.md`、言語サーバーが `lsp.md`、VS Code 拡張が `editors.md`。IDE の中身の文書は、まだない（「IDE の段階」の段ごとに、作るときに書く）。

**この文書は、案。** 道具をユースケースから分けて設計することは決まっている（`decisions.md`「決めたこと」185）。担い手、ユースケース、境目の中身は、利用者が確かめていない（`open.md`「聞かずに決めて、確かめていない決定」）。「今の状態」と書いた行のほかは、どれも、まだ作っていない。

## 担い手

| 担い手 | 責任を持つもの | `.hozo` の文面 |
|---|---|---|
| レビューする人 | 仕様が、作りたいものを言っていること（`requirements.md`「価値と位置づけ」の「人が責任を持つのは仕様」） | 読めなくてよい |
| 書き手の AI | 仕様の文面を書くこと、検査を通すこと、op の中身を書くこと | 書く |
| エンジニア | 文面と中身（コード）を直に扱うこと、設定、プラグイン、CI | 書く |
| 自動の検査（CI） | 入った変更が、検査と生成物の一致を満たすこと | — |

- 一人の人が、レビューする人とエンジニアを兼ねてよい。分けるのは人ではなく、していること。
- プラグインを書く人は、ここに入れない。その道具は SDK（`packages.md`）。

## 仕事の流れ

ユースケースは、次の流れの上に並ぶ。

1. **起こす**: AI が、要求から、仕様を下書きする。
2. **整える**: 検査（`check.md`）を通るまで、足りない宣言を足す。
3. **レビューする**: 人が、仕様が言っていることを読み、それでよいかを判断する。
4. **手直しする**: 人が直す。または、AI に直させる。2 に戻る。
5. **枠を出して、中身を書く**: `hozoc emit` がコードの枠を出し、AI かエンジニアが中身を書く。
6. **確かめる**: 中身が仕様から外れていないことを、ハーネス（`requirements.md`「ハーネス」）が確かめる。
7. **変える**: 仕様が変わる。3 に戻る。レビューするのは、仕様の全体ではなく、変更。

一度目のレビュー（3）は全体を読み、二度目から（7 の後の 3）は変更を読む。回数が多いのは、後者。

## ユースケース

見出しが、ユースケースの名前。「道具」は、それを受け持つ道具。

### レビューする人

| ユースケース | したいこと | 道具 |
|---|---|---|
| 全体をつかむ | このアプリに、どんな概念と担い手があり、何が外から起きるかを知る | IDE |
| 入口を追う | 一つの入口（人の操作、外からの通知、時計）から、何が、どの順に起き、何が変わり、どう失敗し、失敗したとき何が変わっているかを知る | IDE |
| ものの一生を確かめる | 注文や支払いのような、一つのものが取りうる状態と、許した移り変わりと、それを起こす入口を知る | IDE |
| 約束を確かめる | 誰に何を約束していて、どの op が、それを守る役かを知る | IDE |
| 変更をレビューする | 前に認めた版から、設計として何が変わったかを知り、認めるかを決める | IDE |
| 欠けを知る | 検査の error と、検査は通るが目を通すべきところ（説明のない宣言、進める効果のないケース、どの入口からも起きない移り変わり）を、設計の要素の上で知る | IDE |
| 手直しする | 名前、説明、ケース、手順の一行を、文面を書かずに直す。結果は文面に戻る | IDE |
| AI に直させる | 設計の要素を指して、直してほしいことを言う | IDE |

| 人が見るものを確かめる | レビューする人に見えるもの（入口、手順、ものの一生、欠け）を、渡す前に自分で読む | CLI |
| 指摘を受け取る | レビューする人が要素に付けた指摘を、どの宣言へのものかと一緒に受け取る | CLI |
| 枠を出す | 仕様から、コードの枠を出す | CLI |

| レビューの表示へ移る | 文面のカーソルの下の宣言を、IDE の、その要素の表示で開く | VS Code 拡張 |

| ユースケース | したいこと | 道具 |
|---|---|---|
| 入った変更を検査する | 検査と、生成物が仕様から遅れていないことを確かめる | CLI |
| 変更を要約する | プルリクエストに、設計として何が変わったかを出す | CLI |

## 道具

四つの道具は、相手と、扱う単位と、動き方が違う。

| 道具 | 相手 | 扱う単位 | 動き方 |
|---|---|---|---|
| CLI | AI、CI、エンジニア | プロジェクトの全体 | 一度走って、終わる。結果は、人が読む形と JSON |
| 言語サーバー | 文面のエディタ（どれでも） | ファイルと、その中の位置 | エディタが起動する。開いている文書の内容を、ディスクより優先する（`lsp.md`「プロジェクト」） |
| VS Code 拡張 | VS Code で、文面と中身を書くエンジニア | ワークスペース（文面と、コード） | 言語サーバーのクライアント。LSP にないことと、VS Code への配り方を持つ |
| IDE | レビューする人 | 設計の要素（入口、ものの一生、約束、宣言）と、変更 | 動き続ける。ディスクの上のファイルが変わるたびに、検査し直して、表示を追従させる |

### 境目

- **言語サーバーと、VS Code 拡張。** 言語サーバーが持つのは、LSP が定める機能のうち、`.hozo` と `hozo.toml` の文面についてのもの。エディタを選ばない。VS Code 拡張が持つのは、VS Code にしかないもの（色付け、コマンド、コードとの行き来）。拡張は、言語の知識を持たない（今の状態: `editors.md`「VS Code 拡張」）。
- **文面のエディタと、IDE。** 文面のエディタ（言語サーバーと拡張）の単位は、ファイルと位置で、相手は、文面を書く人。IDE の単位は、設計の要素で、相手は、文面を書かない人。IDE の手直しは、要素への操作（「名前を変える」「ケースを足す」）で、文面の自由な編集ではない。
- **IDE は、言語サーバーのクライアントではない。** 言語サーバーは、エディタが開いている文書（保存していない内容を含む）を見る。IDE には、開いている文書がない: 見るのは、ディスクの上のファイル。AI も、エンジニアも、IDE も、ディスクの上のファイルを通してつながる。
- **VS Code 拡張は、レビューの表示を持たない。** 文面の横で図を見たいエンジニアには、拡張が、IDE の、その要素の表示を開く（「レビューの表示へ移る」）。表示を作るものは、一つ。
- **IDE は、中身（コード）を扱わない。** op の中身を書くのは、エディタと AI。IDE がコードについて見せるのは、ハーネスの結果だけ（「IDE の段階」の最後の段）。

## 操作

道具は、同じ操作への、別々の口。操作は、本体のライブラリに一つだけ実装する（今の状態: 検査は、CLI と言語サーバーが同じ実装を使う。`requirements.md`「言語サーバー」）。

| 操作 | 中身 | CLI | 言語サーバー | VS Code 拡張 | IDE |
|---|---|---|---|---|---|
| 検査する | `check.md` の検査 | `hozoc check`（今の状態: ある） | 診断（今の状態: ある） | 言語サーバーのものを出す | 欠けとして、要素に付けて出す |
| 位置を引く | 定義、参照、説明 | — | 定義へジャンプ、ホバー（今の状態: ある）、参照の検索 | 言語サーバーのものを出す | 要素から、文面の位置を出す |
| 足りない宣言を足す | 診断の `Data`（`check.md`「Data」）から、足す文面を作る | コマンド（新しい） | コードアクション（`lsp.md`「段階 4 の後」） | 言語サーバーのものを出す | 欠けの横のボタン |
| 見せるデータを導く | 入口、手順、ものの一生、約束、欠けを、IR から導く | コマンド（新しい。JSON） | — | — | 表示のもと |
| 変更を比べる | 二つの版の仕様の差を、設計の言葉で言う（「変更のレビュー」） | コマンド（新しい。JSON と、人が読む形） | — | — | 変更の表示 |
| 要素を直す | 要素への操作を、文面の書き換えにする（`requirements.md`「UI での手直し」） | — | 名前の変更（LSP の rename） | 言語サーバーのものを出す | 手直し |
| 枠を出す | `hozoc emit` | `hozoc emit`（今の状態: ある） | — | 保存したときと、コマンド | — |
| 指摘を残す、読む | 要素に付けた指摘（「AI への指摘」） | 読むコマンド（新しい） | — | — | 書く |

- 「足りない宣言を足す」は、三つの口（AI のための CLI、エンジニアのためのコードアクション、レビューする人のためのボタン）が、同じ文面を足す。
- 「見せるデータを導く」を CLI にも出すのは、書き手の AI が、人に渡す前に同じものを読めるようにするためと、IDE のほかの見せ方（図だけを出すものなど）が、同じデータから作れるようにするため。
- AI が文面を直すのは、文面を直に書くことによる。「要素を直す」の口は、AI には要らない。

## 変更のレビュー

二度目からのレビューは、変更を読む（「仕事の流れ」）。文面の差分（行の足し引き）は、レビューする人の読むものではない: 文面を読めなくてよく、並べ替えや整形は、設計の変更ではない。

比べるのは、二つの版の IR。差は、ユースケースの言葉で言う:

| 差 | 例 |
|---|---|
| 入口が増えた、なくなった | 担当者の画面に、操作が一つ増えた |
| 入口の手順が変わった | 請求の確定の前に、在庫の確認が入った |
| 入口の失敗が変わった | 失敗が一つ増えた。ある失敗のとき、変わっているものが増えた |
| ものの一生が変わった | ケースが増えた。移り変わりが増えた、なくなった。移り変わりを起こす入口が変わった |
| 約束が変わった | 約束が増えた。約束を守る役の op が変わった |
| 宣言が変わった | 型のフィールド、状態、失敗の運ぶ値 |
| 説明だけが変わった | 振る舞いは変わっていない |

基準の版は、git の版（既定は、今のブランチが `main` から分かれたところ）。git のないプロジェクトでの基準は、決めていない。

## AI への指摘

レビューする人が大きく直したいときは、自分で直さず、AI に直させる（「AI に直させる」）。指摘は、設計の要素（宣言の FQN。手順の一行なら、その位置）を指し、文で書く。

指摘は、設計ではない。仕様（`.hozo`）には入れない（`requirements.md`「ただ一つの正」: 設計を言うものは、仕様だけ）。置き場と形（プロジェクトの中のファイルか、IDE の中だけか、プルリクエストのコメントか）は、決めていない。

## IDE の段階

| 段 | できること | 受け持つユースケース | 要る操作 |
|---|---|---|---|
| 1 | 見る。ファイルの変化に追従する。欠けを要素の上に出す。要素から文面の位置を出す | 全体をつかむ、入口を追う、ものの一生を確かめる、約束を確かめる、欠けを知る | 検査する、見せるデータを導く、位置を引く |
| 2 | 変更を見る | 変更をレビューする | 変更を比べる |
| 3 | 足りない宣言を足す | 欠けを知る（の続き） | 足りない宣言を足す |
| 4 | 要素を直す | 手直しする | 要素を直す |
| 5 | 指摘を残す | AI に直させる | 指摘を残す、読む |
| 6 | 中身の状態を見る（どの op の中身があり、ハーネスが通っているか） | — | 決めていない |

- 段 1 と 2 は、何も書き換えない。段 3 から、文面を書き換える。
- CLI の新しいコマンド（見せるデータ、変更を比べる）は、IDE の同じ段と一緒に作る: 操作は一つで、口が二つ。
- 言語サーバーの、段階 4 の後の機能（補完、参照の検索、コードアクション。`lsp.md`「段階 4 の後」）は、IDE の段とは別に進められる。コードアクションは、IDE の段 3 と、同じ操作を使う。

### 見るものの決まり

- **仕様にあるものは、すべて見せる。** 見せるものを選ばない。決めるのは、読む順と、畳み方だけ（`decisions.md`「決めたこと」184）: 人が責任を持つのは仕様なので、仕様にあって見えないものを作らない。
- 読む順は、ユースケースの順: 全体、約束、入口、ものの一生、その後に、概念ごとのすべての宣言。
- 語彙の意味は、読まない。デコレータは、名前と引数を、そのまま札として出す。語彙ごとの見せ方（`@http.post` を経路として出す、など）を足すかは、決めていない。

### 試作で分かったこと

サンプル `order-app` の IR から、段 1 の「見る」に当たる静的なページを、一度作った（リポジトリには、入れていない）。

- **入口は、「仕様の中の、誰からも呼ばれない op」で足りた。** 37 の入口（画面の操作、通知の入口、時計で動く op）が、語彙を読まずに、そろった。
- **手順の文は、op の説明の一行目で足りた。** 配線の一行を、呼ぶ相手の説明で言う。説明のない宣言は、名前だけになり、欠けとして見える（38 か所）。
- **「失敗と、そのとき変わっているもの」は、検査の計算（`Signature.relations`）を、そのまま表にできた。**
- **ものの一生の図は、値の分類と、効果の行の遷移（`Effect.row`）から描けた。** 移り変わりごとに、それを起こす入口を、入口の `Signature.effects` から引けた。
- **見ると分かる欠けがあった。** 進める効果のないケース（まとめて足す効果が、入るケースを書けないことによる。`open.md`「言語」の、行の並びを受け取る効果の点）。

## IDE の形

決めていない（`open.md`「次の段」）。ユースケースから言えるのは、次の三つ。

- レビューする人は、文面のエディタを持たないことがある。IDE を使うのに、エディタを要らないようにする。
- IDE は、ディスクの上のファイルを見張る。書き手の AI がファイルを書く場所（手元でも、クラウドでも）で、動く必要がある。
- 表示を作るものは、一つ（「境目」）。VS Code 拡張から開くのも、同じ表示。
