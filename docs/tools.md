# 道具とユースケース

## この文書が決めること

誰が、何のために、どの道具で、何をするか。道具は五つ: IDE、MCP サーバー（`hozoc mcp`）、言語サーバー（`hozoc lsp`）、VS Code 拡張、CLI（`hozoc check` など）。この文書が持つのは、担い手、ユースケース、道具の境目、道具が共有する操作、作る順。道具ごとの中身の持ち主は、言語サーバーが `lsp.md`、VS Code 拡張が `editors.md`、CLI が `cli.md`。IDE の設計の文書は、「IDE の設計の段階」の表が名指しする。MCP サーバーの中身の文書は、まだない（作るときに書く）。

**決まっていること**（`decisions.md`「決めたこと」185、186）は、「決まっている前提」の節。**そのほかは、案**で、利用者が確かめていない（`open.md`「聞かずに決めて、確かめていない決定」）。「今の状態」と書いたもののほかは、どれも、まだ作っていない。

## 決まっている前提

- **IDE は、エンジニアでない人のための道具。** プロジェクトのルートを開くと、そのプロジェクトの `.hozo` のファイル、設計の手法ごとの編集の画面、ハーネスの状況、AI とのチャットが、一つの画面に並ぶ。設計の手法ごとの編集の画面は、図ごとの画面ではなく、コンテキストごとのノート（自由なキャンバス）に置く図形として持つ（`decisions.md`「決めたこと」192〜194。`ide-screens.md`）。
- **AI の口は、MCP。** AI が仕様を扱うための口は、CLI ではなく、MCP サーバーとして出す。
- **VS Code 拡張に、画面は作らない。** VS Code を選んだのは、早く形にするためで、ユースケースから選んだのではない。拡張の中に画面を作る形は、直感から遠く、エンジニアでない人には向かない。
- **道具は、ユースケースと、そこでの操作が違うものとして、分けて設計する。**

## 担い手

| 担い手 | していること | 主な道具 |
|---|---|---|
| 設計する人 | 作りたいものを、仕様として決める。AI に書かせ、読み、直し、中身が仕様どおりかを見る。エンジニアでない人を含む。`.hozo` の文面は、書けなくてよい | IDE |
| AI | 仕様の文面を書く。検査を通す。op の中身を書く。IDE の中のチャットの AI も、外のエージェント（ターミナルやエディタで動くもの）も、同じ | MCP サーバー |
| エンジニア | 文面と、中身のコードを、自分のエディタで直に書く。設定、プラグイン、CI を持つ | 言語サーバー、CLI |
| 自動の検査（CI） | 入った変更が、検査と、生成物の一致を満たすことを確かめる | CLI |

- 一人の人が、設計する人とエンジニアを兼ねてよい。分けるのは人ではなく、していること。
- 仕様に責任を持つのは、人（`requirements.md`「価値と位置づけ」）。AI は、書くが、責任を持たない。
- プラグインを書く人は、ここに入れない。その道具は SDK（`packages.md`）。

## 仕事の流れ

設計する人から見た流れ。どの段も、IDE の中で起きる。

1. **開く**: プロジェクトのルートを、IDE で開く。
2. **書かせる**: チャットで、作りたいものを AI に言う。AI が、仕様の文面を書く。
3. **読む**: 書かれた仕様を、設計の手法ごとの画面で読む。二度目からは、変わったところを読む。
4. **直す**: 画面の上で直す。大きな直しは、画面の要素を指して、AI に言う。
5. **整える**: 検査の欠け（足りない宣言）を、AI か、ボタンで埋める。
6. **中身を作らせる**: 仕様からコードの枠を出し、AI に中身を書かせる。
7. **確かめる**: ハーネスの状況（検査、枠の遅れ、中身の欠け、テスト）を見る。
8. 2 に戻る。

## ユースケース

見出しが、担い手。表の一列目が、ユースケースの名前。

| 入口を追う | 一つの入口（人の操作、外からの通知、時計）から、何が、どの順に起き、何が変わり、どんな例外が出て、例外が出たとき何が変わっているかを知る |

| 道具 | 相手 | 扱う単位 | 動き方 |
|---|---|---|---|
| IDE | 設計する人 | プロジェクト。その中の、設計の要素（入口、ものの一生、約束、宣言）と、変更 | プロジェクトを開いている間、動き続ける。ファイルが変わるたびに、検査し直して、画面を追従させる |
| MCP サーバー | AI | プロジェクトと、その中の宣言 | AI の側（IDE のチャット、外のエージェント）が起動する。道具（tool）の呼び出しごとに、今のファイルで答える |
| 言語サーバー | 文面のエディタ | ファイルと、その中の位置 | エディタが起動する。開いている文書の内容を、ディスクより優先する（今の状態: `lsp.md`「プロジェクト」） |
| VS Code 拡張 | VS Code で文面を書くエンジニア | `.hozo` のファイル | 色付けと、言語サーバーへの接続（今の状態: `editors.md`「VS Code 拡張」） |
| CLI | CI、エンジニア | プロジェクトの全体 | 一度走って、終わる |

### IDE の画面

プロジェクトを開いた IDE に並ぶもの（「決まっている前提」）。

| 並ぶもの | 中身 |
|---|---|
| ファイル | プロジェクトの `.hozo` と `hozo.toml`。選ぶと、文面を見られる |
| 設計の手法ごとの画面 | 同じ仕様を、手法ごとの形で見せ、その形の上で直せる（下の表） |
| ハーネスの状況 | 検査、枠の遅れ、中身の欠け、テスト（「ハーネスの状況」） |
| AI とのチャット | 作ること、直すことを、AI に言う。AI は、MCP サーバーを通して仕様を扱う |

**下の表は、筋書きを詰める前に書いた、概要の水準の候補。** その後、設計の場は、図ごとの画面ではなく、ノート（自由なキャンバス）と決めた（`decisions.md`「決めたこと」192〜194）。今の構成は、設計の段 3 の `ide-screens.md` で、食い違えば、そちらが新しい。 画面の一覧と、画面ごとの中身は、ユースケースを具体的な筋書きまで詰めてから、そこから導く。それより前に、画面の一覧を決めたり、見本（模型）を作ったりしない: 先に形を作ると、要件が、その形に引っ張られる（`decisions.md`「決めたこと」189）。

設計の手法ごとの画面の候補。材料になる仕様の記述の持ち主は `requirements.md`「レビューで見せる形」の表。手法に合わせることは目的ではなく（`decisions.md`「決めたこと」177）、画面は、設計する人のユースケースのためにある。

| 画面 | 当たる手法 | 受け持つユースケース | 直せるもの |
|---|---|---|---|
| 地図 | コンポーネント図 | 全体をつかむ | 名前空間の説明 |
| 入口と手順 | ユースケース図、アクティビティ図 | 入口を追う | 手順の行、分かれ道のアーム、例外、説明 |
| ものの一生 | ステートマシン図 | ものの一生を確かめる | ケース、移り変わり、説明 |
| やり取り | シーケンス図 | 入口を追う（名前空間をまたぐところ） | —（見るだけ） |
| 型 | クラス図 | 画面で直す | model のフィールド、scalar、union |
| 約束 | PRD | 約束を確かめる | 約束の文、守る役の op |

- どの画面も、同じ仕様（IR）の別の見え方。画面ごとに別のデータを持たない（`requirements.md`「ただ一つの正」）。
- 仕様にあるものは、どれかの画面で、必ず見える。見せるものを選ばない（`decisions.md`「決めたこと」184）。手法の画面に入らない宣言は、ファイルの文面と、宣言の一覧で見える。
- 語彙の意味は、読まない。デコレータは、名前と引数を、札として出す。語彙ごとの見せ方（`@http.post` を経路として出す、`page` の語彙から画面の流れを出す、など）を足すかは、決めていない。

### 境目

- **IDE と、VS Code 拡張。** IDE は、設計する人の、ただ一つの場所: 読む、直す、AI に頼む、確かめる、が並ぶ。VS Code 拡張は、エンジニアが自分のエディタで文面を書くための、色付けと言語サーバーへの接続だけを持つ。画面も、チャットも、足さない。
- **IDE と、言語サーバー。** IDE の、文面を見せる部分は、言語サーバーのクライアントになる（色、診断、定義へのジャンプを、エディタと同じものにする）。設計の手法ごとの画面、変更、ハーネスは、言語サーバーを通さない: LSP の単位は、ファイルと位置で、設計の要素ではない。
- **MCP サーバーと、CLI。** AI は、MCP サーバーを使う。CLI は、CI と、ターミナルのエンジニアのためのもので、AI のための口を、CLI に足さない。二つは、同じ操作の別の口（「操作」）。
- **IDE のチャットの AI と、外のエージェント。** どちらも、同じ MCP サーバーを使う。IDE だけが使える、AI のための口は、作らない: 外のエージェントが書いた仕様も、IDE の中の AI が書いた仕様も、同じに扱える。
- **ファイルが、つなぎ目。** IDE、AI、エンジニアのエディタは、ディスクの上のファイルを通してつながる。IDE は、ファイルの変化を見張る。誰が書いても、IDE の画面は追従する。
- **IDE は、中身のコードを編集しない。** op の中身を書くのは、AI と、エンジニアのエディタ。IDE が中身について見せるのは、ハーネスの状況。

## 操作

道具は、同じ操作への、別々の口。操作は、本体のライブラリに一つだけ実装する（今の状態: 検査は、CLI と言語サーバーが同じ実装を使う。`requirements.md`「言語サーバー」）。

| 操作 | 中身 | IDE | MCP サーバー | 言語サーバー | CLI |
|---|---|---|---|---|---|
| 検査する | `check.md` の検査 | 欠けとして、要素に付ける | 道具 | 診断（今の状態: ある） | `hozoc check`（今の状態: ある） |
| 位置を引く | 定義、参照、説明 | 要素から文面へ、文面から要素へ | 道具（宣言を引く） | 定義へジャンプ、ホバー（今の状態: ある） | — |
| 足りない宣言を足す | 診断の `Data`（`check.md`「Data」）から、足す文面を作る | 欠けの横のボタン | 道具 | コードアクション（`lsp.md`「段階 4 の後」） | — |
| 見せるデータを導く | 入口、手順、ものの一生、約束、欠けを、IR から導く | 画面のもと | 道具 | — | — |
| 変更を比べる | 二つの版の仕様の差を、設計の言葉で言う（「変更を読む」） | 変更の画面 | 道具 | — | コマンド（CI が、プルリクエストに出す） |
| 要素を直す | 要素への操作を、文面の書き換えにする（`requirements.md`「UI での手直し」） | 画面での編集 | —（AI は、文面を直に書く） | 名前の変更 | — |
| 枠を出す | `hozoc emit` | ボタン | 道具 | — | `hozoc emit`（今の状態: ある） |
| ハーネスの状況を得る | 「ハーネスの状況」 | 状況の表示 | 道具 | — | 決めていない |
| 言語の手引きを引く | 文法、検査の規則、書き方の指針 | — | 資料（resource） | — | — |

- 「足りない宣言を足す」は、三つの口（設計する人のボタン、AI の道具、エンジニアのコードアクション）が、同じ文面を足す。
- 配線の op の `throws` は、足りない宣言に、当たらなくなった: 書かなくてよく、検査器が計算する（`check.md`「状態に触れるもの」の「節に書く要素」）。足すのは、節を書いた op の、足りない例外（THROWS-1）と、ほかの診断が名指しするもの。
- 「見せるデータを導く」を MCP サーバーにも出すのは、AI が、人の画面に出るものを、渡す前に読めるようにするため。
- 「言語の手引き」は、AI が Hozo を書くための資料。持ち主は `docs/` の文書（`grammar.md`、`check.md`、`requirements.md`「書き方の指針」）で、MCP サーバーは、それを配るだけ。

## 変更を読む

二度目からは、仕様の全体ではなく、変わったところを読む（「仕事の流れ」）。AI が書き換えるたびに、これが起きる。文面の差分（行の足し引き）は、設計する人の読むものではない: 並べ替えや整形は、設計の変更ではない。

比べるのは、二つの版の IR。差は、ユースケースの言葉で言う:

| 差 | 例 |
|---|---|
| 入口が増えた、なくなった | 担当者の画面に、操作が一つ増えた |
| 入口の手順が変わった | 請求の確定の前に、在庫の確認が入った |
| 入口の例外が変わった | 例外が一つ増えた。ある例外のとき、変わっているものが増えた |
| ものの一生が変わった | ケースが増えた。移り変わりが増えた、なくなった。移り変わりを起こす入口が変わった |
| 約束が変わった | 約束が増えた。約束を守る役の op が変わった |
| 宣言が変わった | 型のフィールド、状態、例外の運ぶ値 |
| 説明だけが変わった | 振る舞いは変わっていない |

基準の版（何と比べるか）は、決めていない。候補は、git の版（今のブランチが分かれたところ）と、IDE が覚えている「最後に受け入れた版」。

## ハーネスの状況

設計する人が、「中身が、仕様どおりか」を、コードを読まずに知るためのもの（`requirements.md`「ハーネス」）。

| 項目 | 言うこと | 出どころ |
|---|---|---|
| 検査 | 仕様の中に、error と warning がいくつあるか | 検査する（今の状態: ある） |
| 枠の遅れ | 生成したコードの枠が、今の仕様から遅れていないか | `hozoc emit` の、書く予定と、ディスクの比較（今の状態: `cli.md`「emit」の `dryRun`） |
| 中身の欠け | 仕様が求める中身（葉の op、述語、状態の読み書き）のうち、まだ書かれていないもの | 決めていない。今は、コンパイルエラーとして出る（`plugin-go.md`「実装を受け取る口」） |
| テスト | 中身が、仕様の言う振る舞いを守っているか | 決めていない。テストの生成は、まだない（`requirements.md`「段階」） |

「中身の欠け」と「テスト」は、その言語のビルドとテストを走らせないと分からない。誰が、どこで走らせるか（IDE の手元か、CI の結果を読むか。走らせ方を、基底のプラグインが言うか）は、決めていない。エンジニアでない人の手元には、その言語の道具がないことがある。

## 作る順

| 段 | 作るもの | できるようになるユースケース |
|---|---|---|
| 1 | MCP サーバー: 検査する、仕様を読む、足りない宣言を足す、枠を出す、言語の手引き | AI の「言語を知る」「仕様を読む」「検査する」「足りない宣言を足す」「枠を出す」 |
| 2 | IDE: プロジェクトを開く。ファイルと文面。手法ごとの画面（見るだけ）。検査の欠け。ファイルの変化への追従 | 設計する人の「プロジェクトを開く」「全体をつかむ」「入口を追う」「ものの一生を確かめる」「約束を確かめる」「欠けを知る」「文面を見る」 |
| 3 | IDE: AI とのチャット。変更の画面 | 「AI に頼む」「変更を読む」。AI の「人が見るものを確かめる」「変更を確かめる」 |
| 4 | IDE: ハーネスの状況 | 「ハーネスを見る」 |
| 5 | IDE: 画面での編集（文面への書き戻し） | 「画面で直す」 |

- **段 1 を先にする理由**: 今の作り方（AI が、ターミナルで文面を書く）に、すぐ効く。IDE のチャット（段 3）は、これを使う。
- **段 3 を、段 5 より先にする理由**: エンジニアでない人は、チャットで頼み、画面で読み、変更を受け入れる、だけで、仕様を作れるようになる。画面での編集（書き戻し）は、いちばん難しく、それがなくても、流れは回る。
- 「見せるデータを導く」「変更を比べる」は、IDE の同じ段と一緒に、MCP サーバーにも出す（操作は一つで、口が二つ）。
- 言語サーバーの、段階 4 の後の機能（補完、参照の検索、コードアクション。`lsp.md`「段階 4 の後」）は、この順とは別に進められる。コードアクションは、「足りない宣言を足す」と同じ操作を使う。

## IDE の設計の段階

IDE は、次の段を、順に踏んで設計する（`decisions.md`「決めたこと」189、190）。一つの段が終わるごとに、利用者が文書を確かめてから、次に進む。

| 段 | 作るもの | 中身 | 文書 |
|---|---|---|---|
| 1 | ユースケースの筋書きと、設計の手法への写し | ユースケースごとに、具体例（サンプル `order-app`）の上で、誰が、何をきっかけに、一歩ずつ、何を知りたいか、何をしたいか。画面の言葉は使わない。組にして、同じ具体例を、設計の手法（UML など）に写すと、何が出て、何が出ないか | `ide-scenarios.md`、`ide-methods.md`（どちらも、案） |
| 2 | 情報と操作の洗い出し | 筋書きの一歩ごとに、要る情報と、要る操作。今の Hozo と `hozoc` が出せるかは、分けて記す。出せないことは、画面の設計の制約にしない（`decisions.md`「決めたこと」191） | `ide-needs.md`（案） |
| 3 | 画面の構成 | 情報と操作を、IDE の場へ割り当てる。設計の場であるノート（自由なキャンバス）、ノートに置けるもの、図形をプラグインが定義する仕組み、ノートのほかの場、移り方。筋書きを、なぞって確かめる | `ide-screens.md`、`ide-shapes.md`（前提のほかは、案） |
| 4 | 画面の見本 | 構成の見本を作り、段 1 の筋書きを、なぞって確かめる。分かったことを、段 3 に返す | `ide-mock.md`、`ide-mock/notes.html`（案） |
| 5 | 動きの要件と、枠組みの選定 | 規模、追従の速さ、配り方。そこから、画面の枠組みと、キャンバスの部品を選ぶ規準と、候補の比べ。動く試作で確かめてから、決める | `ide-stack.md`（案。枠組みは、まだ決めていない） |
| 6 | `hozoc` との口の設計 | 画面が要るデータと操作の、やり取りの形 | まだない |

## IDE の形

決まっていること（`decisions.md`「決めたこと」187、188）:

- **IDE は、手元のアプリ。** インストールして、プロジェクトのフォルダを開く。ターミナルは要らない。
- **裏方は、`hozoc`。** 検査、トランスパイル、MCP サーバーの立ち上げは、このコマンドが担う。IDE は、同梱した `hozoc` を、別のプロセスとして起動する。
- **殻は、Tauri 2。** 画面は、OS の表示の部品（Windows は WebView2、macOS は WebKit）で描く。Electron は、採らない: ブラウザを丸ごと同梱するので重く、デスクトップのアプリとして嫌われている。Wails（Go で書ける）は、採らなかった: 複数のウィンドウなどが入る v3 が、まだベータ（2026 年 8 月）で、配るための仕組み（インストーラー、署名、自動の更新）は、Tauri が公式にそろえている。
- 殻がすることは、四つだけ: フォルダを選ぶ、`hozoc` を起動する、画面をウィンドウに出す、配る（インストーラー、更新）。設計についての知識は、持たない。

案（利用者が確かめていない）:

```
アプリ（殻）──起動──▶ hozoc ide <フォルダ>
                        ├─ プロジェクトを見張る（検査、トランスパイル、ハーネス）
                        ├─ 画面（HTML / JS）を配る
                        ├─ 画面とやり取りする口（WebSocket の JSON）
                        └─ MCP サーバー（チャットの AI と、外のエージェントが使う）
殻のウィンドウ ◀── http://127.0.0.1:… の画面
```

- **画面は、`hozoc` が配る。** 画面のファイルを `hozoc` に同梱し、`hozoc ide` が、手元のポートで配る。画面と `hozoc` の版が、ずれない。殻なしでも、`hozoc ide` を起動してブラウザで開けば、同じ画面が使える（開発と、リモートの環境のため）。
- **何を見せるかの計算は、`hozoc` の側。** 入口、手順、ものの一生、欠け、変更は、`hozoc` が導き（「操作」の「見せるデータを導く」「変更を比べる」）、画面は、描くだけ。
- **やり取りの形は、スキーマで決める。** 画面の側の型（TS）は、スキーマから生成する（今の状態: IR の型は、`schema/ir.schema.json` から `sdk/ts/src/ir.ts` を生成している。`packages.md`「生成するもの」）。
- **文面の色付けは、今ある TextMate の文法を使う**（`editors.md`「TextMate の文法」）。色付けの決まりを、二つ持たない。
- **置き場**: 画面は `ide/web`、殻は `ide/desktop`。
- 画面は OS ごとの表示の部品で描くので、見え方と速さが、OS ごとに少し違う。図の画面は、OS ごとに確かめる。

決めていないこと（`open.md`「次の段」）:

- 画面の枠組み（フレームワークと、キャンバスの部品）。規準と、候補の比べは `ide-stack.md`。動く試作で確かめてから、決める。
- チャットの AI に、何を使うか（IDE が AI を持つか、利用者が持っているエージェントをつなぐか）。
- プラグインの配り方。このリポジトリのプラグインは、今、手元に Go があることを前提に動く（マニフェストの `command` が `go run …`。`plugin-protocol.md`「マニフェスト `hozo-plugin.toml`」）。エンジニアでない人の手元で動かすには、実行ファイルで配る形が要る。
- ハーネスのうち、その言語のビルドとテストを、手元で走らせるか、CI の結果を読むか（「ハーネスの状況」）。

## 試作で分かったこと

サンプル `order-app` の IR から、段 2 の「見るだけ」に当たる静的なページを、一度作った（リポジトリには、入れていない）。

- **入口は、「仕様の中の、誰からも呼ばれない op」で足りた。** 37 の入口（画面の操作、通知の入口、時計で動く op）が、語彙を読まずに、そろった。
- **手順の文は、op の説明の一行目で足りた。** 配線の一行を、呼ぶ相手の説明で言う。説明のない宣言は、名前だけになり、欠けとして見える（38 か所）。
- **「例外と、そのとき変わっているもの」は、検査の計算（`Signature.relations`）を、そのまま表にできた。**
- **ものの一生の図は、値の分類と、効果の行の遷移（`Effect.row`）から描けた。** 移り変わりごとに、それを起こす入口を、入口の `Signature.effects` から引けた。
- **見ると分かる欠けがあった。** 進める効果のないケース（まとめて足す効果が、入るケースを書けないことによる。`open.md`「言語」の、行の並びを受け取る効果の点）。
