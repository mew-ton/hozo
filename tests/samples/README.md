# サンプル

## この文書が決めること

サンプルとは何か、置き方、テストがそれをどう使うか。これらの事実の持ち主はこの文書（`docs/testing.md`「トランスパイラのテスト」がここを指す）。

## サンプルとは

**（Hozo の仕様、完成したコード）の組**を、手で書いたもの。トランスパイラのプロトコルと、生成するコードの形についての問いは、具体的な組がなければ決められない。サンプルはその具体例で、二つの役目を持つ。

- **トランスパイラの仕様**。サンプルの入力に `hozoc emit` を掛けた出力が、サンプルの期待する出力とバイト単位で同じにならなければならない（ブラックボックスのテスト。`docs/testing.md`「トランスパイラのテスト」）。トランスパイラより先に書く。
- **今の設計の点検**。理想のコードを書く途中で、今の設計（基底の形、プロトコル、語彙）が与えてくれなかったものを、サンプルの `README.md`「分かったこと」に残す。

期待するコードは、本当にコンパイルできて動くものにする。動かないコードは、仕様として信用できない。

生成するコードの規則の持ち主は、トランスパイラごとの設計文書（`docs/plugin-go.md` など）。サンプルは、その規則を当てはめた実物で、規則を自分では持たない。文書とサンプルが食い違ったら、どちらが正しいかを決めてから、正しくない方を直す。

## 置き方

```
tests/samples/<名前>/
  README.md      ファイルごとの出どころ、「分かったこと」
  hozo.toml      本物の設定。単位の transpilers には、まだないトランスパイラの名前を書いてもよい
  *.hozo         仕様
  sample.json    トランスパイラごとの、出すファイル（下）
  go.mod, go.sum サンプル自身の Go のモジュール（Go のサンプルのとき）
  <out>/         単位の out。期待する出力（各トランスパイラのファイルと、記録 .hozoc-outputs.json）
  <plugin_dirs>/ サンプルの中のプラグイン（あれば）。hozo.toml の plugin_dirs に書いたディレクトリの下に、プラグインごとに
                 マニフェスト、語彙、実装（下の「サンプルの中のプラグイン」）
  それ以外       人が書くコード（葉の op の本体、準備、main、テスト）
```

- 期待する出力は、`hozo.toml` の単位の `out` のディレクトリそのものに置く。`hozoc emit` が書き出す場所と同じで、置いたままコンパイルできる。
- 期待する出力のファイルは、どれも、どれかのトランスパイラのもの（hozoc 本体はコードを出力しない。`docs/plugin-protocol.md`「この文書が決めること」）。どのトランスパイラのものかは `sample.json` が決める。どれも人が書き、`hozoc emit` の出力で書き直さない。
- **サンプルの中のプラグイン**: サンプルは、自分のプラグインを持てる（プロジェクトの中のプラグイン。`docs/config.md`「継ぎ目」）。サンプルの `hozo.toml` の `plugin_dirs` のディレクトリに、ふつうのプラグインと同じ形で置く（`docs/plugin-protocol.md`「マニフェスト」）。期待する出力と同じく、マニフェストと語彙と、そのトランスパイラの期待する出力を、実装より先に書く。実装は、サンプルのモジュールの中の `main` パッケージ（マニフェストのディレクトリ）で、マニフェストの `command` は `go run <そのパッケージの import パス>`。プラグインの規則（何を出すか）は、サンプルの `README.md` が持つ。プラグインの単体テストも、そのディレクトリに置く（サンプルの `go` が走らせる）。入力は、リポジトリのプラグインと同じく `testdata/<名前>/` の小さなプロジェクトで、`View` は `tests/pluginviews_test.go` が `views.json` に置く（`docs/testing.md`「単体テスト」。その入力は、リポジトリの `plugins/` と、そのプラグインを置いた `plugin_dirs` のディレクトリからプラグインを探す）。
- サンプルは自分の `go.mod` を持つ、リポジトリのモジュールとは別のモジュールにする。リポジトリの `go build ./...` / `go vet ./...` / `go test ./...` はサンプルの Go を見ない（サンプルだけが使う依存を、リポジトリのモジュールに入れないため）。生成したコードが import する `runtime` は、`replace github.com/mew-ton/hozo => ../../..` で解決する。`gofmt -l .` はモジュールを見ないので、サンプルの Go も整形しておく。

## sample.json

```json
{
  "transpilers": {
    "go":           { "files": ["gen/server/doc.go", "gen/server/ops.go"] },
    "go-http":      { "files": ["gen/server/http.go"] },
    "go-ratelimit": { "files": ["gen/server/ratelimit.go"] }
  }
}
```

- `transpilers` のキーは、`hozo.toml` の単位に書いたトランスパイラの名前（リポジトリのプラグインのものも、サンプルの中のプラグインのものも）。単位に書いた名前はすべてここに要り、ここに書いた名前はどれかの単位が使っていなければならない。`all` という名前は使えない（サブテスト `transpilers/all` と当たる）。
- `files` は、期待する出力のうち、そのトランスパイラが出すファイル（サンプルのルートからの相対パス）。単位の `out` の下のファイルは、出力先ごとの記録を除いて、どれかのトランスパイラの `files` になければならない。
- ほかのキーはない（書けば、読むところで失敗する）。選ぶ宣言を代役に伝える `select` と、保留にするサブテストを書く `pending` は、なくした（`docs/testing.md`「サンプル」）。まだ通せないサブテストは、サンプルが申告するのではなく、テストが、足りないものを自分で調べて飛ばす（下の「飛ばす条件」）。

## テスト

`tests/samples_test.go` の `TestSamples` が、`tests/samples/*/sample.json` のあるディレクトリをサンプルとして見つけ（足せば自動で入る）、サンプルごとに次を確かめる。

| サブテスト | 確かめること |
|---|---|
| `check` | サンプルの仕様と設定が、本物の `hozo.toml` と、サンプルの中のプラグインと、リポジトリの `plugins/` のプラグインで、`hozoc check` を error なしで通る |
| `files` | hozoc を動かさずに確かめられること: 単位に書いたトランスパイラと `sample.json` のトランスパイラが同じ集合で、単位の `out` の下のファイルは、記録を除いてどれも `sample.json` のどれかのトランスパイラの `files` にあり、`files` のファイルはどれもあり、記録 `.hozoc-outputs.json` は、その出力先の下のファイルのパスを辞書順に並べたものと同じ |
| `go` | **サンプルが動く**: サンプルのモジュールで `go vet ./...` と `go test ./...` が通る（期待する出力がコンパイルでき、人が書いたコードと合わせて仕様の通りに動く） |
| `transpilers/<名前>` | **トランスパイラごとのブラックボックスのテスト**: `hozoc emit` の出力のうち、`sample.json` のそのトランスパイラの `files` が、期待する出力とバイト単位で同じ（足りないファイル、内容の違いを、ファイルごとに示す）。サンプルの中のプラグインのトランスパイラも、同じに一つ持つ |
| `transpilers/all` | `hozoc emit` の出力の全体が、期待する出力と同じ: どのトランスパイラの `files` にもないファイルが書かれていない。期待する出力のファイルが、すべて書かれている。記録が同じ |

- `check` と `transpilers/*` は、サンプルの入力（`hozo.toml`、`.hozo`、`go.mod`、`go.sum` と、`plugin_dirs` の下のすべて）を一時ディレクトリに写して走らせる。期待する出力（単位の `out` の下）と、人が書いたコードは写さない。リポジトリのプラグインは、`plugins/` を `HOZO_PLUGIN_PATH` として hozoc に渡す（`docs/plugin-protocol.md`「探索」の 2）。サンプルの中のプラグインは、写した `hozo.toml` の `plugin_dirs` から見つかる（同 1）。`hozoc emit` は一度だけ走らせ、出力を `transpilers/*` が分けて比べる。
- 期待する出力は仕様なので、`-update` では書き直さない。
- `go` は、サンプルの `go.sum` の通りの依存をモジュールキャッシュから使う（`GOFLAGS=-mod=readonly`、`GOTOOLCHAIN=local`、`GOWORK=off`）。キャッシュにあればネットワークは要らない。なければ `go` が `GOPROXY` から取りに行き、取れなければ（オフラインなど）失敗する。先に取っておくには、サンプルのディレクトリで `GOTOOLCHAIN=local go mod download`。
- サンプルだけを手で確かめるには、サンプルのディレクトリで `GOTOOLCHAIN=local go vet ./... && GOTOOLCHAIN=local go test ./...`。

### 飛ばす条件

テストは、最後の形で書いてある。サンプルは、まだないトランスパイラと、今の hozoc がまだ読めない書き方（設定、マニフェスト、言語）で書かれていてよく、その間は、通せないサブテストを、**足りないものを名指しして**飛ばす。足りないものがそろえば、テストもサンプルも変えずに走る。足りないものは、テストがサンプルごとに調べる。

| 足りないもの | 調べ方 |
|---|---|
| 設計文書の版が、今の hozoc の版より先にある（言語か IR を変える決定を、文書とサンプルに先に入れた。サンプルは、文書の版の言語と出力で書く） | `docs/ir.md`「版」の「今の版」と、今の hozoc の版（`internal/plugin` の `Protocol`）が違う。理由には、二つの版を書く |
| 今の hozoc が、サンプルの `hozo.toml` を読めない | `internal/config` で読んで、診断（CFG-7 など）が返る。理由には、その診断を書く |
| 今の hozoc が、サンプルの中のプラグインのマニフェストを読めない | `internal/plugin` で読んで、診断（MAN-4、MAN-2）が返る |
| トランスパイラがまだない | `sample.json` の名前のトランスパイラを、サンプルの `plugin_dirs` と、リポジトリの `plugins/` の、今の hozoc が読めるどのマニフェストも提供していない |
| プラグインの実装がまだない | マニフェストはあるが、`command` が `go run …` で、マニフェストのディレクトリに、テストでない Go のファイルがない（マニフェストと語彙だけを先に書いた、サンプルの中のプラグイン） |

文書の版が先にある間は、ほかの足りないものによらず、hozoc を走らせるサブテスト（`check` と `transpilers/*`）を、どれも飛ばす。`check` を言語の検査に落とすこともしない: 仕様そのものが、今の hozoc の読めない書き方でよい。`files` と `go` は、hozoc を使わないので、走る。下の表は、版がそろっているときのもの。

| サブテスト | 足りないものがあるとき |
|---|---|
| `go` | **飛ばさない**（hozoc を使わない）。動くと確かめていないサンプルを、仕様として通さない |
| `files` | `hozo.toml` を読めないときだけ、飛ばす（単位の `out` と `transpilers` が分からない）。トランスパイラがないだけなら、走る |
| `check` | トランスパイラか、プラグインの実装がないだけなら、それを**代役**（下）に置き換えて、本物の `hozo.toml` で検査する。設定かマニフェストを読めないとき、代役を置けないときは、**言語の検査だけに落として通す**: すべての `.hozo`（サンプルの中のプラグインの語彙を含む）だけを写し、設定なしで `hozoc check` を通す（設定がなければ、hozoc は設定の検査をしない。`docs/config.md`「置き場と探し方」）。落としたことと、足りないものは、ログに書く |
| `transpilers/<名前>` | そのトランスパイラが足りなければ、飛ばす。ほかのトランスパイラが足りないだけなら、それらを代役に置き換えて走る（基底 `go` ができれば、相乗りがそろう前から `transpilers/go` が通る）。設定かマニフェストを読めないとき、代役を置けないときは、どれも飛ばす |
| `transpilers/all` | 一つでも足りなければ、飛ばす（出力の全体は、すべてのトランスパイラがそろわないと同じにならない） |

**代役**は、ファイルを返さないトランスパイラ（sh で動く）。`hozoc emit` は、一つのトランスパイラが起動できなければ何も書き出さないので、まだないトランスパイラを代役に置き換えて、あるトランスパイラの分を確かめられるようにする。置くのは、一時ディレクトリに写したプロジェクトにだけで、サンプルは変えない。

- マニフェストはあるが実装のないプラグイン（サンプルの中のプラグイン）は、写したマニフェストの `command` だけを書き換える。語彙と、`requires`、`seams` は本物のまま（基底は、本物と同じ継ぎ目を出す）。
- プラグインそのものがないトランスパイラは、`HOZO_PLUGIN_PATH` に足した一時ディレクトリに、その単位の基底に相乗りするだけのマニフェストを作る（語彙も `seams` も持たない）。本物が語彙を提供するなら、その語彙が解決できず、`check` が落ちるので、そういうサンプルでは代役を置けたことにならない（言語の検査に落ちる）。
- 単位に、動かせる基底がなければ、代役は置けない。
- 代役を置いて走らせた `hozoc emit` が、動かせるトランスパイラの `files` にないファイルを書けば、失敗（代役はファイルを返さない）。

`check` を、落としてでも通すのは、仕様（`.hozo`）が今の言語で読めることを、設定が読めるようになる前から確かめ続けるため。

## 移行の間

この文書と `tests/samples_test.go` は、トランスパイラを作る段階（`docs/requirements.md`「作り直しの段階」の R2）の後の形で書いてある。その段階の実装は済んでいる。

**次の段階（同 R3: デコレータで言う読み書きと、型に依らない出力）は、文書とサンプルを、実装より先に書いた。** その間（設計文書の版が 0.5、hozoc の版が 0.4 だった間）は、`TestSamples` が、`check` と `transpilers/*` を、二つの版を名指しして飛ばしていた（「飛ばす条件」の一行目）。

その段階の実装も済み、hozoc と、すべてのプラグインのマニフェスト（サンプルの中の `go-ratelimit` を含む）が版 0.5 になって、サンプル `shop-server` の `TestSamples` は、テストもサンプルも変えずに、すべてのサブテストが、飛ばしも、代役もなく通った。

**その次の段階（同 R4: 節の区切りの統一、名前を付けた `read`、`db` の語彙の読む側の二段）も、文書とサンプルを、実装より先に書いた。実装は、まだない。** サンプル `shop-server` は、文書の版（`docs/ir.md`「版」）の言語で書いてあり、版 0.5 の hozoc は、その仕様を読めない（節の `,`、`read` の宣言）。実装が入るまでの `TestSamples` は、テストもサンプルも変えずに、次のとおり。

| サブテスト | hozoc の版が、文書の版より前の間 | hozoc の版が、文書の版になった後 |
|---|---|---|
| `files`、`go` | 通る（hozoc を使わない。手で書いた期待する出力が、人が書いたコードと合わせて動く） | 通る |
| `check` | 飛ぶ（「飛ばす条件」の表の一行目。二つの版を名指しする） | 走る。プラグインのマニフェストの `protocol` が前の版のままなら、それを名指しして、言語の検査に落ちるか、代役が置かれる（同じ表の、マニフェストとトランスパイラの行） |
| `transpilers/*`（`go`、`go-valid`、`go-sqlite`、`go-http`、`go-ratelimit`、`all`） | 飛ぶ（同じ） | マニフェストの `protocol` が前の版のトランスパイラの分は、それを名指しして飛ぶ。上げた後は走り、`go-sqlite` が `docs/plugin-go-sqlite.md`「op の中身」の読む側（`read` の `@db.find` / `@db.list` と、op の `@db.reads`）を出すようになるまで、`transpilers/go-sqlite` と `transpilers/all` は**落ちる**（飛ばない） |

R4 の実装が済めば、どのサブテストも、飛ばしも、代役もなく通る（`docs/requirements.md`「作り直しの段階」の R4 の条件）。そこから、サブテストが飛ぶか、代役が置かれるなら、それは後戻り。
